**Breaking:** **A deserializer receives a `Meter` from its chain** (`spate-core`)

`Deserializer` has two new methods. `component_type` is required and names the deserializer. `ChainBuilder::with_metrics` uses it as the `component_type` label on the chain's `spate_deser_*` series. `attach_metrics` has a default and receives a `DeserMetricsCtx`, whose `meter` is a `Meter` for the deserializer's own families under `spate_<component_type>_deser_*`, labeled `component="<component>.deserializer"` like the stage, so the two join. A deserializer whose `component_type` is `custom` or a reserved root such as `deser` gets no `Meter`. In previous versions every chain labeled its deserializer stage `component_type="deserializer"`. A deserializer written for previous versions must add `component_type` and return the key it is configured under, and dashboards that select its stage series by `component_type` need that value. A deserializer that wraps another should forward both methods to the inner one.

`deser` joins `ROLE_SEGMENTS`, so a `Meter` local name that starts with `deser_` panics, as one that starts with `source_`, `sink_` or `feed_` does. The rule holds in every namespace, including the `spate_custom_*` names `ChainCtx::meter` registers. v0.5.0 accepted such names, so a connector or pipeline author who registered one must rename it.

Three cases may need a code change. A type that implements both `Deserializer` and `Source` and calls `component_type()` with method syntax must name the trait, as in `Source::component_type(&x)`. A type that implements both `Deserializer` and `ShardWriter` and calls `attach_metrics()` with method syntax must do the same, as in `ShardWriter::attach_metrics(&mut x, cx)`. Generic code that calls `ChainBuilder::with_metrics` without a `D: Deserializer<DF>` bound must add one.
