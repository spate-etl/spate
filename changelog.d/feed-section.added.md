**A `feed:` section selects the work feed** (`spate-core`, `spate-s3`, `spate-test`)

A pipeline file can name the feed its source reads with a top-level `feed:` section: one backend key, plus `units_held` and `attempt_cap`. The section is `spate_core::config::FeedSection`, and the runtime hands it to the source through `Source::configure_feed`, whose default refuses the section. The runtime builds the in-process feed itself for `feed: { memory: {} }`, through `MemoryFeed::from_section`. Any other backend is built in code and passed to `Pipeline::feed`, and the runtime refuses a feed whose `Feed::backend` key differs from the section's. `MemoryFeed::with_attempt_cap` sets the delivery on which the in-process feed dead-letters a failed unit. The S3 source reads work units from the feed the section names, with `units_held` bounding its read parallelism (default 96). It publishes no units itself and reads only the units published to the feed. An in-process feed built from the file alone has no publisher, so the run reads nothing; to publish to it, code builds a `MemoryFeed`, keeps a handle, and passes it to `Pipeline::feed`. Units from another process need a durable backend. Without a `feed:` section it plans splits as before, and a file that sets both `feed:` and `coordination:` fails to load.
