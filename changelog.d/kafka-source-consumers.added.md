**The Kafka source can run several consumers per process** (`spate-kafka`)

`source.kafka.consumers` sets how many consumers the source runs, default `1`. Each consumer is a separate member of the consumer group with its own share of the partitions, and each adds one fetch in flight per broker it reads from. Previously the source always ran one consumer, so every partition was fetched through one connection per broker. Raise the count when the source is bound by fetching, as the Kafka source tuning page describes; on one measured setup with the sink's storage removed, two consumers raised steady-state throughput by 38%, and four and eight by 27–28% at the process's CPU limit. With more than one consumer, consumer `k` sends `client.id` with a `-k` suffix, so a broker quota keyed on the unsuffixed id does not apply to it, and the `spate_kafka_source_*` series carry a `client="consumer-k"` label. Consumer `k`'s lines under the `librdkafka` target carry a `consumer=k` field. `group.instance.id` requires `consumers: 1`. With the default of `1`, the client id, every metric series and every log line are unchanged. At every consumer count, the source sets librdkafka's `fetch.queue.backoff.ms` to 10 ms unless the `rdkafka` map sets it. At librdkafka's 1000 ms, a partition whose queue filled was not fetched again for a second, which left pipeline threads idle once several consumers kept the queues full; at one consumer the change measured no difference in throughput or CPU.
