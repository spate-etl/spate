**Breaking:** **Framework sink keys sit beside the sink's component key, and `queue.max_bytes` sizes the shard queues from YAML** (`spate-core`)

A sink section, under `sink:` or a `sinks:` entry, holds one key naming the sink and the framework's sink keys beside it: `queue`, `chunk`, `batch`, `inflight`, `retry` and `breaker`. Any other key beside the component key fails at load as a second component, so a misspelled key is caught at startup.

`queue: { max_bytes: 8MiB }` sets the size of each shard's chunk queue. The pipeline divides it by the sink's `chunk.target_bytes` once at startup, rounding up, to get a number of chunk slots. Unset, each queue holds 8 chunks, as before. Zero is refused, and so is a size that makes more slots than a queue can hold. `SinkOptions::with_queue(QueueSection::new(bytes))` is the code equivalent. `SinkOptions::queue_capacity` and `SinkOptions::with_queue_capacity` are removed. To keep a slot count `n` set in code, pass `n × chunk.target_bytes` bytes.

`chunk` moves out of the component body to sit beside the component key. A `chunk` key inside any component body, a source, deserializer, feed or sink body, is now refused at load, and for a sink body the message names the new place. Move the block up one level: `sink: { clickhouse: { chunk: {...} } }` becomes `sink: { chunk: {...}, clickhouse: {...} }`. Errors in the block start at `sink.chunk` or `sinks.<name>.chunk`, without the component key.

`batch`, `inflight`, `retry` and `breaker` beside the component key overlay the connector's base pool field by field, so `batch: { linger: 2s }` keeps the base's row and byte limits. A block set in code with the new `SinkOptions::with_batch`, `with_inflight`, `with_retry` or `with_breaker` replaces the base block whole. A key set both in YAML and in `SinkOptions` on one sink fails at install. The pool bounds run on the resolved pool when the pipeline installs the sink.

`SinkOptions::resolve` returns a sink's resolved chunking, queue slot count and pool as a `ResolvedSink`, the same values the builder installs, so a pipeline assembled from the primitives reads a sink's YAML keys too. `PipelineConfig::sink` and `PipelineConfig::sinks` now hold a `SinkSection`; `PipelineConfig::new`, `PipelineConfig::new_multi_sink` and `PipelineConfig::sink_config` keep their signatures. `BatchConfig`, `InflightConfig`, `RetryConfig` and `BreakerConfig` implement `Serialize`.
