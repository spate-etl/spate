# Deserialization formats

Which format is cheapest to decode? This rig answers it fairly: the **same
logical data** is encoded as both Avro and JSON and decoded CPU-bound (no broker,
no server, no network in the loop), reported **per record** so every format — and
every JSON framing — is a directly comparable bar. As the framework gains formats
this chart grows with them; today it is Avro and JSON.

Two workloads are measured: a **nested batch** of 50 richer readings (a bool, a
float, and a small nested string array each) and a **single flat 15-field
record**. Both formats are measured on **both** of their decode paths — `typed`
(into your own structs) and `value` (a dynamic tree) — because, as the numbers
below show, which path is cheaper is *not* the same answer for both formats.

## Batch — per-record decode cost

Every bar below decodes the **identical 50 readings**; only the physical layout
differs — Avro's nested datum, JSON as one nested document, as a top-level array,
or as NDJSON (one reading per line). Throughput is normalized per reading.

On the **typed** path JSON is the cheaper format — Avro costs ~**409 ns/record**
against JSON's ~212 (nested document), a **1.9×** gap, even though Avro's wire
format is compact binary and JSON pays to parse text, unescape strings, and
re-parse numbers. The reason is not the format but the decoder: `apache-avro`
0.21 exposes no single-pass datum→`T` decode, so the typed path decodes **twice**
— datum → `AvroValue` → `T` — roughly doubling per-record allocations and CPU.
The `value` chart below shows what Avro's format is actually worth once that
second decode is removed.

Among JSON's framings the difference is small: a nested document and a top-level
array sit within a few percent of each other, while **NDJSON** trails by ~12%
because it re-frames per line (a line split plus a fresh parse per record)
instead of amortizing one parse across the whole batch. NDJSON buys that back in
**per-line error isolation** and true streaming — the design trade-off the
[JSON format](../user-guide/04-connectors/formats/json/README.mdx) page covers.

### Typed vs dynamic

Decoding into your own structs (`typed`) versus a dynamic tree
(`serde_json::Value` / `apache_avro::Value`) is the other lever — and it points
in **opposite directions** for the two formats.

For **JSON**, the dynamic path allocates a node per field and costs ~**1.8×**
more than typed (384 vs 212 ns/record): use it only when the schema is unknown at
compile time. For **Avro** the ordering reverses — the dynamic path is ~**1.6×**
*cheaper* than typed (251 vs 409 ns/record), because `AvroValue` is exactly the
intermediate the typed path already builds before re-decoding it into `T`. The
typed path is therefore a convenience, not an optimization: `spate-avro`'s API docs
say so, and this is the measurement behind that claim.

And on the dynamic path Avro's compact binary format does win — 251 ns/record
against JSON's 384, a **1.5×** margin, the reverse of the typed chart. The same
reversal holds on the flat record below (605 vs 772 ns).

:::tip Choosing an Avro decode path
If decode CPU matters, prefer `build_value()` over `build_serde::<T>()` and
convert yourself, or keep `build_serde` for the clean typed API and accept the
second decode. Note this is a **CPU-rig** finding: an end-to-end pipeline is
normally sink-bound, where a decode difference of this size does not reach the
measured rate at all.
:::

## Single record — a flat 15-field row

The batch shape stresses nested-array and small-object decoding; this one is a
single flat record decoded per payload, so it isolates per-field scalar cost.

The double-decode penalty is **larger** here than on the batch: Avro's typed path
costs ~925 ns/record against JSON's ~353, a **2.6×** gap, because a flat
15-field record is almost entirely per-field scalar work — exactly what gets paid
twice. Avro's `value` path lands at ~605 ns, back under JSON's own dynamic path
(~772 ns) and consistent with the reversal seen on the batch.

## SIMD backend — serde_json vs simd-json {#simd-backend}

Everything above decodes with `serde_json`, the default backend. The byte-slice
→ value step sits behind an internal seam, so the opt-in **`simd`** Cargo feature
(`json-simd` on the `spate` facade) swaps in
[`simd-json`](https://github.com/simd-lite/simd-json) — a SIMD-accelerated parser
— with no API change. Same 50 readings, same typed decode; only the parser
differs.

simd-json parses a **mutable** buffer in place (it unescapes strings into the
buffer). The framework hands the decoder a *borrowed, immutable* payload — for a
Kafka message it is librdkafka-owned memory, and at-least-once replay needs the
original bytes intact — so the payload is copied into a reused thread-local
buffer first, and the parser's own scratch buffers are reused across calls too.
Both are per-message allocations a production integration avoids; the
`memcpy_baseline` bar isolates what remains — the copy itself, about **1 ns per
reading**, under 1% of the decode.

:::caution simd-json is more machine-sensitive than serde_json
This dataset was re-recorded in full when the Avro backend changed. Across that
re-record every `serde_json` and `value`-path arm reproduced within **±2%**, but
the four `simd-json` arms landed **6–8% slower** than the previous dataset — on
the same host, the same `rustc 1.96.1`, the same pinned `simd-json 0.17.3`, with
no change to any crate in its dependency subtree, and reproducibly across two
independent sweeps (grouped and interleaved alike). Treat the simd ratios as
having a wider error bar than the scalar ones, and re-measure on your own
hardware before sizing a deployment on them.
:::

On the **single-document** and **top-level-array** framings — one parse over the
whole payload, and the JSON connector's Kafka-message default — simd-json decodes
roughly **1.3× faster** than serde_json. On **NDJSON** (50 independent line
parses) the gap nearly closes (~1.07×) as per-parse overhead dominates, and on
the flat single-record `order` shape it is ~1.24×. Every arm is faster; the win
is largest exactly where one large document is parsed.

:::note Measured on aarch64
These numbers are from an Apple M5 Max (aarch64, NEON) — the machine every page
here uses. simd-json's speedup is architecture-sensitive; an x86-64 host with
AVX2 was not measured. serde_json remains the default backend, and `simd` is a
per-deployment opt-in worth benchmarking on your own hardware and payloads.
:::

:::warning Not byte-for-byte identical
`simd-json` is a different parser, so decode is not semantically identical to
`serde_json` on every input. It **rejects integer literals outside the
`i64`/`u64` range** that `serde_json` accepts as `f64` (such a document is dropped
as `malformed`, or fails the payload under `on_error: fail`), normalizes `-0` to
`0`, and does not honor the `serde_json`-specific `arbitrary-precision`,
`raw-value`, or `float-roundtrip` features. The duplicate-key guard is unaffected —
it always runs on `serde_json`. Ordinary-range numbers decode identically;
validate against your own payloads before switching.
:::

## Reproduce

The rig is `benchmarks/src/bin/deser_formats.rs`; the shared shapes and both
formats' encoders are in `benchmarks/src/deser_sample.rs`. One invocation
measures one arm (mean of `REPS` reps, Student-t 95% CI). Sweep the matrix:

```sh
RESULTS=benchmarks/results/deser-formats.jsonl
for R in typed value; do
  for F in avro json; do
    SHAPE=order FORMAT=$F RECORD=$R REPS=9 RESULTS=$RESULTS \
      cargo run -p benchmarks --release --bin deser_formats
  done
  SHAPE=batch FORMAT=avro RECORD=$R REPS=9 RESULTS=$RESULTS \
    cargo run -p benchmarks --release --bin deser_formats
  for FR in single array ndjson; do
    SHAPE=batch FORMAT=json FRAMING=$FR RECORD=$R REPS=9 RESULTS=$RESULTS \
      cargo run -p benchmarks --release --bin deser_formats
  done
done

# simd-json backend — rebuild with the feature; JSON typed arms.
SHAPE=order FORMAT=json RECORD=typed REPS=9 RESULTS=$RESULTS \
  cargo run -p benchmarks --release --bin deser_formats --features json-simd
for FR in single array ndjson; do
  SHAPE=batch FORMAT=json FRAMING=$FR RECORD=typed REPS=9 RESULTS=$RESULTS \
    cargo run -p benchmarks --release --bin deser_formats --features json-simd
done

# memcpy-only baseline — the copy simd-json's mutable-buffer parse pays.
SHAPE=order FORMAT=json RECORD=typed COPY_ONLY=1 REPS=9 RESULTS=$RESULTS \
  cargo run -p benchmarks --release --bin deser_formats
for FR in single array ndjson; do
  SHAPE=batch FORMAT=json FRAMING=$FR RECORD=typed COPY_ONLY=1 REPS=9 RESULTS=$RESULTS \
    cargo run -p benchmarks --release --bin deser_formats
done
```

Per-format micro-benchmarks (criterion) live in each format crate —
`crates/spate-json/benches/decode.rs` and `crates/spate-avro/benches/decode.rs`. See
[Methodology](methodology.mdx) for the harness and the Report schema the charts
read.
