# Methodology

Numbers are machine-specific; every chart renders its own provenance (CPU,
commit, date) from the data. The current results were recorded on an Apple M5 Max
(18-core), macos/aarch64, rustc 1.96.1, release profile, commit `63084c56a811`, on
a quiet machine — all unrelated Docker containers were paused for the runs.
Contended runs are called out where they matter.

## How the results are recorded

Every benchmark binary appends one JSON object per line to the file named by its
`RESULTS` environment variable, under `benchmarks/results/`. The record shape is
defined once, versioned, in `benchmarks/src/report.rs`:

- `schema` — the record schema version (currently `1`). The docs site ignores
  any line without `schema == 1`, so older ad-hoc records never render.
- `bench` — the rig that produced the record.
- `kind` — `measurement` or `verdict` (a go/no-go conclusion drawn across arms).
- `trigger` — what produced the run: `manual`, `ci` or `dispatched`. Set from
  `BENCH_TRIGGER`; unset it reads as `ci` under a CI environment and `manual`
  otherwise.
- `run` — provenance: timestamp, short commit, host, CPU brand, cores, OS,
  profile. This is what the "provenance" line under each chart reports.
- `variant` — the arm under test (an open map, e.g. `{"deser":"apache_owned",
  "format":"native"}`).
- `metrics` — each measured quantity with its `value`, `unit`,
  `higher_is_better`, and optional `ci95` / `n`. The direction of goodness
  travels **with** the number, so a chart can never silently draw a
  lower-is-better quantity as a taller bar.

`trigger` is what bars a record from publication. Provenance says *where* a
number came from; it cannot say whether the machine was worth quoting. A `ci`
record comes off a hosted runner, which is contended and virtualised, and a
`dispatched` one answers a single comparison rather than recording a figure.
Both are useful, and neither belongs on these pages, where they would render
beside a quiet-machine recording with nothing to tell them apart.

`make check-results` refuses any record under `benchmarks/results/` whose
trigger bars publication, on every pull request rather than only where somebody
runs the gates, and refuses a trigger it does not recognise so a value added
later cannot slip past an older copy of the check. A barred record also carries
the reason at the front of its `note`, so one line of JSONL says so in prose as
well as in a typed field.

An unrecognised or empty `BENCH_TRIGGER` aborts the run rather than defaulting,
and the names are case-sensitive — `BENCH_TRIGGER=CI` is an error, not `ci`. A
typo that quietly became `manual` would produce exactly the record this field
exists to prevent, so it fails at start-up instead.

### Smoke runs

`SMOKE=1` asks a rig for the shortest window, the smallest corpus and one
repetition — enough to prove it still runs, and never a measurement. Each rig
decides what that means for its own parameters, because they are the parameters
it understands; a caller shrinking a run from outside needs a table of every
knob, and that table drifts from the rigs it describes. A knob set explicitly
still wins, so a smoke run remains steerable.

Nothing about a smoke run makes its numbers publishable: it is the weekly tier
that sets it, `BENCH_TRIGGER=ci` bars that record anyway, and the job writes no
`RESULTS` path.

### Memory

Some rigs report `peak_rss_mb`: the high-water mark of the process's resident
set, as the kernel accounted it. It is a blunter quantity than the heap shape
the instruction-count tier measures under DHAT, and a more operational one — it
includes what the allocator retained rather than returned, and it is the figure
a container limit is set against. The two answer different questions, and a
pipeline's memory is decided by things no micro-benchmark contains: the
in-flight budget, queue depth, and how many chunks are sealed but
unacknowledged. Those move with a configuration change and leave every
instruction count where it was.

The catch is that the figure is a **process** high-water mark. It cannot be
reset, so it measures the thing under test only when nothing else in that
process reached higher. Three conditions follow, and a rig that cannot meet
them reports no memory figure rather than a misleading one:

- **One arm.** A rig sweeping arms in one process would report the same mark
  for all of them, whichever arm reached it.
- **One repetition.** The figure is a *maximum*, where every other metric on the
  record is a mean or a derived rate. Repetition count is not part of a record's
  variant identity, so a maximum over ten repetitions and one over a single
  repetition are two quantities the schema cannot tell apart — and the charts
  would take a median across both.
- **A measured region that set the mark.** Each rig takes a baseline once setup
  is done and reports only if the process rose above it afterwards, which is
  what shows the mark belongs to the measurement. This is a validity check, not
  a subtraction: the value reported is the process peak, so anything still
  resident from setup is inside it.

The object-storage backfill carries a fourth: it will not report from a run that
built its own corpus. Building one grows allocator arenas far past anything the
pipeline needs and never returns them, so a staging run's resident set is not
comparable with a reusing run's — pointing a second run at the same `DATA_DIR`
is what makes the number mean the pipeline. A decode fixture is different and
stays included, because it is resident *while* the arm runs and is therefore
part of what the arm needs.

So an exploratory sweep gets no memory figure, and that is the right answer
rather than a gap. Each rig's usage header names the invocation that does
produce one.

The metric carries `n = 1` and no interval, because one observation of a
high-water mark is not a mean. Where a rig repeats by re-running itself as a
child process, the spread is visible across records rather than within one —
and on the synthetic pipeline rig that spread is around three times wider than
its throughput numbers', so read it across repetitions rather than from a
single record.

## Reproducing

### Comparing two arms

```sh
make bench-ab ARMS=none,gzip REPS=5
```

Most of what makes that comparison sound belongs to the rig, not the target:
it interleaves the arms, runs a discarded pass over every arm before measuring
any of them, and stages each corpus once before the clock starts. Invoking the
binary directly gets all three. What the target adds is a repetition count —
the rig on its own runs once, which yields a point value and no interval — and
an output path under `benchmarks/tuning/`, which is not committed.

That last one is worth the target on its own. An exploratory run on a laptop
is not a published record, and the failure mode is silent: the site draws
everything under `results/` without knowing which machine was busy, so a
contended number and a quiet one render identically. Promoting a number stays
a deliberate copy rather than a consequence of `git add -A`.

The rig records the commit its `git rev-parse` finds at run time, which is the
working tree's. That is right for arms of one build and wrong for anything
else — see below.

### Comparing two builds

```sh
make bench-vs-main                       # against main, 3 recorded repetitions
make bench-vs-main AB_BASE=v0.1.0 AB_REPS=5
```

`make bench-ab` does not do this, and the difference is not cosmetic. It builds
and then immediately measures, so two invocations interleave nothing and the
second build lands after the first measurement — a sequential comparison of the
kind this page's own interleaving rule rejects. A sequential run here once
reported a 30% win that was the machine warming up.

`scripts/bench-drive.sh` is what `make bench-vs-main` calls, and the properties
it holds are the reason to use it rather than two runs by hand:

1. **Both binaries are built before either is measured**, from two checkouts.
   Building one arm while the other is being timed measures the compiler.
2. **The corpus is staged once** and both arms are pointed at it with
   `DATA_DIR`, so the two builds read literally the same bytes. Rigs that take
   no corpus ignore it; today only `s3_backfill` reads it.
3. **`GIT_COMMIT` is set per arm.** The rig otherwise asks git at run time,
   which reports the checkout it is *run* from rather than the one it was
   *built* from — the single most likely way a two-build comparison
   misattributes its numbers.
4. **Arms alternate**, so drift over the run splits evenly between the legs
   instead of landing on whichever went second.
5. **The first pass is discarded.** Page cache, CPU frequency and allocator
   arenas reach steady state after one pass, and the first pass is where they
   are not.
6. **One repetition per process.** `peak_rss_mb` is a whole-process high-water
   mark, so anything sharing a process reports the larger figure for all of it;
   and the comparator pairs repetitions by position, which needs each to be its
   own record. The driver therefore sets `REPS=1` and loops itself rather than
   using a rig's own repetition sweep.

   A rig that sweeps some *other* dimension internally still does so —
   `s3_backfill` runs its three codecs in one process — and suppresses
   `peak_rss_mb` accordingly, so that rig reports no memory figure under the
   driver. Pinning its codec list here would buy the metric by measuring less.

Which rigs it drives comes from the classifier, so it cannot name a different
set from the one CI smokes. It refuses to run against a dirty working tree: the
head arm would not be the commit its records name.

A change that can be expressed as a runtime switch avoids all of this: one
binary, two arms, and the rig's own interleaving applies. Prefer that shape
where the change allows it.

The criterion micro-benches are a separate tier and are **not** driven by
`bench-drive.sh`. `criterion_to_report` converts a criterion run into the same
records, so one comparator reads both, but the interleaving, the discarded pass
and the per-arm commit are all yours to arrange.

```sh
cargo build --release -p benchmarks --locked --bin criterion_to_report
for rep in 1 2 3; do
  export CRITERION_HOME=$(mktemp -d)
  cargo bench -p spate-json --locked --bench decode
  BENCH_TRIGGER=dispatched GIT_COMMIT=$(git rev-parse HEAD) \
    ./target/release/criterion_to_report "$CRITERION_HOME" >> leg.jsonl
done
```

Three things in that snippet are load-bearing:

- **The converter is a binary of the `benchmarks` package**, so `cargo bench -p
  spate-json` does not build it. Build it explicitly first.
- **A fresh `CRITERION_HOME` per repetition.** criterion's default output
  directory is shared and persistent, and each benchmark keeps its `new/` until
  something overwrites it — so converting `target/criterion` converts every
  benchmark that has ever run there, stamped with the current commit. The tool
  takes the directory as a required argument for that reason, and has no
  default.
- **More than one repetition per leg.** The comparator needs at least two
  records per identity to have an interval; with one, every row renders as
  "not judgeable" and the verdict is always negative, however large the real
  movement. Note that this discards criterion's own confidence interval, which
  the comparator does not read.

`BENCH_TRIGGER` is required rather than defaulted: unset, these would record as
`manual`, the one trigger that does not bar publication, and a comparison arm is
not a recording.

It reads criterion's `new/` only, never its `base/` — that directory holds
whatever ran on this disk last, which is the cross-run comparison this page
rejects. It takes the mean rather than the median, because the `benchmarks`
crate carries two disagreeing definitions of the median
([#62](https://github.com/spate-etl/spate/issues/62)) and a value that depends
on which one a reader assumes is worse than no value.

Before quoting a number from a local run, read
[Regression gates](#regression-gates) — the machine has to be quiet, and a
result about parallelism has to state its core count.

### Reading a comparison

```sh
make bench-compare BASE=before.jsonl HEAD=after.jsonl
```

Renders the two result sets as Markdown: what moved, what did not, what is
reported but never judged, and what could not be paired at all. Producing the
two legs is the previous section; this reads them.

A row **moved** when both conditions hold — the paired mean difference is at
least the threshold for that bench in magnitude, and the 95% interval on the
per-repetition differences excludes zero. The thresholds are 5% by default and
10% for the rebalancing rig, which is inherently noisier; peak memory and the
workload counters (records processed, rows written) are rendered and never
judged, the counters because they describe the job rather than its speed — a
run that processed 7% more records is a different run, not a slower one.
Delivery signals such as duplicate rows are **not** exempt: a rise there is
precisely what should be flagged. Requiring both is deliberate: a shift
far smaller than the threshold can be extremely consistent, and a large one can
be entirely noise.

Scenarios pair on the whole `variant` map, so adding or removing a variant key
makes every scenario unpairable at once. The report says so rather than
rendering an empty table, which would read as "nothing changed".

### The committed runs

Reproduce per the usage headers in each binary under `benchmarks/src/bin/`. Each
rig appends to the result file named below; the exact env vars used for the
committed runs are:

```sh
# Framework ceiling → pipeline-synthetic-baseline.jsonl (no broker, no server)
# 30 s window, 256 B payloads, 2 shards, zero per-record work, threads 1/2/4/8.
THREADS_LIST=1,2,4,8 SHARDS=2 PAYLOAD=256 WORK_US=0 DURATION_S=30 \
  RESULTS=benchmarks/results/pipeline-synthetic-baseline.jsonl \
  cargo run -p benchmarks --release --bin pipeline_synthetic

# Thread scaling with egress scaled → pipeline-scaling.jsonl (no broker, no server)
# Same rig under a distinct BENCH name: the published pipeline_synthetic records
# predate the egress/lane/chunk variants, so emitting these under that name would
# give them a different variant identity and double the bars on the
# framework-overhead page. EGRESS=scaled derives SHARDS/IO_THREADS from THREADS;
# the in-flight budget is derived per arm from the DESIGN.md sizing rule.
# Two chunk arms x threads 1/2/4/6/8, 3 reps each. Arms stay within
# threads + io_threads + 1 <= cores; the rig flags any that do not.
for rep in 1 2 3; do for t in 1 2 4 6 8; do for cfg in 64:64 1024:512; do \
  BENCH=pipeline_scaling RUN_ONE=1 EGRESS=scaled THREADS=$t DURATION_S=20 \
  CHUNK_KIB=${cfg%%:*} QUEUE_CAP=${cfg##*:} \
  RESULTS=benchmarks/results/pipeline-scaling.jsonl \
    cargo run -p benchmarks --release --bin pipeline_synthetic; \
done; done; done

# Chunk/queue trade-off vs a real sink → ch-sink-chunk-sizing.jsonl
# MAX_INFLIGHT_MB is pinned so the budget is identical across arms: the sizing
# rule makes the derived budget a function of chunk.target_bytes, so letting it
# float would change two variables at once (that inflated the apparent gain by
# ~1/3 before it was caught). Chunk sweep at the default queue depth, then a
# queue sweep at the default chunk target; the shared arm merges reps.
for rep in 1 2 3; do \
  for ck in 64 128 256 512 1024; do \
    BENCH=ch_sink_chunk_sizing RUN_ONE=1 ENGINE=Null THREADS=8 CHUNK_KIB=$ck \
    QUEUE_CAP=256 MAX_INFLIGHT_MB=8192 DURATION_S=20 WARMUP_S=8 \
    RESULTS=benchmarks/results/ch-sink-chunk-sizing.jsonl \
      cargo run -p benchmarks --release --bin ch_sink_saturation; \
  done; \
  for qc in 8 64 1024; do \
    BENCH=ch_sink_chunk_sizing RUN_ONE=1 ENGINE=Null THREADS=8 CHUNK_KIB=64 \
    QUEUE_CAP=$qc MAX_INFLIGHT_MB=8192 DURATION_S=20 WARMUP_S=8 \
    RESULTS=benchmarks/results/ch-sink-chunk-sizing.jsonl \
      cargo run -p benchmarks --release --bin ch_sink_saturation; \
  done; \
done

# 2 pipeline threads. One invocation = one arm (DESER/FORMAT); the committed matrix
# is the DESER=none rowbinary baseline plus the two avro arms, three runs each; charts
# and quoted figures use per-arm medians. Committed data is ClickHouse 25.6 — pin
# CLICKHOUSE_IMAGE (the default is now 26.3); the sink YAML pins async_insert=0 and
# the run records SELECT version() into its note.
export CLICKHOUSE_IMAGE=clickhouse/clickhouse-server:25.6
for rep in 1 2 3; do
  for arm in "none rowbinary" "apache_owned native" "apache_owned rowbinary"; do
    set -- $arm
    DESER=$1 FORMAT=$2 RATE=0 DURATION_S=30 EVENTS=20 PARTITIONS=4 THREADS=2 \
      EGRESS=fixed LOAD=concurrent \
      RESULTS=benchmarks/results/e2e-kafka-clickhouse.jsonl \
      cargo run -p benchmarks --release --bin e2e_kafka_clickhouse
  done
done

# Source-bound end-to-end → e2e-kafka-source-bound.jsonl (local containers)
# The same rig arranged so the SOURCE is the limiter rather than the sink, which
# is what makes it comparable with the raw-client kafka_source_ceiling numbers:
#   ENGINE=Null      the ~5.9M rows/s Null ceiling finally exceeds the source's
#   LOAD=prefill     fill the topic first, then run with NO producer — against a
#                    concurrent producer the consumer is tail-following, so there
#                    is no backlog to prefetch and the dominant term cannot show
#   EGRESS=scaled    shards/io_threads track THREADS so egress is not the limiter
#   DESER=none       1 row per message, so rows/s and msg/s are the same quantity
# QUEUED_MIN_MESSAGES=0 means "set nothing", exercising the shipped default path
# rather than a value that merely happens to equal it. Pin TOPIC so the prefill
# is paid once: each run gets a fresh per-pid group and re-reads from offset 0.
# PREFILL must outlast the window — the rig exits 3 and emits nothing if the
# source consumed the whole backlog, which measures a drain, not a ceiling.
for rep in 1 2 3; do for q in 1000 10000 0; do
  BENCH=e2e_kafka_source_bound DESER=none FORMAT=rowbinary \
    ENGINE=Null LOAD=prefill EGRESS=scaled TOPIC=bench-e2e-source \
    PARTITIONS=16 PAYLOAD=64 PREFILL=100000000 THREADS=8 RATE=0 \
    DURATION_S=15 PER_PARTITION_DETAIL=1 QUEUED_MIN_MESSAGES=$q \
    RESULTS=benchmarks/results/e2e-kafka-source-bound.jsonl \
    cargo run -p benchmarks --release --bin e2e_kafka_clickhouse
done; done

# ClickHouse sink saturation → ch-sink-saturation.jsonl (Docker ClickHouse 26.3)
# In-process generator (no broker) → real chain → sharded ClickHouse sink at full
# tilt. Throughput = spate_sink_records_total delta / window (works for ENGINE=Null,
# where SELECT count() is 0). The committed sweep is 33 arms × 3 reps = 99 records
# on ClickHouse 26.3.17.4 (the current default image — no CLICKHOUSE_IMAGE pin
# needed). Each record's `variant` is self-describing: it now carries the
# identity-defining budget/shape keys (max_inflight_mb, max_pending_batches,
# batch_max_mb, linger_ms, queue_cap, io_threads, shards, compression,
# clickhouse_cpus), and each record's `note` carries a per-record `limiter` verdict
# (sink / generator / indeterminate-checkpoint / budget) plus its evidence.
#
# Budget: MAX_INFLIGHT_MB is NOT pinned — the rig derives it per arm from the
# deployment sizing rule (2 × in-flight bytes / 0.5 low watermark), so it is always
# rule-compliant and never self-throttles the source below sink capacity. Override
# only to reproduce the invalidated first recording. QUEUE_CAP default is 256,
# MAX_PENDING_BATCHES default 8192.
export RESULTS=benchmarks/results/ch-sink-saturation.jsonl
export CLICKHOUSE_CPUS=8 SHARDS=4 IO_THREADS=4 DURATION_S=15 WARMUP_S=5 PAYLOAD=256
: > "$RESULTS"                                    # fresh; reuse the warm 26.3 server
for rep in 1 2 3; do                             # 3 reps/arm; charts median them
  # Null ceiling search (both formats, sync, threads 2/3/4/5/6/8): find the peak.
  # The binary self-matrixes THREADS_LIST into one arm per thread count.
  ENGINE=Null FORMAT=rowbinary ASYNC_INSERT=0 THREADS_LIST=2,3,4,5,6,8 \
    cargo run -p benchmarks --release --bin ch_sink_saturation
  ENGINE=Null FORMAT=native    ASYNC_INSERT=0 THREADS_LIST=2,3,4,5,6,8 \
    cargo run -p benchmarks --release --bin ch_sink_saturation
  # io-thread sensitivity pair at the peak: Null Native t4, IO_THREADS=8 vs the 4
  # already recorded above (Δ was +3.6%, within noise — not scaled across the matrix).
  RUN_ONE=1 THREADS=4 IO_THREADS=8 ENGINE=Null FORMAT=native ASYNC_INSERT=0 \
    cargo run -p benchmarks --release --bin ch_sink_saturation
  # One t12 contention datapoint (excluded from the ceiling claim).
  RUN_ONE=1 THREADS=12 ENGINE=Null FORMAT=native ASYNC_INSERT=0 \
    cargo run -p benchmarks --release --bin ch_sink_saturation
  # Real sink: MergeTree × {rowbinary, native} × {async 0, 1}, threads 2/4/8.
  for FMT in rowbinary native; do for A in 0 1; do
    ENGINE=MergeTree FORMAT=$FMT ASYNC_INSERT=$A THREADS_LIST=2,4,8 \
      cargo run -p benchmarks --release --bin ch_sink_saturation
  done; done
  # Part-size sweep (MergeTree Native sync t4): bigger batches → bigger parts.
  # The 4M-row arm carries a ~13 GB worst-case in-flight bound (printed at startup).
  for R in 262144 1048576 4194304; do
    RUN_ONE=1 THREADS=4 ENGINE=MergeTree FORMAT=native ASYNC_INSERT=0 \
      BATCH_MAX_ROWS=$R BATCH_MAX_MB=$((R / 2048 + 8)) \
      cargo run -p benchmarks --release --bin ch_sink_saturation
  done
  # Compression codec (MergeTree Native sync t4): zstd / off. The lz4 point IS
  # the MergeTree Native sync t4 matrix arm above (same variant identity), so it
  # is not re-run — the chart's lz4 bar reuses those reps.
  for C in zstd off; do
    RUN_ONE=1 THREADS=4 ENGINE=MergeTree FORMAT=native ASYNC_INSERT=0 COMPRESSION=$C \
      cargo run -p benchmarks --release --bin ch_sink_saturation
  done
  # Writer shards (MergeTree Native sync t4): 2 / 8. The 4-shard point is the
  # matrix arm above (SHARDS defaults to 4), so it too is reused, not re-run.
  for S in 2 8; do
    RUN_ONE=1 THREADS=4 SHARDS=$S ENGINE=MergeTree FORMAT=native ASYNC_INSERT=0 \
      cargo run -p benchmarks --release --bin ch_sink_saturation
  done
done                                              # → 33 arms × 3 reps = 99 records
```

For a **dedicated-server** ceiling (no client/server core contention), point the
rig at an external cluster instead of the local container:
`CLICKHOUSE_URL=http://host:8123 [CLICKHOUSE_USER=… CLICKHOUSE_PASSWORD=…]`.

**Kafka producer sink saturation** ([study](./kafka-sink.mdx)) — an in-process
generator (no source broker) drives the real chain into the Kafka producer sink
at full tilt against `apache/kafka:4.1.0` in Docker. Throughput =
`spate_sink_records_total` delta / window (durable acks). The broker is capped at
`KAFKA_CPUS` cores; each framework arm records a two-axis verdict in its note —
`upstream` (`sink`/`budget`/`generator`/`checkpoint`) and `downstream`
(`client`/`broker`, from the raw baseline and the sink's `spate_kafka_*` broker
statistics). The rig sweeps one env dimension (`SWEEP` over `SWEEP_LIST`), `REPS`
each; children re-exec with `RUN_ONE=1` and reuse the warm broker via `BOOTSTRAP`.

```sh
export RESULTS=benchmarks/results/kafka-sink-saturation.jsonl
: > "$RESULTS"
# Q0 broker-headroom calibration: the raw baseline vs broker cores. FRESH=1
# recreates the capped broker per core count (reuse keys on the port, so --cpus
# only applies on a fresh container). The raw ceiling is flat (~2.5M rec/s), so
# the broker is not the limiter — 6 cores is the cap for every other arm.
for C in 4 6 8; do
  FRESH=1 KAFKA_CPUS=$C MODE=raw REPS=3 DURATION_S=20 WARMUP_S=5 \
    cargo run -p benchmarks --release --bin kafka_sink_saturation
done
# Take the raw@6 median (~2.48M) as RAW_BASELINE_RPS so framework arms record
# framework_over_raw. BATCH_MAX_MB is held at 256 (the rig default) so max_rows is
# the binding seal knob; the raw baseline is a single uncontended feeder.
export KAFKA_CPUS=6 RAW_BASELINE_RPS=2483946 REPS=3 DURATION_S=20 WARMUP_S=5
# Q1 overhead ceiling: raw vs framework at the defaults (recreates the broker @ 6,
# then Q2/Q3 reuse it warm — no FRESH).
FRESH=1 SWEEP=MODE SWEEP_LIST=raw,framework \
  cargo run -p benchmarks --release --bin kafka_sink_saturation
# Q2a batch.max_rows sweep at the fixed 100k producer queue.
SWEEP=BATCH_MAX_ROWS SWEEP_LIST=10000,50000,100000,250000,500000 BATCH_MAX_MB=256 \
  cargo run -p benchmarks --release --bin kafka_sink_saturation
# Q2b queue.buffering.max.messages sweep at the fixed 500k batch.
SWEEP=QUEUE_BUFFERING_MAX_MESSAGES SWEEP_LIST=100000,250000,500000,1000000 \
  cargo run -p benchmarks --release --bin kafka_sink_saturation
# Q3 shards sweep at the default mismatch (batch 500k, queue 100k).
SWEEP=SHARDS SWEEP_LIST=1,2,4 \
  cargo run -p benchmarks --release --bin kafka_sink_saturation
```                                                # → 51 records

For a **dedicated broker** (its own cores), point the rig at an external cluster:
`BOOTSTRAP=host:9092` skips docker entirely.

**Multi-table split vs. MV** ([study](./multi-table-split.mdx)) — three arms
(`single_null` / `null_mv` / `split`) over a type-count sweep, ClickHouse pinned
to 6 cores so the server is the binding constraint and the ETL has the host's
remaining cores. `FRESH=1` recreates the container with the CPU cap; the CPU
budget (CH 6 + ETL threads 6 + io 4 = 16 of 18) keeps both storage arms
`sink`-bound — the validity precondition:

```sh
: > benchmarks/results/multi-table-split.jsonl
# core sweep (recreates the 6-core container on the first invocation)
FRESH=1 CLICKHOUSE_CPUS=6 DURATION_S=20 WARMUP_S=5 \
  ARMS=single_null,null_mv,split TYPES_LIST=4,8,16 SKEWS=skewed LINGERS=1000 \
  RESULTS=benchmarks/results/multi-table-split.jsonl \
  cargo run -p benchmarks --release --bin multi_table_split
# robustness: uniform mix (reuses the warm container)
CLICKHOUSE_CPUS=6 DURATION_S=20 WARMUP_S=5 \
  ARMS=single_null,null_mv,split TYPES_LIST=4,8,16 SKEWS=uniform LINGERS=1000 \
  RESULTS=benchmarks/results/multi-table-split.jsonl \
  cargo run -p benchmarks --release --bin multi_table_split
```

Superseded reference point: an earlier rate-limited E2E smoke (100k rec/s target,
2026-07-05) recorded 89.4k rows/s against local containers. Its backing file
(`e2e-local-smoke.jsonl`) no longer exists — it was replaced by the saturated rig
above (`RATE=0`), which measures the pipeline ceiling instead of a throttled
target.

The micro-benchmarks are separate, one per crate under `crates/*/benches`:
criterion in `spate-avro`, `spate-json` and `spate-clickhouse`, divan in
`spate-core`. Divan's `AllocProfiler` *reports* allocation counts beside each
timing; nothing fails on them. What hard-fails is the counting-allocator
integration test (`crates/spate-core/tests/chain_alloc.rs`), if per-iteration
allocations scale with record count.

A recurring harness lesson, now encoded in the binaries: metric handles created
**before** `metrics::install` bind to the no-op recorder and silently render
nothing. The harnesses install the recorder first; the examples should be
audited for the same pattern.

## Regression gates {#regression-gates}

Wall-clock throughput is not a gating quantity: on a shared CI runner it
measures the runner's neighbours as much as the change under test. The
regression suite is therefore split by what varies:

- **Deterministic counters gate every pull request.** Allocation counts on the
  chain hot path (`crates/spate-core/tests/chain_alloc.rs`), object-store
  request shapes for a coordinated backfill (one LIST per run, one GET per
  object — `crates/spate-s3/tests/request_shape.rs`), and instruction counts
  via gungraun. Each gates on a counter, never on elapsed time, so the
  verdicts hold on any machine.
  The instruction-count benches cover the operator chain, payload decoding,
  row encoding for the wire, and the planning and record framing an
  object-store backfill does. New benches are written as one workload shape
  parameterised over the axis that changes its cost — a listing profile, a
  codec, an entry point — rather than one case per function, because
  attribution below the shape comes from the callgrind profile the run already
  writes and a finer set of cases would only duplicate it. Where a bench
  generates its own corpus, that corpus is produced from a fixed sequence and
  pinned by a test (`crates/spate-s3/tests/bench_fixtures.rs`,
  `crates/spate-clickhouse/tests/bench_fixtures.rs`), because a count is only
  comparable when both legs of the comparison packed byte-identical input.
  Where a format crate wraps a third-party parser, the wall-clock bench keeps
  cases that call the parser directly and the counted bench measures the
  crate's own path over the same bytes. The first is a floor — what the
  underlying library costs — and the second is what the framework adds to it;
  reading the second without the first turns a parser's regression into an
  unexplained framework one.
  The instruction counts are advisory: the comparison lands in the pull-request
  summary without a blocking threshold, movement past the advisory thresholds
  surfaces as the `affects-performance` label, and a bench that fails to build
  or run fails its job like any other. The job wiring is in the
  [CI reference](../user-guide/07-reference/ci.mdx).
- **Wall-clock numbers come from identified hardware.** Every figure on these
  pages is rendered from committed records whose provenance (CPU, commit,
  profile) travels with the data, recorded on a quiet machine. Wall-clock
  comparisons never gate a pull request, and benchmark numbers are never
  hand-written into the docs.
  A result about **parallelism** carries one further obligation: state the core
  count, and measure it on a machine with enough cores to show the effect. A
  concurrency win measured on fewer cores than a deployment would use
  understates itself, and the resulting figure is not comparable with one taken
  on wider hardware — so a directional answer from a small machine is fine,
  while a number that gets quoted is not.
- **A rig that compares arms interleaves them, and discards a pass first.**
  This is the standard for a comparison, not a description of every rig here:
  the object-storage backfill implements it, and a rig that measures one arm
  per process — most of them — has nothing to interleave. Any rig that grows a
  second arm is expected to adopt both halves.
  Interleaving means every arm once per repetition rather than one arm
  finished before the next starts, because anything that drifts over a run —
  thermal state, page cache, a neighbour on the host — otherwise lands entirely
  on whichever arm goes last. That is not sufficient on its own: the first
  repetition still puts some arm first, and that arm absorbs the cold-start
  cost, which is large enough to change which arm appears faster. A discarded
  pass over every arm before any measurement removes it, and the check that it
  worked is that swapping the arm order no longer moves the result.
  Repeated runs report a Student-t interval and the repetition count beside
  the value, so a reader can tell a difference from a spread. Student-t rather
  than a normal approximation because a benchmark repeats five times, not a
  thousand, and an interval that is too narrow is what turns noise into an
  apparent result.

## Accounting note (2026-07 correction) {#accounting-note}

An earlier revision of the framework-ceiling table
([Framework overhead](./framework-overhead)) reported window-scoped `records`
against lifetime `sink_rows_total` (warmup + window + drain), which read as rows
exceeding records by ~10%. The harness now reports `produced_total` alongside
and asserts conservation; a quiet-machine re-run shows `sink_rows_total ==
produced_total` exactly (1,297,595,392 == 1,297,595,392 @ 1 thread) and healthy
1→2 thread scaling (39.4M → 74.6M records/s). The metric itself is proven exact
by `sink_records_metric_matches_rows_written_exactly` in `spate-core`.

## E2E rate accounting (2026-07 correction) {#e2e-rate-accounting}

An earlier revision of the end-to-end rig
([E2E rig](./clickhouse-format.mdx#e2e-rig)) divided every row that landed —
window plus the grace and drain tail — by the 30 s window alone, which under
`RATE=0` (the producer deliberately outruns the pipeline) inflated the reported
`rows_per_s` by roughly 2×. It now divides by the elapsed consumption interval,
so the rate reflects the work actually done in that span; the committed records
were regenerated. Each arm's `events` (rows exploded per message) and `payload`
are now recorded in `variant`, so every row is self-describing.
