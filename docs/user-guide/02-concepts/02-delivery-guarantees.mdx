# Delivery guarantees

Spate delivers **at-least-once**: a source offset is committed only after
every record derived from it has been durably written to the sink or
intentionally dropped. This page explains the machinery that enforces it,
what happens at the hard moments (rebalances, shutdown, crashes), and —
honestly — what at-least-once does *not* give you.

## The ack chain: from record to watermark

**One `AckRef` per source poll batch.** When a lane's poll yields a batch,
the framework creates a single refcounted acknowledgment state for it;
every record deserialized from that batch carries a clone. The refcount
follows the data wherever it goes:

- A record dropped by `filter` (or a Skip policy) resolves its share as
  success — an intentional drop must not stall commits.
- `flat_map` children clone the same ack, so fan-out is covered for free.
- Routing to multiple outputs clones it per output and merges the worst
  status.

When the last clone drops, `(partition, seq, status)` flows over an
**unbounded** channel to the checkpointer — the ack path can never block
behind data, by construction.

**The contiguity tracker.** The checkpointer (a synchronous, tokio-free,
loom-tested module — `spate::checkpoint`) keeps, per partition, a ring of
outstanding batch sequence numbers. It pops the contiguous *acknowledged
prefix* and advances that partition's committable watermark. Out-of-order
acks are fine; the watermark only ever covers a gap-free prefix of
acknowledged data.

**Commit cadence.** Watermarks are stored on advance and committed to the
source on an interval (`checkpoint.interval`, default 5s). The invariant:
**never commit past unacknowledged data.** A failed batch stalls its
partition's watermark rather than being skipped — watch
`spate_checkpoint_watermark_age_seconds`, the primary "stuck pipeline" alert
(see [Monitoring](../05-deployment/monitoring.mdx) and
[docs/METRICS.md](../../METRICS.md)).

**Durability is the sink's ack.** The framework's definition is exactly one
thing: the `ShardWriter` returned `Ok` for that sealed batch. Everything
upstream — the watermark, the commit, the at-least-once claim — is anchored on
that return, so what a sink must prove before returning `Ok` is the sharpest
contract a sink implementation has. A synchronous end-to-end server
acknowledgment and a per-message delivery confirmation are both valid answers;
a fire-and-forget write is not.

## Teardown can't lose data

Two structural contracts guard the seams where acknowledgments travel in
bulk (encoded chunks, worker ledgers, batch accumulators):

- **Collections fail by default.** Every collection of acks on the sink
  path delivers only after an explicit durable write; dropped on any other
  path (a dropped queue, an aborted worker, a runtime shutdown without
  drain), it *fails* its handles. Teardown therefore stalls watermarks
  instead of committing unwritten data.
- **Over-failing is always safe.** A false failure costs a replay; a false
  success costs data. The framework always chooses replay.

## Assignment changes

When work is revoked from this process, the framework drains the owning
threads, flushes and acks in-flight data, and commits watermarks
**synchronously before the revocation completes** — so the next owner resumes
from a correct position. The checkpointer also fences staleness: a full
assignment opens a new per-partition *epoch*, an added partition extends the
current one, and a revoked partition's tracking is dropped on the spot — so
a completion issued under an assignment this process no longer holds is
discarded rather than advancing a watermark that is no longer its own.

That fence is the reason revocation is safe rather than merely fast: it does
not rely on the outgoing owner finishing in time, only on it being unable to
succeed afterwards. The choreography is in
[ADR-0012](../../adr/0012-single-kafka-consumer-with-split-partition-queues.md), and the
fleet-level view in [Work assignment](08-work-assignment.mdx).

## Shutdown and crashes

**Graceful (SIGTERM):** the same drain barrier as a full revocation — lanes
stop, chains flush, sinks force-seal and drain in-flight batches under
`checkpoint.drain_timeout` (default 25s), then a final synchronous commit.
If a sink is down at the deadline, the remaining batches are abandoned
loudly (`spate_sink_abandoned_batches_total` plus a log line) and their
offsets are *not* committed — they replay on restart. See
[Graceful shutdown](../03-guides/graceful-shutdown.mdx).

**Crash (SIGKILL, OOM, panic-and-exit):** nothing was committed past the
last durable write, so on restart the source resumes from the committed
watermark and replays everything after it. At-least-once holds; duplicates
happen. Which brings us to:

## The honest part: duplicates and deduplication

At-least-once means duplicates *will* occur. The framework's one contribution
to narrowing that is the **dedup token**: a deterministic string minted per
sealed batch and reused unchanged across retries of that batch. A sink whose
destination supports insert deduplication can hand the token over and make
same-boundary retries idempotent.

The line the token draws is worth internalizing, because it is not the line
most people assume:

- **Covered — same-batch retries.** A batch that fails and is retried carries
  the same token, so the destination can recognize and drop the repeat.
- **NOT covered — crash replay.** After a restart, replayed records re-batch
  with different boundaries and therefore different tokens. Those rows land
  twice, and no deduplication window will catch them.

So target tables must be designed for replay regardless of what the token
covers. Whether a destination honors the token at all — and what it must be
configured to do so — is the sink's business, and at least one shipped sink has
a silent failure mode here worth reading before going to production.

:::note Connector specifics
Dedup support, and the configuration it depends on:
[ClickHouse](../04-connectors/sinks/clickhouse/README.mdx#deduplication-tokens--and-the-window-warning)
· [Kafka](../04-connectors/sinks/kafka/README.mdx#delivery-semantics-honestly).
:::

:::info
Nothing in Spate is exactly-once, and no configuration makes it so.
If a downstream consumer cannot tolerate duplicates, deduplicate at the
destination or at the query layer.
:::
