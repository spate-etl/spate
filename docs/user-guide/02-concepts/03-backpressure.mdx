# Backpressure

When the sink slows down, something upstream has to give. Spate's answer is one
invariant and the two mechanisms that hold it: one detects the pressure, the
other acts on it.

## The invariant: a source thread never blocks on a channel send

The [chain](../07-reference/glossary.mdx#chain)'s terminal stage hands
encoded [chunks](../07-reference/glossary.mdx#chunk) to the per-shard
queues with `try_send` — never a blocking `send`. When a queue rejects (or
the byte budget crosses its high watermark), the source loop **pauses the
offending [lanes](../07-reference/glossary.mdx#lane) and keeps polling**.

The reason this is non-negotiable rather than a tuning choice: the source
loop is what services the [assignment protocol](08-work-assignment.mdx),
and a loop parked inside `send()` stops servicing it. For a source whose
liveness proof rides the read loop itself, the proof lapses and the
assignment is withdrawn. For a source whose liveness runs in the
background, the [leases](../07-reference/glossary.mdx#lease) stay healthy
but the parked loop cannot answer a reassignment request, so the handoff
stalls to its deadline and the work is
[revoked forcibly](../07-reference/glossary.mdx#cooperative-revocation) —
and replayed by the next owner. Either way the damage is fleet-wide, not
local: peers absorb the moved work, they pause in turn, and "the sink is
slow" has been converted into a churning fleet. Pausing lanes while keeping
the loop running keeps the protocol serviced and confines the slowdown to
exactly where it belongs.

The same reasoning protects the ack path: acknowledgments travel over an
unbounded channel and atomic counters, so a full data path can never block
a completion signal (see
[Delivery guarantees](02-delivery-guarantees.mdx)).

## Detecting the pressure: bounded queues and the byte budget

- **Per-shard bounded queues** between pipeline threads and sink workers.
  Their depth and rejections are visible as `spate_queue_depth` and
  `spate_queue_full_events_total` (every full event is a backpressure signal,
  never a block).
- **A global in-flight byte budget** (`backpressure.max_inflight_bytes`)
  counts every byte that has left the source but has not yet been durably
  written — queued chunks plus
  [sealed batches](../07-reference/glossary.mdx#sealed-batch) in flight at the
  sink. The two are separate units: a worker merges chunks into the batch it
  writes, so chunk size does not bound insert size.

## Acting on it: the pause controller

Pausing a lane is not free for every source, which is what the hysteresis
is for. The pause controller releases a lane only once the budget has
fallen back below the **low watermark** *and* a minimum pause has elapsed;
without both, a budget resting at the boundary would pause and resume every
cycle. Observe it via `spate_backpressure_paused`,
`spate_backpressure_pause_events_total` (a flapping indicator when high),
and `spate_backpressure_inflight_bytes` (see
[Metrics](../../METRICS.md)).

Backpressure is resumable mid-batch: if `try_send` fails partway through a
batch, the chain records the exact resume point — already-processed records
are never re-run through the operators.

The budget bounds what the *framework* holds. A source client with its own
read-ahead buffer holds that data before the framework ever sees it, so it
sits outside the budget entirely — which is a connector-sizing question,
not a framework one, and can dominate a process's memory footprint.

## Sizing the budget {#sizing-the-budget}

This is the one backpressure knob that regularly needs thought. The rule,
motivated by a **24× throughput collapse** under an unthrottled source with
default settings, hand-recorded during the tuning investigation:

```text
max_inflight_bytes × low_ratio  ≥  headroom (≈2×) × (
    shards × inflight.max_per_shard × batch.max_bytes           // pending writes
  + shards × SinkOptions::queue_capacity × chunk.target_bytes ) // queued chunks
```

Every term but one is a configuration key. `queue_capacity` is a builder
knob set through `SinkOptions`, and configuration rejects unknown fields
with the offending key, so a pipeline that names it in YAML fails at
startup.

In words: the budget's low watermark must comfortably hold everything the
sink *legitimately* keeps in flight during steady-state operation. If it
can't, a saturated pipeline lives permanently above the high watermark and
the pause controller duty-cycles at its minimum pause — throughput collapses
even though nothing is wrong.

The framework defaults are deliberately not self-consistent under
saturation: 2 shards at the default batch settings hold about 512 MiB of
pending writes alone, already past the default 256 MiB budget. That is fine
for throttled sources that never fill batches and wrong for saturated ones,
where the budget has to be raised or the batches capped —
[Tuning](../05-deployment/tuning.mdx#the-backpressure-budget-backpressuremax_inflight_bytes)
carries both, worked through.

The flagship example's YAML
([`kafka_avro_to_clickhouse.yaml`](repo:crates/spate/examples/kafka_avro_to_clickhouse.yaml))
carries this rule as a comment next to the knobs — a convention worth copying.
See [Configuring pipelines](../03-guides/configuring-pipelines.mdx) for the
config section itself.

:::note
Symptoms of an undersized budget: `spate_backpressure_paused` pinned at 1
or `spate_backpressure_pause_events_total` climbing fast, low sink batch
sizes, and throughput far below what the sink can absorb — while
`spate_sink_errors_total` stays quiet. The sink isn't failing; the source
is being duty-cycled.
:::

## What backpressure looks like when it engages

Sustained `spate_backpressure_paused == 1` means the sink genuinely can't
keep up (a capacity problem: add replicas or shards, or tune batching) —
or the budget is undersized as above. Paused lanes translate into a growing
backlog at the source, visible as `sum(spate_source_lag_records)` for
sources that publish lag. That is the correct, bounded failure mode: data
waits at the source, not in process memory.
