# Multi-sink split

A pipeline can write to **more than one destination**, routing each record to
exactly one of several typed sinks — each with its own schema, encoder, router,
and batch/linger tuning. Where [sink sharding](05-sink-sharding.mdx) fans one
destination's writes across a cluster, the **split terminal** fans a
heterogeneous stream across *different destinations*: one per record kind, so
each is laid out and indexed for the shape of the records it holds.

The alternative is to land every kind in one destination and let the receiving
system derive the per-kind ones itself. Splitting in the pipeline moves that
fan-out CPU off the destination — usually the scarce, hard-to-scale tier — and
onto the horizontally-scalable pipeline tier, and it puts each destination's
write sizing under its own configuration.

## The shape

```text
                         ┌─ branch "gauge"  → encoder → router → table_gauge
source → deserialize →   ├─ branch "text"   → encoder → router → table_text
        (one stream)     └─ unmatched → ErrorPolicy (Fail | Skip)
```

Each branch is an ordinary sink — the same route → encode → per-shard queue →
worker path as a single `.sink(...)`, just one per destination. The addition is
the **classifier**: a single closure that inspects each record and dispatches it
to one branch. Classification and the (per-branch, differently-typed) row
extraction are the *same* `match` arm, so there is no double-dispatch.

## The routing DSL

Each destination is declared with `add`, which returns a `Copy`, typed handle;
`route` then takes a closure that emits each record to one of them. The closure
mirrors [`flat_map`](../03-guides/assembling-a-pipeline.mdx)'s emitter — one
`match`, doing classification and row extraction in the same arm.

The chain below is the one in `crates/spate/examples/multi_table_split.rs`,
which splits a stream of typed metric readings across two destinations:

```rust file=crates/spate/examples/multi_table_split.rs region=split
```

The record family is explicit at every seam. The chain deserializes into
`Owned<MetricBatch>`; `flat_map` fans each batch out into `Owned<Sample>`
readings, which is what the classifier sees; and each `add` fixes its own
branch's row family — `Owned<GaugeRow>` and `Owned<TextRow>` here, two rows
with genuinely different columns. `ctx.sink("<name>")` resolves the sink
installed under that name, handing the branch that sink's queues **and** its
own resolved chunking (from that sink's `chunk:` block, so each branch tunes
independently). Declaration order fixes the handle indices.

`out.emit(handle, row)` type-checks per arm (the handle fixes the row's family)
and dispatches in O(1) — a branch index and one downcast, no per-record name
lookup. Each branch stores its encoder and router boxed (that is what lets
branches with different encoders share one split), so relative to a single
`.sink()` — whose encoder and router are concrete types — a split pays one
`Any` downcast plus a virtual call into the branch's router and encoder per
record. No allocation, no locks; the routing closure itself stays monomorphic.

The sinks themselves are installed by name before the chain is built, and
configured as a [`sinks:` map](../07-reference/configuration.mdx#sinks):

```rust file=crates/spate/examples/multi_table_split.rs region=install_sinks
```

## Unmatched records: an explicit policy, not a silent drop

A record that reaches no branch (the closure emits to none) follows the
`unmatched` [`ErrorPolicy`](04-error-handling.mdx) passed to `.split(...)`:

- **`Fail`** (the operator default): the pipeline stops — the same fail-stop a
  `Fail`-policy encoder or `try_map` triggers. It fits where an unroutable
  record means the classifier is wrong and halting beats losing data.
- **`Skip`**: the record is dropped, its ack share released as success (exactly
  like a [`filter`](../03-guides/assembling-a-pipeline.mdx) drop), and counted on
  `spate_operator_records_dropped_total{reason="unrouted"}`. It fits where
  unknown kinds are expected and discardable.

There is **no built-in catch-all**. A catch-all *destination* is just another
branch, added and routed to on purpose — it is not framework-special.

:::note
The per-branch shard routers are unchanged and still **total** (see
[sink sharding](05-sink-sharding.mdx)): they always return a shard for a record
they're given. The Skip/Fail policy lives only on the classifier tier —
the one place routing can legitimately produce "no destination".
:::

## At-least-once across destinations is free

The split adds **no new delivery machinery**. Each branch clones the source poll
batch's ack handle, so — exactly as with [`flat_map` fan-out](02-delivery-guarantees.mdx)
— a source batch's offsets commit only once **every** destination its records
landed in has durably written. Two properties fall straight out of the shared
ack:

- **Worst-status merge.** If the write to any one destination fails, that batch
  resolves `Failed` and its watermark stalls — even if every other destination
  wrote successfully. A failure anywhere replays the whole batch. Nothing
  commits past unacknowledged data.
- **Held until all.** A batch whose records fan across three destinations is not
  committable until all three have flushed the batches those records landed in.

## The trade: write size vs. checkpoint lag

Per-destination write size is governed by each sink's
[`batch`](../07-reference/configuration.mdx#sink-pool) (`max_rows` /
`max_bytes` / `linger`). Building **large writes** on a low-volume destination
means raising its `linger`. But the watermark is **poll-batch-granular**, and
a batch is held until every destination it touched has flushed. The hold has
two halves: the chain-side chunk buffer, which the framework bounds
(partial chunks are sealed on every commit tick, so while the pipeline is
unblocked this half stays within ~`checkpoint.interval` — even for a branch
too cold to ever fill a chunk), and
the sink-side batch `linger`, which is the trade being made here:

:::info
If a source batch mixes hot and rare records, its offsets are held until the
**rare** destination's `linger` fires. Rare records are sprinkled across many
batches, so a long rare-destination `linger` inflates checkpoint lag and
restart-replay volume. **Huge rare-kind writes and low checkpoint lag cannot
coexist while rare and hot records occur in the same source batches.**
:::

Two levers soften it:

- **Seal on `max_rows` too, not just `linger`.** With `max_rows` sized to the
  target write, `linger` only bites in genuine lulls, and steady-state a rare
  destination still emits target-size writes without paying the full linger
  hold every time.
- **Segregate the source.** The tracker is per-partition: where a source
  partition carries one record kind, its watermark advances at that
  destination's own cadence and the tension largely dissolves. Interleaved
  partitions pay it in full.

## One dead destination stalls the pipeline

Because the source is shared and records are typed to their destination, a
destination that is **hard-down** (its shard unreachable, circuit breaker open
past retries) correctly stalls the whole pipeline: its records cannot be
written, their batches cannot resolve, and the source cannot advance past them.
This is fail-stop, not data loss, and `checkpoint.stalled_fail_after` converts
a permanent stall into a clean `Failed` exit and a restart. Transient failures
are absorbed by the sink's retry + circuit breaker; only a genuine outage halts
progress.

## Split vs. fan-out at the destination

A receiving system that can derive per-kind destinations from one landing
stream offers the same end state. Both fan a stream into per-kind destinations;
they differ in **who** does the fan-out.

| | Split in the pipeline | Fan-out at the destination |
|---|---|---|
| Fan-out CPU | on the scalable pipeline tier | on the receiving system, per write it accepts |
| Per-destination write size | tuned per sink (`batch`/`linger`) | coupled to the landing stream's writes — rare kinds get small writes that cannot be decoupled |
| Checkpoint cadence | poll-batch, held across destinations (see the trade above) | single-cadence (one landing write) |
| At-least-once | held until all destinations + worst-status merge | the landing write's durability covers what it derives |
| Distinct schemas | one record family + encoder per destination | one derivation per target |

The split wins where the destination is the scarce resource and per-destination
write sizing matters; leaving the fan-out to the destination keeps a simpler
single-cadence checkpoint.
