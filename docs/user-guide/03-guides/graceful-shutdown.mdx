# Graceful shutdown

A pipeline drains on SIGTERM (or SIGINT, or a programmatic
`ShutdownHandle::trigger`): it stops taking new data, flushes what it has,
commits exactly what was durably written, and exits with a meaningful code.
This guide covers the choreography, how to size the one timeout that
governs it, and what happens when the deadline is not met. For what a failure
during the drain means for your data, see
[Error handling](../02-concepts/04-error-handling.mdx).

## The drain choreography

Shutdown deliberately reuses the same drain path as a full partition
revocation, one choreography tested constantly by every rebalance:

1. **Lanes stop.** The controller stops event polling and tells every
   driver thread to shut down. Each driver stops polling its lanes and
   drops them, so no new data enters the pipeline. A coordinated source
   that passes the stop to its driver, as the built-in sources do, also
   stops waiting on its coordination store. A commit, failure report or
   revocation reply already waiting returns at once, and the positions of a
   commit the stop cuts short go out in the final commit in step 4.
2. **Chains flush.** Each driver flushes its operator chain: parked chunks
   and partial buffers are pushed to the shard queues, then the chain (and
   with it that thread's `ShardQueues` clone) is dropped as the thread
   exits.
3. **Sink batches complete**, bounded by `checkpoint.drain_timeout`. Once
   every queue sender is gone, the sink workers see their queues close,
   force-seal partial batches, and get the remaining deadline to finish
   in-flight writes. At the deadline a worker aborts whatever is still
   writing and abandons it (see below); a worker that somehow fails to do
   that is force-aborted a second later, so this step always terminates.
4. **Offsets commit.** The controller drains the checkpointer and runs a
   final synchronous commit + `flush_commits`, committing only watermarks
   that cover durably written data, per the at-least-once invariant. A
   coordinated source that forwards `Source::commit_final` to
   `CoordinationDriver::commit_final`, as the built-in
   [S3 source](../04-connectors/sources/s3/README.mdx) does, runs this commit
   under one budget, `coordination.op_timeout`, for all its splits together.
   Splits it does not reach before the budget ends keep their last committed
   position, and the next owner may replay records from it.
5. **The source closes.** A coordinated source departs its job: it hands
   back its splits, its leadership and its membership, so peers take over
   without waiting out a lease. The departure is bounded by
   [`coordination.op_timeout`](../07-reference/configuration.mdx#coordination);
   whatever it cannot hand back expires.

The I/O runtime stops only after the source has closed. Then everything
joins and `run` returns an `ExitReport`.

## Sizing `drain_timeout` for Kubernetes

`checkpoint.drain_timeout` (default 25s) is the total drain budget. On
Kubernetes, SIGTERM starts both this drain and the pod's
`terminationGracePeriodSeconds` clock (default 30s), after which the
kubelet sends SIGKILL. The rule:

:::warning
Keep `drain_timeout` comfortably **below**
`terminationGracePeriodSeconds`. Steps 1 to 3 run inside the budget; the
gap has to absorb what follows it: the pool's one-second backstop, the
final commit (step 4), the source closing (step 5) and process teardown.
The defaults (25s vs 30s) encode this; if you raise one, raise the other. A
coordinated source that forwards `Source::commit_final` can take up to
`coordination.op_timeout` (10s by default) for the final commit against a
slow store, and up to `op_timeout` again to close. Where a slow store at
shutdown is likely, size the gap to at least twice `op_timeout` plus a few
seconds. At the default that is more than the 5s gap. The same sizing holds
when the store stopped answering before SIGTERM, because the stop ends any
wait on the store already under way. A coordinated source that does not
forward `Source::commit_final` can take up to three times `op_timeout` for
each split in turn at the final commit. One whose `open` does not pass
`SourceCtx::stop` to `CoordinationDriver::set_stop` can wait as long for a
commit already under way at SIGTERM, and one whose coordinator ignores
`SplitCoordinator::set_stop` can wait up to three times `op_timeout` for the
one command under way
([Custom sources](../06-extending/custom-source.mdx#3-delegate-the-choreography-coordinationdriver)).
Keep `op_timeout` above about (2N + 3) times your store's write latency,
where N is the number of splits an instance holds (at most `max_in_flight`).
Below that, the final commit leaves splits to replay even on a healthy
store. That figure is derived from the commit and heartbeat path and was not
measured
([ADR-0059](../../adr/0059-final-coordinated-commit-runs-under-one-op-timeout-budget.md)).
:::

```yaml
checkpoint:
  drain_timeout: 25s    # keep below terminationGracePeriodSeconds
```

A SIGKILL mid-drain is still safe for data (nothing uncommitted is lost;
it replays), but it forfeits the clean commit, so the restart replays more
than it needed to. A SIGKILL while the source closes costs what a crash costs
for whatever it had not handed back: those leases expire, and each takeover of
one of those splits consumes a delivery attempt.

## Exit codes via `ExitReport`

`run` returns an `ExitReport` describing how the pipeline stopped. This
terminal call is from
[`storefront_pipeline.rs`](repo:crates/spate/examples/storefront_pipeline.rs)
(`cargo run -p spate --example storefront_pipeline`), which keeps the
signal handling a deployed process wants: as shipped its source exhausts a
fixed budget and drains on its own, and SIGTERM runs that same drain at
whatever point it arrives.

```rust file=crates/spate/examples/storefront_pipeline.rs region=run title="storefront_pipeline.rs"
```

`report.log()` logs the outcome at the matching level (`info` when clean,
`error` when failed). Pair `report.exit_code()` with `std::process::exit`
(`0` for a clean drain, `1` for a failure) so your orchestrator can tell one
from the other, or take `report.ok()` when your `main` prefers `?`.

`ExitState::Completed` means the drain finished and the final commit ran. A
signal-initiated drain reports it even where the sink deadline expired and
batches were abandoned (see below; the report's `sink_drain` field says so).
A source that reaches the end of its input is held to more, needing every
batch acknowledged and the final commit persisted, or the run exits `Failed`.
`ExitState::Failed` carries the failing component and reason; Kubernetes
restarts the pod and the data replays.

## Abandoned batches: replay, not loss

If the sink cannot flush everything by the deadline (a destination outage
mid-shutdown, say), the remaining batches are **abandoned loudly**: a log
line and a metric, their acknowledgments are failed, and their partitions'
watermarks never advance past them. The final commit therefore commits only
what was written, and the abandoned data **replays after restart**. An
abandon costs duplicate-tolerant replay, never silent loss.

Batch dedup tokens do not survive a restart
(re-batching changes boundaries), so replayed rows land again. Design
target tables to tolerate duplicates. See
[Delivery guarantees](../02-concepts/02-delivery-guarantees.mdx) and the
[ClickHouse connector](../04-connectors/sinks/clickhouse/README.mdx) deduplication notes.

## Why the drain always terminates

The deadline is **cooperative**: each sink worker watches it and, when it
fires, aborts its in-flight writes and abandons what is left. Underneath
that sits a **hard backstop**. A worker that has not returned one second
past the deadline is force-aborted by the pool. The backstop should never
fire; it exists so that an unforeseen stall degrades shutdown to a lost
drain report rather than an unbounded hang, and it says so on
`spate_sink_drain_overrun_total`. A non-zero reading there is a framework
bug worth reporting.

A `write_batch` that blocks its thread between await points cannot be
aborted at all. Give your sink's client a request timeout and let the retry
policy handle the failure.

The cooperative layer is only sound because **nothing on a worker's intake path
blocks outside the `select!` that arms the deadline.** Anything a worker waits
on sits in a branch alongside the deadline branch. Otherwise the deadline is
not being polled while the worker waits, and shutdown deadlocks rather than
degrading. That is why dispatch parks a sealed batch waiting for a permit
instead of awaiting one: an await there would be outside the `select!`, and the
backstop would become the normal path instead of the never-fires path.

### Leaked queues {#leaked-queues-bounded-loud-contained}

The sink workers only enter their drain phase once **every** `ShardQueues`
clone is dropped. The builder makes the correct drop order structural
(queues are lent per chain factory call and die with the driver threads;
see the drain contract in
[Assembling a pipeline](assembling-a-pipeline.mdx)). If an assembly
nevertheless smuggles a queue clone into long-lived state, shutdown does
not hang: the drain deadline breaks the workers out of intake and the sink
abandons loudly exactly as in an outage, a **deadline-bounded loud abandon**
instead of an unbounded wait. Fix the leak anyway, because every shutdown
until then replays data unnecessarily.

## Testing shutdown

Disable signal handling with `handle_signals: false` in `runtime_options`
and drive the drain yourself, with the `into_runtime` + `shutdown_handle`
pattern in [Testing pipelines](testing-pipelines.mdx). From
[`memory_pipeline.rs`](repo:crates/spate/examples/memory_pipeline.rs)
(`cargo run -p spate --example memory_pipeline`):

```rust file=crates/spate/examples/memory_pipeline.rs region=handoff title="memory_pipeline.rs"
```

Push records through the source handle and wait for the commit, then
`shutdown.trigger()` and join the spawned run. The `ExitReport` it hands
back is the one a SIGTERM produces, because it is the same drain.
