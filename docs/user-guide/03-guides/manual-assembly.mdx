# Manual assembly

The `Pipeline` builder is a **thin composition of public primitives**,
following the hyper/axum layering contract: the convenience layer composes
lower-level APIs that are themselves public, semver-committed, and
documented. Nothing in the builder is magic or privileged; this page
desugars every step into the primitives it calls, so you can drop below the
builder at any point, for exotic wiring, for embedding, or to understand
what you are running. The rationale is in
[ADR-0014](../../adr/0014-pipeline-builder-as-primary-assembly.md).

Every snippet below comes from
[`manual_assembly.rs`](repo:crates/spate/examples/manual_assembly.rs),
which assembles and drives a whole pipeline this way and runs as-is with
`cargo run -p spate --example manual_assembly`.

:::note
Prefer the builder. Manual assembly re-exposes the footguns the
builder was designed to make unconstructible: init ordering, doubled I/O
runtimes, leaked queue clones. Use it when you need it, not by default.
:::

## The desugaring map

| Builder step | Public primitives |
|---|---|
| `Pipeline::from_config(config)` | `telemetry::init` → `metrics::install(&metrics_settings(&config))` → `tokio::runtime::Builder` (`io_threads` workers) → `InflightBudget::new` |
| `.sink(bundle)` | `SinkBundle::into_parts` → `shard_queues` → `ComponentLabels` + `SinkShardMetrics::try_new` per shard → `SinkPool::spawn` → a boxed drain closure. It also resolves this sink's `ChunkConfig` from the YAML `chunk:` block — the one step with no manual equivalent, since the config layer is what carries `chunk:`, so by hand you pass a `ChunkConfig` yourself. |
| `.chains(f)` | the chain factory handed to `PipelineRuntime::new`, with queue/budget/name plumbing pre-threaded per call |
| `.into_runtime(source)` / `.run(source)` | `PipelineRuntime::new(config, source, factory, SinkRuntime, budget)` + `with_options` + `with_io_runtime` + `run` |

Module paths (all under the `spate` facade, which re-exports `spate_core` at
the root): `spate::telemetry`, `spate::metrics`, `spate::pipeline`
(`PipelineRuntime`, `SinkRuntime`, `metrics_settings`, `RuntimeOptions`,
`SinkOptions`), `spate::sink` (`shard_queues`, `SinkPool`, `SinkBundle`,
`SinkParts`), and `spate::backpressure` (`InflightBudget`).

## The metric scopes the builder wires

The mapping above is exact but for its metrics: the builder attaches scopes
an assembly below it does not get for free.

- **The queue-depth series** (`spate_queue_*`), attached to the shard
  queues before any chain terminal clones them. The seam that attaches it
  is crate-internal, so a manual assembly publishes no queue series at all,
  and a dashboard or an alert reading one needs a builder assembly.
- **The sink writer's own `spate_<component_type>_sink_*` scope** — the
  `Meter` a connector registers its own families through. Attaching one is
  public (`ShardWriter::attach_metrics`); the builder derives
  that namespace from the bundle's `component_type` and the writer's wiring
  position, so by hand you name it yourself with `Meter::with_namespace`, and
  a name that drifts from the connector's own docs takes its families with
  it.

Everything else in [Metrics](../../METRICS.md) is identical: the
stage metrics, the per-shard sink metrics, the process metrics, and
whatever your own components register through a `Meter` of their own.

## Step by step

### Process init — what `from_config` does

The config, telemetry, the exporter, the I/O runtime and the in-flight
byte budget, in that order. The order is why the builder owns this step:

```rust file=crates/spate/examples/manual_assembly.rs region=init
```

Do this from a plain thread, usually `main`: a tokio runtime dropped inside
async context panics. The builder refuses that case up front with
`BuildError::AsyncContext`; by hand there is nothing to refuse it.

`metrics::install` is **idempotent**, which matters when you are embedding a
pipeline in a larger program. A second call returns the first exporter rather
than failing or replacing it, so you can install early (right after loading
configuration, before anything else runs) and the runtime's own install
reuses what you created. `exporter: none` never claims the process slot,
so a pipeline with metrics disabled leaves the recorder free for
whatever else in the process wants it.

### Connectors

Exactly as under the builder: your factories read the opaque `source:`,
`deserializer:` and `sink:` sections of the config. A connector that needs
an async pre-step takes `io.handle()` or `io.block_on(...)` directly, which
is all `Pipeline::io_handle` and `Pipeline::block_on` forward to.

### The sink — what `.sink(bundle)` does

`SinkBundle::into_parts` is the seam every sink crosses: out of it come the
writer, the `[shard][replica]` topology, the pool tuning and the readiness
probe. This step turns those into the shard queues the chain terminals send
into, the per-shard metric handles, the worker pool, and the drain hook the
runtime calls once at shutdown:

```rust file=crates/spate/examples/manual_assembly.rs region=sink
```

`SinkRuntime::queues` takes one entry per installed sink, so a single-sink
assembly passes a one-element vector. Writing to several destinations means
repeating this step per sink and passing one entry each. See
[Multi-sink split](../02-concepts/06-multi-sink.mdx).

### The runtime — what `.chains` + `.into_runtime` do

The chain factory takes a bare thread index, and you thread the queues, the
budget and the pipeline name into it yourself; that is the whole of what
`ChainCtx` does for you. `PipelineRuntime::new` then takes the config, the
source, that factory, the `SinkRuntime` and the budget:

```rust file=crates/spate/examples/manual_assembly.rs region=runtime
```

Without `with_io_runtime`, `run` builds a runtime of its own and the process
carries `2 × io_threads`
workers. `run` owns that runtime's shutdown either way, so tasks you
spawned on it earlier keep running until then.

From the shutdown handle on, a manual assembly drives exactly as a builder
assembly does: push records, wait for the watermark, trigger the drain and
join for the `ExitReport`. [Testing pipelines](testing-pipelines.mdx) walks
that half.

## What you take responsibility for

The builder turned each of these from a documented rule into a structural
impossibility; manually, they are yours again:

- **Init order** — exporter before any handle, telemetry before anything
  logs, all of it before threads spawn.
- **One I/O runtime** — build once, pass to `SinkPool::spawn` by handle and
  to the runtime by value.
- **Queue drop ordering** — the sink drains only when every `ShardQueues`
  clone is gone; audit every clone you make (see
  [Graceful shutdown](graceful-shutdown.mdx)).
- **Topology validation** — shard, label and receiver counts must agree.
  The builder checks them all and returns `BuildError::Sink`. By hand an
  empty topology panics out of `shard_queues` and a shard with no replicas
  out of `SinkPool::spawn`, but replica labels that do not match their
  shard's endpoints are caught nowhere: a surplus label publishes health
  for a replica that does not exist, and a missing one drops a live
  replica's health silently.

## The layering contract

Both layers are public and semver-committed. The builder grows no capability
the primitives cannot express, bar the standing exceptions above (the
queue-depth series, which has no public seam, and resolving a per-sink
`chunk:` block, which is the config layer's job), and the primitives will
not break under you to make the builder prettier. If you
outgrow one builder step, desugar *that step* and keep the rest; the two
paths compose because they are the same path.
