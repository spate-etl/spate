# Securing connections (TLS, mTLS, SASL)

Spate has no framework-wide security layer: **transport security is a property
of each connector**, because every connector talks to its system over that
system's own client, with that client's own TLS and auth knobs. This page is
the hub. It covers what *is* framework-wide (how secrets reach the config, and
what happens when authentication fails) and points at each connector for the
concrete mechanism.

|---|---|---|---|
| Kafka source | TLS, mTLS, SASL | opt-in `kafka-tls` feature | [Kafka source → Security](../04-connectors/sources/kafka/README.mdx#security-tls-mtls-sasl) |
| Kafka sink | TLS, mTLS, SASL | opt-in `kafka-tls` feature | [Kafka sink → Security](../04-connectors/sinks/kafka/README.mdx#security-tls-mtls-sasl) |

| Avro format | TLS, registry basic auth | none | [Avro → Security](../04-connectors/formats/avro/README.mdx#security-tls-and-registry-credentials) |

Connectors that share a client share a matrix; the Kafka source and sink
render the same one, from the same partial.

## Secrets stay out of the file

Never commit credentials. Every value in the config, including inside connector
bodies, is
[environment-interpolated](configuring-pipelines.mdx#environment-interpolation)
before parsing, so pass secrets in from the environment (a Kubernetes
Secret, a vault sidecar) and reference them with `${VAR}`:

```yaml
sink:
  clickhouse:
    password: "${CLICKHOUSE_PASSWORD}"     # quote the site — see interpolation caveats
```

Interpolation is textual and pre-parse, so **quote the value site** when a secret
may contain YAML-significant characters. The four `${...}` forms and the
quoting rules are in
[Configuring pipelines](configuring-pipelines.mdx#environment-interpolation).

A pipeline config's `Debug` output shows its keys and renders every value
inside a connector body as `<redacted>`. A bundled connector's own config
renders its passwords, the values of its passthrough option maps, and any
userinfo, query or fragment in its URLs as `<redacted>`. Other fields print as
configured, including usernames.

Secrets that never enter the config file are better still: a connector
that resolves ambient cloud credentials, or reads a mounted credentials file,
gives you nothing to leak.

## What a security failure does at runtime

Every connector applies one rule
([ADR-0047](../../adr/0047-a-rejected-credential-or-tls-handshake-is-fatal.md)).
A rejection is fatal:

- a certificate the client's TLS stack fails to verify;
- a fatal TLS alert from the server that names the certificate, the credential
  or the negotiation;
- no protocol version, cipher suite or other handshake parameter in common with
  the server;
- an authentication or authorization error from the server;
- a `401` or `403` from the service.

A failure to obtain credentials or reach the server is retryable, and so are a
connection reset, closed or timed out during the handshake, a malformed TLS
message, and any other alert. Some client libraries do not report every
rejection, and a connector's security section lists the cases that stay
retryable there.

The class and the stage that meets the failure decide what you see:

- **Fatal, at startup.** Startup fails, and the error carries the reason.
- **Fatal, in a source or deserializer.** The pipeline stops, and the exit
  report carries the reason. A component that connects on demand meets the
  failure at the first record that needs the connection.
- **Fatal, in a sink.** The batch is abandoned, and the `sink write failed`
  warning and the `abandoning sink batch` error carry the reason. The pipeline
  fails once a partition's watermark has stalled behind that batch for
  `checkpoint.stalled_fail_after`, and the exit report names the partition, the
  sink and the reason. `spate_sink_abandoned_batches_total` counts the batch.
- **Retryable, in a source.** The source retries. Its connector page names any
  deadline or attempt budget that ends the retries. The error at that limit
  names the limit, and the reason is in the warnings logged before it. The
  connector page says whether that error also carries the reason.
- **Retryable, in a deserializer.** The batch is held and replayed while the
  failure lasts, counted by `spate_deser_not_ready_total`.
- **Retryable, in a sink.** Under the default sink retry settings the sink
  retries without limit, and the pipeline keeps running with nothing written.
  `/readyz`, `spate_sink_shard_healthy`, `spate_backpressure_paused` and
  `spate_checkpoint_watermark_age_seconds` show it.

covers how a fatal error stops the pipeline, and
[Monitoring](../05-deployment/monitoring.mdx#starting-alerts) the alerts for
