# Testing pipelines

The `spate-test` crate is the first-class way to test pipelines you build
with this framework: deterministic in-memory mocks, no Docker, no external
infrastructure. Every mock pairs with a scripting/observation handle (the
`tower-test` philosophy) — you drive the source side, script the sink side,
and assert on what actually got written and committed.

Everything below comes from `crates/spate/examples/memory_pipeline.rs` —
the same pattern as a runnable demo, which runs as-is with
`cargo run -p spate --example memory_pipeline`. In your own project you
need `spate` and `spate-test`, the latter as a dev-dependency.

## The pieces

| Mock | Handle | Role |
|---|---|---|
| `memory_source()` → `MemorySource` | `SourceHandle` | Scripts lane assignments/revocations, pushes payloads, observes commits and pauses. |
| `capture_sink(shards, replicas)` → `CaptureSink` | `SinkScript` | A full `SinkBundle` over a `CaptureWriter`; records every write, scripts failures and probe health. |
| `TestDeserializer` | — | Payload → records: `passthrough()`, `split_on(b',')`, `fail_on_prefix(...)` for poison payloads. |
| `TestEncoder` / `decode_rows` | — | Length-prefixed row encoder whose frames tests can decode back into rows. |

## The pattern: `into_runtime` + `shutdown_handle` + a spawned run

A test imports the `spate` prelude and the mocks it drives:

```rust file=crates/spate/examples/memory_pipeline.rs region=imports
```

A test config is an ordinary config:

```rust file=crates/spate/examples/memory_pipeline.rs region=config
```

The `memory` and `capture` tags in `source:` and `sink:` are informational
here — the in-memory pieces are built programmatically, not from those
sections. Two things bite once a second pipeline runs beside this one,
because both are process-wide:

- **The admin server's address.** The runtime binds `metrics.listen`
  whatever the exporter is set to, and a bind failure stops the run — so
  the default `0.0.0.0:9090` collides. Give each test
  `metrics: { listen: "127.0.0.1:0" }` and let the kernel pick the port,
  or `metrics: { exporter: none, listen: "127.0.0.1:0" }` where the test
  wants no process-global recorder at all.
- **Metric series ownership.** A gauge series has one live owner per
  process, keyed on the pipeline and component labels — so two pipelines
  alive at once under the same `pipeline.name` fail to build rather than
  quietly describing one series from two writers. Name each one for its
  test. A claim is released when its handles drop, so pipelines built one
  after another may share a name.

Each mock comes back paired with its handle — the source handle pushes
records and reads committed watermarks back, the sink script reads every
durable write back:

```rust file=crates/spate/examples/memory_pipeline.rs region=mocks
```

The batch `linger` defaults to 1s, which is a long time to wait for a
flush. Shrinking it on the sink's pool config, as above, is what lets a
test finish in milliseconds.

Assemble with the ordinary `Pipeline` builder — the sink, the chain factory
and the chunking are the production steps unchanged, and
[Assembling a pipeline](assembling-a-pipeline.mdx) walks them. Two things
differ. Turn signal handling off with `handle_signals: false` in
`runtime_options`, because the test triggers shutdown itself rather than
raising SIGTERM at its own process. Then finish with `into_runtime` instead
of `run`, so you hold the shutdown handle before anything starts, and spawn
the blocking `run` on a thread:

```rust file=crates/spate/examples/memory_pipeline.rs region=handoff
```

:::note
`Pipeline::from_config` must run outside any async runtime, so write
these as plain `#[test]` functions, not `#[tokio::test]`.
:::

## Driving the source: `SourceHandle`

Assign a lane, push payloads, wait for the committed watermark to cover the
last offset, then trigger the drain and join the spawned run for its
`ExitReport`:

```rust file=crates/spate/examples/memory_pipeline.rs region=drive
```

- `assign_lanes` queues an assignment event, exactly as a real rebalance
  would surface one. Pushing to a partition with no active lane yet is
  allowed — payloads wait.
- `push` / `push_many` queue payloads and return their offsets;
  `push_at` sets an explicit event timestamp.
- `revoke_lanes` returns a `DrainBarrierProbe` for testing rebalance drain
  choreography; `paused_lanes()` observes backpressure.
- The mock is deliberately strict: misuse that would indicate a runtime bug
  (pausing an unassigned lane, duplicate lane ids) panics with a clear
  message rather than passing silently.

## Asserting the commit: one-past-last watermarks

Waiting for the watermark is the strongest assertion a test can make,
because watermarks advance only after the sink durably acknowledged every
record — the at-least-once contract itself. **Committed positions are one past the last
offset** — the "next position to read", the same convention the framework
commits everywhere, which is why the target is `last + 1`.

Bound the wait, whichever way you write it: an unbounded one turns a broken
pipeline into a hung test rather than a failing one.
`handle.wait_committed(partition, last + 1, timeout)` is the blocking
equivalent of the poll loop, waking on each commit instead of sleeping, and
returns whether the target was met. `handle.committed()` returns every
watermark ever committed, in call order, when you need more than the
latest.

## Asserting the writes: `SinkScript` and `decode_rows`

Everything the sink wrote is captured, in order, with shard/replica
targeting, row and byte counts, and the batch's dedup token:

```rust file=crates/spate/examples/memory_pipeline.rs region=capture
```

`decode_rows` inverts `TestEncoder`'s length-prefixed framing back into the
row payloads.

### Scripting failures

Unscripted writes succeed, so happy-path tests need no scripting. For
failure paths:

- `script.enqueue_for(shard, replica, WriteOutcome::retryable("boom"))` —
  the next write to that endpoint fails retryably (the framework retries the
  same sealed batch, rotating replicas); `WriteOutcome::fatal(...)` abandons
  the batch and stalls the watermark; `.after(duration)` adds a delay.
- `script.enqueue_global(...)` — same, for the next write to any endpoint.
- `script.fail_probe(shard, replica, "down")` / `heal_probe` — drive the
  readiness probe, and with it `/readyz`.

## Testing stages in isolation

You do not need a whole pipeline to test a deserializer or encoder:
`TestDeserializer`, `TestEncoder`, and `EmitCollector` exercise single
stages, and the `spate-test` crate docs walk the full life of one record —
poll, deserialize, encode, acknowledge, commit — against a real
`Checkpointer` with no runtime at all. For property tests, the `proptest`
feature adds ready-made `strategies`.
