The bundled librdkafka is built **without TLS/SASL by default**, so connecting
to a secured cluster needs the opt-in **`kafka-tls`** feature. The feature
builds OpenSSL from vendored sources, which adds to the
[toolchain requirements](../01-getting-started/01-installation.mdx#toolchain-requirements).
Once enabled,
every security property is set through the connector's raw `rdkafka:`
passthrough; these keys are **not** on the denylist, and the configuration is
identical for the Kafka source and the Kafka sink. Setting any security
property **without** the feature fails fast at config load with an actionable
message rather than an obscure runtime error. Every `rdkafka:` value renders
`<redacted>` in the config's `Debug` output; the keys stay visible.

```toml
# Cargo.toml
spate = { version = "0.2", features = ["kafka-tls"] }   # implies "kafka"
```

### TLS (server authentication only)

Encrypt the connection and verify the broker's certificate against a CA, the
minimum for a cluster that terminates TLS but authenticates clients by SASL (or
not at all):

```yaml
rdkafka:
  security.protocol: ssl
  ssl.ca.location: /etc/kafka/ca.pem   # omit to use the system trust store
```

Without `ssl.ca.location` or `ssl.ca.pem`, the CA default depends on which
OpenSSL the build links:

- **Vendored OpenSSL**, the `kafka-tls` default: the connector sets
  `ssl.ca.location: probe`. On Linux and BSD, librdkafka then loads the first
  standard CA location it finds, such as `/etc/ssl/certs/ca-certificates.crt`.
  When that location is a bundle file, librdkafka reads no other, and a CA
  installed only in a hashed certificate directory is not trusted; set
  `ssl.ca.location` to that directory. The hashed directory `/etc/ssl/certs`
  is itself on the probe list. When no standard location exists, librdkafka
  falls back to the vendored OpenSSL's default verify paths under
  `/usr/local/ssl`.
- **System OpenSSL**, built with `OPENSSL_NO_VENDOR=1`: the connector leaves
  the key unset and librdkafka's native default applies. On Linux and BSD that
  is the system OpenSSL's default verify paths, including its hashed
  certificate directory, unless librdkafka links libcrypto statically, in
  which case it probes as above.

If `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, the connector leaves the key unset
in either build. On macOS, librdkafka applies `probe` itself and does not read
the Keychain. On Windows, it reads the system certificate store.

### mTLS (client-certificate authentication)

Add the client certificate and its private key; the broker authenticates the
pipeline by certificate instead of (or alongside) SASL:

```yaml
rdkafka:
  security.protocol: ssl
  ssl.ca.location: /etc/kafka/ca.pem
  ssl.certificate.location: /etc/kafka/client.pem
  ssl.key.location: /etc/kafka/client.key
  ssl.key.password: "${KAFKA_KEY_PASSWORD}"   # only if the key is encrypted
```

A PKCS#12 keystore works too (`ssl.keystore.location` + `ssl.keystore.password`)
if you prefer a single bundle to separate PEM files.

### SASL SCRAM or PLAIN over TLS

Username/password authentication carried inside the TLS tunnel. Use `sasl_ssl`
and never `sasl_plaintext`, which sends credentials in the clear:

```yaml
rdkafka:
  security.protocol: sasl_ssl
  sasl.mechanism: SCRAM-SHA-256          # or SCRAM-SHA-512, or PLAIN
  sasl.username: "${KAFKA_USER}"
  sasl.password: "${KAFKA_PASSWORD}"
  ssl.ca.location: /etc/kafka/ca.pem     # for the TLS side of sasl_ssl
```

Set `sasl.mechanism`: it defaults to `GSSAPI` (Kerberos), which the feature does
not compile in. A client configured with `GSSAPI` fails at startup with
`No provider for SASL mechanism GSSAPI`.

`OAUTHBEARER` has no production token source: the OIDC method is not compiled
in, and the connector registers no token-refresh callback. With the default
method, a client never connects to a broker and raises no authentication error.
The source fails once `startup_timeout` passes; the sink retries as it would
through a broker outage. librdkafka's unsecured token handler
(`enable.sasl.oauthbearer.unsecure.jwt`) does connect, and is for development
and testing only.

### When authentication or TLS fails

The source fails at once on a SASL authentication failure or a rejected TLS
handshake, and the exit report carries the reason. A rejected handshake is one
of:

- a broker certificate the client fails to verify. The reason reads
  `certificate verify failed` whether the CA is untrusted, the name does not
  match or the certificate has expired by the client's clock.
- a TLS alert listed in `spate::error::TLS_REJECTION_ALERTS`, with which the
  broker rejects the handshake. The reason carries the alert's name and
  number, such as `handshake failure` (`SSL alert number 40`), which a TLS 1.2
  broker sends for a missing client certificate or no cipher suite in common,
  `unknown ca` (48), `protocol version` (70) or, under TLS 1.3,
  `certificate required` (116).

A rejection by any broker the source connects to fails it. Any other TLS
failure, such as a connection reset or closed during the handshake, a
malformed message or an `internal error` alert (80), is retryable.
`startup_timeout` bounds the wait for a first partition assignment, and
`assignment_timeout` the wait after an assignment is lost. Either ends in a
`no partition assignment` error that also names the last consumer error, such
as a refused connection, and how long ago it arrived.

The sink sees both failures as timed-out deliveries. A timed-out delivery is
fatal when it follows a rejection by a broker the sink connects to, a SASL
authentication failure or a rejected handshake as listed above, by at most
`delivery_timeout` + 35s + `reconnect.backoff.max.ms` (10s by default). This
holds for a delivery bound for any broker. The batch fails once
`delivery_timeout` passes, and the pipeline fails once
`checkpoint.stalled_fail_after` elapses. The `sink write failed` warning ends
with how long ago the rejection arrived and librdkafka's text, such as
`a broker rejected the connection 33.5300315s ago: … Invalid username or password`.
The `sink probe failed` warning carries the same text, and `/readyz` reports
not ready.

Any other timed-out delivery is retryable. Under the default
[`retry` settings](../07-reference/configuration.mdx#sink-pool) the pipeline
then keeps running with nothing written, and `/readyz` reports not ready.
