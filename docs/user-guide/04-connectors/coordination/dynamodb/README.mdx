# DynamoDB (coordination store)

The DynamoDB store (`spate-coordination`, feature `coordination-dynamodb` on
the `spate` facade) keeps a coordinated job's split records, leases and plan in
one DynamoDB table. It needs no servers of its own and authenticates through
IAM. Its watches list their prefix every `poll_interval` and report the
difference; the store does not read DynamoDB Streams
([ADR-0050](../../../../adr/0050-coordination-stores-may-declare-a-polled-watch.md)).
Discovery is therefore slower than on a store that pushes changes, and every
poll is a billed read. Leases carry no expiry the table enforces: each worker
judges a lease expired from its own reads.

Select it under `store:` in the pipeline's
[`coordination:` section](../../../07-reference/configuration.mdx#coordination):

```yaml file=crates/spate/examples/dynamodb_coordinated_backfill.rs region=coordination
```

`table` and `job` are the two required keys of the `dynamodb` body. The keys
beside `store:` are the coordinator's tuning, and `lease_duration` is also the
lease TTL the store is built with. The values suit a demo against DynamoDB
Local, and the example's comment gives each one's default and why it differs.
`endpoint` and `create_table` are there for DynamoDB Local; a deployment leaves
both unset.

That section comes from
[`dynamodb_coordinated_backfill.rs`](repo:crates/spate/examples/dynamodb_coordinated_backfill.rs),
one instance per process against DynamoDB Local, the emulator AWS publishes,
on `http://127.0.0.1:8000` (override with `DYNAMODB_ENDPOINT`). DynamoDB Local
accepts any key pair, so the environment gives the provider chain a dummy pair
and a region. Two terminals, each with a distinct `POD_NAME` (the section's
`instance_id`), divide one backfill between them, and two live workers claiming
one identity is detected and fatal:

```sh
docker run --rm -p 8000:8000 amazon/dynamodb-local -jar DynamoDBLocal.jar -inMemory
export AWS_ACCESS_KEY_ID=local AWS_SECRET_ACCESS_KEY=local AWS_REGION=us-east-1
POD_NAME=worker-a cargo run -p spate --features s3,json,coordination-dynamodb --example dynamodb_coordinated_backfill
POD_NAME=worker-b cargo run -p spate --features s3,json,coordination-dynamodb --example dynamodb_coordinated_backfill
```

Run the `export` line in both terminals. A binary built without the
`coordination-dynamodb` feature rejects a `dynamodb` store at startup, naming
the feature.

Construction is synchronous and lazy. The first store operation, the
coordinator's startup probe, loads the AWS configuration and checks the table,
so a table still being created rides the startup retry budget. A check that
the coordinator's `op_timeout` deadline cancels runs again on the next
operation over the same connection, keeping the credentials it already loaded.
A connect or check that returns an error, including one the SDK's own operation
timeout ends, drops the connection: the next attempt reads the AWS config and
credentials files, the trust store and the region again, and its error names
the reason as it stands then.
Misconfiguration, such as a malformed table name or an endpoint that is not a
URL, fails startup with a fatal error that names the key.

## Configuration

The `coordination: { store: { dynamodb: ... } }` section deserializes into
`DynamoDbConfig`
([`spate-coordination/src/store/dynamodb/config.rs`](repo:crates/spate-coordination/src/store/dynamodb/config.rs));
unknown fields are rejected with the offending key. Errors name the key as
`dynamodb.<key>`, and `Debug` output redacts the endpoint's userinfo and query.

| Key | Type | Default | Description |
|---|---|---|---|
| `table` | string | `required` | Table name (3 to 255 characters of `[A-Za-z0-9_.-]`) or table ARN. Many jobs can share one table. |
| `job` | string | `required` | Job identity, `[A-Za-z0-9_-]{1,64}`. Prefixes the partition keys of every item the job writes. Every worker of one job uses the same value; two different jobs must never share one. |
| `region` | string | `none` | AWS region. Unset, the AWS provider chain supplies it (`AWS_REGION`, the shared config file, instance metadata). Startup fails when neither does, or when the chain has not answered within a quarter of `coordination.op_timeout`. |
| `endpoint` | string | `none` | An `http://` or `https://` URL in place of the region's endpoint, such as DynamoDB Local's. |
| `create_table` | boolean | `false` | Create the table when it is missing, with on-demand billing, and enable time to live on `x` when it is off on an active table. See [The table](#the-table). |
| `poll_interval` | duration | `2s` | Time between two listings of a watched prefix. See [Latency and cost](#latency-and-cost). |

`coordination.lease_duration` has two floors on this store: at least `1s`, and
at least five poll intervals. `coordination.op_timeout` sets the SDK's
deadlines, so the store's attempts, retries and backoff all finish inside it.

A store built in code takes the same fields as `DynamoDbConfig`
(`DynamoDbConfig::new(table, job)` plus the optional fields), and
`DynamoDbStore::new(config, lease_ttl, op_timeout)` takes the lease TTL and the
operation deadline. Both must equal the coordinator's `lease_duration` and
`op_timeout`, and the coordinator rejects a store whose values differ.

Values are capped at 384 KiB, leaving room in DynamoDB's 400 KB item for the
key and the store's own attributes. A larger value fails before any request,
naming the key.

## Security (credentials and TLS)

Credentials come from the AWS provider chain and never from the pipeline file.
The chain tries, in order, the environment (`AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`), the shared config and credentials files (including
SSO sessions and `credential_process`), web identity tokens (IAM roles for
service accounts on EKS), container credentials (ECS task roles and EKS Pod
Identity), and EC2 instance metadata (IMDSv2).

Requests to DynamoDB and to the credential providers go through the proxies
the standard variables name (`HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY`),
except for hosts `NO_PROXY` lists.

The store verifies the endpoint's certificate against the system trust store,
read when the store connects: at its first operation, and again after a
connect or startup check that returns an error. An attempt the coordinator's
deadline cancels reads nothing again. When `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, the
certificates they name replace the system store. If the store yields no
certificates, the store logs a warning and uses the Mozilla root bundle
compiled into the binary.

TLS runs on rustls with the `aws-lc-rs` provider. The AWS client enables
rustls's `prefer-post-quantum` feature, and Cargo enables a feature for the
whole build. Every rustls client on `aws-lc-rs` in a binary built with
`coordination-dynamodb` therefore offers the X25519MLKEM768 hybrid key exchange
first, and its ClientHello grows by that key share. A TLS-inspecting proxy that
rejects a large ClientHello breaks those connections.

Credential and TLS failures are classified as
[ADR-0047](../../../../adr/0047-a-rejected-credential-or-tls-handshake-is-fatal.md)
states:

| Failure | Class |
|---|---|
| `AccessDeniedException`, `UnrecognizedClientException`, `InvalidSignatureException`, `MissingAuthenticationTokenException`, `IncompleteSignatureException`, `ExpiredTokenException`, or a 401 or 403 from DynamoDB | Fatal |
| A certificate the store does not trust, or a handshake the server refuses | Fatal |
| A failure to load or refresh credentials | Retryable; the message carries the provider's reason |

The store classifies the other failures itself:

| Failure | Class |
|---|---|
| `ResourceNotFoundException`, `ValidationException`, `ItemCollectionSizeLimitExceededException` | Fatal |
| No region from the config or the provider chain | Fatal |
| Throttling, a 5xx, a timeout, a connection failure (including a proxy that refuses the tunnel), a conflict, or a code the store does not know | Retryable |

The SDK retries throttling and server errors itself, up to three attempts
inside `op_timeout`, before the store reports them. An attempt that gets no
response within a quarter of `op_timeout` ends and is retried. A response whose
body delivers nothing for 5 s, the SDK's stalled-stream grace period, which the
store leaves at its default, ends and is retried when that and the backoff fit
inside the SDK's operation timeout of 0.9 × `op_timeout`. Otherwise it runs to
the operation timeout and is reported as Retryable. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

The SDK also stops retrying while its retry quota is empty, and a burst of
failed attempts can empty it. The creates that seed a plan's split records draw
on a quota of their own, so a throttled seeding burst leaves lease renewals and
commits their retries. Every other call shares one quota with any other
DynamoDB client in the process that uses the SDK's default retry partition for
the same region.

## IAM policy

A worker needs these actions on the table:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["dynamodb:DescribeTable", "dynamodb:DescribeTimeToLive"],
      "Resource": "arn:aws:dynamodb:<region>:<account>:table/<table>"
    },
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:UpdateItem",
        "dynamodb:ConditionCheckItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query"
      ],
      "Resource": "arn:aws:dynamodb:<region>:<account>:table/<table>",
      "Condition": {
        "ForAllValues:StringLike": { "dynamodb:LeadingKeys": ["<job>#*"] }
      }
    }
  ]
}
```

The `Condition` is optional. It confines a worker to its own job's items, so
two jobs sharing a table cannot touch each other's records. With
`create_table: true`, add `dynamodb:CreateTable` and `dynamodb:UpdateTimeToLive`
to the first statement. Without `dynamodb:DescribeTimeToLive` the store logs a
warning at startup and continues.

## The table

One table holds any number of jobs. Its key schema is fixed:

| Attribute | Key | Type |
|---|---|---|
| `pk` | partition (hash) | string |
| `sk` | sort (range) | string |

Each job writes four partition keys: `<job>#d` holds its durable records,
`<job>#e` its leases and presence keys, `<job>#f` the revision floor each
deleted lease or presence key leaves, and `<job>#m` the settings it started
with. The record key is the sort key.

At startup the store refuses, with a fatal error:

- a key schema other than the one above;
- a local secondary index, which caps a partition key's items at 10 GB;
- replicas, whose conditional writes do not order against each other across
  regions;
- a table that is being deleted, is archived, or is in any status other than
  creating, active or updating.

A global secondary index logs a warning, since every write also updates it.

The store writes `x`, an epoch-seconds time to live, on every lease write and
every revision floor (a day ahead) and on every durable delete marker (seven
days ahead), so the table collects items nothing renews. Expiry never reads `x`. The store logs a
warning at startup, and starts, when time to live is off or on another
attribute, or when `DescribeTimeToLive` is denied and its status is unknown.
Those items then stay in the table.

With `create_table: true`, a missing table is created with on-demand billing,
and a table that already exists is adopted. On either, the store enables time
to live on `x` when startup reads it as off on an active table, including while
it is being disabled. A table that is updating, for example during an index
backfill, keeps its time to live as it is, and the store logs the warning
above. When `DescribeTimeToLive` is denied, the store leaves time to live
unset. When DynamoDB refuses the enable, as it does for up to an hour after a
change to the table's time to live
([`UpdateTimeToLive`](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_UpdateTimeToLive.html)),
the store logs the reason as a warning and starts. Creating takes one or more
startup attempts; if the table is still not active when they run out, raise
`coordination.startup_max_attempts`. To create the table by hand:

```sh
aws dynamodb create-table --table-name spate-coordination \
  --attribute-definitions AttributeName=pk,AttributeType=S AttributeName=sk,AttributeType=S \
  --key-schema AttributeName=pk,KeyType=HASH AttributeName=sk,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST
aws dynamodb update-time-to-live --table-name spate-coordination \
  --time-to-live-specification Enabled=true,AttributeName=x
```

A job's first worker records the lease TTL and the item layout in the job's
settings item. A later worker with a different lease fails at startup with a
fatal error naming both values. Finish the job, or delete its items, before
changing `lease_duration`. `poll_interval` is not recorded, so it can change in
a rolling restart.

DynamoDB serves each physical partition of a table at up to 3,000 read units
and 1,000 write units per second, as its
[partition key guidance](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html)
states. All of a job's leases share one partition key, and so do all of its
durable records, so each set starts on one physical partition. Those limits
bound how large one job's fleet can grow on this store.
[Latency and cost](#latency-and-cost) gives the read rate against the fleet
size.

## Lease expiry

A lease item carries a revision and no expiry the table enforces. Each worker
judges expiry from its own consistent reads, on its own clock:

- A worker notes when it first read a lease at its current revision.
- The lease is expired once a later read that began at least one lease
  duration after that still returns the same revision.
- A read that fails judges nothing. A worker whose reads fail through an
  outage expires no lease in its view, however long the outage lasts.

A peer that is watching sees a dead worker's lease expire up to one lease plus
two poll intervals after the worker's last heartbeat, plus the time its polls
spend querying the table. The peer first reads the heartbeat at its next poll,
up to one interval later, and the poll that judges the lease starts up to one
interval after the lease has run from that read, since each poll starts one
`poll_interval` after the previous one ends. A worker that starts watching
after the death sees the lease expire one lease after its own first read of it,
plus up to one poll interval: close to two leases after the death when it
starts just before the lease would have run out. No decision
compares clocks across machines. The owner stops its splits at its first
renewal tick or poll after one lease has run from its last successful renewal,
measured from when the renewal returned, and a peer's lease measure starts when
its read returned. The two can overlap by one renewal's response time plus up
to one poll interval and its query; the epoch fence on every commit makes that
overlap safe, as it does on every store.

A lease a worker creates takes its revision from that worker's wall clock, kept
above every revision the worker has seen for the key. Deleting a lease or
presence key first raises its revision floor to one above the revision it
removes, and a create checks that floor in the same transaction that writes the
key, retrying once just above a higher floor. A re-created key therefore lands
above every revision it held. A renewal or takeover lands at least two above
the revision it replaces. A watcher reports a delete, on expiry or on removal,
one above the highest revision its worker saw for the key, which for a removal
is at most the floor it left. A renewal, takeover or re-create therefore lands
above every delete a watcher reported for the key.

That holds while the table keeps the key's floor and its last item. Time to
live collects a floor no sooner than a day after the key's last delete, and a
lease no sooner than a day after its last write, each by the wall clock of the
worker that wrote it, so a lagging clock brings collection forward by its lag.
A lease that time to live collects leaves no floor. Once either is gone, a
re-create lands at or below the key's last revision only when its creator's
clock trails the clock that wrote that revision by at least a day, less that
lag. A watcher holding the higher revision then reports a delete and then the
new lease.

## Latency and cost

A change reaches a watch at the watcher's next poll, so discovery takes up to
one `poll_interval` (default `2s`). Takeover of a dead worker's splits waits for
the leader to see its lease expire, as [Lease expiry](#lease-expiry) bounds it,
then `coordination.rebalance_delay` while the leader withholds the splits, then
up to one poll interval for the leader's next assignment and one more for the
new owner to read it. The new owner reads its assignment with an eventually
consistent query, so each of its polls that reads a replica the write has not
reached yet adds one more poll interval. The new owner claims a split only once the split's lease
has expired in its own view too. A worker that was watching before the death
has seen that by then. A worker that started watching after the death sees it
one lease plus up to one poll interval after it started.

By arithmetic at the defaults (a `30s` lease, a `2s` poll interval and a `20s`
`rebalance_delay`), before query time and when the first poll after each write
sees it: a watching worker takes over within 58 s
of the last heartbeat. A worker that joins just before the leader reassigns,
about 56 s after the heartbeat, takes over about 88 s after it.

A graceful stop deletes the worker's leases, its presence item and, if it led,
the leader item, and clears the owner of each split it held. Takeover then
waits for no lease expiry and no `rebalance_delay`. It takes the leader's next
poll to see the departure and the new owner's next poll to read the
assignment. When the departing worker led, a peer first sees the leader item
gone at its next poll, takes the leadership and lists the job's records before
it assigns.

`coordination.reconcile_interval` sets how often the leader lists every split
record. On this store it is a billed read of the job's whole split history, so
`5m` suits it. A section that builds this store with an interval below `1m`
logs a warning.

The terms that dominate cost, for `W` workers with `L` lanes each
(`max_in_flight`), polling every `P` seconds, and `S` split records:

| Term | Rate |
|---|---|
| Lease poll | `W × ⌈(W × L × 184 B + W × 157 B + 164 B) / 4 KiB⌉ / P` read units per second |
| Commits | about `W × L / checkpoint interval` write units per second while busy |
| Split turnover | about 10 write units and 4 read units per completed split |
| Leader reconcile | `⌈S × 452 B / 4 KiB⌉ / reconcile_interval` read units per second |

The lease poll grows with the square of the fleet: at about 100 workers it nears
2,000 read units per second on one partition key. `poll_interval` scales it
down, at the cost of discovery latency. Larger splits cut turnover and the time
lanes spend waiting for their next split. The item sizes come from serialized
records in the
[cost model on issue #17](https://github.com/spate-etl/spate/issues/17#issuecomment-5879131523),
which also gives modelled totals for 1M to 20M rows per second with the
assumptions it rests on. At 10M rows per second with 64 MiB splits it models 27
workers at about 210 write units and 320 read units per second. The revision
floor each lease delete writes adds one write unit per completed split, and the
lease create's transaction three more, since DynamoDB charges two writes for
each of its two items. Lease renewals add about 16 more, one write unit per held
split at each heartbeat. That model then comes to about 329 write units per
second.

## What an outage does

Throttling, server errors and timeouts are retryable. Heartbeats fail, and a
worker that goes one full lease without a successful write **self-fences** and
stops its splits. Commits surface as retryable. A failed poll judges no lease
expired, so an outage does not make peers take over live work when the table
returns. Everything resumes where it left off.

## Metrics

This store registers no families of its own. Its round-trips appear in the
framework's coordination families:
`spate_coordination_store_op_duration_seconds` by `op`, where `op="poll"` times
each poll of a watched prefix, and
`spate_coordination_writes_total{outcome="conflict"}` for lost
compare-and-swaps. Fencing loses some in normal running, so only a sustained
rate calls for attention. See [Metrics](../../../../METRICS.md) § Coordination.
