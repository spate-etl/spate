# DynamoDB (coordination store)

The DynamoDB store (`spate-coordination`, feature `coordination-dynamodb` on
the `spate` facade) keeps a coordinated job's split records, leases and plan in
one DynamoDB table. It needs no servers of its own and authenticates through
IAM. DynamoDB has no change feed a client library can consume, so its watches
list their prefix every `poll_interval` and report the difference
([ADR-0050](../../../../adr/0050-coordination-stores-may-declare-a-polled-watch.md)).
Discovery is therefore slower than on a store that pushes changes, and every
poll is a billed read. Leases carry no expiry the table enforces: each worker
judges a lease expired from its own reads.

Select it under `store:` in the pipeline's
[`coordination:` section](../../../07-reference/configuration.mdx#coordination):

```yaml
coordination:
  instance_id: "${POD_NAME}"
  lease_duration: 30s
  reconcile_interval: 5m
  store:
    dynamodb:
      table: spate-coordination
      job: exports-backfill
      region: eu-west-1
```

`table` and `job` are the two required keys of the `dynamodb` body. The keys
beside `store:` are the coordinator's tuning, and `lease_duration` is also the
lease TTL the store is built with. A binary built without the
`coordination-dynamodb` feature rejects a `dynamodb` store at startup, naming
the feature.

Construction is synchronous and lazy. The first store operation, the
coordinator's startup probe, loads the AWS configuration and checks the table,
so a table still being created rides the startup retry budget.
Misconfiguration, such as a malformed table name or an endpoint that is not a
URL, fails startup with a fatal error that names the key.

## Configuration

The `coordination: { store: { dynamodb: ... } }` section deserializes into
`DynamoDbConfig`
([`spate-coordination/src/store/dynamodb/config.rs`](repo:crates/spate-coordination/src/store/dynamodb/config.rs));
unknown fields are rejected with the offending key. Errors name the key as
`dynamodb.<key>`, and `Debug` output redacts the endpoint's userinfo and query.

| Key | Type | Default | Description |
|---|---|---|---|
| `table` | string | `required` | Table name (3 to 255 characters of `[A-Za-z0-9_.-]`) or table ARN. Many jobs can share one table. |
| `job` | string | `required` | Job identity, `[A-Za-z0-9_-]{1,64}`. Prefixes the partition keys of every item the job writes. Every worker of one job uses the same value; two different jobs must never share one. |
| `region` | string | `none` | AWS region. Unset, the AWS provider chain supplies it (`AWS_REGION`, the shared config file, instance metadata). Startup fails when neither does, or when the chain has not answered within a quarter of `coordination.op_timeout`. |
| `endpoint` | string | `none` | An `http://` or `https://` URL in place of the region's endpoint, such as DynamoDB Local's. |
| `create_table` | boolean | `false` | Create the table when it is missing, with on-demand billing and time to live on `x`. See [The table](#the-table). |
| `poll_interval` | duration | `2s` | Time between two listings of a watched prefix. See [Latency and cost](#latency-and-cost). |

`coordination.lease_duration` has two floors on this store: at least `1s`, and
at least five poll intervals. `coordination.op_timeout` sets the SDK's
deadlines, so the store's attempts, retries and backoff all finish inside it.

A store built in code takes the same fields as `DynamoDbConfig`
(`DynamoDbConfig::new(table, job)` plus the optional fields), and
`DynamoDbStore::new(config, lease_ttl, op_timeout)` takes the lease TTL and the
operation deadline. Both must equal the coordinator's `lease_duration` and
`op_timeout`, and the coordinator rejects a store whose values differ.

Values are capped at 384 KiB, leaving room in DynamoDB's 400 KB item for the
key and the store's own attributes. A larger value fails before any request,
naming the key.

## Security (credentials and TLS)

Credentials come from the AWS provider chain and never from the pipeline file.
The chain tries, in order, the environment (`AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`), the shared config and credentials files (including
SSO sessions and `credential_process`), web identity tokens (IAM roles for
service accounts on EKS), container credentials (ECS task roles and EKS Pod
Identity), and EC2 instance metadata (IMDSv2).

Requests to DynamoDB and to the credential providers go through the proxies
the standard variables name (`HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY`),
except for hosts `NO_PROXY` lists.

The store verifies the endpoint's certificate against the system trust store,
read once per worker. When `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, the
certificates they name replace the system store. If the store yields no
certificates, the store logs a warning and uses the Mozilla root bundle
compiled into the binary.

TLS runs on rustls with the `aws-lc-rs` provider. The AWS client enables
rustls's `prefer-post-quantum` feature, and Cargo enables a feature for the
whole build. Every rustls client on `aws-lc-rs` in a binary built with
`coordination-dynamodb` therefore offers the X25519MLKEM768 hybrid key exchange
first, and its ClientHello grows by that key share. A TLS-inspecting proxy that
rejects a large ClientHello breaks those connections.

Failures are classified as
[ADR-0047](../../../../adr/0047-a-rejected-credential-or-tls-handshake-is-fatal.md)
states:

| Failure | Class |
|---|---|
| `AccessDeniedException`, `UnrecognizedClientException`, `InvalidSignatureException`, `MissingAuthenticationTokenException`, `IncompleteSignatureException`, `ExpiredTokenException`, or any 401 or 403 | Fatal |
| A certificate the store does not trust, or a handshake the server refuses | Fatal |
| `ResourceNotFoundException`, `ValidationException`, `ItemCollectionSizeLimitExceededException` | Fatal |
| No region from the config or the provider chain | Fatal |
| A failure to load or refresh credentials | Retryable; the message carries the provider's reason |
| Throttling, a 5xx, a timeout, a connection failure, a conflict, or a code the store does not know | Retryable |

The SDK retries throttling and server errors itself, up to three attempts
inside `op_timeout`, before the store reports them. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

## IAM policy

A worker needs these actions on the table:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["dynamodb:DescribeTable", "dynamodb:DescribeTimeToLive"],
      "Resource": "arn:aws:dynamodb:<region>:<account>:table/<table>"
    },
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:Query"
      ],
      "Resource": "arn:aws:dynamodb:<region>:<account>:table/<table>",
      "Condition": {
        "ForAllValues:StringLike": { "dynamodb:LeadingKeys": ["<job>#*"] }
      }
    }
  ]
}
```

The `Condition` is optional. It confines a worker to its own job's items, so
two jobs sharing a table cannot touch each other's records. With
`create_table: true`, add `dynamodb:CreateTable` and `dynamodb:UpdateTimeToLive`
to the first statement. Without `dynamodb:DescribeTimeToLive` the store logs a
warning at startup and continues.

## The table

One table holds any number of jobs. Its key schema is fixed:

| Attribute | Key | Type |
|---|---|---|
| `pk` | partition (hash) | string |
| `sk` | sort (range) | string |

Each job writes three partition keys: `<job>#d` holds its durable records,
`<job>#e` its leases and presence keys, and `<job>#m` the settings it started
with. The record key is the sort key.

At startup the store refuses, with a fatal error:

- a key schema other than the one above;
- a local secondary index, which caps a partition key's items at 10 GB;
- replicas, whose conditional writes do not order against each other across
  regions;
- a table that is being deleted, is archived, or is in any status other than
  creating, active or updating.

A global secondary index logs a warning, since every write also updates it.

The store writes `x`, an epoch-seconds time to live, on every lease write (a
day ahead) and on every durable delete marker (seven days ahead), so the table
collects items nothing renews. Expiry never reads `x`. With time to live off,
or on another attribute, the store logs a warning at startup, and those items
stay in the table.

With `create_table: true`, a missing table is created with on-demand billing
and time to live on `x`, and a table that already exists is adopted. Creating
takes one or more startup attempts; if the table is still not active when they
run out, raise `coordination.startup_max_attempts`. To create the table by hand:

```sh
aws dynamodb create-table --table-name spate-coordination \
  --attribute-definitions AttributeName=pk,AttributeType=S AttributeName=sk,AttributeType=S \
  --key-schema AttributeName=pk,KeyType=HASH AttributeName=sk,KeyType=RANGE \
  --billing-mode PAY_PER_REQUEST
aws dynamodb update-time-to-live --table-name spate-coordination \
  --time-to-live-specification Enabled=true,AttributeName=x
```

A job's first worker records the lease TTL and the item layout in the job's
settings item. A later worker with a different lease fails at startup with a
fatal error naming both values. Finish the job, or delete its items, before
changing `lease_duration`. `poll_interval` is not recorded, so it can change in
a rolling restart.

DynamoDB serves each partition key at up to 3,000 read units and 1,000 write
units per second. All of a job's leases share one partition key, and so do all
of its durable records. Those limits bound how large one job's fleet can grow
on this store. [Latency and cost](#latency-and-cost) gives the read rate against the
fleet size.

For development, DynamoDB Local stands in for the service:

```sh
docker run --rm -p 8000:8000 amazon/dynamodb-local -jar DynamoDBLocal.jar -inMemory
```

Point `endpoint` at `http://127.0.0.1:8000`, set `create_table: true`, and give
the provider chain any key pair, for example `AWS_ACCESS_KEY_ID=local` and
`AWS_SECRET_ACCESS_KEY=local`, since DynamoDB Local accepts any.

## Lease expiry

A lease item carries a revision and no expiry the table enforces. Each worker
judges expiry from its own consistent reads, on its own clock:

- A worker notes when it first read a lease at its current revision.
- The lease is expired once a later read that began at least one lease
  duration after that still returns the same revision.
- A read that fails judges nothing. A worker whose reads fail through an
  outage expires no lease in its view, however long the outage lasts.

A dead worker's splits are therefore claimable one lease plus up to one poll
interval after its last heartbeat. A worker that starts watching late sees a
stale lease expire one lease after its own first read of it. No decision
compares clocks across machines. The owner stops its splits one lease after
its last successful renewal, measured from when the renewal returned, and a
peer's lease measure starts when its read returned. The two can overlap by one
renewal's response time; the epoch fence on every commit makes that overlap
safe, as it does on every store.

A lease a worker creates takes its revision from that worker's wall clock, kept
above every revision the worker has seen for the key. When skew between two
machines puts a re-created lease below the revision a watcher holds, the
watcher reports a delete and then the new lease.

## Latency and cost

A change reaches a watch at the watcher's next poll, so discovery takes up to
one `poll_interval` (default `2s`). Takeover of a dead worker's splits takes one
lease plus up to one poll interval.

`coordination.reconcile_interval` sets how often the leader lists every split
record. On this store it is a billed read of the job's whole split history, so
`5m` suits it. A section that builds this store with an interval below `1m`
logs a warning.

The terms that dominate cost, for `W` workers with `L` lanes each
(`max_in_flight`), polling every `P` seconds, and `S` split records:

| Term | Rate |
|---|---|
| Lease poll | `W × ⌈(W × L × 184 B + W × 157 B + 164 B) / 4 KiB⌉ / P` read units per second |
| Commits | about `W × L / checkpoint interval` write units per second while busy |
| Split turnover | about 6 write units and 4 read units per completed split |
| Leader reconcile | `⌈S × 452 B / 4 KiB⌉ / reconcile_interval` read units per second |

The lease poll grows with the square of the fleet: at about 100 workers it nears
2,000 read units per second on one partition key. `poll_interval` scales it
down, at the cost of discovery latency. Larger splits cut turnover and the time
lanes spend waiting for their next split. The item sizes come from serialized
records in the
[cost model on issue #17](https://github.com/spate-etl/spate/issues/17#issuecomment-5879131523),
which also gives modelled totals for 1M to 20M rows per second with the
assumptions it rests on. At 10M rows per second with 64 MiB splits it models 27
workers at about 210 write units and 320 read units per second.

## What an outage does

Throttling, server errors and timeouts are retryable. Heartbeats fail, and a
worker that goes one full lease without a successful write **self-fences** and
stops its splits. Commits surface as retryable. A failed poll judges no lease
expired, so an outage does not make peers take over live work when the table
returns. Everything resumes where it left off.

## Metrics

This store registers no families of its own. Its round-trips appear in the
framework's coordination families:
`spate_coordination_store_op_duration_seconds` by `op`, where `op="poll"` times
each poll of a watched prefix, and
`spate_coordination_writes_total{outcome="conflict"}` for lost
compare-and-swaps. Fencing loses some in normal running, so only a sustained
rate calls for attention. See [Metrics](../../../../METRICS.md) § Coordination.
