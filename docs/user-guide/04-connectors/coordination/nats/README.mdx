# NATS JetStream (coordination store)

The NATS JetStream store (`spate-coordination`, feature `coordination-nats` on
the `spate` facade) is the production coordination backend. Coordinated
instances of one job meet in it to agree who holds which
[split](../../../07-reference/glossary.mdx#split). Records never flow through
it; it carries split records, leases, and the plan, at roughly one small write
per held split per third of a lease, so a handful of writes per second per
worker.

Select it under `store:` in the pipeline's
[`coordination:` section](../../../07-reference/configuration.mdx#coordination):

```yaml file=crates/spate/examples/nats_coordinated_backfill.rs region=coordination
```

`servers` and `job` are the two required keys of the `nats` body; the keys
beside `store:` are the coordinator's tuning, and `lease_duration` is also the
TTL the store is built with. That section comes from
[`nats_coordinated_backfill.rs`](repo:crates/spate/examples/nats_coordinated_backfill.rs),
one instance per process against a JetStream server on `nats://127.0.0.1:4222`
(override with `NATS_URL`) meeting the [Requirements](#requirements) below.
Two terminals, each with a distinct `POD_NAME` (the section's `instance_id`),
divide one backfill between them, and two live workers claiming one identity
is detected and fatal:

```sh
POD_NAME=worker-a cargo run -p spate --features s3,json,coordination-nats --example nats_coordinated_backfill
POD_NAME=worker-b cargo run -p spate --features s3,json,coordination-nats --example nats_coordinated_backfill
```

A binary built without the `coordination-nats` feature rejects a `nats` store
at startup, naming the feature.

Construction is synchronous and lazy, so the connection and bucket provisioning
happen on the first store operation, which is the coordinator's startup probe.
An unreachable server therefore rides the startup retry budget. Misconfiguration,
such as a `servers` entry that is not a URL or joins several with commas, fails
startup with a fatal error that names the cause, and so does a credential
rejected on the first connection, or a certificate or TLS handshake rejected by
the last server it tries. After startup, the store fails with a fatal error
once every server has failed since the last successful connection, each with a
rejection as its latest failure.

## Configuration

The keys of the `nats` body under `coordination.store`. Errors name the key as
`coordination.store.nats.<key>`, and `Debug` output redacts every secret.

| Key | Type | Default | Description |
|---|---|---|---|
| `servers` | list of strings | `required` | Server URLs (`nats://host:4222`, `tls://…`, `ws://…`, `wss://…`). At least one. Userinfo and any query render `<redacted>` in `Debug` output. |
| `job` | string | `required` | Job identity, `[A-Za-z0-9_-]{1,64}`. Suffixes both bucket names. Every worker of one job uses the same value; two different jobs must never share one. |
| `credentials` | mapping | `none` | Anonymous by default. See [Security](#security-authentication-and-tls). |
| `tls` | mapping | `none` | TLS material. Its presence requires TLS on every server and rejects a `ws://` server. |
| `replicas` | integer | `1` | Replication factor for both buckets (1, 3, or 5). 3 or more needs a JetStream cluster. |

`coordination.lease_duration` is the lease TTL, with a floor of 2s on NATS
because expiry-marker precision is one second.

A store built in code instead takes the same fields as `NatsConfig`
(`NatsConfig::new(servers, job)` plus the optional fields), and `NatsStore::new`
takes the lease TTL as its second argument. That value must equal the
coordinator's `lease_duration`: one drives the bucket's age limit and the other
drives the lease protocol, and the coordinator rejects a store whose TTL
differs.

Values are capped at 512 KiB, well below the NATS 1 MiB message ceiling, so a
split descriptor cannot grow into an unwritable record.

## Security (authentication and TLS)

`credentials` selects the mechanism. Supply secrets through
[environment interpolation](../../../07-reference/configuration.mdx#environment-interpolation):

| Value | Use |
|---|---|
| `none` | Anonymous. Development clusters only. |
| `{ user_password: { username: …, password: "${NATS_PASSWORD}" } }` | Username and password. The password renders `<redacted>` in all `Debug` output. |
| `{ token: "${NATS_TOKEN}" }` | A bearer token. |
| `{ creds_file: /etc/nats/worker.creds }` | A `.creds` file (NKey + JWT) — the NATS-native mechanism, and the right choice for a managed cluster. |

`tls` carries `root_ca` (a PEM bundle, for private CAs), and `client_cert` +
`client_key` for mutual TLS. Those two are set together or not at all; half a
client identity fails at startup rather than connecting without mutual TLS.
Setting the `tls` field at all requires TLS on every server in `servers`. A
`ws://` server never uses TLS, so with `tls` set it fails at startup; use
`wss://` instead.

The store verifies servers against the system trust store, which on macOS
includes the Keychain. When `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, the
certificates they name replace the system store. If the store yields no
certificates, the store logs a warning and uses the Mozilla root bundle compiled
into the binary. The certificates in `root_ca` are trusted in addition to these
roots. A relative path resolves against the working directory.

The first connection fails with a fatal error when a `root_ca`, `client_cert` or
`client_key` file cannot be read or holds no PEM item, or when the certificate
and key do not match. It also fails when the connection uses TLS and the trust
store cannot be read. A credential the server rejects is fatal, and so is a
certificate either side rejects. A TLS alert with which the server rejects the
handshake, such as `HandshakeFailure` or `ProtocolVersion`, is fatal too, and
so is a server that shares no protocol version, cipher suite or other handshake
parameter with the client. The message names the alert or the mismatch. Any
other TLS failure, such as a malformed message, an `InternalError` alert or a
connection closed during the handshake, is retryable. These rules hold for the
first connection, which tries each server in `servers` once. A rejected
credential stops it at once; after any other failure it moves on to the next
server, and the last server's failure decides.

After startup the client reconnects on its own without limit. Once every server
has failed since the last successful connection, each with one of these
rejections as its latest failure, store operations fail with a fatal error that
names them, and the coordinator stops. Every server means each `servers` entry
and every address the cluster advertises to clients, so a cluster should
advertise only addresses its clients can reach.

A server not yet tried, or one whose latest failure is a refused or timed-out
connection, keeps the store retrying like an [outage](#what-an-outage-does).
So does a server that refuses by closing the connection, a trust store that
cannot be read, or a WebSocket upgrade refused with HTTP 401 or 403. A server
whose name stops resolving records no failure, so the rejection it met before
still counts. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

## The two buckets

One job means two KV buckets, split by durability:

- **`spate_coordination_{job}_state`** — durable, no age limit. Split records
  and the plan record survive the death of whoever wrote them. A deleted key
  leaves a marker that the server removes one lease TTL later.
- **`spate_coordination_{job}_lease`** — ephemeral, with a bucket-level
  `max_age` equal to the lease TTL.

The lease bucket is where the server version floor comes from. NATS KV cannot
re-arm a per-key TTL on update, but `max_age` applies per *message*, so every
compare-and-swap rewrite restarts that key's clock, which **is** the heartbeat.
An untouched key expires on its own, and the expiry surfaces to watchers as a
limit marker. The store reports a limit marker and a graceful delete the same
way, as a deleted key. Whether a split was released or its owner died is read
from its split record.

## Requirements

- **A NATS server on a [supported line](#supported-server-versions)**, with
  JetStream enabled (`-js`). The worker verifies the version at startup and
  fails actionably against an older one.
- **`sync_interval: always` on every server in production.** By default the
  server acknowledges a write before it reaches disk and syncs every two
  minutes, so an OS crash or power loss can lose writes it acknowledged
  ([Jepsen's NATS 2.12.1 analysis](https://jepsen.io/analyses/nats-2.12.1)).
  The worker does not check the setting. [What an outage
  does](#what-an-outage-does) says what a lost write breaks.
- **One job name per coordinated job.** A fingerprint check rejects
  misconfigured workers before they can touch anything.
- **Permission to update the state bucket's stream** when an earlier version
  created it. A worker enables per-message TTLs on that stream at startup. If
  its credentials lack `$JS.API.STREAM.UPDATE`, it logs a warning and deleted
  keys keep their markers.

Development and CI need nothing more than a single container:

```yaml
# docker-compose.yml
services:
  nats:
    image: nats:2.11-alpine
    command: ["-js"]
    ports: ["4222:4222"]

  pipeline:
    image: your-pipeline
    deploy: { replicas: 2 }
    environment:
      NATS_URL: nats://nats:4222
      # the pipeline file sets instance_id: "${HOSTNAME}", unique per replica
```

For production, run a 3-node cluster with JetStream and set `replicas: 3` in
the `nats` body so the buckets survive losing a node. The client learns the other
nodes from the first server it reaches, so one reachable entry in `servers` is
enough. List more than one, or a DNS name that resolves to every node, so the
first connection survives a node being down.

Set [`sync_interval`](https://docs.nats.io/reference/config/jetstream/sync_interval)
in each server's configuration file:

```text
jetstream {
  sync_interval: always
}
```

A configuration reload does not apply it, so restart each server. Every write
then waits for an fsync before the server acknowledges it.
`spate_coordination_store_op_duration_seconds` shows what that adds to this
store's operations. The setting is server-wide, so every other stream on those
servers pays the same cost. Once a server runs with it, its `/varz` monitoring
endpoint reports `jetstream.config.sync_always: true`.

## Supported server versions

| NATS | Support |
| --- | --- |
| 2.11 | Guaranteed |

Guaranteed means every change to this store runs against that line before it
ships, and a defect you hit on it is a defect this project fixes. The store
needs per-message age limits and limit markers, and the worker refuses a server
too old to have them at startup. Later releases are accepted, and CI does not
run them.

## What an outage does

Heartbeats fail, and workers **self-fence** after one full lease without a
successful write, stopping their splits rather than running unfenced. Commits
surface as retryable. Everything resumes where it left off when the store
returns: degraded, never corrupted.

This is the store being unavailable, not the store lying. Correctness does not
rest on the store staying up; it rests on the compare-and-swap, which a
partitioned worker cannot win.

The compare-and-swap relies on the server never losing a write it acknowledged.
A server that loses one can put a split record back at an earlier revision, and
a worker the lost write had fenced can then win its next compare-and-swap.

## Metrics

This store registers no families of its own. Its round-trips appear in the
framework's coordination families: `spate_coordination_store_op_duration_seconds`
by `op`, and `spate_coordination_writes_total{outcome="conflict"}` for lost
compare-and-swaps, which is fencing working as designed and alarming only in
bulk. See [Metrics](../../../../METRICS.md) § Coordination.
