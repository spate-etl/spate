# Kafka (feed)

import SecuringKafka from '../../_securing-kafka.mdx';
import LoggingKafka from '../../_logging-kafka.mdx';

The Kafka feed (`spate-kafka`, feature `kafka` on the `spate` facade) carries
[work units](../../../07-reference/glossary.mdx#work-unit) as messages on a work
topic that every worker of a pipeline reads as one consumer group. Before a
unit is read, its attempt is recorded on a compacted attempt topic, and a unit
whose recorded attempts have reached the attempt cap goes to a dead-letter
topic without being read. A unit's offset is committed once every record in it
is acknowledged and the tombstone of its attempt record is confirmed. A unit
its reader fails is written to a retry topic, which the group reads beside the
work topic, or at the attempt cap to the dead-letter topic, and its offset is
committed once that write is confirmed, and for the dead-letter topic the
tombstone after it. A unit whose worker stops is read again by the member its
partition moves to. The backend lives in the Kafka connector's crate, so a
source names no backend
([ADR-0069](../../../../adr/0069-feed-backends-live-in-their-own-crates.md)).

Construct it from the pipeline's opaque section, with the I/O runtime handle,
and pass it to `Pipeline::feed`:

```rust file=crates/spate/examples/s3_kafka_backfill.rs region=connect
```

That code comes from
[`s3_kafka_backfill.rs`](repo:crates/spate/examples/s3_kafka_backfill.rs),
which reads a staged `file://` backfill through Kafka topics:

```sh
KAFKA_BROKERS=localhost:9092 \
  cargo run -p spate --features s3,json,kafka --example s3_kafka_backfill
```

`KafkaFeed::connect` checks the feed's topics (see
[Startup checks](#startup-checks)), then builds the feed's clients and starts
its four threads: the consumer thread, which polls the group member; the
follower thread, which reads the attempt topic; the gate thread, which
records each unit's attempt before the unit is read (see
[Counting deliveries](#counting-deliveries)); and the depth thread, which
answers a bounded job's depth reads (see
[Ending a bounded job](#ending-a-bounded-job)). The checks read from the
brokers, so an unreachable broker fails the call within 30 seconds.

## Configuration

The `feed: { kafka: ... }` section deserializes into `KafkaFeedConfig`
([`spate-kafka/src/feed/config.rs`](repo:crates/spate-kafka/src/feed/config.rs));
unknown fields are rejected with the offending key.

```yaml file=crates/spate/examples/s3_kafka_backfill.rs region=feed
```

| Key | Type | Default | Description |
|---|---|---|---|
| `brokers` | string | `required` | Comma-separated bootstrap servers. |
| `group_id` | string | `required` | The consumer group every worker of the pipeline joins. |
| `topic` | string | `required` | The work topic, where a publish writes a unit. |
| `retry_topic` | string | `required` | Where a unit failed below the attempt cap is written again. The group reads it beside the work topic. Must differ from `topic`. |
| `dead_letter_topic` | string | `required` | Where a unit goes at the attempt cap, failed by its reader or moved unread, and a message that names no unit. A bounded job reads its end offsets, as [Ending a bounded job](#ending-a-bounded-job) describes. Must differ from `topic` and `retry_topic`. |
| `attempt_topic` | string | `required` | The compacted topic each unit's attempt is recorded on before the unit is read (see [Topics](#topics)). Must differ from `topic`, `retry_topic` and `dead_letter_topic`. |
| `delivery_timeout` | duration | `30s` | How long one write waits for its delivery report (librdkafka `message.timeout.ms`), and the bound on one pass of the gate, which can run up to 2 s past it. An attempt, tombstone, retry or dead-letter write that times out is sent again, and a publish that times out is reported to its caller as retryable. From `1ms` to about 24.8 days. |
| `statistics_interval` | duration | `5s` | librdkafka's statistics interval for the feed's consumer and producer. The attempt follower sends no statistics. `0s` disables statistics; a non-zero value under `1ms` is refused. |
| `rdkafka` | string map | `{}` | Raw librdkafka properties for every client of the feed, applied after validation — see below. |

`units_held` beside `kafka:` sets how many units a worker holds at once, and
`attempt_cap` the attempt at which a unit goes to the dead-letter topic: a
unit its reader fails on that attempt or later, and a unit whose recorded
attempts have reached it, which moves without being read (see
[Counting deliveries](#counting-deliveries)). `attempt_cap` inside the
`kafka:` body is refused.

## The `rdkafka` passthrough and the denylist

One map configures the feed's consumer, its attempt follower, its depth
reader, its producer, and the two clients its startup checks read the topics
with. A property that
applies to one client only draws a warning from librdkafka in the others.
Properties the feed owns are **rejected at load time with an explanation**,
under their own name and under `topic.<name>`. librdkafka reads
`topic.<name>` as `<name>` when `<name>` is a topic-level property, as `acks`
and `message.timeout.ms` are. Aliases are denied beside the canonical names,
because passthrough and feed values apply in unspecified order.

| Denied property | Why |
|---|---|
| `group.id` | Owned by the typed `group_id` field. |
| `group.instance.id` | A static member sends no LeaveGroup when it closes, so its partitions wait out `session.timeout.ms` before another member reads them. |
| `group.protocol` | The feed runs the classic consumer group protocol with eager assignment. |
| `partition.assignment.strategy` | The feed relies on eager assignment, under which a rebalance revokes every partition before it assigns any. Any value is refused. |
| `auto.offset.reset` | A partition with no committed offset starts at its earliest offset. |
| `enable.auto.commit`, `auto.commit.enable` (alias) | The feed commits each partition up to its first unfinished unit itself. |
| `enable.auto.offset.store` | The feed decides which offsets may be committed. |
| `enable.partition.eof` | The feed reads only messages from the consumer. |
| `acks`, `request.required.acks` (alias) | Forced to `all`: a unit is read once the delivery report confirms its attempt write, and its offset completes once the report confirms its tombstone or retry write. |
| `enable.idempotence` | Forced on, so librdkafka's own retries neither reorder nor duplicate a write. |
| `transactional.id` | The feed does not use transactions; a write is confirmed by its delivery report. |
| `message.timeout.ms`, `delivery.timeout.ms` (alias) | Owned by the typed `delivery_timeout` field. |
| `delivery.report.only.error` | A unit is read only once its attempt write is confirmed, and its offset finishes only once its tombstone or retry write is, both by their delivery reports. |
| `allow.auto.create.topics` | Forced off: a write to a missing topic, or a startup check's read of one, fails, and never creates the topic with the broker's defaults. |
| `statistics.interval.ms` | Owned by the typed `statistics_interval` field. |
| `bootstrap.servers`, `metadata.broker.list` (alias) | Owned by the typed `brokers` field. |

The attempt follower sets the same group, offset and commit properties the
consumer does, so the denylist covers it too.
`session.timeout.ms`, `heartbeat.interval.ms` and `max.poll.interval.ms` pass
through, and set how long a member that dies keeps its partitions (see
[No lease](#no-lease)).

## Security (TLS, mTLS, SASL)

<SecuringKafka />

A SASL authentication failure or a rejected TLS handshake, as listed above,
fails connecting. `KafkaFeed::connect` and `KafkaFeedPublisher::connect` return
`KafkaFeedError::Refused` as soon as the client reports the rejection, naming
the read under way and librdkafka's text, such as these:

```text
… SSL handshake failed: … certificate verify failed …
… SASL authentication error: Authentication failed: Invalid username or password …
```

A refused or reset connection stays retryable: the checks wait for a broker the
client can use, and fail with `KafkaFeedError::Unavailable` once their bound
passes.

Once the feed has connected, its consumer, its attempt follower and its
producer treat a SASL authentication failure and a rejected handshake as the
source does, and the feed stops with the reason. A publish-only handle stops
the same way through its producer. An attempt, tombstone, retry or dead-letter
write that times out is sent again.

## A publish-only handle

`KafkaFeedPublisher::connect` builds a handle that writes units to the work
topic and reads none, for a process that only publishes, such as a lister run
(see [The lister run](../../sources/s3/README.mdx#the-lister-run)).
It reads the workers' own `feed: { kafka: … }` section and refuses any section
a worker refuses, so every key stays required. Its writes use `brokers`,
`topic`, `delivery_timeout`, `statistics_interval` and the `rdkafka`
passthrough, and the other three topic names serve its checks. Connecting runs
the [startup checks](#startup-checks) a worker runs, then builds one producer
with the settings the feed owns. The handle joins no group, starts none of the
feed's four threads and writes no attempt record, so it takes no partition
from the workers and charges no unit an attempt.

A publish is confirmed by its delivery report and fails as
[Message mapping](#message-mapping) describes. A credential a broker rejects,
or a TLS handshake either side rejects, after connecting stops the handle with
the reason, and so does a fatal producer error such as a refused idempotent
producer id; every later publish fails with it. Dropping the handle reports
each publish it has not confirmed to its caller as retryable. A caller that
publishes such a unit again can leave two copies on the work topic, and both
are read.

The handle's identity needs the `Describe` and `DescribeConfigs` operations on
the four topics, and `Write` on the work topic. It needs no `Read` and no
group ACL.

Connecting logs `the Kafka feed's publisher started` with the work topic, its
`cleanup.policy` and its `message.timestamp.type`. Passed to `Pipeline::feed`
as a worker's feed, the handle fails the worker at its first read, with an
error naming `KafkaFeed::connect`.

## Topics

Create the four topics before the first worker starts. The feed never creates a
topic, and connecting refuses a missing one (see
[Startup checks](#startup-checks)). A topic can still go missing after the feed
connects, as when it is deleted while the feed runs. librdkafka holds a write to
a topic it has not yet seen in metadata. Once
`topic.metadata.propagation.max.ms` (30 s by default) has passed since the
worker first wrote to the topic, the next metadata response that lacks it marks
the topic missing, and every write still held then stops the feed. After that, a
publish to the missing work topic is reported to its caller as retryable, and an
attempt, tombstone, retry or dead-letter write is sent again until the topic
exists, with its partition committing nothing past it meanwhile. A write that
times out while held is handled the same way. A deleted attempt topic also stops
the feed through its follower, whose read of the topic then fails with an error
the feed treats as fatal.

The work topic's partitions bound how many workers read at once: each partition
of the work and retry topics is read by one member of the group.

The feed reads the codecs the
[Kafka source](../../sources/kafka/README.mdx#compression-codecs) reads, and a
batch it cannot read stops the feed in the same cases.

Kafka deletes a message when its topic's retention ends, whether or not the
group has read it. A unit deleted before it is read is lost, which INV-1 places
outside its property (see [the invariants](../../../../INVARIANTS.md#inv-1)).

Create the work topic with `message.timestamp.type=LogAppendTime`, so the
broker stamps each message as it appends it and retention counts from then. A
store that publishes storage notifications to the work topic sets each
message's timestamp itself. Under the default `CreateTime`, a message stamped
earlier than the topic's retention window is deleted at the broker's next
retention check, read or not. Connecting refuses any other value. The
[S3 source](../../sources/s3/README.mdx) states each store's notification
settings.

A unit moved to the retry or dead-letter topic is a new message, stamped
when the feed writes it, so each topic's retention counts from the move. The
work topic's retention does not limit how long a moved unit is kept:

- the retry topic's retention bounds how long a failed unit can wait to be
  read again. A retry backlog older than that loses the unit;
- the dead-letter topic's retention is how long a unit that reached the
  attempt cap waits for someone to inspect it or publish it again. Set it
  for that window, or to `-1` to keep messages without limit.

The attempt topic holds one record, keyed by the unit's publish identity,
for each unit in flight or waiting to be retried, and for each unit lost to
retention after a read (see [Counting deliveries](#counting-deliveries)):

- its `cleanup.policy` is `compact` and nothing else. Time or size retention
  would delete the count of a unit still in flight, and connecting refuses
  `delete` and `compact,delete`;
- its partition count is fixed for its life. The feed places each record by
  the count it reads at connect, and does not detect a change. Workers
  started before and after a change count a unit separately, so the unit can
  be read up to `attempt_cap` more times;
- `segment.ms` and `delete.retention.ms` keep a worker's start short. Every
  worker reads the attempt topic from its start before its first unit is
  read, and the cleaner removes superseded records and tombstones only from
  closed segments, which `segment.ms` rolls;
- `delete.retention.ms` must exceed the longest time a worker takes to read
  the attempt topic. A worker still reading when the cleaner removes a
  tombstone keeps the count the tombstone cleared;
- each group and work topic needs an attempt topic of its own, and a work
  topic that is deleted and created again needs a fresh one. A publish
  identity names the work topic and the message's position in it, and
  neither the group nor which incarnation of the topic wrote it.

The attempt follower joins the feed's group by its `group.id` and assigns
the attempt topic's partitions itself, so it never takes part in a rebalance
and needs no group ACL beyond the feed's own. The client's identity needs
`Read`, `Write`, `Describe` and `DescribeConfigs` on the attempt topic.

Use fresh topics, and a fresh group, for each bounded job: the work, attempt,
retry and dead-letter topics. A continuous job keeps its work topic, and
needs attempt, retry and dead-letter topics of its own. The topics keep no
record of which job published a unit, so a job that reuses them reads every
unit an earlier job left unread or uncommitted. The broker drops a group's
committed offsets once the group has been empty for its
`offsets.retention.minutes`, and a group whose offsets are gone reads each
partition again from its earliest retained offset.

## Startup checks

`KafkaFeed::connect`, and `KafkaFeedPublisher::connect` for a
[publish-only handle](#a-publish-only-handle), read the metadata and
configuration of the work, retry, dead-letter and attempt topics before any of
the feed's clients joins the group, and refuse topics the feed cannot run on:

- a missing work, retry, dead-letter or attempt topic;
- a work, retry or dead-letter topic whose `cleanup.policy` includes
  `compact`. Compaction keeps only the latest message for each key, and a
  unit's id is its key, so it can delete a copy of a unit nobody has read;
- an attempt topic whose `cleanup.policy` is anything but `compact`;
- an attempt topic that reports no partitions;
- a work topic whose `message.timestamp.type` is anything but `LogAppendTime`.

The attempt topic's partition count, read here, places each attempt record. The
checks read through two clients built from `brokers` and the `rdkafka`
passthrough, one for metadata and an admin client for configuration, with
`allow.auto.create.topics` off, so reading a missing topic does not create it.
The client's identity needs the `Describe` and `DescribeConfigs` operations on
the four topics, and `Read` and `Write` on the attempt topic once the feed runs.
A read the cluster refuses as unauthorized, or for an invalid topic name, fails
with `KafkaFeedError::Refused`. So does a topic the cluster describes no
configuration entry for, which is what a client without `DescribeConfigs` on it
receives, and a rejected credential or TLS handshake (see
[Security](#security-tls-mtls-sasl)). Any other failed read fails with
`KafkaFeedError::Unavailable`. The checks take at most 30 seconds, and an error
past that bound names the read under way. A publish-only handle's identity needs
these operations on the four topics too, and `Write` on the work topic (see
[A publish-only handle](#a-publish-only-handle)). A worker whose source
publishes units, such as the
[S3 source](../../sources/s3/README.mdx#reading-a-notifications-object)
re-enqueueing an overwritten object, needs `Write` on the work topic as well.
Each unit published there starts its own delivery count.

When a topic reports no `cleanup.policy`, or the work topic no
`message.timestamp.type`, the feed logs a warning and skips that check.
A worker's feed logs at connect each topic's `cleanup.policy`, the work
topic's `message.timestamp.type` and the attempt topic's partition count; a
publish-only handle logs its own line.

The checks run only when the feed connects. A topic whose policy, partition
count or timestamp type changes later goes unnoticed, and a topic deleted later
is handled as [Topics](#topics) describes.

## How a unit finishes

The group uses eager assignment: a rebalance takes every partition from every
member before it hands any out. A member starts each partition it is assigned
at the group's committed offset, or at the earliest offset where none is
committed.

An acknowledged unit's offset finishes once the tombstone of its attempt
record is confirmed. A failed unit's offset finishes once its write to the
retry topic is confirmed, or, for a write to the dead-letter topic, once the
tombstone sent after that write is. A unit waiting at the gate, or with its
attempt write in flight, holds its offset unfinished. Each partition commits
up to its first unfinished offset, every second and when the partition is
revoked. A unit still unfinished blocks the commits of its partition, so the
next owner of the partition reads that unit again and every unit read after
it.

A rebalance that fails gives up every partition with nothing committed. The
units read since the last commit are delivered again.

## Ending a bounded job

A [bounded job](../../sources/s3/README.mdx#how-a-bounded-job-ends) reads the
feed's depth on a thread of the feed's own, through a consumer that carries the
feed's `group_id` and never joins the group, so the reads take nothing from the
member's poll interval. One read takes the group's committed offset on every
partition of the work and retry topics, in one `OffsetFetch` request, and
then each partition's log start and end offsets. The depth is the sum of each
partition's end offset less its committed offset. A partition with no commit,
or with a commit below its log start, counts from its log start, so a
partition that never held a unit, or whose records retention deleted unread,
reads as drained. The committed offsets are read first: a unit failed between
the two reads has its retry write confirmed before its work offset is
committed, so it shows on the retry topic's end offset either way. Kafka's
offsets are exact, so the window guards only against a peer still holding a
unit.

Once the window passes, the worker reads the dead-letter topic's end offsets,
and any partition above zero fails the job as stalled, naming the topic. The
end offset stays where it is when retention deletes the record, so a unit
dead-lettered at any point in the job counts. Give each bounded job fresh work,
retry, dead-letter and attempt topics: a dead-letter topic an earlier job
wrote fails a later job as stalled.

The reads need `Describe` on the work, retry and dead-letter topics, which the
[startup checks](#startup-checks) already need, and `Describe` on the feed's
group, which the `Read` a member needs on the group includes. An
authorization failure fails the job; any other failed read starts the window
again, or reads the dead-letter topic again 15 seconds later.

## Backpressure

The consumer pauses its partitions once the feed holds 128 units for the
reader, counting the units waiting at the gate and those whose attempt write
is in flight, and resumes them once that count is down to 64. A stalled
attempt topic therefore pauses the partitions. So does one attempt partition
that cannot be read: the units of the other attempt partitions get through
until its units waiting at the gate fill the 128, and then every work
partition stays paused until that partition can be read. The consumer keeps
polling while paused, so a slow reader does not cost the member its
partitions through `max.poll.interval.ms`.

## No lease

A unit has no lease. A member keeps its partitions while the feed's consumer
thread polls and its heartbeats reach the group, whatever the reader is
doing. A worker whose control plane wedges, so that its reader stops
acknowledging and failing units, keeps its partitions and their unfinished
units until the process exits. A worker that dies loses them at the group's
session timeout, `session.timeout.ms` (librdkafka's default is 45 seconds),
and the next owner reads them again.

## Counting deliveries

A unit's attempts are counted under its publish identity:
`<topic>/<partition>/<offset>` of the work-topic message a publish wrote. A
unit read from the work topic counts under its own position. A copy the feed
writes to the retry or dead-letter topic carries the identity in a
`spate.origin` header, and a retry copy counts under it. A retry copy whose
header is missing or unreadable counts under its own position, with a
warning, so its count starts again. Each publish starts its own count,
whatever the unit's id.

Before a unit is read, the gate reads the high watermark of the unit's
attempt partition and waits until the follower has read that partition up to
it. The gate then writes the recorded count plus one, and the unit reaches
the reader with that count once the write is confirmed. A unit whose recorded
attempts have reached `attempt_cap` goes to the dead-letter topic without
being read. When the reader fails a unit below `attempt_cap`, the unit is
written to the retry topic. At or past the cap it is written to the
dead-letter topic.

Every read counts, including a read whose worker dies and a read cut short by
a graceful stop or a rebalance. A unit that kills its worker on every read
reaches the dead-letter topic at the cap. The cap must exceed the stops and
rebalances a unit can see: under eager assignment, a rolling restart of N
members can cost a unit up to 2N attempts. Two copies of one publish read at
the same time, as after a rebalance, can count once between them.

An acknowledged unit's attempt record is tombstoned, so a later read of the
same message counts from zero. A retry write leaves the record in place. A
dead-letter write is followed by a tombstone too, which opens a window. If a
worker crashes within a commit interval after the tombstone is confirmed, or
loses the partition while the tombstone is in flight, the next owner reads the
unit again from a count of zero and moves a second copy to the dead-letter
topic, after at most `attempt_cap` more reads.

The attempt topic therefore holds records for units in flight or waiting to
be retried. A unit that retention deletes after a read keeps its record too,
since only an acknowledgment or a confirmed dead-letter write tombstones it,
and every worker holds that record's count in memory.

An acknowledged unit whose tombstone is not confirmed, because its worker
stops or loses the partition while the tombstone is in flight, keeps its
record, and the next owner reads the unit again with its count. A unit
acknowledged on its `attempt_cap`-th read goes to the dead-letter topic
without being read.

A unit's offset finishes only once the write that settles it is confirmed. An
attempt, tombstone, retry or dead-letter write that fails transiently, or gets
no report within `delivery_timeout`, is sent again after a backoff from 200 ms
up to 5 s, and its partition's commits wait for it. An attempt write is sent
again only while the worker still owns the unit's partition. A write that
retrying cannot fix stops the feed and the pipeline: a refused authorization,
a message over the topic's size limit, or a fenced producer. [Topics](#topics)
covers a write to a missing topic. A unit written to the retry topic is a new
message, so it is read after the units already there.

A gate pass that cannot read an attempt partition's watermark logs a warning
naming the partition, admits the units whose attempt partitions it could
read, and keeps that partition's units at the gate, where they count against
the buffer described under [Backpressure](#backpressure). The next pass starts
up to 1 s later. A pass that reaches `delivery_timeout` before it has read
every partition it needs does the same with the partitions it has not read,
and its warning names them and the partition whose read took longest. A pass
whose follower has not caught up within `delivery_timeout` logs a warning
naming the partition and tries all its units again. A watermark read refused
in a way retrying cannot fix, and an attempt record the worker cannot read,
stop the feed.

A message with no key is a unit named by its position,
`<topic>/<partition>/<offset>` of the message as read, and is counted, read and
finished like any other unit. Its retry and dead-letter copies carry that id as
their key. A message whose key is not UTF-8 names no unit. It goes to the
dead-letter topic at once, with its key, value and headers as read, and its
offset finishes once that write is confirmed. A message librdkafka reports
as corrupt, as `check.crcs` detects, stops the feed. librdkafka does not stop on
such a message, and reports it again on each fetch that reads it. For a message
in format v0 or v1, librdkafka skips its offset when the same fetch also returns
a later readable message, and a commit past it would lose the unit. For a record
batch in format v2, librdkafka either fetches the same batch again, so the feed
would read no further on that partition, or moves its fetch position to an
offset read from the wrong bytes, where `auto.offset.reset` decides what is read
next. A feed that has stopped commits nothing more, so the next owner of the
partition reads it again from the last commit.

## What counting costs

Before its read starts, each unit costs a watermark read of its attempt
partition, the follower's catch-up to that watermark, and one confirmed
produce. The gate takes every unit waiting at once, and one watermark read
serves every unit of a partition in that pass. A partition whose two
watermarks are equal, as an empty one's are, has them read again with one
request each, because librdkafka reports a refused low-watermark request that
way too. Every worker holds in memory
the count of each identity with a live record, whichever worker reads the
unit, and reads the attempt topic from its start when it connects.
[ADR-0070](../../../../adr/0070-on-kafka-a-units-attempt-is-recorded-before-the-unit-is-read.md)
gives the measured gate latency and memory per record.

## Stop

A stop follows
[the drain choreography](../../../03-guides/graceful-shutdown.mdx#the-drain-choreography).
Once it begins, the feed pauses every partition it owns, and every partition a
rebalance assigns it from then on. A unit still waiting at the gate gets no
attempt record. The consumer keeps polling, so the worker stays in the group
while its reader finishes what it holds.

A unit the reader hands back stays held. Its offset never finishes, so the
partition's commit stays below it, and the next owner of the partition reads it
once the worker leaves the group. Units buffered for the reader and not handed
out are read again the same way, and so are units still being read; each has
used an attempt.

After the final commit the runtime closes the feed within what is left of
`checkpoint.drain_timeout`. The feed waits up to half of that time for its
writes in flight to be confirmed, commits each partition up to its first
unfinished offset, and then leaves the group. An acknowledged unit whose
tombstone is not confirmed by then is read again after the stop, and that read
counts. One acknowledged on its `attempt_cap`-th read goes to the dead-letter
topic without being read instead. A dead-letter write confirmed during the
close is not followed by a tombstone, so the next owner finds the unit's record
at the cap and moves another copy to the dead-letter topic without reading it.

The commit can wait up to `session.timeout.ms` for a coordinator and up to
`socket.timeout.ms` for each attempt once sent, and the leave up to 5 seconds
for its answer. Either can run past the drain deadline, on the feed's consumer
thread, and dropping the feed waits for them. A worker killed before it leaves
keeps its partitions until `session.timeout.ms` lapses (see
[No lease](#no-lease)).

A feed dropped without a close waits up to 1 s for its writes in flight, then
commits and leaves the group the same way. A feed that stopped on an error
commits nothing more and leaves the group at once, so every unit since its last
commit is read again.

Startup refuses a `checkpoint.drain_timeout` of `5s` or less with the Kafka
feed (see [`checkpoint:`](../../../07-reference/configuration.mdx#checkpoint)).

## Message mapping

| Unit | Message |
|---|---|
| Id | The key, as UTF-8. A message with no key takes its own position, `<topic>/<partition>/<offset>`, as the unit's id. |
| Body | The value. A message with no value is a unit with an empty body. |
| Delivery count | The unit's attempt record, written before the read. |

A publish writes the unit to the work topic, partitioned by its key, and is
confirmed by its delivery report. A unit over librdkafka's `message.max.bytes`
(1,000,000 bytes by default), or over the topic's limit, is refused. Any other
failure that retrying can fix is reported as retryable, and one that it cannot
stops the feed and is reported with the feed's error.

A copy written to the retry or dead-letter topic carries the unit's id as its
key, the unit's publish identity in `spate.origin`, and the count of the
delivery it was written from in `spate.deliveries`. The feed writes
`spate.deliveries` for an operator reading the dead-letter topic, and does not
read it.

An attempt record's key is the unit's publish identity, and it lives on
partition `(murmur2(identity) & 0x7fffffff) % partitions` of the attempt
topic, where Kafka's Java client and librdkafka's `murmur2` partitioner place
that key. Its value is the JSON object `{"v":1,"attempts":n}`, and a null
value is a tombstone. A worker that reads a record at another version, with
a field it does not know, or that is not that object, stops the feed with an
error naming the record's offset.

## Metrics

The Kafka feed registers no metric families of its own.
