# Amazon SQS (feed)

The Amazon SQS feed (`spate-sqs`, feature `sqs` on the `spate` facade) carries
[work units](../../../07-reference/glossary.mdx#work-unit) in one SQS standard
queue that every worker of a pipeline reads. A received unit stays hidden from
the other workers while its reader renews it, is deleted once every record in it
is acknowledged, and returns to the queue when its reader fails it or stops. The
queue's redrive policy moves a unit that keeps failing to the dead-letter queue.
The backend lives in its own crate so that a source names no backend
([ADR-0069](../../../../adr/0069-feed-backends-live-in-their-own-crates.md)).

Construct it from the pipeline's opaque section, with the I/O runtime handle,
and pass it to `Pipeline::feed`:

```rust file=crates/spate/examples/s3_sqs_backfill.rs region=connect
```

That code comes from
[`s3_sqs_backfill.rs`](repo:crates/spate/examples/s3_sqs_backfill.rs), which
reads a staged `file://` backfill through a queue as one bounded job:

```sh
JOB_LOCATION="file://$(mktemp -d)/" \
  SQS_QUEUE_URL=https://sqs.eu-west-2.amazonaws.com/111122223333/jobs \
  cargo run -p spate --features s3,json,sqs --example s3_sqs_backfill
```

`SqsFeed::connect` reads the queue and its dead-letter queue once and runs
the [startup checks](#startup-checks), so a missing queue, a refused
credential or a queue the feed cannot dead-letter from fails there, before the
pipeline starts. Connecting takes at most 30 seconds, every step included;
past that it fails as unavailable, naming the step it was on.

## Configuration

The `feed: { sqs: ... }` section deserializes into `SqsFeedConfig`
([`spate-sqs/src/config.rs`](repo:crates/spate-sqs/src/config.rs)); unknown
fields are rejected with the offending key.

```yaml file=crates/spate/examples/s3_sqs_backfill.rs region=feed
```

| Key | Type | Default | Description |
|---|---|---|---|
| `queue_url` | string | `required` | The queue's URL, as `GetQueueUrl` returns it. An `http` or `https` URL. A FIFO queue, whose URL ends in `.fifo`, is refused. |
| `visibility` | duration | `60s` | How long a received unit stays hidden from other workers without a renewal. Whole seconds from `3s` to `12h`. |
| `region` | string | `none` | The AWS region. Unset, the region in a `sqs.<region>.amazonaws.com` queue URL applies, then `AWS_REGION`, the shared config file and instance metadata. |
| `endpoint` | string | `none` | An endpoint in place of the region's, such as a local emulator or a VPC endpoint. Calls go to this endpoint when it is set, and to the region's otherwise, so a VPC endpoint in `queue_url` is reached only when it is also set here. `AWS_ENDPOINT_URL` in the environment sets one too. |

`units_held` beside `sqs:` sets how many units a worker holds at once. The
section's `attempt_cap` is refused on `sqs`, because SQS counts deliveries
through the queue's `maxReceiveCount`.

## Security (credentials, permissions and TLS)

Credentials come from the AWS SDK's default provider chain: the
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`
environment variables, a profile in the shared config and credentials files
(`AWS_PROFILE`, SSO and `credential_process` included), a web identity token
(IRSA), the container credentials endpoint (ECS task roles, EKS Pod Identity)
and instance metadata. The section takes no secret of its own. The general
model is on the [securing hub](../../../03-guides/securing-connections.mdx).

The identity a worker runs as needs these actions:

| Action | On |
|---|---|
| `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:ChangeMessageVisibility` | The queue |
| `sqs:GetQueueAttributes` | The queue and its dead-letter queue |
| `sqs:SendMessage` | The queue, for a process that publishes units, a worker whose source re-enqueues units included |
| `kms:Decrypt`, and `kms:GenerateDataKey` for a process that sends | The queue's key, when a customer-managed KMS key encrypts the queue |

A [lister run](../../sources/s3/README.mdx#the-lister-run) publishes units and
receives none, so it needs only `sqs:GetQueueAttributes` and `sqs:SendMessage`,
and the two KMS actions above on a queue a customer-managed key encrypts.

The client verifies SQS against the system trust store. When `SSL_CERT_FILE`
or `SSL_CERT_DIR` is set, the certificates they name replace the system store.
If the store yields no certificate the client can parse, it logs a warning and
uses the Mozilla root bundle compiled into the binary. It goes through the
proxy that `HTTPS_PROXY`, `HTTP_PROXY` or `ALL_PROXY` names, except for the
hosts in `NO_PROXY`.

A rejected credential, signature or token, a 401 or 403 answer that is not
throttling, a missing queue, a rejected TLS handshake, a KMS key the queue
cannot use (access denied, disabled, not found, in an invalid state, needing
opt-in, or not usable for the operation) and any other 400 answer that
carries an error code are fatal: connecting fails with them, and after
startup the feed returns the error to every call and the pipeline stops.
Throttling, KMS throttling included, and the in-flight message limit are
retried at 400 or 403, and so are a 5xx answer, a 400 with no error code,
any other 4xx answer such as a 408 or 429, a timeout and a failure to load
credentials.

## Startup checks

The operator creates the queue and its dead-letter queue. Spate creates neither.
`SqsFeed::connect` refuses a queue it cannot dead-letter from:

- a FIFO queue, told by the `.fifo` ending of the name in its ARN;
- a queue with no redrive policy, or one whose policy it cannot read or that
  names no SQS queue;
- a dead-letter queue it cannot read, because it does not exist or the
  identity lacks `sqs:GetQueueAttributes` on it;
- a queue or dead-letter queue that does not report
  `ApproximateNumberOfMessages`, `ApproximateNumberOfMessagesDelayed` and
  `ApproximateNumberOfMessagesNotVisible` as numbers, which a bounded job's
  [end check](#ending-a-bounded-job) reads;
- a dead-letter queue whose `MessageRetentionPeriod` is no longer than the
  queue's. SQS counts retention from a message's first send, so such a queue
  can delete a unit as soon as it arrives. SQS keeps a message for at most 14
  days, so the queue must keep messages for less than that.

The dead-letter queue's URL is the queue URL with its last segment replaced
by the dead-letter queue's name from its ARN in the redrive policy, so the feed
needs no `sqs:GetQueueUrl`. When either queue reports no
`MessageRetentionPeriod`, the feed logs a warning and skips the retention
comparison. Connecting logs the queue's retention, its default visibility
timeout, `maxReceiveCount` and the dead-letter queue's retention.

The checks run only when the feed connects. A redrive policy removed, or a
dead-letter queue deleted or shortened, while the pipeline runs goes
unnoticed (see [Retention](#retention)).

## Visibility and renewal

A worker receives each unit hidden from the other workers for
`visibility`. Every third of that period the feed extends the visibility of
each unit handed to its reader or renewed since the last extension, back to
the full period. Units the feed has received and not yet handed out are
extended on the same tick while the reader keeps calling the feed, so a unit
waiting for room in the reader keeps its place. From a stop until the feed
closes, every unit handed to the reader is extended on each tick, renewed or
not (see [Stop](#stop)). A worker that stops renewing, because it crashed or
its control loop stalled, loses its units at most one visibility period after
their last extension, those not yet handed out included, and SQS hands them
to another worker.

The long-poll wait is `visibility / 3` seconds, rounded down and at most 20.
A unit that arrives at the end of a poll therefore still has two renewal
periods before its visibility lapses. A unit that is less than one renewal
period from its lapse when the reader asks for it is dropped unread and
returns to the queue when it lapses. A unit not yet handed out whose
extension SQS refused, because its receipt no longer holds the message, is
dropped unread too. A visibility under `60s` polls more often on an idle
queue.

## The 12-hour hold

SQS keeps a message hidden for at most 12 hours from the receive that issued
its receipt handle. The feed counts the hold from the moment each receive's
reply arrives, less 30 seconds, and clamps the first visibility and every
extension to it.

A reader therefore holds a unit for at most 12 h − 30 s from the receive that
handed it out. After that its visibility lapses and SQS hands the unit to a
reader again, under a new hold. At a `12h` visibility, a unit the reader asks
for more than 12 h − 30 s − `visibility / 3` after its receive, about 8 hours,
is dropped unread, as any unit less than one renewal period from its lapse
is.

## Failing a unit

A worker fails a unit it cannot read by setting its visibility to zero, so
the queue hands it out again at once. A unit whose visibility has already
lapsed is not touched, since it is back in the queue. The visibility change,
the SDK's retries included, is given up at the earliest deadline among the
units in its batch; a request already sent by then can still reach SQS just
after. After
`maxReceiveCount` receives the queue's redrive policy moves the unit to the
dead-letter queue. The feed never sends to the dead-letter queue itself.

## Redrive

Every receive counts toward `maxReceiveCount`: a worker failing the unit, a
worker that handed it back at a stop or crashed with it held, a crash loop
around a sink outage, and a receive that drops a unit too close to its
lapse. Set `maxReceiveCount` above
the number of such receives a unit can see, or a unit that would have been
read reaches the dead-letter queue.

## Retention

SQS deletes a message when the queue's retention period ends, counted from
when it was first sent and kept when the message moves to the dead-letter
queue. A unit deleted that way is lost, which INV-1 places outside its
property (see [the invariants](../../../../INVARIANTS.md#inv-1)). A
dead-letter queue deleted after the pipeline starts loses the units moved to
it; nothing checks for it while the pipeline runs.

## Ending a bounded job

A [bounded job](../../sources/s3/README.mdx#how-a-bounded-job-ends) reads the
queue's depth from `GetQueueAttributes`: `ApproximateNumberOfMessages` as
ready, `ApproximateNumberOfMessagesDelayed` as delayed, and
`ApproximateNumberOfMessagesNotVisible` as received and not yet deleted. The
feed adds the deletes and fails it has accepted and not yet sent. A worker
reads them every 15 seconds over the settling window, and the window starts
again on any read that is not all zeros. Once the window passes, the worker
reads the dead-letter queue's three counts, and any message there fails the
job as stalled, naming the dead-letter queue.

SQS's counts are estimates, and AWS documents them as taking at least a minute
after the producers stop to settle, so `sqs` refuses a `settling_window` below
`1m`. ElasticMQ, which the CI suite runs against, reports exact counts, so no
test checks the window against counts that lag. A read of the queue that SQS
fails transiently starts the window again, and such a read of the dead-letter
queue is tried again 15 seconds later. A read SQS refuses, such as for a missing
permission, fails the job. The reads need `sqs:GetQueueAttributes` on both
queues, which [the startup checks](#startup-checks) already need.

The dead-letter queue is read only after the window passes. A unit moved there
earlier in the job and deleted at the end of the dead-letter queue's retention,
counted from the unit's first send, leaves no trace, and the job ends
completed over it. Keep a bounded job shorter than the dead-letter queue's
retention, and alert on the dead-letter queue's
`ApproximateNumberOfMessagesVisible` in CloudWatch: Spate does not see a
message move there while a job runs, and a job with no `location` never reads
the dead-letter queue at all.

Give each bounded job a queue and a dead-letter queue of its own. A dead-letter
queue that holds an earlier job's messages fails a later job as stalled, and a
queue that also receives storage notifications keeps the window from closing.

## Stop

A stop follows
[the drain choreography](../../../03-guides/graceful-shutdown.mdx#the-drain-choreography).
Once it begins, the feed receives nothing more and sets each unit it received
and had not handed to the reader visible at once. A receive already waiting
returns its units the same way, and one that answers after the feed closes
leaves its units to return after one visibility period. That receive can take
a unit the reader has just handed back. The feed then hands it back again,
which costs the unit one more receive toward `maxReceiveCount`, and the close
waits up to a second after the last hand-back for that receive to answer.
Until each unit is
acknowledged or handed back, the feed extends every unit it has handed out on
each renewal tick.

A unit the reader hands back is set visible at once, and another worker can
receive it. A unit already past its deadline is visible again, and the feed
sends it nothing; a deadline never falls after
[the 12-hour hold](#the-12-hour-hold) ends. Each handed-back unit keeps the
receive it used toward `maxReceiveCount`.

After the final commit the feed sends its queued deletes and sets each unit it
still holds visible, within what is left of `checkpoint.drain_timeout`. A
delete not sent by then leaves its unit to return after one visibility period
and be read again, and so does every unit of a worker killed before its
hand-back reaches SQS.

Startup refuses a `checkpoint.drain_timeout` of `5s` or less with the SQS feed
(see [`checkpoint:`](../../../07-reference/configuration.mdx#checkpoint)).

## Message mapping

| Unit | Message |
|---|---|
| Body | The message body, sent as text. A body that is not UTF-8, is empty, or holds a character SQS does not accept is refused before it is sent. |
| Id | The String message attribute `spate.unit`. A message without it takes its `MessageId` as the unit's id. |
| Delivery count | `ApproximateReceiveCount`, or 1 when absent. |

A unit is at most 1 MiB as a message, its body and the `spate.unit`
attribute counted together; a larger one is refused before it is sent.
Publishes go out in batches of up to ten units and 1 MiB. Each publish is
confirmed by its own entry: an entry SQS rejects as the sender's fault is
refused, and any other failed entry is reported as retryable. When the feed
stops on a fatal error, the batch it is sending is reported as retryable,
since SQS may have stored it, and the publishes not yet sent are rejected
with the error. A batch whose first send attempt fails on the fatal error
is rejected with it too. The feed makes each send attempt itself, backing off
from 200 ms up to 5 s between them. A delete or visibility change SQS fails
for one entry is dropped, and that unit returns to the queue when its
visibility lapses.

## Storage notifications

An AWS S3 bucket can send its notifications to the queue, and a source that
reads them takes each message as one unit. A notification carries no
`spate.unit` attribute, so its unit's id is the message's `MessageId`. The
queue receives the bucket's notifications only when
([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ways-to-add-notification-config-to-bucket.html)):

- its access policy lets the bucket's account send to it from
  `s3.amazonaws.com`;
- an encrypted queue uses a customer managed KMS key whose key policy lets
  Amazon S3 use it;
- its maximum message size is at least 64 KB;
- it is in the bucket's region.

The bucket's side, and which records the source reads, are on the
[S3 source](../../sources/s3/README.mdx#storage-notifications) page.

## Cost per request

Each unit costs a send, a receive and a delete, each batched up to ten to a
request, plus one visibility change per renewal period while it is held,
batched the same way. A unit handed back at a stop costs one more visibility
change. A worker that wants more units than it holds keeps one
long poll open, so an idle worker sends a receive every `visibility / 3`
seconds, at most every 20: three a minute at the default visibility, and
thirty a minute at `6s`.

## Metrics

The SQS feed registers no metric families of its own.
