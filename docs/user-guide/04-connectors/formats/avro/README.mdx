# Avro format

The Avro deserializer (`spate-avro`, feature `avro` on the `spate` facade)
decodes bare Avro datums carried by a source into records, either serde types
or dynamically-typed values. Several framings are supported; the framework
handles the framing bytes, so schemas and structs only ever describe the datum
itself.

Construct it from the pipeline's opaque section, handing it the builder's
I/O runtime handle (the registry fetcher lives there):

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=deserializer
```

That is from
[`kafka_avro_to_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_to_clickhouse.rs),
a complete program that builds under the `kafka`, `clickhouse` and `avro`
features. The `deserializer:` section is optional in the framework's config,
so the factory takes the unwrapped section, and a pipeline whose source emits
ready-made records configures none.

## Configuration

The `deserializer: { avro: ... }` section deserializes into `AvroSettings`
([`spate-avro/src/config.rs`](repo:crates/spate-avro/src/config.rs)); unknown
fields are rejected with the offending key.

```yaml
deserializer:
  avro:
    mode: confluent                # confluent | raw | single_object
    registry:                      # required for confluent
      url: https://registry.internal:8081
      username: ${SR_USER}         # optional basic auth
      password: ${SR_PASSWORD}
      tls:
        root_ca: /etc/spate/registry-ca.pem  # optional: a private CA
    prewarm_subjects: [orders-value]
    negative_cache_ttl: 30s
    reader_schema:                 # optional: pin the resolved shape
      path: /etc/spate/orders.avsc   # (or `inline: '{"type": ...}'`)
    # schema: { inline | path }    # required for raw / single_object
```

| Key | Type | Default | Description |
|---|---|---|---|
| `mode` | string | `confluent` | Payload framing: `confluent`, `raw`, or `single_object`. |
| `registry.url` | string | `required` | Base URL of a Confluent-compatible schema registry. Required in `confluent` mode; rejected in the others. Credentials in the URL are rejected at configuration load. |
| `registry.username` / `registry.password` | string | `none` | Basic auth (interpolate secrets via `${VAR}`). A password requires a username. The password and any userinfo in `registry.url` render `<redacted>` in `Debug` output. |
| `registry.tls.root_ca` | path | `none` | PEM bundle of root CAs trusted in addition to the system trust store. Requires an `https://` URL. |
| `prewarm_subjects` | string list | `[]` | Subjects whose latest schemas are fetched at startup (`confluent` mode only). |
| `negative_cache_ttl` | duration | `30s` | The longest a schema id the registry could not serve stays negatively cached before a refetch is allowed. The cache holds at most 1,024 such ids and drops the oldest for a new one, so a dropped id is refetched on its next record. At least `100ms`, so a negative entry outlives the replay of the record it holds; a shorter value fails at startup in every mode. |
| `reader_schema` | `{ inline }` or `{ path }` | `none` | Reader schema pinning the resolved record shape (`confluent` and `raw` modes; not `single_object`). A reader schema that recurses through a union limits how deep a datum may recurse; see [Schema evolution](#schema-evolution). |
| `schema` | `{ inline }` or `{ path }` | `required` | The writer schema. Required in `raw` and `single_object` modes; rejected in `confluent` mode (writer schemas come from the registry there). |

Mode requirements are validated at construction with explicit messages:
`confluent` without a `registry`, a `registry.url` that is not an `http://` or
`https://` URL, `raw` without a `schema`, `prewarm_subjects` outside
`confluent`, and so on all fail fast at startup. A `negative_cache_ttl` under
`100ms` fails at the same point in every mode, `raw` and `single_object`
included. Registry URLs with a parsed
nonempty username or a password fail at configuration load, before schema
loading, TLS client construction or prewarm. Credentials belong in
`registry.username` and `registry.password`, including when no separate
credentials are supplied. A `registry.password` without a `registry.username`
fails at the same point. A username without a password is accepted.

## Security (TLS and registry credentials)

An `https://` registry is verified against the system trust store. On macOS
and Windows the operating system verifies the certificate. On Linux and other
Unix systems the client reads the system store, and when `SSL_CERT_FILE` or
`SSL_CERT_DIR` is set, the certificates they name replace it. There, an
`https://` registry fails the deserializer at startup when neither the store nor
`registry.tls.root_ca` holds a certificate the client can use, as on a container
image without a CA package. The error is at `registry.tls.root_ca` and names the
fixes. An `http://` registry starts without one, and a redirect or proxy that
takes it to `https://` then fails the handshake.

For a private CA, set `registry.tls.root_ca` to a PEM file. Its certificates are
trusted in addition to the system store, and on Linux and other Unix systems
also when `SSL_CERT_FILE` or `SSL_CERT_DIR` replace that store. A relative path
resolves against the working directory. A file that cannot be read, holds no
certificate or holds one that does not parse fails the deserializer at startup,
and so does `registry.tls.root_ca` with a registry URL that is not `https://`.
Android builds reject the setting.

`registry.username` and `registry.password` carry basic auth to the schema
registry. Interpolate them from the environment (`${SR_USER}` /
`${SR_PASSWORD}`) rather than committing them. The registry URL must omit
credentials.

A non-empty `registry.password` with an `http://` registry URL logs one warning
when the deserializer is built, and the pipeline keeps running. A loopback host
gets the same warning. Use an `https://` URL to send the password over TLS.

```text
deserializer.avro.registry.password: registry.url uses http://; the credential is sent without TLS
```

For migration, remove userinfo from `registry.url` and set the separate
credential fields. Percent-encoded URL credentials become decoded text in
these fields. Username-only URLs need only `registry.username`. If separate
credentials are already configured alongside URL credentials, retain the
separate fields and remove the URL userinfo. Programmatic configurations
using `RegistrySection::new` follow the same requirement when loaded by
`AvroDeserializerBuilder::from_settings`.

A registry that answers `401` or `403`, or whose certificate fails
verification, stops the pipeline whatever the deserializer's `ErrorPolicy`.
An expired or untrusted intermediate certificate counts as a failed
verification. A TLS alert with which the registry rejects the handshake, such
as `HandshakeFailure` or `ProtocolVersion`, stops the pipeline too, and so does
a registry that shares no protocol version, cipher suite or other handshake
parameter with the client. The registry client presents no client certificate.
A registry that requires one refuses the client with an alert such as
`CertificateRequired`, during the handshake or, under TLS 1.3, after it, and
that stops the pipeline too. A refusal after the handshake can close the
connection before the request is sent, and that fetch is transient, so the stop
can take a few fetches of the schema, each after a backoff that starts at
200 ms and doubles up to 5 s, with each wait drawn at random between 80% and
100% of its step. The error names the registry URL, without credentials, and
the status with the start of the registry's response, the certificate error,
the alert or the mismatch.
The deserializer learns of the rejection from a fetch, so the pipeline stops at
the first payload whose schema is not cached. Schemas already cached keep
decoding until then, and a pipeline that receives no payload keeps running.
A `401` on a `prewarm_subjects` fetch counts too. A `403` there refuses one
subject, so it is logged and the subject's schema is fetched by id when a
payload needs it. A `403` on that fetch stops the pipeline. Any other TLS or
transport failure, such as an `InternalError` alert or a connection closed
during the handshake, is transient: the batch is held and replayed while it
lasts, logging `registry fetch failed transiently` and counting
`spate_deser_not_ready_total`. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

## The three modes

- **`confluent`** — Confluent wire format: each payload starts with a
  5-byte header (magic byte `0` plus a 4-byte schema id) followed by the
  datum. The framework parses the header, resolves the id against the
  registry, and decodes; producers using Confluent-ecosystem serializers
  work without adaptation.
- **`raw`** — bare datums with a fixed configured schema (`inline` or a
  mounted `.avsc` file).
- **`single_object`** — Avro single-object encoding (marker plus Rabin
  schema fingerprint), verified against the configured schema's
  fingerprint.

## Typed or dynamic records

The builder hands out these deserializer flavors:

- `build_serde_datum::<T>()` (and the record-family form `build_datum::<F>()`)
  — decodes each datum **directly** into `T` in a single pass, driven by the
  writer schema, never materializing an intermediate value tree. This is the
  throughput path. With a borrowed record family, string and bytes fields
  point straight into the payload buffer (zero-copy;
  [`spate-avro/tests/zero_copy_flat_map.rs`](repo:crates/spate-avro/tests/zero_copy_flat_map.rs)
  is the worked example).
  The constraints: no `reader_schema` (rejected at build time, since records
  decode in the writer schema's shape; additive evolution works through
  `#[serde(default)]`/`#[serde(alias)]`, and unknown fields are skipped),
  and no `duration`/`big-decimal` logical types. A fixed schema breaks the
  logical-type rule at build time; in registry mode the writer schema only
  arrives at runtime, so an incompatible schema id surfaces **per record**
  as `SchemaUnavailable`, dropped and counted under the Skip policy and fatal
  under Fail, while the same id stays fully decodable on the paths
  below.
- `build_serde::<T>()` — decodes each datum into a
  `T: serde::de::DeserializeOwned` struct via an intermediate `AvroValue`,
  applying Avro's schema-resolution rules when a `reader_schema` is
  configured (field reordering, type promotions, defaults).
  This is the flavor the construction snippet above builds.
- `build_value()` — decodes into dynamically-typed `AvroValue` records, for
  pipelines that inspect or route on structure not known at compile time.

## Schema fetching never blocks a pipeline thread

In `confluent` mode, registry schemas are fetched by an **asynchronous task
on the I/O runtime** and cached per process. When a payload references a
schema that is not cached yet, the deserializer does not wait: it reports
"not ready", the operator chain holds the batch (backpressure pauses the
source if needed), and **the batch retries once the fetch lands**. Records
are never dropped or duplicated by this mechanism, and the
pipeline threads never perform I/O. A rejected registry is the exception:
see [Security](#security-tls-and-registry-credentials). These knobs shape the
edge cases:

- `prewarm_subjects` fetches the configured subjects' latest schemas at
  startup, so the first batch does not pay the miss.
- Ids the registry *cannot* serve are negatively cached for up to
  `negative_cache_ttl`, and their records are handled by the deserializer's
  `ErrorPolicy` (Skip or Fail) like any other poison payload. With the
  engine's default settings a held batch is replayed inside the `100ms` floor,
  so a permanent bad id cannot wedge the pipeline into an infinite retry.
- The cache holds at most 1,024 compiled schemas and an estimated 64 MiB of
  them. At either bound it evicts the oldest schema that no record has used
  since the cache last considered it. Among schemas older than the 256
  newest, one in use is evicted after those that are not. An evicted id is
  fetched again on its next record, and that fetch can fail as a first fetch
  can: an outage holds the batch, and a rejection stops the pipeline.
- The cache evicts its 256 newest schemas last, so a held batch replays
  before its schema can leave. Records that name 256 fresh ids inside one
  replay interval, 2 ms by default, can evict a schema before its batch
  replays, and the batch then fetches it again. Schemas large enough to reach
  the 64 MiB bound in fewer than 256 inserts have the same effect.
- A pipeline thread keeps the schemas it last saw until its next record, so
  each thread that receives no records can hold up to the bounds again.
- `prewarm_subjects` above either bound keeps the subjects listed last, and
  the rest are fetched by id when a record needs them.
- A schema estimated to hold more than 64 MiB compiled is refused. Its id is
  negatively cached and its records follow the `ErrorPolicy`. The estimate is
  20 bytes for each byte of the schema's JSON, and 20 more for each byte of a
  record, enum or fixed, once per name it has and again inside each record
  that holds it. A 240 KB schema of 40 equal records, each inside the last,
  is over the bound, and so is a 30 KB record with 110 aliases.

## Error handling

Undecodable payloads follow the deserializer's `ErrorPolicy`, Skip or Fail,
like any other poison payload: Fail stops the pipeline on the first bad datum;
Skip drops it and continues. A record naming a schema id the registry cannot
serve reaches the same policy when it is replayed within `negative_cache_ttl`
of the registry's answer, so a permanently bad id ends in an error. A
registry that rejects the client is not a payload error and stops the pipeline
under either policy.

A datum decode that attempts to read past the payload returns a malformed
record error and follows the configured Skip or Fail record error policy.

Every deserializer also refuses a datum past the bounds below, as a malformed
record under the same policy. The bounds keep one record from exhausting the
pipeline thread's stack or memory:

- **Nesting.** `build_value` and `build_serde` accept 32 levels. A level is a
  record field, an array or map item, a union branch, a named-type reference,
  or the bytes of a `decimal` or `big-decimal`. A list whose `next` field is
  `["null", "Node"]` takes three levels per node, so 10 nodes is the deepest
  these two accept. `build_datum` accepts 128 levels. Where the target reads
  the list, it does not count a named-type reference as a level, so it
  accepts 64 nodes. Where the target ignores the field, it counts all three,
  so it accepts 42.
- **Collection items.** The arrays and maps of one datum may claim as many
  items as the payload has bytes, or 65,536 if that is more. An item that
  takes no bytes on the wire, such as a `null` or an empty record, counts like
  any other. In a field the target ignores, `build_datum` skips a block that
  gives its size in bytes, and does not count its items.
- **Decoded size.** `build_value` and `build_serde` build the whole decoded
  tree in memory. They refuse a datum whose tree would take more than 1,024
  bytes for each payload byte, or 64 MiB if that is more. The estimate counts
  each value, the field names copied into every record, enum symbols, and
  string, bytes and map key contents. With a `reader_schema` it also counts
  the fields and defaults that resolution into it adds. A record of long
  strings takes about 3 bytes per payload byte, and one of many `null` fields
  with long names about 240. `build_datum` builds no such tree.

A datum that recurses past the resolution limit of a recursive `reader_schema`
is also a malformed record, and follows the same policy.
[Schema evolution](#schema-evolution) states the limit.

The error text for a refused datum quotes no string, bytes or field value from
the record. The typed single-pass path names what the record type expected,
such as the type or the enum's variants. The other paths say that the decode
failed or that the record does not match the target type, and name a reader
field the record lacks. A refusal by the bounds above names the count, length,
union index or limit it read. Those numbers come from the payload, so in a
datum that does not match its schema they can be a field's bytes read as a
length.

The unit is the payload. One datum is one record here, so there is no partial
outcome to reason about. Drops surface in the framework's stage families,
below.

## Schema evolution

Writer schemas come from the payload (registry id or fingerprint) or
configuration; an optional `reader_schema` pins the shape records resolve
into, using Avro's standard schema-resolution rules: field reordering,
defaults for missing fields, type promotions. Pin a reader schema to keep a
struct stable while producers evolve. Registry schemas using schema references
are not supported and surface as unavailable, and so does a registry schema
whose type is not `AVRO`, such as `PROTOBUF` or `JSON`.

A reader **field** alias is not applied. A reader field that renames a writer's
field and lists the old name in `aliases` reports that field missing on every
payload, and the record then takes the deserializer's `ErrorPolicy`, so the
default Skip policy drops the entire stream. Rename on the Rust side with
`#[serde(alias)]` instead, which both typed paths support.

A record-level alias is a different rule. Resolution never compares record
names, so a payload resolves against any structurally compatible reader record
whatever it is named. Keep the alias in the schema, which the Avro
specification and a registry's compatibility check both read.

Promotion runs one way. A reader may widen a field an `int` was written as
to a `long`, and a `float` to a `double`; the reverse is not a promotion.
Narrowing is nonetheless accepted, and only one direction of it is checked:
a `long` too large for the reader's `int` fails the record, which then takes
the deserializer's `ErrorPolicy`. A `double` narrowed to a `float` is **not**
checked and saturates to infinity, and a `long` narrowed to a `float` or a
`double` loses precision, both without an error and without a metric moving.
Widen a field freely; do not narrow one.

A reader schema that recurses through a union limits how deep a datum may
recurse. A linked list whose `next` field is `["null", "Node"]` is such a
schema. Resolution tries a value against a union's branches and then resolves it
again, so each time a datum passes through the same union again, the cost of
everything below doubles. Each datum is therefore weighed before it is resolved.
A value weighs one, plus one for each 64 bytes of text, binary content, field
names or map keys it holds. It weighs double for each time its path has already
passed through the union it is under. Where the union a value is under has
several branches the value could resolve into, the value is weighed against
each branch. A value the reader schema drops is weighed like any other, because
resolution copies it.

A datum is refused as a malformed record when the doubling adds more than 1,024
to its weight, and more than three times what the datum weighs with no
doubling. Where the datum's encoded length in bytes is less than that undoubled
weight, the length takes its place, because a value such as a null takes no
bytes to encode. The refused record takes the deserializer's `ErrorPolicy`.

How deep a datum may recurse therefore depends on how much it holds. A linked
list whose nodes have one other field resolves up to 9 nodes, and one whose
nodes have 40 other fields up to 5 nodes. A binary tree with no other fields
resolves up to 5 levels. The tests in
[`spate-avro/src/resolve.rs`](repo:crates/spate-avro/src/resolve.rs) pin these
figures.

Under a reader schema that does not recurse, nothing in a datum is doubled,
because the schema fixes how its unions nest and no datum can deepen them.
This limit never refuses such a datum.

## Metrics

This deserializer registers no families of its own. Decode outcomes surface in
the framework's stage families: `spate_deser_records_total{outcome}`,
`spate_deser_records_dropped_total{reason="skip_policy"}`, and
`spate_deser_not_ready_total` for payloads held waiting on a registry fetch,
which is neither an error nor backpressure. On a chain built with
`with_metrics`, these series carry `component_type="avro"`. See
[Metrics](../../../../METRICS.md).
