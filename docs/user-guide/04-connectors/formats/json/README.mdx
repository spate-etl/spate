# JSON format

The JSON deserializer (`spate-json`, feature `json` on the `spate` facade)
decodes JSON payloads carried by a source into records, either serde types or
dynamically-typed values. The framings map onto the framework's "one payload →
0..N records" contract, and `serde_json` (stable 1.x) parses by default.

Construct it from the pipeline's opaque section with
`JsonDeserializerBuilder::from_component_config`, or from a
`JsonDeserializerConfig` built in code with `JsonDeserializerBuilder::new`. The
runnable JSON Lines example builds one in code, starting from the config's
`Default`:

```rust file=crates/spate/examples/json_skip_bad_records.rs region=deserializer
```

That example is
[`json_skip_bad_records.rs`](repo:crates/spate/examples/json_skip_bad_records.rs):
one payload of four lines, one of them malformed, over the in-memory
connectors, so it needs nothing running:
`cargo run -p spate --features json --example json_skip_bad_records`.
Both `new` and `from_component_config` return the builder behind a `Result`
and run `JsonDeserializerConfig::validate`. The chain's `with_metrics` scopes
the families under [Metrics](#metrics).

## Configuration

The `deserializer: { json: ... }` section deserializes into
`JsonDeserializerConfig`
([`spate-json/src/config.rs`](repo:crates/spate-json/src/config.rs)); unknown
fields are rejected with the offending key.

```yaml
deserializer:
  json:
    on_error: skip               # skip | fail
    reject_duplicate_keys: false # error on any repeated object key
```

| Key | Type | Default | Description |
|---|---|---|---|
| `on_error` | string | `skip` | Per-record policy for a document that does not parse or match the target type: `skip` (drop, and count on a chain built with `with_metrics`) or `fail` (surface a decode error). |
| `reject_duplicate_keys` | bool | `false` | Reject (rather than silently keep the last value of) any JSON object with a duplicate key, at any depth. Parses each document a second time for the check. |

## The three framings

`JsonDeserializerBuilder::framing` sets the framing in code, with a
`JsonFraming`. The section has no `framing` key, and one there is rejected as
an unknown field.

- **`Single`** — the whole payload is one JSON document → one record. The
  default, and what a source emitting whole payloads produces. An empty or
  whitespace-only payload is a **tombstone**: zero records, no error.
- **`Lines`** — newline-delimited JSON ([JSON Lines](https://jsonlines.org/)):
  one JSON value per `\n`-separated line → one record per line. Blank lines are
  skipped. Under `on_error: skip` a malformed line is dropped and the other
  lines still decode. Under `on_error: fail` the first malformed line fails the
  whole payload; see [Error handling](#error-handling).
- **`Array`** — a top-level JSON array → one record per element, decoded in a
  single pass. Error handling is **atomic**: one malformed element drops the
  whole array, or fails it as one payload.

A source that frames its own byte stream supplies this crate's `JsonLinesFramer`
instead. The deserializer then keeps `Single`: under such a source it refuses
`Lines` and `Array` when the pipeline starts, and the run returns an error
before the source opens. See
[Framing vs deserialization](../README.mdx#framing-vs-deserialization).

## Typed or dynamic records

- `build_serde::<T>()` — decodes each document into a
  `T: serde::de::DeserializeOwned` struct. No `serde_json` types leak into the
  pipeline. This is the flagship path, and the one the example on this page
  takes.
- `build_value()` — decodes into dynamically-typed `serde_json::Value` records,
  for pipelines that inspect or route on structure not known at compile time.

## Error handling

A document that does not parse (or does not match the target type) is a
record-level error, handled by `on_error`:

- **`skip`** (default) — drop the record, count it in
  `spate_json_deser_records_dropped_total{reason}` on a chain built with
  `with_metrics` (see [Metrics](#metrics)), and continue. Under `Lines`
  the good lines around a bad one still flow. Under `Array` one bad element
  drops the whole array.
- **`fail`** — surface a decode error on the first bad record. Under every
  framing, no record from that payload is emitted.

:::note `on_error: fail` and the chain's policy
`fail` makes the deserializer *return* a decode error; whether that **stops**
the pipeline or **drops the payload** is then the chain's deserializer error
policy (`ErrorPolicy`, default `Skip`). Set the chain's policy to `Fail`
(`.deser_error_policy(ErrorPolicy::Fail)`) for a bad record to stop the
pipeline. The common case, per-record **skip**, needs no chain-side change.
:::

Undecodable data that stops the pipeline replays under at-least-once; replay
never loses records.

The `WARN` line for a skipped record and the failure reason carry no content
from the record. The `WARN` line carries the record's `partition` and `offset`.
The error text says that the document does not parse, that it does not match
the record type, or that it repeats an object key. With `serde_json` the text
ends in the line and column. A deserializer that decodes with `simd-json`
(see [Backends](#backends)) gives the character index for a parse error, and
no position for a document that does not match the record type.

Under `Lines` framing the position counts within the refused line, so the line
is always 1. The text does not say which line of the payload was refused.

## Fidelity & features

- `reject_duplicate_keys` (config) turns `serde_json`'s silent last-value-wins
  on duplicate object keys into a hard error, a guard against upstream
  corruption.
- The `float-roundtrip` Cargo feature makes `f64` values survive
  text→float→text exactly.
- The `raw-value` feature exposes `serde_json`'s `RawValue` for late/partial
  parsing (route on one field, forward the rest untouched).

:::warning `arbitrary-precision`
The `arbitrary-precision` feature preserves integers beyond `u64` and exact
decimals, but it is **crate-wide** once enabled and interacts with
`#[serde(flatten)]`, `#[serde(untagged)]`, and `RawValue`. Enable it
deliberately for a decimal/money pipeline, not by default.
:::

By default, integers up to 64-bit are exact; values beyond that fall to `f64`
(the standard JSON interop limit). Duplicate keys are last-value-wins unless
`reject_duplicate_keys` is set. `NaN`/`Infinity` are not valid JSON and are
rejected.

## Backends

Decoding uses `serde_json` (stable 1.x) by default. Cargo feature `simd-json`
(`json-simd` on the `spate` facade) adds
`JsonDeserializerBuilder::with_simd_json`. Each deserializer built from a
builder that calls it decodes with
[`simd-json`](https://github.com/simd-lite/simd-json), a SIMD-accelerated
parser. The feature alone changes no deserializer, so two deserializers in one
binary can use different parsers.
`build_serde` and `build_value` are the same for both parsers. `from_reader` is
never used on the hot path. Decoding always operates on the in-memory payload
slice, which is both faster and lets the parser see the whole document at once.

`simd-json` is faster than `serde_json` on some payloads and slower on others,
and the difference depends on the CPU. The table gives the change in decode
time with `simd-json` on three AWS 8xlarge hosts: c7i (Intel Xeon Platinum
8488C, x86_64), c7a (AMD EPYC 9R14, x86_64) and c8g (Graviton, aarch64). A
negative figure means `simd-json` is faster. "Under 5%" means the difference
was too small for the measurement to resolve.

| Payload | Framing | c7i | c7a | c8g |
|---|---|---:|---:|---:|
| Event lines of about 600 bytes, nested and mostly strings | `Lines` | under 5% | −7.7% | +13.4% |
| Flat records of seven fields | `Lines` | under 5% | −9.3% | under 5% |
| Flat records of seven fields | `Array` | −8.5% | −15.0% | −16.4% |
| One array of 40 objects, each nested 64 levels deep | `Single` | −7.9% | −13.3% | −12.9% |
| One string of half a megabyte | `Single` | −44.4% | −73.7% | −26.3% |
| An array of 40,000 numbers | `Single` | +113.4% | +162.3% | +58.9% |
| One object of 4,000 fields | `Single` | under 5% | under 5% | −5.5% |

The record rows decode into a struct, and the `Single` rows decode into
`serde_json::Value`. The figures come from the
[`decode_wall.rs`](repo:crates/spate-json/benches/decode_wall.rs) bench, run
with `simd-json` 0.19 and `serde_json` 1.0 over 20 interleaved replicates.

The `simd-json` parser chooses its code at run time from the CPU's features. On
both x86_64 hosts it chose its AVX2 code. A CPU without both AVX2 and PCLMULQDQ
runs SSE4.2 code for some or all of the parse, and a CPU without SSE4.2 runs
scalar code. Neither fallback was measured. The
[`cpu features` log line](../../../05-deployment/monitoring.mdx#check-which-simd-features-a-host-offers)
shows which of these features a host offers.

`serde_json` is the default, because `simd-json` is slower on some payloads. It
is slower on number-heavy payloads on every host, and on the event lines on
Graviton.

simd-json parses a mutable buffer in place, so the
framework copies each borrowed payload into a reused thread-local buffer
first (measured at ~1% of the decode on flat and nested records, by a rig this
repository no longer carries). The
`reject_duplicate_keys` guard
always runs on `serde_json`, so duplicate-key handling is identical either
way.

The backends differ on some valid numbers. `simd-json`
**rejects integer literals outside the `i64`/`u64` range** (which `serde_json`
accepts, coercing to `f64`) and normalizes `-0` to `0`. Both backends reject a
NUL byte after a number and underscore separators in numbers as malformed JSON.

The parsers also enforce different nesting limits: `serde_json` has a recursion
limit of 128, while `simd-json` limits nested arrays and objects to 1024. With
`reject_duplicate_keys` enabled, the `serde_json` guard runs first and applies
its recursion limit under either backend. Inputs beyond the applicable limit
produce a `malformed` decode error. Under `on_error: skip`, the affected record
or payload is dropped; under `on_error: fail`, decoding fails.

Because parsing is done by `simd-json` rather than `serde_json`, the
`serde_json`-specific knobs `json-float-roundtrip`, `json-arbitrary-precision`,
and `json-raw-value` do **not** apply to a deserializer that decodes with it
(arbitrary precision is silently lost; `RawValue` capture is unsupported).
Benchmark **and** validate against real data before switching.

## Metrics

Registered through the `Meter` the chain hands the deserializer (component type
`json`, role `deser`), so every family is prefixed `spate_json_deser_`. The
families exist only on a chain built with `.with_metrics(pipeline, component)`.

The family exists because the framework's payload-granular `spate_deser_*` stage
metrics cannot see a drop under `on_error: skip`. Under every framing the
`deserialize` call returns `Ok` after the drop, so no
`spate_deser_records_total{outcome="error"}` is counted. Under `Lines` the good
lines around a bad one are still emitted. Under `Array` the whole array is
dropped.

The family carries the standard labels with the values of the chain's
`spate_deser_*` series: `pipeline` from that call,
`component="<component>.deserializer"` and `component_type="json"`, so the two
join. Extras are noted per family.

| Metric | Type | Extra labels | Description |
|---|---|---|---|
| `spate_json_deser_records_dropped_total` | counter | `reason` (`malformed`\|`duplicate_key`) | Records dropped by `on_error: skip` because they did not parse / match the target type (`malformed`) or contained a duplicate object key under `reject_duplicate_keys` (`duplicate_key`). A dropped array counts once. |

These sit alongside the framework's generic `spate_deser_*` stage metrics, which
wrap every decoder. See [Metrics](../../../../METRICS.md).
