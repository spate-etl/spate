# ClickHouse column types

Which column types each of the sink's wire formats writes, and what to do about
the ones it does not. The `format` key selects between them; they carry the
same rows and differ in which column types they can express.

They reach that limit differently. `format: native` is type-driven: the encoder
builds one writer per column from the type `system.columns` reports, so a type
it does not model is rejected **at construction**, before any row is sent, with
an error naming the column. RowBinary never sees the column type at all. The row
struct's field types alone decide the bytes, positionally.

That gives the two format columns different meanings. Under Native, `no` is a
refusal by the encoder. Under RowBinary, `no` means no field type, wrapper or
serde module in the crate produces the bytes the column expects, and `manual`
means one does, on a value the row has already scaled or ordered by hand.

Which Rust field, wrapper or `#[serde(with = "…")]` module a given column takes
is in the `rowbinary` module of the
[`spate-clickhouse` reference](https://docs.rs/spate-clickhouse).

## Aggregate states

An `AggregateFunction` column holds an opaque, version-dependent serialization
of a partial aggregation, and neither format writes one: reproducing that
serialization in a client ties the pipeline to a single server version. Insert
raw rows into an `ENGINE = Null` landing table and let a `MATERIALIZED VIEW`
compute the states into the target instead.
[Ingesting into AggregatingMergeTree](./aggregating-mergetree.mdx) works that
pattern end to end.

Startup validation refuses such a column and names that pattern, under
`validate_schema: names` and `full` alike. `format: native` upgrades `off` to
`names`, so the check always runs there; a RowBinary sink left at
`validate_schema: off` skips it.
