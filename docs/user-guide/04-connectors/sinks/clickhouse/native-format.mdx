# ClickHouse Native format

The ClickHouse sink defaults to **RowBinary** (row-wise). It can instead
encode the **Native** format (ClickHouse's own columnar, block-framed
representation) with one config knob:

```yaml
sink:
  clickhouse:
    format: native   # rowbinary (default) | native
```

Native transposes each chunk of rows into per-column buffers and emits one
self-describing **block** (`INSERT … FORMAT Native`). Because a Native insert
body is a stream of complete blocks, the sink's batching, deduplication, and
at-least-once semantics are **unchanged**; only the encoding differs.

## When to use it

Native **moves the row→column pivot off the ClickHouse server onto the (more
easily scaled) ETL workers**. That is a deliberate trade, measured on a dev
laptop with an **idle, single-threaded ClickHouse 25.6** server (200k-row
inserts, a realistic mixed schema). These are per-query, parse-isolated
figures; a sustained-saturation rig on a busier server measures whole-server
CPU differently, and measured it against Native, so size a loaded cluster by
measuring it rather than from this table:

| Axis | RowBinary | Native | Delta |
|---|---|---|---|
| Client encode CPU | 34.3 ns/row | 66.7 ns/row | ~2× **more** (still 15.0M rows/s) |
| Compressed wire (lz4 / zstd) | baseline | — | **49% / 71% smaller** |
| Server parse CPU (`ENGINE=Null`) | 94.8 ms | 7.7 ms | **92% less** |
| Server CPU end-to-end (`MergeTree`) | 123.6 ms | 37.1 ms | **70% less** |

The server win is largest when the destination has `LowCardinality`,
`Array`, or `Map` columns. RowBinary makes the *server* build those
dictionaries and columnar structures row-by-row; Native hands it the finished
block.

**Choose `native` when** the ClickHouse cluster is CPU-bound, or when network
egress / wire size is the constraint (cross-region, metered links).
**Keep `rowbinary` (the default) when** ETL-worker CPU is the constraint;
RowBinary's row encode is near-memcpy-fast and hard to beat.

Native also encodes a narrower set of column types, and rejects the rest at
construction, before any row is sent. What `rowbinary` does with a column Native
refuses varies by type, and some it refuses too, so a table holding one is a
question for [ClickHouse column types](./column-types.mdx) rather than for the
CPU trade above.

## Enabling it

`format: native` is **type-driven**. The encoder needs each column's
ClickHouse type to lay bytes out columnar, so selecting it always fetches
`system.columns` (it upgrades `validate_schema: off` to `names`).

The row is an ordinary `serde::Serialize` struct, the same one RowBinary
takes.
[`kafka_avro_flatmap_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_flatmap_clickhouse.rs)
decodes a placed order and fans it out into one such row per line; it needs
a Kafka topic of Avro orders and the target table, and runs with
`cargo run --release -p spate --features full --example kafka_avro_flatmap_clickhouse`:

```rust file=crates/spate/examples/kafka_avro_flatmap_clickhouse.rs region=record
```

`OrderLineRow` is the row the terminal stage encodes; the two types above it
are what the chain decodes and explodes into it. Its field order is the
positional contract against the configured `columns`, and `DateTime64Millis`
declares the timestamp's scale, which is what lets `validate_schema: full`
check it against the column's declared precision.

The encoder is built from the schema that sink fetched, where `sink` is the
[ClickHouse sink](./README.mdx) constructed from its config section:

```rust file=crates/spate/examples/kafka_avro_flatmap_clickhouse.rs region=encoder
```

The type parameter is the record *family*, not the row type: an owned row
struct is wrapped as `Owned<OrderLineRow>` (a zero-copy borrowed row uses its
own family type). The encoder goes to the chain's terminal `.sink(...)` stage,
which clones one per shard. Because Native blocks are larger per unit of work,
a larger terminal-stage chunk target (the sink's YAML
[`chunk.target_bytes`](../../../07-reference/configuration.mdx#chunk), e.g.
512 KiB) keeps each block substantial; the sink still merges blocks up to
`batch.max_bytes` per insert.

:::warning
The Native writer emits the raw little-endian `Int64` and does not rescale
to the column's declared precision, so a `DateTime64(6)` column fed
milli-scaled values silently lands wrong timestamps. Declare the scale
through the wrapper (`DateTime64Millis`, …) and set `validate_schema:
full`: a wrapper whose scale disagrees with the table's declared precision
then fails fatally on the first record, before anything is inserted. A
plain `i64` field declares no scale, so nothing can validate it and the
mismatch stays silent.
:::

## Semantics that do **not** change

- **At-least-once / deduplication.** Same `insert_deduplication_token`,
  `insert_deduplicate=1`, `wait_end_of_query=1`. The
  [dedup-window warning](./README.mdx#deduplication-tokens-and-the-window-warning)
  applies identically.
- **Replica rotation, circuit breaker, retries, batching, backpressure** —
  all identical; the format only changes the bytes in the request body.
- **Compression** (`compression: lz4|zstd|off`) applies to the Native body
  exactly as to RowBinary, and Native compresses noticeably smaller.
