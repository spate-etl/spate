# ClickHouse schema validation

A ClickHouse pipeline has two descriptions of the same row: the columns
`#[derive(ClickHouseRow)]` generates from the Rust row struct's field order,
and the live table's schema. Building the sink fetches the table's columns and
holds one against the other, and the insert's wire format carries them so the
server holds them again on every batch.

## The wire contract

The sink sends `INSERT INTO t (col1, col2, ...) FORMAT
RowBinaryWithNamesAndTypes` with each row serialized field by field, in
declaration order. The body opens with a header naming every column and its
type; the rows that follow are positional, so the row struct's field order is
the wire contract. `OrderRow` below is the row; the two types above it are what
the chain decodes and totals into it. All three come from
[`kafka_avro_to_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_to_clickhouse.rs),
a complete program that builds under the `full` facade feature, as does the
wiring further down:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=record
```

Reordering the struct's fields is a breaking change to the pipeline. Which
column types each format writes is in
[ClickHouse column types](./column-types.mdx); the Rust field each one takes
lives in the `spate-clickhouse` crate's `rowbinary` module docs.

## The three checks

| When | What |
|---|---|
| Building the sink | Every declared column exists and is insertable on **every replica of every shard**; replica drift and missing tables fail with a readable diff. |
| The first record, per pipeline thread | Struct field names, order, and a class-based type-compatibility check per position. |
| Every insert, server-side | The header's column names and types against the table's. |

The client-side type check is deliberately permissive: a `u32` may feed
`UInt32`, `DateTime`, or `IPv4`; server types the client does not know always
pass. One mismatch always fails regardless: `Nullable` on the server versus a
non-`Option` field (or the reverse). That one is wire corruption, not a
judgment call.

The two client-side checks are not made redundant by the server's. The header
carries the *table's* types, so the server never sees the struct's, and a
`Decimal64<2>` field against a `Decimal(9, 2)` column is caught client-side or
not at all.

## Wiring it up

The fetch is an async step that runs on the builder's I/O runtime via
`pipeline.block_on`. A failure exits the process before any pipeline thread or
sink worker exists:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=sink
```

The sink hands the encoder the schema it fetched, so the two cannot describe
different tables:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=encoder
```

with the matching YAML:

```yaml
sink:
  clickhouse:
    table: orders
```

## What each check is for

**Building the sink** fetches `system.columns` from every replica and checks
`OrderRow`'s *derived columns* against the *live tables*. Because it queries
every replica independently, it also catches replica drift, a replica whose
table was altered out of step with the others. It returns the parsed schema as
an `Arc` of `RowSchema`, reachable from the sink as `schema()`.

**The first record** is where the struct is compared against that schema, on
each pipeline thread. For an ordinary `#[derive(Serialize)]` struct this agrees
with the derived columns by construction, so in practice it is a safety net: it
still catches a hand-written `Serialize` impl whose emission order disagrees
with declaration order, a hand-written `ClickHouseRowFamily` implementation
(for a borrowed record family) whose declared columns disagree with what it
actually serializes, and — the one case that needs a real value regardless — a
type-class mismatch, since a shape needs a value to record. A mismatch is a
fatal error that stops the pipeline before the batch is sent. Steady-state cost
after the first record is one predictable branch, with nothing on the
per-record hot path.

**Every insert** is the server's own check, against the header. This is the one
that survives a table altered while the pipeline is already running: the client
looked once, but the header travels with every batch, so an `ALTER` that keeps
a column's byte width — a `Decimal` scale change within one precision band, a
`DateTime64` precision change, a signedness change — is rejected as
`INCORRECT_DATA` rather than silently storing rescaled values. The sink sends
`input_format_with_names_use_header` and `input_format_with_types_use_header`
with every insert so a server or profile default cannot turn that check off.

`ClickHouseEncoder::<F>` takes its record family independently of `with_row`,
so nothing stops naming a different row type at each call site; agreement holds
only when the same struct names both. Getting this wrong is exactly what the
first-record check catches.
