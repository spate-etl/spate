# ClickHouse schema validation

A ClickHouse pipeline has two descriptions of the same row: the columns
`#[derive(ClickHouseRow)]` generates from the Rust row struct's field order,
and the live table's schema. RowBinary, the wire format, carries **no column
names**, so nothing catches a disagreement at the protocol level: misaligned
columns are silent data corruption, not an error. Opt-in schema validation
closes that gap at startup and at the first record, before any misaligned
batch can be sent.

## The wire contract

The sink sends `INSERT INTO t (col1, col2, ...) FORMAT RowBinary` with each
row serialized field by field, in declaration order. The server maps bytes to
columns purely by position, so the row struct's field order is the wire
contract. `OrderRow` below is the row; the two types above it are what the
chain decodes and totals into it. All three come from
[`kafka_avro_to_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_to_clickhouse.rs),
a complete program that builds under the `full` facade feature, as does the
wiring further down:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=record
```

Reordering the struct's fields is a breaking change to the pipeline. Which
column types each format writes is in
[ClickHouse column types](./column-types.mdx); the Rust field each one takes
lives in the `spate-clickhouse` crate's `rowbinary` module docs.

## The three modes

`validate_schema` in the `sink: { clickhouse: ... }` section:

| Mode | Startup (before any thread spawns) | First record (per pipeline thread) |
|---|---|---|
| `off` (default) | Nothing — no queries issued. | Nothing. |
| `names` | Every declared column exists and is insertable on **every replica of every shard**; replica drift and missing tables fail with a readable diff. | Struct field names and order match the declared columns. |
| `full` | Everything `names` does. | `names` plus a class-based type-compatibility check per position. |

The `full` type check is deliberately permissive: a `u32` may feed
`UInt32`, `DateTime`, or `IPv4`; server types the client does not know
always pass. One mismatch always fails regardless: `Nullable` on the server
versus a non-`Option` field (or the reverse). That one is wire corruption,
not a judgment call.

## Wiring it up

Validation is an async pre-flight step that runs on the builder's I/O runtime
via `pipeline.block_on`, **after** `with_row` and **before** handing the sink
to `.sink(...)`. A failure exits the process before any pipeline thread
or sink worker exists. In `off` mode the call returns `Ok(None)` instantly
and issues no queries, which is why the encoder is built from a `match`
rather than behind a flag:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=encoder
```

with the matching YAML:

```yaml
sink:
  clickhouse:
    table: orders
    validate_schema: full     # off | names | full
```

## The two halves

**Startup half** — `ClickHouseSink::validate_schema()` fetches
`system.columns` from every replica and checks `OrderRow`'s *derived
columns* against the *live tables*. It returns the parsed schema as an
`Arc` of `RowSchema` (or `None` when `off`).

**First-record half** — `ClickHouseEncoder::with_schema(schema)` carries
that expected schema into the encoder, which checks the first record each
pipeline thread encodes: field names and order always, type classes in
`full` mode. For an ordinary `#[derive(Serialize)]` struct this agrees with
the derived columns by construction, so in practice it is a safety net
rather than a live check: it still catches a hand-written `Serialize` impl
whose emission order disagrees with declaration order, a hand-written
`ClickHouseRowFamily` implementation (for a borrowed record family) whose
declared columns disagree with what it actually serializes, and — the one
case that needs a real value regardless — a type-class mismatch, since a
shape needs a value to record. A mismatch is a fatal error that stops the
pipeline before the batch is sent. Steady-state cost after the first record
is one predictable branch, with nothing on the per-record hot path.

`with_row::<F>()` and `ClickHouseEncoder::<F>` take the record family
independently, so nothing stops naming a different row type at each call
site; agreement holds only when the same struct names both. Getting this
wrong is exactly what the first-record half above still catches.

Because the startup half derives its expected columns from the same struct
the encoder serializes, a struct-vs-table disagreement is caught before any
thread spawns rather than at the first record. Because it queries every
replica independently, it also catches replica drift, a replica whose table
was altered out of step with the others.

:::warning
`validate_schema: off` means nothing is checked. A declared column the
table lacks fails loudly (a server error on the first insert), but a field
whose type the column cannot take, or a hand-written `Serialize`/
`ClickHouseRowFamily` implementation that emits fields in a different order
from its own declared columns, does not: the bytes still leave for the
wrong column with no protocol error. Turn on at least `names` for any table
not created in the same commit as the pipeline.
:::
