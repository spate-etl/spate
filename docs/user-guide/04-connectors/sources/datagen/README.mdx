# Datagen (source)

The datagen source (`spate-datagen`, feature `datagen` on the `spate` facade)
generates a synthetic storefront event stream in process, so a pipeline can be
assembled, run and measured with no broker, bucket or coordination store behind
it. **It keeps no durable progress**: every run regenerates its stream from the
beginning, which makes it reproducible and not resumable. It is a demo and test
source, and a pipeline that depends on it for delivery is depending on
something that replays in full after any restart.

It is deliberately not part of the `full` feature, for that reason.

Construct it from the pipeline's opaque section:

```rust
let source = DatagenSource::from_component_config(&pipeline.config().source)?;
```

## Configuration

The `source: { datagen: ... }` section deserializes into `DatagenSourceConfig`
(`crates/spate-datagen/src/config.rs`); unknown fields are rejected with the
offending key.

```yaml
source:
  datagen:
    dataset: storefront
    encoding: json
    partitions: 4
    seed: 42
    tick_interval: 100ms
    events_per_tick: 25
    count: 20000
    clock: fixed
```

| Key | Type | Default | Description |
|---|---|---|---|
| `dataset` | enum | `storefront` | The built-in model to generate. `storefront` is the only value. |
| `encoding` | enum | `json` | Payload wire format: `json`, or `avro` under feature `datagen-avro`. |
| `partitions` | integer | `4` | Lanes, and therefore the partitions the pipeline sees. Each owns a disjoint slice of the order-id space, so changing it reshuffles which lane mints which order. At least 1. |
| `seed` | integer | `0` | Seed of the whole stream. Each lane derives its own from it. |
| `tick_interval` | duration | `100ms` | How often a lane releases a batch. `0s` means unthrottled — generate as fast as the pipeline consumes. |
| `events_per_tick` | integer | `10` | Events released per lane per tick. Ignored when unthrottled. At least 1. |
| `count` | integer | `none` | Stop after this many events **across all lanes**, then drain to a clean exit. Absent means the stream never ends. |
| `clock` | enum | `fixed` | Timestamp source: `fixed` derives them from `epoch_ms` and the record's offset; `wall` reads the clock. |
| `epoch_ms` | integer | `1767225600000` | Base instant for the `fixed` clock, in milliseconds since the Unix epoch. Ignored by `wall`. |

The effective rate is `partitions × events_per_tick ÷ tick_interval` — the
defaults give 400 events per second. There is no `rate` key, because two keys
already determine it and a third could disagree with them.

`count` is rejected when it is smaller than `partitions`: the budget is split
across lanes, so a lane would be given none. `partitions` and `events_per_tick`
are rejected at zero.

There is no raw passthrough. A generator authors its own payloads, so a
property bag would be a schema language arriving by the back door.

## What it generates

Three event kinds under one envelope, so a single deserializer target decodes
the whole stream:

```text
order_placed     { order_id, customer_id, region, placed_at, lines: [{ sku, qty, unit_cents }] }
payment_captured { order_id, amount_cents }
refund_issued    { order_id, amount_cents, reason }
```

`region`, `sku` and `customer_id` are drawn from fixed dimension sets, so
routing and sharding produce a distribution rather than uniform noise. The
nested `lines` array is what a fan-out stage expands.

**A referencing event never arrives before the order it references.** Each lane
mints order ids from a disjoint slice and only captures or refunds orders it
placed itself, so a payment always lands on the same partition, at a strictly
greater offset, than its order. That holds with no coordination between lanes,
which is what lets the guarantee survive lanes running on different threads.

The record key carries the order id, so a key-hashing router colocates an
order, its payment and its refund on one shard.

## Determinism

Under `clock: fixed`, the stream is a pure function of `seed`, `partitions`,
`dataset` and `encoding` — the same configuration produces byte-identical
payloads on every run, which is what lets a test assert an exact count.

`clock: wall` reads the system clock instead. Counts stay deterministic;
payload bytes do not.

## Delivery semantics

`commit` records watermarks in memory and nowhere else. There is no durable
upstream to resume from: a restart begins every lane at offset 0, so with a
fixed seed the entire stream replays — strictly more duplication than a real
source would produce, not less. A `resume_from` key is deliberately absent,
because a demo source that appears to resume durably is one somebody builds a
pipeline on.

A bounded run — one with `count` set — reaches `ExitState::Completed` only
after every batch has been acknowledged and the final watermark committed, so
a clean exit from a bounded run is a real end-to-end delivery assertion. That
is the one durability claim this source makes.

Payloads are framed one record each, so a deserializer takes its granularity
from the source rather than from a `framing` key.

## Metrics

Registered through a `Meter` under the `datagen` namespace in its source role,
so every family is prefixed `spate_datagen_source_`. Standard labels
(`pipeline`, `component`, `component_type`) are on all of them; extras are
noted per family.

| Metric | Type | Labels | Description |
|---|---|---|---|
| `spate_datagen_source_events_generated_total` | counter | `event` | Events emitted, by kind: `order_placed`, `payment_captured`, `refund_issued`. |
| `spate_datagen_source_ticks_total` | counter | — | Rate ticks released. |
| `spate_datagen_source_tick_overrun_total` | counter | — | Ticks whose deadline had already passed on wake — the configured rate exceeds what the pipeline absorbs. |
| `spate_datagen_source_events_remaining` | gauge | — | Events left in a bounded budget across all lanes. Zero when unbounded. |
| `spate_datagen_source_open_orders` | gauge | — | Orders placed but not yet captured, summed across lanes. |
| `spate_datagen_source_committed_offset` | gauge | `partition` | The last watermark committed. Registered only when `metrics.per_partition_detail` is on. |

Counters are incremented by the lanes and gauges are published by the control
plane, because a gauge series has exactly one live owner per process while a
counter may have many.

There is no consumer-lag family. For an unbounded stream the lag is infinite,
so the series would appear and disappear with a configuration key;
`spate_datagen_source_events_remaining` carries the bounded case instead.

See [Metrics](../../../../METRICS.md) for the taxonomy, the reserved roots and
the series-ownership rules.
