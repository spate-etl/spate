# Kafka source

import SecuringKafka from '../../_securing-kafka.mdx';

The Kafka source (`spate-kafka`, feature `kafka` on the `spate` facade) is
built on `rdkafka` with a **single consumer per process**: one
consumer-group member per pod, whose assigned partitions are split into
per-partition queues (`split_partition_queue`) and fanned across pipeline
threads as lanes. Payload borrows stay local to the polling thread, with zero
copies out of librdkafka's buffers. Rationale and the validated trade-offs
(group scale, unified drain choreography, ~3% vs per-thread consumers) are
in [ADR-0012](../../../../adr/0012-single-kafka-consumer-with-split-partition-queues.md).

Construct it from the pipeline's opaque section:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=source
```

That is from
[`kafka_avro_to_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_to_clickhouse.rs),
a complete program that builds under the `full` facade feature.

## Configuration

The `source: { kafka: ... }` section deserializes into `KafkaSourceConfig`
([`spate-kafka/src/config.rs`](repo:crates/spate-kafka/src/config.rs));
unknown fields are rejected with the offending key.

```yaml
source:
  kafka:
    brokers: ${KAFKA_BROKERS:-localhost:9092}
    topic: orders
    group_id: orders-etl
    commit_interval: 5s
    rdkafka:
      auto.offset.reset: earliest
      fetch.message.max.bytes: "1048576"
```

| Key | Type | Default | Description |
|---|---|---|---|
| `brokers` | string | `required` | Comma-separated bootstrap servers. |
| `topic` | string | `required` | The topic to consume. **One topic per pipeline**: the framework's `PartitionId` is the Kafka partition number, unique only within a topic. |
| `group_id` | string | `required` | Consumer group id. |
| `commit_interval` | duration | `5s` | How often stored offsets are auto-committed (maps to librdkafka `auto.commit.interval.ms`). |
| `startup_timeout` | duration | `30s` | How long to wait for the first partition assignment before the source reports a fatal startup error (fail fast on unreachable brokers or a wrong topic). `0s` disables it, and the source waits for as long as the group takes. |
| `assignment_timeout` | duration | `5m` | How long the member may hold no partitions, after having held some, before the source reports a fatal error. The deadline counts from the moment ownership is released, and any accepted assignment clears it, an empty one included, so a member the group assigns nothing keeps running. `0s` disables it. |
| `statistics_interval` | duration | `5s` | librdkafka statistics emission interval, feeding the lag metrics and the `spate_kafka_source_*` families (broker health, latency, queue saturation, group stability). `0s` disables statistics and those families with it — **including `spate_source_lag_records`**, which has no other source: the series then does not exist at all (the source logs a warning at startup). Consumer lag is a golden signal, and disabling statistics gives it up. |
| `rdkafka` | string map | `{}` | Raw librdkafka properties, applied verbatim after validation — see below. |

## The `rdkafka` passthrough and the denylist

The passthrough exists to reach anything librdkafka exposes
(security, fetch sizing, and the prefetch depth `queued.min.messages` /
`queued.max.messages.kbytes`, which the framework leaves at librdkafka's
defaults; see [performance tuning](./performance-tuning.mdx#prefetch))
without waiting for a typed field. But
properties the framework owns for correctness are **rejected at load time
with an explanation**, because overriding them silently breaks the delivery
guarantees or the threading model. Aliases librdkafka accepts for the same
setting are denied alongside the canonical names, because passthrough and
framework values apply in unspecified order.

| Denied property | Why |
|---|---|
| `enable.auto.offset.store` | The framework stores offsets itself when checkpoint watermarks advance; overriding breaks at-least-once. |
| `enable.auto.commit`, `auto.commit.enable` (alias) | Interval auto-commit of framework-stored offsets *is* the commit mechanism; disabling it means nothing is ever committed. |
| `auto.commit.interval.ms` | Owned by the typed `commit_interval` field. |
| `enable.partition.eof` | EOF events would pollute the partition queues the pipeline polls. |
| `bootstrap.servers`, `metadata.broker.list` (alias) | Owned by the typed `brokers` field. |
| `group.id` | Owned by the typed `group_id` field. |
| `statistics.interval.ms` | Owned by the typed `statistics_interval` field. |
| `group.protocol` | Only the classic consumer protocol is supported; eager assignment is a framework invariant. |

`partition.assignment.strategy` is additionally validated, and any
`cooperative` strategy is rejected, because the framework relies on eager
(full) rebalances.

## How offsets are committed

The framework never uses librdkafka's position-based auto-commit. Instead:

- `enable.auto.offset.store` is forced to `false`, so librdkafka never stores
  the "consumed" position on its own.
- When the checkpointer advances a partition's watermark (every record up
  to it durably written or intentionally dropped), the source **stores**
  that offset explicitly.
- `enable.auto.commit` is forced to `true`, so librdkafka commits the *stored*
  offsets every `commit_interval`.
- Rebalance revocations and shutdown drain first, then store and commit
  **synchronously** while the member still owns the partitions, so another
  member never starts from an offset covering unwritten data.
- A rebalance *error* (an event that is neither an assignment nor a
  revocation) releases ownership immediately, as the client library's
  contract requires. The lanes still drain, but their offsets can no longer
  be stored; that work is redelivered after the member rejoins, and the
  refusal is logged. At-least-once holds either way; the difference is
  replay instead of a clean release.

This is the mechanical heart of at-least-once; see
[Delivery guarantees](../../../02-concepts/02-delivery-guarantees.mdx).

## Lanes: partitions on pipeline threads

Each assigned partition becomes one lane, mapped m:n onto pipeline threads
under local control. The assignment choreography guarantees no message
leaks past the split: newly accepted partitions are paused immediately,
before any fetch can complete, then split into queues and resumed. Kafka
tombstones
(null payloads) surface as empty payload slices. Splitting means group
liveness never depends on the controller, because every lane poll resets
`max.poll.interval.ms`.

## Backpressure: pause and resume

When the in-flight budget crosses its high watermark or a shard queue
rejects, the runtime pauses the affected lanes' partitions at the consumer
**and keeps polling**. A paused partition fetches nothing but the poll
loop stays live for rebalance callbacks and liveness. Resume happens under
hysteresis (low watermark + `backpressure.min_pause`), because pausing a
Kafka partition purges its prefetch buffer, so resume is not free and
flapping would thrash the fetch pipeline.

:::note
A source thread never blocks on a channel send. A poll loop parked in
`send()` would stop polling, trip `max.poll.interval.ms`, get the member
evicted, and turn sink slowness into a rebalance storm. This is a
framework invariant, not a tuning choice. See
[Backpressure](../../../02-concepts/03-backpressure.mdx).
:::

## Dependency note

`spate-kafka` deliberately re-exports nothing from `rdkafka`, so its types stay
out of public signatures so `rdkafka` major bumps are not breaking changes
here ([ADR-0011](../../../../adr/0011-msrv-and-dependency-policy.md)).

## Metrics

Registered through this source's `Meter` (namespace `kafka`, role `source`), so
every family is prefixed `spate_kafka_source_`. They translate the librdkafka
statistics snapshot, emitted every `statistics_interval` (default `5s`; `0s`
disables the whole family) and drained on the controller thread, never on the
record path.

Counters are **absolute-mapped librdkafka totals** scoped to one consumer
lifetime. The handles mirror the client's cumulative values (idempotent under
duplicate delivery; `rate()`/`increase()` work natively), and after a process
restart the series restart from the new consumer's totals, an ordinary
counter reset to PromQL. The `broker` label is the librdkafka broker name
(`host:port/id`), bounded by cluster topology and always on. The `rtt`/
`throttle` gauges are librdkafka's HDR-histogram rolling-window estimates,
converted to seconds; they are per-broker sampled quantiles and **cannot be
aggregated** across brokers or processes (`max()` is the only defensible
cross-series operator). Series backed by data librdkafka has not produced yet
(an empty latency window, an unknown lag) are absent rather than `0`.

Standard labels (`pipeline`, `component`, `component_type`) are on all of
them; extras, `broker` among them, are noted per family.

| Metric | Type | Extra labels | Description |
|---|---|---|---|
| `spate_kafka_source_tx_requests_total` | counter | | Requests sent to brokers. |
| `spate_kafka_source_tx_bytes_total` | counter | | Bytes transmitted to brokers. |
| `spate_kafka_source_rx_responses_total` | counter | | Responses received from brokers. |
| `spate_kafka_source_rx_bytes_total` | counter | | Protocol bytes received. |
| `spate_kafka_source_rx_messages_total` | counter | | Messages consumed (excluding ignored). |
| `spate_kafka_source_rx_message_bytes_total` | counter | | Message bytes consumed (including framing). |
| `spate_kafka_source_broker_tx_retries_total` | counter | | Request retries, summed across brokers. |
| `spate_kafka_source_broker_req_timeouts_total` | counter | | Requests timed out, summed across brokers. |
| `spate_kafka_source_broker_connects_total` | counter | | Connection attempts (including failed), summed across brokers. |
| `spate_kafka_source_broker_disconnects_total` | counter | | Disconnections (broker, network, or otherwise), summed across brokers. |
| `spate_kafka_source_broker_up` | gauge | `broker` | 1 while any connection to the broker (regular or a logical coordinator link) is up; `sum()` gives the brokers-up count. |
| `spate_kafka_source_broker_tx_errors_total` | counter | `broker` | Transmission errors, attributed per broker. |
| `spate_kafka_source_broker_rtt_avg_seconds` | gauge | `broker` | Mean broker round-trip time over the last statistics window. |

| `spate_kafka_source_broker_throttle_p99_seconds` | gauge | `broker` | p99 broker throttle time over the last window (non-aggregatable). |
| `spate_kafka_source_fetch_queue_messages` | gauge | | Prefetched messages queued client-side for the pipeline's topic. |
| `spate_kafka_source_fetch_queue_bytes` | gauge | | Prefetched bytes queued client-side. |
| `spate_kafka_source_reply_queue_depth` | gauge | | librdkafka ops awaiting `poll()` service (poll starvation indicator). |
| `spate_kafka_source_group_rebalances_total` | counter | | Rebalances counted by librdkafka (`spate_source_rebalances_total` counts the callback events the framework observed). |
| `spate_kafka_source_group_assignment_size` | gauge | | Partitions in the current group assignment. |
| `spate_kafka_source_group_healthy` | gauge | | 1 while the member is settled (`up` + `steady`); 0 during joins/rebalances (state detail goes to debug logs). |
| `spate_kafka_source_partition_fetch_queue_messages` | gauge | `partition` ⚠ | Per-partition prefetch queue depth. A partition this member has never held has no series at all, and one it has lost reads 0. |
| `spate_kafka_source_partition_lag_stored_records` | gauge | `partition` ⚠ | Lag against the **stored** (not yet committed) offset — reflects processing progress between commits; `spate_source_lag_records` is the committed-basis view. Unlike that one, this series *is* gated by `per_partition_detail`. A partition this member has never held has no series at all; librdkafka reports `-1` while the lag is unknown, so the series stays absent through that window too. A partition this member has lost reads 0 once its lag has been known at least once. |
| `spate_kafka_source_partition_not_fetching` | gauge | `partition` ⚠ | 1 while a partition this member holds is in a fetch state other than fetching, 0 while it is fetching and 0 once the member has lost it. A partition this member has never held has no series at all. The value holds through a rebalance and is released once the new assignment is known, so a partition handed straight back keeps reading 1. The state name goes to a log line rather than a label. Backpressure does not move the gauge, since librdkafka counts a paused partition as fetching. |

Labels marked ⚠ are cardinality-sensitive and appear only under
`metrics.per_partition_detail: true`.

### Alerting

- `spate_kafka_source_group_healthy == 0` sustained — the member is stuck
  joining or rebalancing. Pair it with
  `rate(spate_kafka_source_group_rebalances_total[15m])` to tell churn from a
  wedged join.
- `rate(spate_kafka_source_broker_tx_errors_total[5m]) > 0` or
  `spate_kafka_source_broker_up == 0` — broker connectivity trouble, attributed
  by the `broker` label. On large clusters a broker the member currently needs
  no connection to also reads 0 (sparse connections), so alert on brokers the
  assignment depends on rather than on the cluster-wide sum.
- `spate_kafka_source_partition_not_fetching == 1` — the member holds the
  partition and is not consuming it. The pipeline then goes quiet with a full
  assignment, a healthy group and no error anywhere. The alert wants a `for:`
  window of a minute or so, since a partition reads 1 while librdkafka resolves
  its offset after an assignment.

A partition that is not fetching is logged as well as measured, whether or not
`per_partition_detail` is on. The line names the librdkafka fetch state and the
partition's offsets, and is emitted once for each state an episode goes
through rather than once per statistics window. Six of librdkafka's seven fetch
states are not fetching, so that is at most six lines. A long episode is
restated every 60 windows on top of those, which is 5 minutes at the default
`statistics_interval`, so a log read part-way through an episode still carries
it.

```text
WARN assigned partition is not fetching partition=26 state=stopped windows=2 next_offset=-1001 query_offset=-1 hi_offset=1250000
```

`windows` counts the statistics windows in which this member held the partition
and it was not fetching, so at the default `statistics_interval` each one is 5
seconds. A rebalance in flight leaves the member holding nothing, and those
windows are not counted, so an episode spanning one lasted a little longer than
`windows` says. The state names the cause. `stopped` or `none` is a partition
this process stopped fetching, and `offset-query` or `offset-wait` is a leader
or an offset lookup that has not answered; librdkafka retries a failed lookup by
moving the partition between those two, so an episode of one cause reports both.
An `INFO` line closes the episode when the partition resumes, so the log says
whether it is still going.

Consumer lag is a framework family (`spate_source_lag_records`) and is alerted
on separately; see [Metrics](../../../../METRICS.md) for the taxonomy, the
reserved roots and the series-ownership rules.
