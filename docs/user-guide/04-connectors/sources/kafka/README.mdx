# Kafka source

import SecuringKafka from '../../_securing-kafka.mdx';
import LoggingKafka from '../../_logging-kafka.mdx';
import ClientIdKafka from '../../_client-id-kafka.mdx';

The Kafka source (`spate-kafka`, feature `kafka` on the `spate` facade) is built
on `rdkafka` with **one consumer per process by default**: one consumer-group
member per pod, whose assigned partitions are split into per-partition queues
(`split_partition_queue`) and fanned across pipeline threads as lanes. Payload
borrows stay local to the polling thread, with zero copies out of librdkafka's
buffers. `consumers` runs several members in the process, each with its own
share of the partitions, for a source bound by one client's fetch path; see
[More consumers in one process](./performance-tuning.mdx#more-consumers-in-one-process).
The rationale is in
[ADR-0090](../../../../adr/0090-a-kafka-source-runs-a-configured-number-of-consumers.md).

Construct it from the pipeline's opaque section:

```rust file=crates/spate/examples/kafka_avro_to_clickhouse.rs region=source
```

That is from
[`kafka_avro_to_clickhouse.rs`](repo:crates/spate/examples/kafka_avro_to_clickhouse.rs),
a complete program that builds under the `kafka`, `clickhouse` and `avro`
features.

## Configuration

The `source: { kafka: ... }` section deserializes into `KafkaSourceConfig`
([`spate-kafka/src/config.rs`](repo:crates/spate-kafka/src/config.rs));
unknown fields are rejected with the offending key.

```yaml
source:
  kafka:
    brokers: ${KAFKA_BROKERS:-localhost:9092}
    topic: orders
    group_id: orders-etl
    commit_interval: 5s
    rdkafka:
      auto.offset.reset: earliest
      fetch.message.max.bytes: "1048576"
```

| Key | Type | Default | Description |
|---|---|---|---|
| `brokers` | string | `required` | Comma-separated bootstrap servers. |
| `topic` | string | `required` | The topic to consume. **One topic per pipeline**: the framework's `PartitionId` is the Kafka partition number, unique only within a topic. A name with a leading `^` is a subscription pattern, and is refused. |
| `group_id` | string | `required` | Consumer group id. |
| `consumers` | int | `1` | Consumers this process runs, at least 1. Each is a separate member of `group_id` that owns its own share of the partitions. Raise it when one client's fetch path bounds the source; see [More consumers in one process](./performance-tuning.mdx#more-consumers-in-one-process). Static membership (`group.instance.id`) requires `1`. |
| `commit_interval` | duration | `5s` | How often stored offsets are auto-committed (maps to librdkafka `auto.commit.interval.ms`). A value under `1ms` or above `24h` is refused. |
| `startup_timeout` | duration | `30s` | How long to wait for the first partition assignment before the source reports a fatal startup error (fail fast on unreachable brokers or a wrong topic). The error names the last consumer error, such as a refused connection, and how long ago it arrived. `0s` disables it, and the source waits for as long as the group takes. |
| `assignment_timeout` | duration | `5m` | How long the source may hold no partitions, after having held some, before it reports a fatal error. The window covers all of the source's consumers together, so a consumer the group assigns nothing keeps running while another holds partitions. The deadline counts from the moment ownership is released, and any accepted assignment clears it, an empty one included, so a member the group assigns nothing keeps running. An empty assignment accepted beside an offer the source discarded clears neither deadline. The error names the last consumer error and how long ago it arrived. `0s` disables it. |
| `statistics_interval` | duration | `5s` | librdkafka statistics emission interval, feeding the lag metrics and the `spate_kafka_source_*` families (broker health, latency, queue saturation, group stability). `0s` disables statistics and those families with it — **including `spate_source_lag_records`**, which has no other source: the series then does not exist at all (the source logs a warning at startup). Consumer lag is a golden signal, and disabling statistics gives it up. A non-zero value under `1ms` or above `24h` is refused. |
| `rdkafka` | string map | `{}` | Raw librdkafka properties, applied verbatim after validation except for an `auto.offset.reset` of `latest` — see below. |

## The `rdkafka` passthrough and the denylist

The passthrough exists to reach anything librdkafka exposes
(security, fetch sizing, and the prefetch depth `queued.min.messages` /
`queued.max.messages.kbytes`, which the framework leaves at librdkafka's
defaults; see [performance tuning](./performance-tuning.mdx#prefetch))
without waiting for a typed field. But
properties the framework owns for correctness are **rejected at load time
with an explanation**, under their own name and under `topic.<name>`, because
overriding them silently breaks the delivery guarantees or the threading
model. librdkafka reads `topic.<name>` as `<name>` when `<name>` is a
topic-level property. Every name librdkafka accepts for the same setting is
denied, because passthrough and framework values apply in unspecified order.

| Denied property | Why |
|---|---|
| `enable.auto.offset.store` | The framework stores offsets itself when checkpoint watermarks advance; overriding breaks at-least-once. |
| `enable.auto.commit` | Interval auto-commit of framework-stored offsets *is* the commit mechanism; disabling it means nothing is ever committed. |
| `auto.commit.enable` | librdkafka's legacy topic-level auto-commit property, which the consumer does not read; the framework commits through `enable.auto.commit`. |
| `auto.commit.interval.ms` | Owned by the typed `commit_interval` field. |
| `enable.partition.eof` | EOF events would pollute the partition queues the pipeline polls. |
| `bootstrap.servers`, `metadata.broker.list` | One librdkafka property, owned by the typed `brokers` field. |
| `allow.auto.create.topics` | Forced off: a metadata read of a missing topic fails, and never creates the topic with the broker's defaults. |
| `group.id` | Owned by the typed `group_id` field. |
| `statistics.interval.ms` | Owned by the typed `statistics_interval` field. |
| `group.protocol` | Only the classic consumer protocol is supported; eager assignment is a framework invariant. |

The source also sets a few properties to values other than librdkafka's
defaults. The passthrough may still set each of them, and its value wins, except
that the source passes an `auto.offset.reset` of `latest` to librdkafka as
`earliest`.

| Property | Source default | librdkafka default | Why |
|---|---|---|---|
| `fetch.queue.backoff.ms` | `10` | `1000` | Each partition has its own queue, so a partition that fills it is fetched again promptly once a pipeline thread drains it. See [the refill backoff](./performance-tuning.mdx#refill-backoff). |
| `client.id` | `spate-source-consumer`, with `-k` appended above one consumer | `rdkafka` | Broker logs and quotas name the client. See [Client identity](#client-identity). |
| `auto.offset.reset` | `earliest` when the policy is `latest` or unset | `latest` | The source settles each start under `latest` itself, so librdkafka's policy only moves a fetch position the log no longer holds. A partition with no commit still starts at its end. See [How offsets are committed](#how-offsets-are-committed). |
| `ssl.ca.location` | `probe`, on builds with vendored OpenSSL when neither `ssl.ca.location` nor `ssl.ca.pem` is set and neither `SSL_CERT_FILE` nor `SSL_CERT_DIR` is in the environment | unset | See [Security](#security-tls-mtls-sasl). |

`partition.assignment.strategy` is additionally validated, and any
`cooperative` strategy is rejected, because the framework relies on eager
(full) rebalances.

librdkafka reads `topic.auto.offset.reset` as `auto.offset.reset`, and so does
the source. A configuration
that sets both fails at load, because the two keys reach librdkafka in no set
order.

Static membership is allowed through `group.instance.id` when `consumers` is
`1`. Several consumers would all join under the one id and fence each other, so
the combination is refused at load. A member fenced by another member with the
same `group.instance.id` stops the pipeline, and the error names the id.

## Compression codecs

The source reads batches compressed with gzip, snappy, lz4 and zstd. A batch
in a codec librdkafka cannot read fails the pipeline with a fatal error, before
any record after it is delivered. A retry would fetch the same batch again.
A batch in a codec librdkafka reads whose payload does not decompress fails the
same way. So does a zstd batch that decompresses to more than
`receive.message.max.bytes`, which librdkafka reports as invalid compressed
data.

A batch in a message format librdkafka does not know fails the same way when
the source reads it from its first record. When the committed offset falls
inside such a batch, librdkafka fetches it again without reporting an error,
and the partition reads nothing further.

In each case the committed offset does not move past the batch, and a restart
on the same group reads from it. A partition the group has never committed
starts under `auto.offset.reset`.

## How offsets are committed

The framework never uses librdkafka's position-based auto-commit. Instead:

- `enable.auto.offset.store` is forced to `false`, so librdkafka never stores
  the "consumed" position on its own.
- When the checkpointer advances a partition's watermark (every record up
  to it durably written or intentionally dropped), the source **stores**
  that offset explicitly.
- `enable.auto.commit` is forced to `true`, so librdkafka commits the *stored*
  offsets every `commit_interval`.
- Rebalance revocations and shutdown drain first, then store and commit
  **synchronously** while the member still owns the partitions (the removed
  member below is the exception), so another member never starts from an offset
  covering unwritten data.
- A rebalance *error* (an event that is neither an assignment nor a
  revocation) releases ownership immediately, as the client library's
  contract requires. The lanes still drain, but their offsets can no longer
  be stored; that work is redelivered after the member rejoins, and the
  refusal is logged. At-least-once holds either way; the difference is
  replay instead of a clean release.
- The client refuses a commit from a member the group has removed, since another
  member may already own its partitions. The refusal is logged and the
  revocation continues, and the partition is redelivered from its committed
  offset.
- A partition with no committed offset starts under `auto.offset.reset`. Under
  `latest`, the default, the source reads the partition's end and commits it
  synchronously before any lane reads it. That commit acknowledges nothing.
  Every later start resumes from a committed offset, so a restart, a process
  joining and a member the group removes all read from that position. A failed
  read or commit holds the assignment and retries it, until `startup_timeout` or
  `assignment_timeout` ends the run, and a permanent refusal such as a failed
  group authorization stops the run at once. A member the group has removed, or
  whose commit it refuses during a rebalance, gets no lanes and rejoins. The
  source passes `earliest` to librdkafka under `latest`, so a committed offset
  below the log start or past the log end resumes at the log start. librdkafka
  logs that reset at `WARN` under the `librdkafka` target, naming `BEGINNING`.
  Under `earliest` the partition starts at its beginning.
  Under `error` librdkafka applies the policy, and the source fails with a fatal
  error. That covers a partition with no committed offset, such as one added to
  the topic or one whose group offsets expired, and a partition whose fetch
  offset is out of range, such as a committed offset below the log start or past
  the log end. A run stopped this way stops again on each restart until the
  group has a valid offset for the partition.
- A failed read of the committed offsets under `earliest` or `error` leaves the
  start to librdkafka.
- A held assignment from a generation the group has left is answered empty, and
  the consumer rejoins after one more drain.

:::danger
Under `latest` a partition added to the topic starts at its end, and records
written before the group first assigned it are skipped.
`topic.metadata.refresh.interval.ms` defaults to five minutes. A group left
empty past its offset retention, `offsets.retention.minutes` on Apache Kafka and
`group_offset_retention_sec` on Redpanda, seven days by default on each, starts
at the end again. Set `auto.offset.reset: earliest` where that loss matters.
:::

A message librdkafka reports as corrupt, as `check.crcs` detects, fails the
source with a fatal error, because librdkafka can read on past it
([Kafka feed → Counting deliveries](../../feeds/kafka/README.mdx#counting-deliveries)
says when). Records read before it that the sink has not yet written are not
acknowledged. After a restart, a partition with a committed offset is read from
it, and the source stops again at the same message until the group's committed
offset is moved past it. Under `latest` a partition the group has been assigned
has one. A partition with no committed offset under `earliest` stops at the same
message too.

The source leaves `check.crcs` at librdkafka's default, which is off, unless
the `rdkafka` passthrough sets it. With it off, librdkafka does not verify a
record batch's checksum, so a batch whose bytes changed after the checksum was
computed is delivered as read, and the committed offset moves past it. Set
`check.crcs: "true"` under `rdkafka` to have the source stop on such a batch as
described above.

The check covers accidental corruption. A party able to change a batch can also
write a checksum that matches.

This is the mechanical heart of at-least-once; see
[Delivery guarantees](../../../02-concepts/02-delivery-guarantees.mdx).

### Transaction markers

A transaction marker takes an offset and is never delivered. Under
`read_committed`, the default, an aborted transaction's records are skipped the
same way. librdkafka moves the consumer's position past them when a partition's
queue is polled. When a poll finds nothing to deliver, every batch the source
handed out on the partition has reached a watermark, and the position is past
the last offset it handed out, the source issues an acknowledgement covering
those offsets. So the committed offset passes a marker once every record below
it is acknowledged, and markers behind a batch the sink has not acknowledged
wait for it. A caught-up partition reads a lag of 0, and the broker's group lag
agrees.

A few readings differ:

- A marker counts as lag until the partition's next poll serves it and the sink
  acknowledges the records below it, which can take the sink's `batch.linger`.
  The figure then settles within two `checkpoint.interval`, plus
  `commit_interval` and `statistics_interval`. A partition idle beside a busy
  one on the same pipeline thread reads its position less often, so its figure
  settles later.
- While a producer holds a transaction open, the last stable offset stays below
  it, and later records stay unread until the transaction ends. Under
  `read_committed` lag reads 0 for a group committed at that offset. A group
  with no committed offset, or with one past it after reading under
  `read_uncommitted`, has no lag series until the transaction ends. The broker's
  group lag counts to the log's end, so it reads above the source's figure until
  then.
- A gap with no record and no marker, which compaction can leave, stays in the
  figure until the next record or marker.
- After a poll error, the source does not pass a marker until it delivers
  another record.
- A fetch answered out of range can take a partition back. If that happens
  within one `checkpoint.interval` of passing a marker, or while a commit is
  being retried, the source does not pass a later marker until it delivers
  another record, and lag reads above 0 until then.
- After a message reaches the main queue, which the source logs at `WARN` as a
  rewind, that consumer does not pass a marker again until the process restarts.

A group keeps its committed offset when `isolation.level` changes. A group that
passed an aborted transaction under `read_committed` does not deliver those
records under `read_uncommitted`.

## Changing the consumer count

The count is read at startup, so changing it is a restart, and each restart is a
group rebalance like any member joining or leaving. A process stopping drains
its lanes and commits each partition through the consumer that owns it before
the consumers leave the group, and the members that remain or replace them
start from those commits. Lowering or raising `consumers` across a restart
therefore replays nothing that was durably written, unless the group had already
removed the consumer before its commit. A process that dies without
draining replays from the last commit, as with one consumer.

A release of `spate-kafka` without the `consumers` key refuses a configuration
that sets it.

## Lanes: partitions on pipeline threads

Each assigned partition becomes one lane, mapped m:n onto pipeline threads
under local control. The assignment choreography guarantees no message
leaks past the split: newly accepted partitions are paused immediately,
before any fetch can complete, then split into queues and resumed. Kafka
tombstones
(null payloads) surface as empty payload slices. Splitting means group
liveness never depends on the controller, because every lane poll resets
`max.poll.interval.ms`.

## Backpressure: pause and resume

When the in-flight budget crosses its high watermark or a shard queue
rejects, the runtime pauses the affected lanes' partitions at the consumer
**and keeps polling**. A paused partition fetches nothing but the poll
loop stays live for rebalance callbacks and liveness. Resume happens under
hysteresis (low watermark + `backpressure.min_pause`), because pausing a
Kafka partition purges its prefetch buffer, so resume is not free and
flapping would thrash the fetch pipeline.

:::note
A source thread never blocks on a channel send. A poll loop parked in
`send()` would stop polling, trip `max.poll.interval.ms`, get the member
evicted, and turn sink slowness into a rebalance storm. This is a
framework invariant, not a tuning choice. See
[Backpressure](../../../02-concepts/03-backpressure.mdx).
:::

## Metrics

Registered through this source's `Meter` (namespace `kafka`, role `source`), so
every family is prefixed `spate_kafka_source_`. They translate the librdkafka
statistics snapshot, emitted every `statistics_interval` (default `5s`; `0s`
disables the whole family) and drained on the controller thread, never on the
record path.

Counters are **absolute-mapped librdkafka totals** scoped to one consumer
lifetime. With `consumers` above 1, every family carries a `client` label,
`consumer-0`, `consumer-1` and so on, one series per consumer, so a total across
the source is a `sum without (client)` in the query. The handles mirror the
client's cumulative values (idempotent under duplicate delivery;
`rate()`/`increase()` work natively), and after a process restart the series
restart from the new consumer's totals, an ordinary counter reset to PromQL. The
`broker` label is the librdkafka broker name (`host:port/id`), bounded by
cluster topology and always on. The `rtt`/ `throttle` gauges are librdkafka's
HDR-histogram rolling-window estimates, converted to seconds; they are
per-broker sampled quantiles and **cannot be aggregated** across brokers or
processes (`max()` is the only defensible cross-series operator). Series backed
by data librdkafka has not produced yet (an empty latency window, an unknown
lag) are absent rather than `0`. A broker that leaves librdkafka's statistics
keeps its series, with `broker_up` and its latency gauges at `0`.

Standard labels (`pipeline`, `component`, `component_type`) are on all of
them; extras, `broker` among them, are noted per family.

| Metric | Type | Extra labels | Description |
|---|---|---|---|

### Alerting

- `spate_kafka_source_group_healthy == 0` sustained — the member is stuck
  joining or rebalancing. Pair it with
  `rate(spate_kafka_source_group_rebalances_total[15m])` to tell churn from a
  wedged join.
- `rate(spate_kafka_source_broker_tx_errors_total[5m]) > 0` or
  `spate_kafka_source_broker_up == 0` — broker connectivity trouble, attributed
  by the `broker` label. On large clusters a broker the member currently needs
  no connection to also reads 0 (sparse connections), and so does a broker that
  left librdkafka's statistics. Alert on brokers the assignment depends on
  rather than on the cluster-wide sum.
- `spate_kafka_source_partition_not_fetching == 1` — the member holds the
  partition and is not consuming it. The pipeline then goes quiet with a full
  assignment, a healthy group and no error anywhere. The alert wants a `for:`
  window of a minute or so, since a partition reads 1 while librdkafka resolves
  its offset after an assignment.

A partition that is not fetching is logged as well as measured, whether or not
`per_partition_detail` is on. The line names the librdkafka fetch state and the
partition's offsets, and is emitted once for each state an episode goes
through rather than once per statistics window. Six of librdkafka's seven fetch
states are not fetching, so that is at most six lines. A long episode is
restated every 60 windows on top of those, which is 5 minutes at the default
`statistics_interval`, so a log read part-way through an episode still carries
it.

```text
WARN assigned partition is not fetching partition=26 state=stopped windows=2 next_offset=-1001 query_offset=-1 hi_offset=1250000
```

`windows` counts the statistics windows in which this member held the partition
and it was not fetching, so at the default `statistics_interval` each one is 5
seconds. A rebalance in flight leaves the member holding nothing, and those
windows are not counted, so an episode spanning one lasted a little longer than
`windows` says. The state names the cause. `stopped` or `none` is a partition
this process stopped fetching, and `offset-query` or `offset-wait` is a leader
or an offset lookup that has not answered; librdkafka retries a failed lookup by
moving the partition between those two, so an episode of one cause reports both.
An `INFO` line closes the episode when the partition resumes, so the log says
whether it is still going.

Consumer lag is a framework family (`spate_source_lag_records`) and is alerted
on separately; see [Metrics](../../../../METRICS.md) for the taxonomy, the
reserved roots and the series-ownership rules.
