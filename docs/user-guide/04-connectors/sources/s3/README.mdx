# S3 (object storage) source

The S3 source (`spate-s3`, feature `s3` on the `spate` facade) runs a
**coordinated, bounded backfill**: point it at a bucket prefix and it
streams every object's records through the pipeline and terminates the
pipeline itself — `run()` returns `ExitState::Completed` — once every
split of the prefix is committed complete. `Completed` is a strong claim
here: every record was durably written by the sink(s) *and* committed; an
unacknowledged tail converts the exit into a failure so an incomplete
backfill is never reported as done.

Work is planned as **splits**. The fleet's elected leader lists the
prefix once and packs the sorted listing into splits — batches of whole
objects, ~`split_target_bytes` each — with deterministic ids and
self-contained descriptors (member keys, sizes, ETags). Workers lease
splits through the coordination store and read them straight from the
descriptors: **workers never list**. Solo and multi-instance are the same
code path; the only difference is which coordination store the
coordinator points at.

Built on the [`object_store`](https://crates.io/crates/object_store)
client (internal only — no `object_store` types in the public API), so
`s3://`, and `file://` for infrastructure-free runs and tests, work out of
the box.

Construct it from the pipeline's opaque section, with the pipeline's I/O
runtime handle and a framer (the framer is **required** — see
[Decoding records](#decoding-records)):

```rust
let pipeline = Pipeline::from_config(config)?;
let source = S3Source::from_component_config(&pipeline.config().source, pipeline.io_handle())?
    .with_framer(|| Box::new(NdjsonFramer::new(64 << 20)));
let report = pipeline.sink(sink)?.chains(/* … */).run(source)?;
// report.state == ExitState::Completed ⇒ the backfill is done and committed.
```

## Configuration

The `source: { s3: ... }` section deserializes into `S3SourceConfig`
(`crates/spate-s3/src/config.rs`); unknown fields are rejected with the
offending key. Coordination is deliberately **not** here — it is assembly
wiring ([why](../../../07-reference/configuration.mdx#code-level-knobs-not-yaml)),
covered under [Scaling out](#scaling-out--and-the-solo-default).

```yaml
source:
  s3:
    url: "s3://my-bucket/exports/2026-07/"
    compression: auto
    split_target_bytes: 64MiB
    store:
      region: ${AWS_REGION:-eu-west-2}
```

| Key | Type | Default | Description |
|---|---|---|---|
| `url` | string | `required` | Bucket and prefix to backfill. Every object under the prefix is read. `file://` works for local runs. Part of the job fingerprint — byte-identical across every instance of a coordinated job. |
| `compression` | `auto` \| `none` \| `gzip` \| `zstd` | `auto` | Object codec. `auto` decides per object by extension (`.gz`/`.gzip`, `.zst`/`.zstd`, else uncompressed). Multi-member gzip and multi-frame zstd are read fully; truncated or corrupt streams poison the split. Part of the job fingerprint. |
| `split_target_bytes` | bytes | `64MiB` | Target size of one split — the unit of distribution. Objects pack toward it in listing order with a per-object cost floor of a sixteenth of the target (so ≤ ~16 objects per split); an object at or above the target gets a split of its own. Floor `1MiB`. Part of the job fingerprint. |
| `refresh_listing` | bool | `false` | Re-list on the coordinator's replan interval, planning new objects as additional splits. `true` makes the job **open** (never self-terminates). Part of the job fingerprint. |
| `prefetch_bytes` | bytes | `8MiB` | Per-lane read window (one bounded ranged GET at a time, drained before the next). Total read-ahead ≈ in-flight splits × this. |
| `chunk_bytes` | bytes | `512KiB` | Target size of one buffered chunk. |
| `store` | string map | `{}` | Raw `object_store` options, applied on top of the environment — see [below](#the-store-passthrough). |

Mind the units on the fingerprinted keys: `MB` and `MiB` parse to
different byte counts (`64MB` = 64,000,000; `64MiB` = 67,108,864), and
`split_target_bytes` enters the job fingerprint as its **decoded byte
count** — so a replica spelling it `64MB` is refused at startup against a
fleet on the `64MiB` default. Spellings that decode to the same number of
bytes (`64MiB`, `67108864`) are interchangeable; it is the value that must
match across replicas, not the text.

The record **format is not a config key** — the S3 source is a transport and
owns no framing. The format's framer is wired into the source in code (see
[Decoding records](#decoding-records)); the per-record size bound lives on the
framer (e.g. `NdjsonFramer::new(max_record_bytes)`), not in this table.

Removed in the coordinated rework (a stale config fails at load with the
offending key): `lanes` (read parallelism is the coordinator's
`max_in_flight` — one data lane per in-flight split) and the entire
`checkpoint:` section (progress lives in the coordination store).

### Sizing splits against `pipeline.threads`

A split is read by one lane, and a lane is pinned to the pipeline thread it
was handed to — there is no work stealing between threads. So the split
count, not just the split size, sets how evenly the work divides: a plan
yielding five equal splits across two threads gives one thread three and the
other two, and the job finishes when the loaded thread does.

Aim for a split count that is a multiple of `pipeline.threads`, or large
enough that one extra split is a small share of the total. Prefixes of many
small objects get this for free (packing coalesces them); a handful of large
objects is where it bites, since an object at or above the target always
gets a split of its own and the count is then fixed by the data. Raising
`split_target_bytes` coarsens the split set and can make imbalance *worse* —
check the resulting count rather than assuming bigger is better.

## The `store` passthrough

`store` reaches any `object_store` client option without waiting for a typed
field — `region`, `endpoint`, static credentials, `allow_http`, timeouts. Its
values are applied **on top of the environment** when the client is built from
`url`, so anything set here overrides what the environment resolved.

Bucket keys are rejected in any case spelling: the bucket comes from `url`, and
two sources of truth for it would be a silent misroute.

## Security (credentials and region)

For `s3://` URLs, credentials and region resolve from the **standard AWS
environment variables** automatically — the source seeds the client with
`AmazonS3Builder::from_env()`. That covers **EKS Pod Identity**
(`AWS_CONTAINER_CREDENTIALS_FULL_URI` +
`AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`), **IRSA**
(`AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN`), ECS task roles, EC2 IMDS,
static keys (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` /
`AWS_SESSION_TOKEN`), and `AWS_REGION` / `AWS_DEFAULT_REGION`. A correctly
configured EKS pod (Pod Identity or IRSA) needs **no** `store` credentials at
all.

Only **environment variables** are read — **not** file-based profiles
(`AWS_PROFILE`, `~/.aws/credentials`, `~/.aws/config`) or SSO token caches;
`object_store` carries no AWS SDK, so it resolves neither. To authenticate
locally with a named profile or `aws sso login`, materialize that profile's
credentials into the environment first. The AWS CLI v2 resolves the profile
(SSO included) and prints ready-to-eval exports:

```sh
eval "$(aws configure export-credentials --profile my-profile --format env)"
```

That sets `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`,
all of which `from_env` picks up (run `aws sso login` first if the session has
expired). The alternatives are static keys under `store`, or a `file://` URL to
skip AWS entirely for local runs.

Credentials can also be pinned explicitly through `store` (values interpolate
from the environment):

```yaml
    store:
      # Usually unnecessary — EKS injects these and from_env picks them up;
      # shown for when they need pinning explicitly.
      aws_container_credentials_full_uri: "${AWS_CONTAINER_CREDENTIALS_FULL_URI}"
      aws_container_authorization_token_file: "${AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE}"
```

Credential, permission and client-configuration errors fail the pipeline
immediately — no peer would fare better. Non-S3 schemes (`file://`) do not read
the AWS environment. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

## Scaling out — and the solo default

The coordinator is **assembly wiring**: build one over a durable
[coordination store](../../coordination/README.mdx) and inject it, and every
replica of the same pipeline shares the backfill — splits are leased, moved
between live instances by the elected leader, and taken over from dead ones,
with per-split fenced commits making revocations replay-safe.

```rust
let coordinator = StoreCoordinator::new(store, tuning, pipeline.io_handle(), None)?;
let source = S3Source::from_component_config(&source_section, pipeline.io_handle())?
    .with_framer(|| Box::new(NdjsonFramer::new(64 << 20)))
    .with_coordinator(Box::new(coordinator));
```

Building the `store` and `tuning` values is the store's business — see
[NATS JetStream](../../coordination/nats/README.mdx) for the production
backend. Deployment shape, tuning, and failure modes are in
[Scaling out](../../../05-deployment/scaling-out.mdx). The runnable
two-instance version is `crates/spate/examples/s3_coordinated_backfill.rs`.

:::warning No coordinator ⇒ solo, with **ephemeral** progress

With no `with_coordinator(...)`, the source runs the same coordinated
path over an internal in-process store. That is correct and
self-terminating — but the store dies with the process, so **a restart
replays the whole prefix** (at-least-once: wasteful, never lossy). A
startup WARN says exactly this. Durable resume requires a durable
coordination store; there is no manifest checkpoint anymore.

:::

## Split identity and drift

A split's id digests its sorted member keys **and their ETags** (plus a
packing-version constant), and every GET is pinned `If-Match` to the
descriptor's ETag. What that buys:

- **Replans are no-ops** over an unchanged prefix: same listing, same
  packing, same ids — create-if-absent in the store, completed splits
  stay completed.
- **An overwritten object can never splice.** Under an in-flight split
  the pin trips (a `Precondition` failure poisons the split); on a
  replanned listing the new content is a *new* split id, never a silent
  match against stale progress.
- **A deleted object** poisons only the splits that still needed it.

An **append-only prefix** is the right shape for the lifetime of a backfill.
By default the listing is taken once (`refresh_listing: false`), so keys
that arrive later are simply not part of the job; with
`refresh_listing: true` the leader re-lists on the coordinator's replan
interval and plans new objects as additional splits (an **open** job that
never self-terminates — stop it with a signal drain).

## Offsets, progress, resume

A lane's `i64` offset packs *(member ordinal within the split, record
index within the object)*, which keeps one monotonic offset stream per
split across object boundaries — the same watermark contract every other
source honors. `commit` routes acked watermarks into **per-split fenced
progress records** in the coordination store; each carries a versioned
key/ETag pin for its position. Fencing means a split's previous owner can
never overwrite its successor's progress — a stale commit loses the CAS,
writes nothing, and the split simply replays its uncommitted tail on the
new owner.

On a gain with carried progress, the source drift-checks the progress
against the split's descriptor (key and ETag at the watermark's ordinal;
a mid-object resume with no pin anywhere is refused), replays the
in-progress object from its start discarding exactly the committed record
count, and continues. Delivery is **at-least-once**: everything after the
last committed watermark replays after a crash or forced revocation; duplicates are
possible, loss is not.

Limits: ~1.1 × 10¹² records per object (2⁴⁰ − 2); an object that
overflows it **poisons its split** before any offset can be corrupted —
handed back, retried, and quarantined at the attempt cap like any other
object-terminal failure (see below). Split member counts are structurally
capped by the packing floor, far below the ordinal limit. The leader holds the listing in
memory once per plan; budget roughly 100 bytes per key.

## Decoding records

The source frames records but is **format-agnostic** — it streams object
bytes through a [`RecordFramer`](../../../06-extending/custom-source.mdx#framing-turning-bytes-into-records)
supplied by the caller, and **deserialization stays in the operator chain**.
Framing a byte stream is a format concern, so the framer is owned by the format
crate: for NDJSON, that is
[`spate-json`](../../formats/json/README.mdx)'s `NdjsonFramer`.

```rust
let source = S3Source::from_component_config(source_section, io)?
    .with_framer(|| Box::new(NdjsonFramer::new(64 << 20))); // 64 MiB/record cap
```

A framed source emits one record per payload, so its framing contract is
`PerRecord` and the deserializer decodes a single document. Let
`for_source_framing` derive the deserializer's granularity from the source's
`ctx.source_framing` — no hand-set `framing: single`, and a `framing:` that
would double-frame is rejected at startup:

```rust
let deser = JsonDeserializerBuilder::from_component(deser_section)?
    .for_source_framing(ctx.source_framing)? // → single, or reject double-framing
    .build_serde::<MyRecord>();
```

A different object layout needs a different `RecordFramer` — a custom one via
`S3Source::with_framer`, or another format's framer — no fork required. The
framer is **required**: a source built without one refuses to start.

## Errors: poison splits, not skipped objects

Object-level read problems are not record errors, and they are not instant
pipeline failures either. Transient failures are retried inside the source
(capped backoff, ranged re-reads pinned to the ETag). Anything
object-terminal — a key deleted after planning, an overwrite tripping the
`If-Match` pin, corrupt or truncated content, an exhausted retry budget —
**poisons the split**: the split is handed back to the coordinator (counted in
`spate_s3_source_objects_failed_total{reason}`), retried on another
delivery attempt, and **quarantined** at the attempt cap. A bounded job
with quarantined splits ends **failed** (`Stalled`), never as a silently
partial `Completed` — alert on `spate_coordination_splits_quarantined > 0`.
There is no skip-an-object mode: losing a whole object silently is not a
policy, it's an incident — quarantine keeps it loud *and* lets the rest of the
backfill finish first.

## Testing

The whole coordinated lifecycle runs against `file://` URLs with no
infrastructure: solo (`crates/spate/examples/s3_backfill.rs`) and
two-instance (`crates/spate/examples/s3_coordinated_backfill.rs`, over a
shared in-process store). The Docker-gated suites run against a
**SeaweedFS** S3 gateway, and — for durable resume and multi-instance
over the production backend — SeaweedFS plus a NATS 2.11 container
(`cargo test -p spate-s3 -- --ignored --test-threads=1`).

## Metrics

Registered through this source's `Meter` (namespace `s3`, role `source`), so
every family is prefixed `spate_s3_source_`. All handles are resolved once at
`open`, and counters are incremented at object/chunk/batch boundaries — never
per record. The framework's `spate_source_records_total` /
`spate_source_bytes_total` count framed records as for any source; these
families add the object-level view of a bounded backfill.

| Metric | Type | Extra labels | Description |
|---|---|---|---|
| `spate_s3_source_objects_listed_total` | counter | | Objects enumerated by the planner's listing. **Leader-only**: only the instance that runs the plan increments it (once per plan run; open plans re-count on every replan tick). |
| `spate_s3_source_objects_completed_total` | counter | | Objects fully framed and handed to the pipeline by this instance. |
| `spate_s3_source_objects_remaining` | gauge | | Objects not yet completed across **this instance's currently-held splits** (rises on split gain, falls per completed object, settles on split close). Fleet totals come from the `spate_coordination_*` split gauges, not from summing this. |
| `spate_s3_source_bytes_read_total` | counter | | Bytes read from the store, as stored (pre-decompression). |
| `spate_s3_source_bytes_decoded_total` | counter | | Bytes after decompression (equals `bytes_read` for uncompressed objects; the ratio is the effective compression). |
| `spate_s3_source_get_retries_total` | counter | | Object GET attempts beyond the first (transient failures, resumed with ranged reads). A rising rate means a flaky store or network; an exhausted attempt budget poisons the split rather than failing the pipeline. |
| `spate_s3_source_objects_failed_total` | counter | `reason` | Objects that poisoned their split: `not_found` (deleted after planning), `etag_drift` (overwritten under the `If-Match` pin, or content shorter than committed progress), `undecodable` (corrupt/truncated content, over the per-object record limit, or unverifiable without an ETag), `retries_exhausted`. Each report hands the split back; quarantine at the attempt cap shows up in `spate_coordination_splits_quarantined`. |

A coordinated run adds the framework's `spate_coordination_*` families. See
[Metrics](../../../../METRICS.md).
