# S3 (object storage) source

The S3 source (`spate-s3`, feature `s3` on the `spate` facade) runs a
**coordinated, bounded backfill** over a bucket prefix, or, with a `feed:`
section, reads work units and storage notifications from a feed (see
[Reading from a feed](#reading-from-a-feed)). On a backfill it streams every
object's records through the pipeline, and it terminates the pipeline
itself: `run()` returns `ExitState::Completed` once every split of the
prefix is committed complete. `Completed` is a strong claim here. Every
record was durably written by the sink(s) *and* committed. An
unacknowledged tail converts the exit into a failure, so an incomplete
backfill is never reported as done.

Work is planned as [**splits**](../../../07-reference/glossary.mdx#split). The
fleet's elected leader lists the prefix once and packs the sorted listing into
splits of roughly `split_target_bytes`, with deterministic ids and
self-contained descriptors (member keys, sizes, ETags). A split is a batch of
whole objects, or one byte range of a
[large object](#large-objects-and-byte-ranges). Workers lease splits through the
coordination store and read them straight from the descriptors, so
**workers never list**. Solo and multi-worker are the same code path; the only
difference is which coordination store the coordinator points at.

Built on the [`object_store`](https://crates.io/crates/object_store)
client (internal only, with no `object_store` types in the public API), so
`s3://`, and `file://` for infrastructure-free runs and tests, work out of
the box.

Construct it from the pipeline's opaque section, with the pipeline's I/O
runtime handle and a framer (the framer is **required**; see
[Decoding records](#decoding-records)):

```rust file=crates/spate/examples/s3_backfill.rs region=source
```

Runnable examples carry the Rust on this page, and none needs
infrastructure; each stages a `file://` bucket in a temporary directory.
[`s3_backfill.rs`](repo:crates/spate/examples/s3_backfill.rs) runs the solo
backfill (`cargo run -p spate --features s3,json --example s3_backfill`), and
[`s3_coordinated_backfill.rs`](repo:crates/spate/examples/s3_coordinated_backfill.rs)
runs two instances over one shared store
(`cargo run -p spate --features s3,json,coordination --example s3_coordinated_backfill`).

## Configuration

The `source: { s3: ... }` section deserializes into `S3SourceConfig`
([`spate-s3/src/config.rs`](repo:crates/spate-s3/src/config.rs)); unknown
fields are rejected with the offending key. Coordination is not a key of the
source body: it is the pipeline's top-level
[`coordination:` section](../../../07-reference/configuration.mdx#coordination),
covered under [Scaling out](#scaling-out-and-the-solo-default).

```yaml
source:
  s3:
    url: "s3://my-bucket/exports/2026-07/"
    compression: auto
    split_target_bytes: 64MiB
    store:
      region: ${AWS_REGION:-eu-west-2}
```

| Key | Type | Default | Description |
|---|---|---|---|
| `url` | string | `required` | Bucket and prefix to backfill. Every object under the prefix is read. `file://` works for local runs; `memory://` fails at load, because it builds a fresh empty store per component and so cannot be shared. Part of the job fingerprint — byte-identical across every worker of a coordinated job or a [bounded feed job](#bounded-jobs-and-the-job-location). |
| `compression` | `auto` \| `none` \| `gzip` \| `zstd` | `auto` | Object codec. `auto` decides per object by extension (`.gz`/`.gzip`, `.zst`/`.zstd`, else uncompressed). Multi-member gzip and multi-frame zstd are read fully; truncated or corrupt streams [poison the split](#object-errors-poison-the-split). Part of the job fingerprint. |
| `split_target_bytes` | bytes | `64MiB` | Target size of one split — the unit of distribution. Objects pack toward it in listing order with a per-object cost floor of a sixteenth of the target (so ≤ ~16 objects per split). An object above the target is [cut into byte ranges](#large-objects-and-byte-ranges) when it qualifies, and otherwise gets a split of its own. On the [feed path](#reading-from-a-feed) nothing packs, and the target sets the size of the byte ranges a whole-object unit is cut into. Floor `1MiB`. Part of the job fingerprint. |
| `refresh_listing` | bool | `false` | Re-list on the coordinator's replan interval, planning new objects as additional splits. `true` makes the job **open** (never self-terminates). Part of a coordinated job's fingerprint; the feed path never reads it. |
| `prefetch_bytes` | bytes | `8MiB` | Target window size for ETag-pinned ranged GETs; see [read-ahead memory sizing](#read-parallelism-on-a-solo-run). Must be at least `chunk_bytes`; a smaller value fails at load. |
| `chunk_bytes` | bytes | `512KiB` | Target size of one buffered chunk. Zero fails at load. |
| `store` | string map | `{}` | Raw `object_store` options, applied on top of the environment. Bucket keys fail at load, and so do keys `object_store` does not recognize under an S3 URL — see [the `store` denylist](#the-store-passthrough-and-the-denylist). |

Mind the units on the fingerprinted keys: `MB` and `MiB` parse to
different byte counts (`64MB` = 64,000,000; `64MiB` = 67,108,864), and
`split_target_bytes` enters the job fingerprint as its **decoded byte
count**, so a worker spelling it `64MB` is refused at startup against a
fleet on the `64MiB` default. Spellings that decode to the same number of
bytes (`64MiB`, `67108864`) are interchangeable; it is the value that must
match across workers, not the text.

The framer's resync delimiter (see [Decoding records](#decoding-records)) is
part of the job fingerprint too, so every worker of a job needs a framer that
declares the same one.

The record **format is not a config key**. The S3 source is a transport and
owns no framing. The format's framer is wired into the source in code (see
[Decoding records](#decoding-records)); the per-record size bound lives on the
framer (e.g. `NdjsonFramer::new(max_record_bytes)`), not in this table.

A stale config still carrying `lanes` (read parallelism is the coordinator's
`max_in_flight`, one data lane per in-flight split; see
[Read parallelism on a solo run](#read-parallelism-on-a-solo-run)) or the
source's own `checkpoint:` block (progress lives in the coordination store)
fails at load with the offending key. The pipeline-level
[`checkpoint:`](../../../07-reference/configuration.mdx#checkpoint) section is
unaffected and still governs commit cadence.

### Sizing splits against `pipeline.threads`

A split is read by one lane, and a lane is pinned to the pipeline thread it
was handed to; there is no work stealing between threads. So the split
count, not just the split size, sets how evenly the work divides: a plan
yielding five equal splits across two threads gives one thread three and the
other two, and the job finishes when the loaded thread does.

Aim for a split count that is a multiple of `pipeline.threads`, or large
enough that one extra split is a small share of the total. Prefixes of many
small objects get this for free (packing coalesces them), and so do large
objects cut into byte ranges. A handful of large objects read whole is where
it bites, since each gets a split of its own and the count is then fixed by
the data. Raising `split_target_bytes` coarsens the split set and can make
imbalance *worse*, so check the resulting count instead of assuming bigger is
better.

### Large objects and byte ranges

The planner cuts an object above `split_target_bytes` into
`ceil(size / split_target_bytes)` byte ranges of near-equal length, one split
each, when all of these hold:

- the object is uncompressed under `compression`;
- the listing reports an ETag for it;
- the framer declares a resync delimiter (see
  [Decoding records](#decoding-records));
- it is at most 50,000 GiB, the largest object S3 can hold;
- the S3 client can address its key (see
  [Object errors poison the split](#object-errors-poison-the-split)).

Any other object at or above the target gets a split of its own, and one lane
reads it from start to end.

A byte-range split owns the records whose first byte lies inside its range, so
each record of the object belongs to exactly one split. The split reads from
the byte before its range to find the first record that starts inside it, and
past the range's end to finish its last record. The bytes around each boundary
are therefore read twice. Records within one range reach the pipeline in
order, but the ranges of one object are read in parallel, so the object's
records as a whole arrive in no fixed order.

## The `store` passthrough and the denylist

`store` reaches any `object_store` client option without waiting for a typed
field: `region`, `endpoint`, static credentials, `allow_http`, timeouts. Its
values are applied **on top of the environment** when the client is built from
`url`, so anything set here overrides what the environment resolved.

Bucket keys are **rejected at load time with an explanation**. The client is
built from `url`, so a passthrough bucket could never take effect; rejecting it
keeps the configuration honest instead of leaving two sources of truth to
disagree silently. `object_store` accepts several spellings of the same option
(with and without the `aws_` prefix, plus historic aliases) and lowercases keys
before parsing, so every spelling is denied and the match is case-insensitive:

| Denied property | Why |
|---|---|
| `bucket` | Owned by the typed `url` field. |
| `bucket_name` | Owned by the typed `url` field. |
| `aws_bucket` | Owned by the typed `url` field. |
| `aws_bucket_name` | Owned by the typed `url` field. |

The error names the key as written, so the spelling in the message matches the
spelling in the file:

```text
invalid configuration: source.s3.store."Bucket" cannot be overridden: owned by the typed `url` field
```

For an S3 URL (`s3://`, `s3a://`, or an `https://` URL on an `amazonaws.com` or
`r2.cloudflarestorage.com` host), a key that `object_store` does not recognize
as an S3 option also fails at load. Every spelling and case `object_store`
accepts is recognized. A misspelled `endpoint` would otherwise leave the client
on the default AWS endpoint with the configured credentials:

```text
invalid configuration: source.s3.store."endpont" is not an object_store S3 option
```

The client for a `file://` URL reads no `store` options, and its keys are not
checked.

## Security (credentials and region)

For `s3://` URLs, credentials and region resolve from the **standard AWS
environment variables** automatically; the source seeds the client with
`AmazonS3Builder::from_env()`. That covers **EKS Pod Identity**
(`AWS_CONTAINER_CREDENTIALS_FULL_URI` +
`AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE`), **IRSA**
(`AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN`), ECS task roles, EC2 IMDS,
static keys (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` /
`AWS_SESSION_TOKEN`), and `AWS_REGION` / `AWS_DEFAULT_REGION`. A correctly
configured EKS pod (Pod Identity or IRSA) needs **no** `store` credentials at
all.

Only **environment variables** are read, **not** file-based profiles
(`AWS_PROFILE`, `~/.aws/credentials`, `~/.aws/config`) or SSO token caches;
`object_store` carries no AWS SDK, so it resolves neither. To authenticate
locally with a named profile or `aws sso login`, materialize that profile's
credentials into the environment first. The AWS CLI v2 resolves the profile
(SSO included) and prints ready-to-eval exports:

```sh
eval "$(aws configure export-credentials --profile my-profile --format env)"
```

That sets `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`,
all of which `from_env` picks up (run `aws sso login` first if the session has
expired). The alternatives are static keys under `store`, or a `file://` URL to
skip AWS entirely for local runs.

Credentials can also be pinned explicitly through `store` (values interpolate
from the environment):

```yaml
    store:
      # Usually unnecessary — EKS injects these and from_env picks them up;
      # shown for when they need pinning explicitly.
      aws_container_credentials_full_uri: "${AWS_CONTAINER_CREDENTIALS_FULL_URI}"
      aws_container_authorization_token_file: "${AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE}"
```

A listing, an object read, the HEAD after an overwrite, or a read or write at
the [job location](#bounded-jobs-and-the-job-location) the store answers with
`401` or `403`, and a client-configuration error, fail the pipeline
immediately, because no peer would fare better. The error names the status.

A worker that reads [storage notifications](#storage-notifications) needs
these permissions besides `s3:GetObject`:

- `s3:ListBucket` on the bucket, so that an object deleted before its read
  answers `404`. Without it AWS S3 answers `403`, which fails the pipeline.
- `s3:GetObjectVersion` on a versioned bucket, since a notification from one
  names a version and the read sends it. Without it every such unit fails the
  pipeline. It can be scoped to the source's prefix, and it lets anyone who
  can write to the feed have a past version of an object there read.
- The feed's send permission, for the unit it re-enqueues after an overwrite.
  The
  [SQS feed](../../feeds/sqs/README.mdx#security-credentials-permissions-and-tls)
  and [Kafka feed](../../feeds/kafka/README.mdx#startup-checks) pages name it.

RustFS and Ceph RGW have not been tested with a role that lacks list
permission.

A TLS rejection by the store or by the credential endpoint fails the pipeline
the same way. That covers a certificate that fails verification, including one
expired by the client's clock, and a TLS alert with which the server rejects
the handshake, such as `HandshakeFailure` or `CertificateRequired`. It also
covers a server that shares no protocol version, cipher suite or other
handshake parameter with the client. The message names the alert, the mismatch
or the verification failure. Before a handshake failure reaches the source, the
client retries the connection up to 10 times, usually for a few seconds and at
most about a minute. A refusal after the handshake, when the alert arrives, is
not retried. Any other TLS failure, such as a malformed message or an
`InternalError` alert, is retried like a transport error.

Any other failed listing is retried on each replan tick, and the pipeline fails
with the listing error after eight consecutive failures. Credentials that
cannot be resolved or refreshed, including a `401` or `403` from the credential
endpoint, are retried like a transport error. For a read, the split is then
handed back and quarantined at the attempt cap. Non-S3 schemes (`file://`) do
not read the AWS environment. See
[Securing connections](../../../03-guides/securing-connections.mdx) for the
generic model.

## Scaling out and the solo default

Point the pipeline's
[`coordination:` section](../../../07-reference/configuration.mdx#coordination)
at a durable [coordination store](../../coordination/README.mdx), and every
worker running the same pipeline shares the backfill. Splits are leased, moved
between live workers by the elected leader, and taken over from dead ones, with
per-split [fenced](../../../07-reference/glossary.mdx#fencing-token) commits
making revocations replay-safe. The source builds its coordinator from the
section when the pipeline starts, with no code in `main`:

```yaml file=crates/spate/examples/nats_coordinated_backfill.rs region=coordination title="nats_coordinated_backfill.rs"
```

[NATS JetStream](../../coordination/nats/README.mdx) is the durable store.
Deployment shape, the production values, and failure modes are in
[Scaling out](../../../05-deployment/scaling-out.mdx).

A coordinator built in code goes in through `with_coordinator(...)` instead,
and setting both it and the section fails startup. The in-process example
below uses it, because two instances in one process need one shared in-memory
store:

```rust file=crates/spate/examples/s3_coordinated_backfill.rs region=coordinator title="s3_coordinated_backfill.rs"
```

:::warning Solo runs have **ephemeral** progress

With no `coordination:` section and no `with_coordinator(...)`, the source
runs the same coordinated path over an internal in-process store with the
default tuning. A section naming `store: { memory: {} }` runs that store with
the section's tuning. Either way the store dies with the process, so **a
restart replays the whole prefix** (at-least-once: wasteful, never lossy), and
no other instance shares it: a second instance reads the whole prefix again. A
startup WARN says this. Durable resume requires a durable coordination store,
which is the only place split progress lives.

:::

### Read parallelism on a solo run

A solo run reads `max_in_flight` splits at once, one lane each, and the default
is 8. A lane is pinned to one pipeline thread, so with the default no more than
8 pipeline threads do source work. Select the in-process store in the
`coordination:` section to raise it:

```yaml
coordination:
  max_in_flight: 48
  store: { memory: {} }
```

On the ETag-pinned ranged path, read-ahead memory grows with active lanes,
current GET windows and backing windows retained by queued chunks. As
[`spate-s3/src/fetch.rs`](repo:crates/spate-s3/src/fetch.rs) shows, chunks share
an entire GET buffer, so a previous full window and the next full window can
coexist. That overlap uses about `2 × max_in_flight × prefetch_bytes` across
fully active lanes. This is an overlap estimate: short windows can leave
several distinct backing buffers queued, and byte-range boundary reads can
add `chunk_bytes` to a GET window, as specified in
[`spate-s3/src/trim.rs`](repo:crates/spate-s3/src/trim.rs). Framing,
decompression, decoded records and client overhead require additional memory.
The estimate gives no total-process memory ceiling.

The split count still sets how evenly the lanes divide over threads; see
[Sizing splits against `pipeline.threads`](#sizing-splits-against-pipelinethreads).

## Reading from a feed

A [`feed:` section](../../../07-reference/configuration.mdx#feed) moves the
source onto the feed path. It reads
[work units](../../../07-reference/glossary.mdx#work-unit) from the feed the
section names. On a durable feed it lists nothing itself: a bounded job's units
come from a [lister run](#the-lister-run), and a continuous job's from
[storage notifications](#storage-notifications) or code. On the in-process feed
the run lists the prefix itself; see
[A solo run on the in-process feed](#a-solo-run-on-the-in-process-feed). Every
delivery is read in full, resuming from no earlier delivery, and the unit is
acknowledged once the sink has acknowledged every record in it. Two units are
the exceptions: a notification unit whose object is overwritten while it is
read, as [Reading a notification's object](#reading-a-notifications-object)
describes, and a unit handed back at a [graceful stop](#a-graceful-stop).

```yaml
feed:
  memory: {}
  units_held: 32
```

### Work units

A unit the lister publishes names one object or one byte range of one object, as
an encoded `SplitDescriptor`, and a notification message is one unit with one
part per non-empty created object (see
[Storage notifications](#storage-notifications)). A unit whose body is neither,
or a descriptor naming more than one object, is failed back to the feed. Nothing
packs on the feed path. A whole-object part is cut into byte ranges on the
conditions in [Large objects and byte ranges](#large-objects-and-byte-ranges),
with the ETag taken from the descriptor or the notification, so a part with no
ETag is read whole on one lane. A unit naming a byte range is failed back when
its range is cut on a delimiter other than the framer's, or when `compression`
decodes its object. The unit is acknowledged once, after every part and range
has been read and committed. An object failure on one range fails the whole unit
back, and its other parts and ranges stop. An overwrite of a notification unit's
object stops that object's ranges and re-enqueues the object once, as
[Reading a notification's object](#reading-a-notifications-object) describes.

The lister publishes no unit for an object of size 0, which holds no records.
An object whose key the S3 client cannot address is one whole unit, which
poisons on its first read and names the key; one with no bytes, such as a
folder marker `dir/`, gets none.

Each range in progress takes one slot of `units_held`. Deliveries received
alongside a large object wait until all of its ranges have opened, and the
deliveries held stay at or below `units_held`. A waiting delivery is held
unread, and a stop on a feed that hands back hands it back unread. SQS ends
every hold 12 hours after the receive, so a delivery still waiting then goes
back to the queue unread, one receive closer to `maxReceiveCount`. On Kafka a
waiting delivery's offset holds back its partition's commit point.

`units_held` bounds the lanes the source reads at once, one per whole object or
range, and with them its read parallelism. The default is 96. On a durable
feed the source lists nothing. It reads the units and storage notifications
published to the feed, and publishes only the notification unit it
re-enqueues after an overwrite; a startup WARN says so. On
the in-process feed the run lists the prefix into that feed, and code may also
publish to a `MemoryFeed` it keeps a handle to and passes to `Pipeline::feed`
with `feed: { memory: {} }` in the file. Units from another process need a
durable [feed backend](../../feeds/README.mdx). A bounded job ends on its own,
as [How a bounded job ends](#how-a-bounded-job-ends) describes, and so does a
solo run on the in-process feed the runtime built, once its listing is read. A
run given a `MemoryFeed` in code, and any job on a durable feed with no
`location`, ends at a shutdown. A lister run ends once it has published the
listing. Without a `feed:` section the source plans
splits as described above.

### A graceful stop

On a graceful stop with a feed that
[hands back](../../../07-reference/glossary.mdx#hand-back), the source receives
no more units. It keeps reading and renewing the units it holds, and opens
their remaining byte ranges as `units_held` allows, until each is read to its
end or until 5s before the drain deadline. A unit is read to its end once every
part and range has opened and reached its end of input, with no object failure
and no re-enqueue the feed has yet to confirm. Such a unit stays held and is
acknowledged once the sink has acknowledged every record in it.

The source then hands back every other unit it holds, including a delivery
still waiting for its ranges to open. Another instance reads a handed-back unit
from its start, so records read from it before the stop reach the sink twice.
A unit with an object failure is failed back to the feed. A failed run hands
back at once, with no reading.
[Graceful shutdown](../../../03-guides/graceful-shutdown.mdx#the-drain-choreography)
describes the drain around it. None of the built-in
[feeds](../../feeds/README.mdx) hands back, so on each of them the source
starts the drain at once.

### A solo run on the in-process feed

A run whose `feed:` section names `memory` lists its own prefix into the
in-process feed when it opens, and reads units while the listing runs. A
listing that fails fails the run, whatever the store error.

:::warning A solo run lists from the beginning after a restart
The in-process feed keeps nothing across a restart, and a solo run keeps no
checkpoint, so a restarted run lists and reads the whole prefix again, and a
startup WARN says so. A solo run on the in-process feed the runtime built ends
by itself once its listing is published and every unit is read, with no
settling window; when the in-process dead-letter list then holds a unit it
fails as a [stalled job](#how-a-bounded-job-ends). A run given a `MemoryFeed`
in code ends at a shutdown, since code may publish to it after the listing.
Two solo instances, on one host or several, each list
and read the whole prefix. The listing publishes as fast as the store lists,
and the in-process feed holds one unit for each listed part not yet read, in
memory and outside `units_held`. A single instance that must resume reads a
durable feed with a `location`, filled by a separate
[lister run](#the-lister-run).
:::

### Storage notifications

The source reads the notifications a store publishes to the feed when an
object is created. A message is one of:

- an S3 `Records[]` message;
- the same records inside the `{"EventName", "Key", "Records"}` envelope
  RustFS sends;
- the S3 test event (`"Event": "s3:TestEvent"`), acknowledged with nothing
  read.

Each record is decided on its own:

- a record with no `eventName`, or one that is not a string, fails the whole
  message;
- a record whose `eventName` is not `ObjectCreated:*`, with or without the
  `s3:` prefix, is dropped, whatever its bucket;
- a created object of size 0 in the source's bucket, under its prefix and
  with a key that decodes, is dropped, since it holds no records, even under a
  key `object_store` cannot read under its own name;
- every other created record is one part of the message's unit. Its key is
  decoded as `application/x-www-form-urlencoded` (`+` is a space, then
  percent-decoding as UTF-8), so `%2F` and a raw `/` give the same key. Its
  ETag is sent quoted in `If-Match`.

The message is failed back to the feed, which dead-letters it at its cap, when
any created record:

- lacks `s3.bucket.name` or `s3.object.key`, or carries a field of the wrong
  type;
- names a bucket other than the one in the source's `url`;
- names a key outside the `url`'s prefix, taken with the `/` the listing
  appends;
- has no size, or a size that is not a non-negative integer;
- has a key that does not decode;
- has a key `object_store` cannot read under its own name, for an object of
  one byte or more: an empty, `.` or `..` segment, an ASCII control
  character, or a leading or trailing `/`;
- has an ETag holding a control byte other than a tab, which `If-Match`
  cannot carry, for an object of one byte or more.

A body that is neither a notification nor a descriptor is failed back the same
way, and that includes an S3 message inside an SNS envelope. So is a
descriptor whose ETag `If-Match` cannot carry. On a store that
puts several records in one message, one such record dead-letters the message
with its other records. A source whose `url` names the whole bucket
(`s3://bucket/`) reads every created key in it. The message is acknowledged
once, after every part of it has been read and committed.

The records read for a notification take its `eventTime` as their event time,
and those read for a listed object take the listing's `LastModified`. The
records of a unit the source re-enqueued take the `LastModified` its HEAD
reported. A
notification with no `eventTime`, or one that does not parse, gives its records
event time 0, which under `metrics.e2e_basis: event` counts their end-to-end
latency from 1970.

A notification names an object, and its read pins the ETag the notification
carries. An object deleted before it is read fails that read on every delivery,
so the feed dead-letters its message at the cap. An object overwritten before or
during its read is re-enqueued at its current ETag when its notification carries
an ETag, and is read in its new contents when the notification carries none. A
notification's unit is a unit of its own, with the feed message's id (the SQS
`MessageId`, or the Kafka message key), so an object that both a listing and a
notification announce is read twice. A unit the source re-enqueues keeps the id
of the unit it replaces. A store sends no notification for an object written
before the bucket's notification configuration takes effect; on AWS S3 that
window lasted at least 181 seconds after the configuration was written, in one
measured run
([ADR-0072](../../../../adr/0072-missed-storage-notifications-are-not-reconciled-by-re-listing.md)).
Spate does not re-list to find a notification the store never sent.

Each store needs its own settings for its notifications to arrive:

- **AWS S3.** The bucket's notification configuration sends `s3:ObjectCreated:*`
  to the queue
  ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ways-to-add-notification-config-to-bucket.html)).
  A later `PutBucketNotificationConfiguration` from another tool replaces the
  bucket's whole configuration, this rule with it
  ([AWS](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutBucketNotificationConfiguration.html)).
  The queue's own settings are on the
  [SQS feed](../../feeds/sqs/README.mdx#storage-notifications) page.
- **RustFS.** The Kafka notification target needs a `queue_dir`. Without one,
  an event that fails to send is lost
  ([RustFS](https://docs.rustfs.com/en/operations/event-notifications)).
  RustFS writes each event with timestamp 0, so the work topic needs the
  setting the [Kafka feed](../../feeds/kafka/README.mdx#topics) page states,
  and the feed refuses a work topic without it.
- **Ceph RGW.** The source does not read RGW's notifications. RGW sends them
  over HTTP, AMQP or Kafka, never to SQS
  ([Ceph](https://docs.ceph.com/en/latest/radosgw/notifications/)), and it
  produces each Kafka message without a key, which the
  [Kafka feed](../../feeds/kafka/README.mdx#counting-deliveries) dead-letters.
  RGW also writes a record's key unencoded, and the source decodes every key,
  so a key holding `+` or `%` decodes to another key.

#### Reading a notification's object

A notification unit's object may have changed since the store sent the event.
Its read handles each case as the
[notification-read record](../../../../adr/0077-a-notification-units-read-classifies-a-deleted-or-overwritten-object.md)
decides:

- A `404` fails the unit back, and the feed dead-letters it at its cap.
- A `401` or `403` fails the pipeline, as for any object read.
- A record whose `versionId` is a string other than `""` and `"null"` names a
  version, and the read sends that version with the ETag pin. An absent or
  JSON null `versionId`, `""` and `"null"` read the key. A `versionId` longer
  than 1,024 bytes, or holding a space or a control byte, fails the message.
  A failed precondition on a read that names a version fails the unit back.
- A failed precondition (`412`) on a read that names no version means the
  object was overwritten. So does a `416` on such a read, which RustFS sends
  for a range past the end of a smaller new object before it checks the
  precondition. The read stops, and the source sends a HEAD for the
  key. It publishes a notification unit for the key at the ETag and size the
  HEAD reports, under the old unit's id, with a re-enqueue count one higher
  than the old unit's. On SQS the new unit goes to the queue, and on Kafka to
  the work topic. The old unit is acknowledged once the feed has stored the
  new one and the sink has acknowledged every record read from the old one.
- A HEAD that answers `404` is handled as a `404` on the read, and one that
  answers `401` or `403` as a `403`. A HEAD that reports the ETag the read was
  pinned to fails the unit back. A HEAD that reports size 0 acknowledges the
  unit with nothing published.
- A publish the feed refuses, or cannot confirm, fails the old unit back, and
  its next delivery reads the object again. A publish the feed answers as
  fatal, such as a send its permissions deny, fails the pipeline.

An object overwritten while it is read delivers the records read before the
overwrite, and the rest of that version is never read. Each range read under the
old ETag costs one HEAD, and the key costs one feed message per delivery. A key
overwritten faster than it is read is re-enqueued on every overwrite up to the
cap, and its last version is read once for each unit still in the chain. Two
notifications for one overwritten key start two chains.

:::danger An overwrite can be dropped at the re-enqueue cap
A unit whose re-enqueue count has reached the cap is acknowledged on a `412`
without a re-enqueue, and counted in `spate_s3_source_overwrites_dropped_total`.
The cap is the `feed:` section's `attempt_cap`, 10 when the section sets none;
the SQS feed refuses `attempt_cap`, so a job on SQS caps at 10. The key's later
versions arrive through their own notifications, but a version written by an
overwrite that sent no notification is lost.
:::

Units from a lister keep the classification in
[Object errors poison the split](#object-errors-poison-the-split).

### Bounded jobs and the job location

A job on a durable feed is bounded when its `feed:` section names a
[`location`](../../../07-reference/configuration.mdx#feed), and continuous when
it names none. Every worker of a bounded job reads the job fingerprint at the
[job location](../../../07-reference/glossary.mdx#job-location) before it
reads a unit. A continuous job's workers read no job location. The in-process
feed refuses a `location`.

```yaml
feed:
  sqs:
    queue_url: https://sqs.eu-west-2.amazonaws.com/123456789012/events-backfill-0042
  location: s3://ops-bucket/spate-jobs/events-backfill-0042/
```

The location is a prefix, and `…/events-backfill-0042` names the same one.
The job fingerprint is the object named `fingerprint` there, which the job's
lister creates before it publishes a unit. A lister run also deletes an object
named `end` there before its first publish, and writes `end` once the feed has
confirmed every unit of the run and the last checkpoint is written. `end`
holds `run=` and an id fresh to that run. A run that fails writes none, except
when its write of `end` reached the store and the reply was lost; the next run
deletes that one before it publishes. Every worker reads `end` to end the job,
as [How a bounded job ends](#how-a-bounded-job-ends) describes. A new job
takes a new location.

The lister's checkpoint is the object named `checkpoint` there. It holds the
last listed key for which the feed has confirmed every unit of it and of every
key listed before it; the [SQS](../../feeds/sqs/README.mdx#message-mapping) and
[Kafka](../../feeds/kafka/README.mdx#message-mapping) feed pages say when a
publish is confirmed. The lister rewrites it at most once every 1,000 listed
keys and once when its listing ends. A run whose location holds `checkpoint`
beside its own fingerprint lists only the keys after it, through
`ListObjectsV2`'s `StartAfter`, and logs the key at INFO. A run that finds no
fingerprint deletes a `checkpoint` it finds, logs that at INFO, creates the
fingerprint and lists the whole prefix. A run that stops publishes the units
after the last checkpoint again. A lister on a `file://` source, or on an S3
directory bucket (`aws_s3_express`, or `AWS_S3_EXPRESS` in the environment),
keeps no checkpoint and logs a WARN: every run lists the prefix from the start.

Resume finds every key while the store lists keys in the same order in the run
that wrote `checkpoint` and in the run that resumes from it. AWS S3
general-purpose buckets list in UTF-8 byte order; the CI suite checks resume on
RustFS only. Resume is unsupported on SeaweedFS, where it skips keys: SeaweedFS
lists in directory-tree order, so a resume after a key that is also a
directory prefix (`q/r` beside `q/r/s`) skips that directory. Its listings can
also end early; see [Testing](#testing).

:::danger
A run at a location that holds the job's fingerprint and a `checkpoint` never
reads the keys up to the checkpoint. A re-run of a finished job publishes the
keys that list after the checkpoint, and again each object the S3 client cannot
address that lists after it; a key added since that lists before the checkpoint
is never read. A job whose feed lost its units, such as a purged queue or a new
queue or topic at the same location, never reads its keys up to the checkpoint.
If the store's list order may have changed since `checkpoint` was written, such
as across a store upgrade, stop the lister, delete `checkpoint`, and start it
again. To start a job over, delete the whole location prefix.
:::

The fingerprint covers the unit format version, `url`, `compression`,
`split_target_bytes` and the framer's resync delimiter. At startup a worker of a
bounded job reads `fingerprint` every five seconds until it appears, and
compares it with its own before it receives a unit. A worker whose fingerprint
differs fails startup, and the error prints both. A worker that finds none
within one settling window, five minutes unless the `feed:` section's
`settling_window` sets another, exits non-zero. A read the store fails retryably
is logged at WARN and tried again at the next step. The exit error names the
last failed read's error, says "none appeared" when the reads found nothing, and
says the store answered no read when it answered none within the window. While
it waits a worker holds no unit and reports not ready on `/readyz`, and a
shutdown ends the wait within one step, a read in flight included. On a feed
that records an attempt before a unit is read, such as the
[Kafka feed](../../feeds/kafka/README.mdx#counting-deliveries), the feed spends
an attempt on each unit it readies for a waiting worker, and each rebalance of
the group during the wait spends another. A fleet started well before its
lister, or a worker restarting into a refusal, can move the head of each
partition to the dead-letter destination unread.

The location's store is built from its URL with the source's `store` options
and the environment, so it shares the endpoint, region and credentials those
give the source, and may sit in another bucket. A region the source takes from
an `https://` `url` does not reach an `s3://` location; set it under `store`.
On every store, write the location as `s3://<bucket>/<prefix>` or
`s3a://<bucket>/<prefix>`, with the endpoint and region under `store`, or as
`file://`. Each of these is refused at startup:

- any other form, an `https://` URL and `memory://` included;
- an `s3://` or `s3a://` location naming no bucket, a `file://` location
  naming a host, and a prefix with an empty segment, a control character or
  bytes that are not UTF-8;
- a location carrying userinfo, a query or a fragment; credentials go under
  `store`;
- an S3 location beside a source `url` that names a store other than AWS by
  its `https://` host, unless `store` sets that store's endpoint;
- an S3 location when `store` or the environment sends virtual-hosted requests
  to a set endpoint, which then addresses one bucket whatever the location
  names;
- an S3 location when a `store` key is not an S3 option, under a `file://`
  `url` as well;
- a location at or under the source's prefix in the same bucket, since the
  source would read its objects.

The location also belongs outside the prefix of any notification rule that
publishes to the job's feed, where each write to it arrives as a message the
source dead-letters; nothing checks that.

Workers need read access to the location. The lister needs to read, write and
delete there. On AWS S3 that read access includes `s3:ListBucket` on the
location's bucket: without it a read of an absent object answers `403`, so a
worker started before its lister fails at once and a lister at a new location
fails on the absent fingerprint. The error says so. Write access at the location
decides where a lister run resumes. The lister creates `fingerprint` only when
absent, so a lister whose `store` sets `aws_conditional_put: disabled` fails.
Run one lister per location: a second lister with another fingerprint is refused
when it reads the first's fingerprint, and, when both read before either wrote
one, by the conditional create on a store that honors `If-None-Match`, which the
CI suite checks on RustFS only. The location needs read-after-write and
read-after-delete consistency, which means `consistency_mode = "consistent"` on
Garage and one zone on Ceph RGW. A `file://` location serves the processes of
one host.

### How a bounded job ends

A worker of a bounded job ends the job once all three hold:

- the object `end` names the same lister run at the start and at the end of a
  settling window, five minutes unless the `feed:` section's
  [`settling_window`](../../../07-reference/configuration.mdx#feed) sets
  another;
- every read of the feed's depth over the window, at most 20 seconds apart,
  finds no unit ready, delayed or held by any worker, and the worker holds
  none and has no acknowledgement in flight;
- the feed's dead-letter destination is empty, read once after the window.

Each worker decides on its own reads and exits zero. A read that finds a unit, a
read that fails retryably or comes late, a unit the worker takes, or an `end`
that changes or disappears starts the window again from a new read of `end`. A
read of the feed or of `end` that fails for good, such as for a missing
permission, and an `end` that does not hold a lister run's marker fail the run
with exit code 1. The worker reads `end` only at the start and the end of a
window, and its feed every 15 seconds within one, so that no two reads fall more
than 20 seconds apart. A feed that cannot report its depth fails a bounded job
at startup. The
[work feed](../../../02-concepts/09-work-feed.mdx#how-a-bounded-job-ends) page
states the rule, and each [feed's page](../../feeds/README.mdx) how it reads its
depth.

When the dead-letter destination holds units, the job ends **stalled**: the
run fails with an error that includes `bounded feed job stalled:` and names the
destination and its count, and the process exits non-zero. To re-run a stalled
job, fix what made its units fail, then start a new job at the same location on
a fresh queue or topics, with its own dead-letter destination. Copy the dead
letters into the new job's feed by hand before you start its lister. The
lister resumes after the checkpoint and publishes only the keys listed after
it, and the workers read both. A copied unit that arrives after the new job's
workers have seen its `end` over a settling window of empty reads is left
unread. A re-run whose fix changes the fingerprint, such as a new
`compression`, `split_target_bytes` or framer, takes a new location, lists the
whole prefix and needs no copied units.

A bounded job cannot share its feed with storage notifications, and nothing
checks that. Notifications keep the window from closing until they stop for a
whole window, and an object both the lister and a notification announce is
read twice. A unit the feed deletes at the end of its retention, before any
worker reads it, leaves no trace, and the job can end over it.

### The lister run

A bounded job's units come from one lister run per job: the same binary,
started once in place of a worker, that lists the prefix, publishes its units,
writes `end` and exits. `main()` starts it with
[`S3Source::list_once`](https://docs.rs/spate-s3/latest/spate_s3/struct.S3Source.html#method.list_once),
whose rustdoc example is a binary that runs the lister when its first argument
is `list`. The run reads the source and `feed:` sections of the workers' own
pipeline file and builds no sink. Build its feed with the backend's
publish-only handle where it has one, such as the Kafka feed's
[publish-only handle](../../feeds/kafka/README.mdx#a-publish-only-handle),
which joins no group the workers read. It refuses the in-process feed, a section
with no `location`, a feed other than the one the section names, a source
given a coordinator, and a call from a thread in a Tokio runtime context,
such as async code or a `spawn_blocking` closure.

A unit the feed rejects as retryable is published again, up to five attempts,
after waits of 200 ms, 400 ms, 800 ms and 1.6 s. A unit the feed refuses, or
still rejects after the fifth attempt, fails the run, and the error names its
object. A failed run returns its error, so a binary that returns it from
`main()` exits non-zero, and the next run resumes after the checkpoint.

The lister adds no timeout of its own. Each request to the store is bounded by
`object_store`'s retries, about three minutes. A publish waits as long as its
[feed backend](../../feeds/README.mdx) keeps trying it, which has no bound on
a backend that retries a transient failure until it stops. Bound the run as a
whole where it is deployed, such as a Kubernetes Job's
`activeDeadlineSeconds`.

Two lister runs over one prefix:

- at two locations publish every unit twice, and nothing detects it;
- at one location with one fingerprint, the later run resumes after the
  checkpoint the earlier wrote, or lists the whole prefix when both start
  before either writes one, and the first to finish writes `end` while the
  other may still hold units the feed has not confirmed, so the workers can
  end the job while those units are still on their way to the feed, where
  they stay unread;
- at one location with two fingerprints, the later run is refused when it
  reads the earlier's fingerprint, on any store; when both read before either
  wrote one, the conditional create refuses the later run only on a store
  that honors `If-None-Match`.

## Split identity and drift

A split's id digests its sorted member keys **and their ETags** (plus a
packing-version constant), and a byte-range split's id also digests its range
and delimiter. Every GET is pinned `If-Match` to the descriptor's ETag. What
that buys:

- **Replans are no-ops** over an unchanged prefix: same listing, same
  packing, same ids; create-if-absent in the store, completed splits
  stay completed.
- **An overwritten object can never splice.** Under an in-flight split
  the pin trips (a `Precondition` failure poisons the split); on a
  replanned listing the new content is a *new* split id, never a silent
  match against stale progress.
- **A deleted object** poisons only the splits that still needed it.

An **append-only prefix** is the right shape for the lifetime of a backfill.
By default the listing is taken once (`refresh_listing: false`), so keys
that arrive later are not part of the job; with
`refresh_listing: true` the leader re-lists on the coordinator's replan
interval and plans new objects as additional splits (an **open** job that
never self-terminates; stop it with a signal drain).

## Offsets, progress, resume

A lane's `i64` offset packs
*(member ordinal within the split, record index within the object)*, which keeps
one monotonic offset stream per split across object boundaries, the same
watermark contract every other source honors. A byte-range split has one member,
at ordinal 0, and counts record indexes from the first record its range owns.
`commit` routes acked watermarks into **per-split fenced progress records** in
the coordination store; each carries a versioned key/ETag pin for its position.
Fencing means a split's previous owner can never overwrite its successor's
progress. A stale commit loses the CAS, writes nothing, and the split replays
its uncommitted tail on the new owner.

On a gain with carried progress, the source drift-checks the progress against
the split's descriptor (key and ETag at the watermark's ordinal; a mid-object
resume with no pin anywhere is refused), replays the in-progress object or byte
range from its start discarding exactly the committed record count, and
continues. Delivery is **at-least-once**. Everything after the last committed
watermark replays after a crash or forced revocation; duplicates are possible,
loss is not.

Limits: ~1.1 × 10¹² records per object or byte range (2⁴⁰ − 2); an object
that overflows it **poisons its split** before any offset can be corrupted:
handed back, retried, and quarantined at the attempt cap like any other
[object-terminal failure](#object-errors-poison-the-split). Split
member counts are structurally capped by the packing floor, far below the
ordinal limit.

The leader holds the **whole listing** in memory for the duration of a plan:
one entry per object, carrying that object's key and ETag. Packing moves those
entries into splits rather than copying them, so the keys are held once. Peak
scales with object count *and* key length: a prefix of long keys costs
materially more than the same number of short ones. A
[cut object](#large-objects-and-byte-ranges) adds one split and one encoded
descriptor per range, so its cost also grows with its size divided by
`split_target_bytes`. At the default target, one 50,000 GiB object plans 800,000
splits and takes the leader about 362 MB to plan, measured by planning that one
listing entry in a release build. Planning runs on the leader only, once per
plan and, for an open plan, on every replan tick.

Every instance keeps the records of the splits it tracks in memory until the
job ends, and by the time the job ends, every instance tracks every split. A
completed split costs up to about 1,100 bytes with a 16-byte key, plus about
2.7 bytes per further key byte, since its descriptor and its resume state carry
the key as JSON and then base64. That object's 800,000 splits therefore hold
up to about 878 MB on each instance with 16-byte keys, and up to about 1.30 GB
with 212-byte keys. These figures assume the default 38-character
`instance_id` and a 40-character ETag, and a longer `instance_id` adds bytes
per split; they were measured by building those records under a counting
allocator. The
coordination store holds two records per split, so seeding them is 1.6 million
store writes, and each `reconcile_interval` the reconcile listing reads every
split record again.

## Decoding records

The source frames records but is **format-agnostic**. It streams object bytes
through a
[`RecordFramer`](../../../06-extending/custom-source.mdx#framing-turning-bytes-into-records)
supplied by the caller, and **deserialization stays in the operator chain**.
Framing a byte stream is a format concern, so the framer is owned by the format
crate: for NDJSON, that is [`spate-json`](../../formats/json/README.mdx)'s
`NdjsonFramer`.

`with_framer` takes a factory rather than a framer, because framers are
per-object stateful and each object gets a fresh one; the bound the framer is
built with (`64 << 20` here) caps a single record's decoded bytes:

```rust file=crates/spate/examples/s3_backfill.rs region=framer
```

A framed source emits one record per payload, so its framing contract is
`PerRecord` and the deserializer decodes a single document. Let
`for_source_framing` derive the deserializer's granularity from the source's
`ctx.source_framing`. There is no hand-set `framing: single`, and a `framing:`
that would double-frame is rejected at startup:

```rust file=crates/spate/examples/s3_backfill.rs region=deserializer
```

`deser_section` is the pipeline's `deserializer:` section, cloned before the
chain factory so each thread's closure owns it.

A different object layout needs a different `RecordFramer`, either a custom one
via `S3Source::with_framer` or another format's framer, and no fork is
required. The framer is **required**: a source built without one refuses to
start.

A framer takes part in [byte-range splits](#large-objects-and-byte-ranges)
through `RecordFramer::resync_delimiter`. Returning `Some(byte)` declares that
a record starts after every occurrence of that byte, which `NdjsonFramer` does
with `\n`. A format with a header, a byte-order mark, magic bytes or a quoted
delimiter, as CSV has, returns `None`, which is the default. The planner then
reads every object whole, and the source logs that at `INFO` when it opens.

## Object errors poison the split

Object-level read problems are not record errors, and they are not instant
pipeline failures either. Transient failures are retried inside the source
(capped backoff, ranged re-reads pinned to the ETag). Anything object-terminal
**poisons the split**: a key deleted after planning, an overwrite tripping the
`If-Match` pin, corrupt or truncated content, or an exhausted retry budget. The
split is handed back to the coordinator (counted in
`spate_s3_source_objects_failed_total{reason}`), retried on another
delivery attempt, and
[**quarantined**](../../../07-reference/glossary.mdx#quarantine) at the attempt
cap. A bounded job with quarantined splits ends **stalled**, which is fatal by
default, so `run()` returns `ExitState::Failed` rather than a silently partial
`Completed`. `CoordinationDriver::stall_drains(true)` trades that for a drain
with a WARN. Either way, alert on
`spate_coordination_splits_quarantined > 0`.

A key the S3 client cannot address poisons as well. The client rejects a key
with an empty segment (`d//x.ndjson`), a `.` or `..` segment, or an ASCII
control character, and reads a key that starts or ends with `/` under a
different key. The listing still returns every other object. Each object with
such a key is planned in a split of its own, which poisons on its first read
and names the key, and the objects listed beside it are read. An object with
such a key and no bytes, such as a folder marker `dir/`, holds no records and
is not planned.

There is no skip-an-object mode; the reasoning is in
[ADR-0035](../../../../adr/0035-s3-poison-policy.md), which also covers why
credential and configuration failures fail the pipeline instead. Quarantine
lets the rest of the backfill finish first. An overwrite of a notification
unit's object is re-enqueued instead, as
[Reading a notification's object](#reading-a-notifications-object) describes.

## Testing

The whole coordinated lifecycle runs against `file://` URLs with no
infrastructure, which is what the examples this page draws on do: solo,
and two-instance over a shared in-process store. The Docker-gated suites run
against a **RustFS** S3 store, and, for durable resume and multi-instance
over the production backend, RustFS plus a
[NATS](../../coordination/nats/README.mdx#supported-server-versions) container
(`cargo test -p spate-s3 -- --ignored --test-threads=1`).

The S3 source ends a listing at the first `ListObjectsV2` page that carries no
continuation token. The store must return one on every page that has keys after
it. When a store omits it, a backfill completes without the remaining objects
and reports no error. SeaweedFS 4.48 omits the token when a page ends on a
folder marker, a key ending in `/`, and every key after it sits under that
marker.

## Metrics

Registered through this source's `Meter` (namespace `s3`, role `source`), so
every family is prefixed `spate_s3_source_`. All handles are resolved once at
`open`, and counters are incremented at object/chunk/batch boundaries, never
per record. The framework's `spate_source_records_total` /
`spate_source_bytes_total` count framed records as for any source; these
families add the object-level view of a bounded backfill. Standard labels
(`pipeline`, `component`, `component_type`) are on all of them; extras are
noted per family.

| Metric | Type | Extra labels | Description |
|---|---|---|---|
| `spate_s3_source_objects_listed_total` | counter | | Objects enumerated by the planner's listing. **Leader-only**: only the worker that runs the plan increments it (once per plan run; open plans re-count on every replan tick). |
| `spate_s3_source_objects_completed_total` | counter | | Objects fully framed and handed to the pipeline by this worker. A cut object counts once per range, so completed over listed can exceed 100%. |
| `spate_s3_source_objects_remaining` | gauge | | Objects not yet completed across **this worker's currently-held splits** (rises on split gain, falls per completed object, settles on split close). A cut object counts once per range. Fleet totals come from the `spate_coordination_*` split gauges, not from summing this. |
| `spate_s3_source_bytes_read_total` | counter | | Bytes read from the store, as stored (pre-decompression), including the bytes a byte-range split reads around its range and drops. |
| `spate_s3_source_bytes_decoded_total` | counter | | Bytes after decompression; for a byte-range split, the bytes of the records it owns. Equals `bytes_read` for uncompressed objects read whole; the ratio is the effective compression. |
| `spate_s3_source_get_retries_total` | counter | | Object GET and HEAD attempts beyond the first (transient failures, resumed with ranged reads). A rising rate means a flaky store or network; an exhausted attempt budget poisons the split rather than failing the pipeline. |
| `spate_s3_source_objects_failed_total` | counter | `reason` | Objects, or byte ranges of one, that poisoned their split: `not_found` (deleted after planning, or a key that is not a valid object path), `etag_drift` (overwritten under the `If-Match` pin, or content shorter than committed progress; a notification unit's re-enqueued overwrite is counted in `objects_overwritten_total` instead), `undecodable` (corrupt/truncated content, over the per-object record limit, or unverifiable without an ETag), `retries_exhausted`. Each report hands the split back; quarantine at the attempt cap shows up in `spate_coordination_splits_quarantined`. |
| `spate_s3_source_objects_overwritten_total` | counter | | Objects a notification unit's read found overwritten under its ETag pin, once per object and delivery, whether re-enqueued or not. See [Reading a notification's object](#reading-a-notifications-object). |
| `spate_s3_source_overwrites_dropped_total` | counter | | Of those, the objects whose unit was at the re-enqueue cap and was acknowledged without a re-enqueue. A non-zero value means an overwrite may have been dropped. |

[Metrics](../../../../METRICS.md).
