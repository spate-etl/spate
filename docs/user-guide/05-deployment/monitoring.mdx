# Monitoring

Every stage of a pipeline is instrumented, and the instrumentation API is
deliberately not framework-specific: it is the
[`metrics`](https://crates.io/crates/metrics) facade. Anything you record
with `metrics` macros or handles exports through the same endpoint as the
framework's own series — there is no extra registry to learn.

:::note
The **canonical metric taxonomy** — every metric name, type, label and
histogram bucket — lives in [Metrics](../../METRICS.md).
:::

## The exporter and the admin server

These are separate settings in separate sections, because they answer separate
questions. `metrics.exporter` decides whether series are recorded at all; `admin.listen`
decides whether an HTTP server publishes them — and that same server carries
the liveness and readiness probes, which are worth serving whether or not
anything is exported:

```yaml
admin:
  listen: 0.0.0.0:9090    # /metrics, /healthz, /readyz; `none` runs no server

metrics:
  exporter: prometheus    # default; `none` disables export
```

With `prometheus` (the default), the exposition endpoint mounts at
`GET /metrics` on the admin server, next to the probes described in
[Docker](docker.mdx). Scrape it with a PodMonitor or scrape annotations.

The combinations, and what each is for:

| `admin.listen` | `metrics.exporter` | What you get |
|---|---|---|
| an address | `prometheus` | Probes and a scrape endpoint. The deployment default. |
| an address | `none` | Probes only. `/metrics` answers 404: there is no exposition to serve, and an empty 200 would read to a scraper as a healthy target delivering nothing. |
| `none` | `prometheus` | Series recorded, nothing serving them. For a host process that renders the exposition itself, through `Pipeline::metrics`, and mounts it on a server it already runs. The start logs a warning, because this is equally what disabling the server and forgetting the exporter produces. |
| `none` | `none` | No port and no recorder. What a test or a local demo wants ([Testing pipelines](../03-guides/testing-pipelines.mdx)). |

`/metrics` follows the exposition rather than the setting. Where another
library installed a recorder before the pipeline did, the pipeline records
into that recorder and has none of its own to render, so the endpoint answers
404 even though `exporter` says `prometheus`. The start does log this — a
recorder was already installed, and the pipeline continued against the
existing one with a detached render handle. What stays silent is the
`admin.listen: none` warning from the table above, which fires only for a
handle that exports an exposition of its own. The exposition is that other
library's to publish.

Two pipelines on one host collide unless they name different addresses, or one
of them names `none` — left alone, both take the same default. Failing to take
an address stops the start and names the address it wanted.

Ordering is handled for you under the builder. Assembling by hand puts it back
in your hands — see [Manual assembly](../03-guides/manual-assembly.mdx).

## Conventions you can rely on

- **Prefix**: all framework metrics start with `spate_`; process metrics
  (`process_*`) follow their own standard. Counters end in `_total`; units
  get suffixes (`_seconds`, `_bytes`, `_rows`).
- **Standard labels on every framework metric**:
  - `pipeline` — the `pipeline.name` from config;
  - `component` — the instance id (e.g. `orders_source`, `main.deserializer`);
  - `component_type` — the implementation, which for a connector is the system
    it talks to and for an operator is its kind (`map`, `filter`); custom sinks
    set it via `SinkParts::with_component_type`.
- **Cardinality is mostly opt-in**: `partition`-labeled series appear only
  with `metrics.per_partition_detail: true` (default `false`), because their
  cardinality grows with the assignment. The one exception is
  `spate_source_lag_records`, which is always per partition — consumer lag has
  no aggregate series to fall back to, so a cardinality knob is not allowed to
  delete it. Budget one series per assigned partition per member for that
  family even on the default config. `shard` and `replica` labels are bounded
  by your cluster topology and always on.

## The hot-path discipline

These rules keep instrumentation off the per-record path, and they bind your
custom metrics as much as the framework's:

1. **Pre-register handles at build time.** Resolve metric names and labels
   once, keep the returned handle, and only touch the handle afterwards.
   Never call `metrics::counter!(...)` with computed labels inside the
   record loop.
2. **Count at batch boundaries.** Counters increment once per batch with
   the batch's totals; per-record durations are observed as batch means
   (duration divided by n), never per record.

The rules in one place:
[`custom_metrics.rs`](repo:crates/spate/examples/custom_metrics.rs) puts custom
handles side by side with a framework stage handle, prints the exposition it
produced, and runs as-is with `cargo run -p spate --example custom_metrics`.
Its raw-facade handles are the smallest form of the pattern:

```rust file=crates/spate/examples/custom_metrics.rs region=facade
```

## Starting alerts

These catch the failure modes that matter most; verify thresholds
against your latency budget. The full list of starting points is at the end
of [Metrics](../../METRICS.md).

- **Stuck pipeline (watermark stall)** —
  `spate_checkpoint_watermark_age_seconds > 300` while
  `rate(spate_source_records_total[5m]) > 0`. The watermark age is the age of
  the oldest unacknowledged batch; a failed batch stalls its partition's
  watermark rather than silently advancing (the at-least-once invariant),
  so this is the primary "data is flowing but nothing is committing"
  signal. The pipeline self-terminates after
  `checkpoint.stalled_fail_after` (default 120s) behind a permanently
  failed batch, but you want the alert regardless — restarts that don't
  clear the cause will loop.
- **Abandoned sink batches** —
  `increase(spate_sink_abandoned_batches_total[10m]) > 0`. A batch is
  abandoned when a fatal error class or exhausted `retry.max_attempts`
  ends its write, when a write task panics, or when a drain deadline
  expires at shutdown with the sink still down. Its data replays after
  restart, so this is a duplicates-incoming signal, not data loss. Only
  the last of those three is a shutdown event, so read the class
  breakdown on `spate_sink_errors_total{error_type}` before reaching for
  sink liveness: a dropped target table, revoked credentials or a schema
  mismatch abandons in steady state with no drain in sight.
- **Sustained backpressure** — `spate_backpressure_paused == 1` sustained
  (e.g. `avg_over_time(spate_backpressure_paused[10m]) > 0.9`). The source is
  paused because the in-flight budget is above its high watermark: the sink
  cannot keep up, or the budget is undersized for the batch settings — see
  the sizing rule in [Tuning](tuning.mdx).
- **A shard asleep between retries** — `spate_sink_retry_backoff_seconds`
  sustained above `(1 - retry.jitter) * retry.max`. The shard is not idle, it
  is parked between write attempts; with an unbounded `retry.max_attempts` it
  will stay there. The retry *counter* goes flat while this happens (it only
  moves on an attempt), which is exactly why the gauge exists. Threshold below
  the ceiling rather than at it: jitter only shortens a delay, so the published
  step never sits exactly on `retry.max`. This covers backoff against a replica
  that is still available — when every replica is quarantined the shard sleeps
  waiting for a probe instead, and `spate_sink_shard_healthy == 0` is the
  signal for that.
- **A slow sink** — the p99 of
  `spate_sink_write_duration_seconds{outcome="ok"}` above your write budget.
  Reach for this one, not `spate_sink_flush_duration_seconds`: flush spans seal
  to settle and carries the wait for an `inflight.max_per_shard` slot and every
  backoff sleep on top of the write, so it fires on a saturated pipeline as
  readily as on a slow server. The sink-latency families each answer a
  different question — permit wait says *queued*
  (`spate_sink_permit_wait_duration_seconds`), backoff says *asleep between
  attempts* (`spate_sink_retry_backoff_seconds`), shard health says *no
  replica is usable* (`spate_sink_shard_healthy == 0`, where the backoff gauge
  reads `0`) — which covers both waiting for a probe and writing one, so it is
  the wider signal rather than an "asleep" one — write says *slow*, and
  `spate_sink_flush_duration_seconds` is all of them at once, which makes it a
  commit-lag budget rather than a diagnosis. See [What a flush
  contains](../../METRICS.md#what-a-flush-contains).

  Before escalating a high write p99 to whoever runs the server, rule out the
  sink's own I/O runtime: the measurement is wall-clock across the write call,
  so it charges time the runtime spent elsewhere. Where a sink does its own
  request compression on that runtime, high byte rates can make the runtime the
  limit rather than the server — `io_threads` is the lever there.

For alerting on skipped records (schema drift, poison messages), replica and
shard health, and queue saturation, use the `*_dropped_total`,
`spate_sink_replica_healthy`, `spate_sink_shard_healthy` (0 = no circuit-closed
replica left in the shard — the whole-shard outage escalation, with
`spate_sink_replica_errors_total` attributing the failures per endpoint), and
`spate_queue_full_events_total` series described in
[Metrics](../../METRICS.md).
