# Scaling out

One process runs one pipeline. Scaling *up* means threads and shards
(see [Tuning](tuning.mdx)); scaling *out* means several
identical replicas dividing one source's work. How that division happens
depends on the source:

| Source kind | Scale-out story |
|---|---|
| Brokered | Native: the source's own group protocol divides the work across replicas. Nothing extra to deploy. |
| Coordinated | Native via the [coordination seam](../02-concepts/07-source-coordination.mdx): the elected leader plans the work into splits once, and replicas lease the splits it assigns them, hand them back on reassignment, and take over dead workers' splits — all with fenced per-split commits. Deploy a [coordination store](../04-connectors/coordination/README.mdx) and run N replicas. |
| Custom | Bring a planner and hand the source a coordinator. See [custom sources](../06-extending/custom-source.mdx#coordination-aware-sources). |

:::note Connector specifics
Which kind each shipped source is, and how to wire it:
[Kafka source](../04-connectors/sources/kafka/README.mdx) (brokered) ·
[S3 source](../04-connectors/sources/s3/README.mdx#scaling-out--and-the-solo-default)
(coordinated) ·
[Datagen source](../04-connectors/sources/datagen/README.mdx#delivery-semantics)
(neither — every replica generates its own stream from offset 0).
:::

The rest of this page is about the coordinated case: what a fleet does, what it
costs, and how it fails. The store itself is a connector with its own page —
requirements, provisioning, and outage behavior live there, not here.

## Deploying the fleet

The coordinator is assembly wiring — there is no `coordination:` YAML on the
source ([why](../07-reference/configuration.mdx#code-level-knobs-not-yaml)).
What deployment has to guarantee is narrower than it looks:

- **Every replica runs the same binary with the same source config.** A
  coordinated source folds its identity-bearing settings into a **job
  fingerprint**, and a worker whose fingerprint differs is rejected at startup
  with both fingerprints in the message. That is a feature: a half-upgraded
  fleet cannot quietly plan the job two different ways.
- **Every replica points at the same store, under the same job name.** The job
  name is what separates two coordinated jobs sharing one store.
- **Every live replica has a distinct `instance_id`.** Two live processes
  sharing one is detected and fatal.

## Kubernetes

A plain `Deployment` — no StatefulSet, no persistent volumes, no
per-replica configuration:

- **`instance_id` from the pod name.** It must be unique per live
  replica; a stable identity lets a restarted pod reclaim its own splits
  instantly instead of waiting out the lease. Two live processes sharing
  an id is detected and fatal. (A pod name is already unique per live
  replica; the id charset is `[A-Za-z0-9_-]`, 1–128 bytes, so a name
  containing dots is rejected — substitute them, e.g. with `-`.)
- **`terminationGracePeriodSeconds` > drain timeout.** A SIGTERM'd
  replica drains, commits, and releases its splits on the way out, so
  peers pick them up immediately; a SIGKILL'd one is covered by lease
  expiry instead.
- Readiness/liveness probes are unchanged (the admin server's endpoints).

Scaling events are *cooperative* rebalances, but the decision is central
rather than pairwise. The elected leader computes a
desired assignment for the whole fleet — balanced on split **weight**, not
split count, since one large unit of work can outweigh several small ones — and
publishes it as one `assign.{instance}` record per live worker. Every
worker then reconciles toward its own record: claim what is named and not
yet held, revoke what is held and no longer named. Workers never choose
for themselves, so there is nothing to negotiate and no one to out-race.

The assignment is deliberately sticky. A move costs a drain, so the leader
keeps every split whose owner is still alive where it is, fills unassigned
work to the least-loaded worker heaviest-first, and only then moves splits
that strictly reduce imbalance. Feeding the result back in reproduces it,
which is why a steady fleet republishes nothing and therefore drains
nothing.

### What a rebalance costs {#what-a-rebalance-costs}

A rebalance move is a **cooperative revocation**. The split leaves one
worker's assignment, and that worker stops intake for it at a safe boundary of
the source's choosing, lets everything it already emitted reach the sink and
acknowledge, commits the final watermark, and releases the split. The new
owner resumes from exactly that commit — **a cooperative revocation
replays nothing**. Its cost is latency, not rows: the drain is bounded by
the split's in-flight depth — whatever the source had already read past the
boundary, plus queued-but-unacked records.

`drain_deadline` (default 10s) is what stops one wedged drain from pinning
a rebalance open. A source that declines to stop at a safe boundary, or a
drain still running when the deadline elapses, has its release **forced**:
the split goes back the replaying way instead of the clean one. (If the
leader takes the move back mid-drain the revocation is cancelled and the
deadline stops applying — nothing is waiting for the split. The drain is
then bounded by silence instead: no commit at all for `drain_deadline` and
it is released anyway, so a wedged drain cannot leave a split owned with
nothing reading it.) Its next
owner resumes from the last *committed* watermark and re-reads what came
after, so a forced revocation costs up to one commit interval
(`checkpoint.interval`) of duplicates. A decline is forced immediately
rather than after the deadline — the source has already said the answer
will not change.

Unlike the peer-to-peer protocol this replaced, a revocation does not
require the split to have committed once already: the drain manufactures
the resume point, so even a freshly-claimed fleet rebalances cleanly.

### When a rebalance happens {#when-a-rebalance-happens}

Whenever the leader observes a fleet or plan change that its assignment
pass can improve on: a replica joining or leaving, splits completing, a
new plan generation. A replica that joins with nothing claimable is given
work by the next assignment, not by asking for it.

A departing worker's splits are withheld from reassignment for
`rebalance_delay` (default 20s) so a pod bounce reclaims its own work
instead of the fleet churning around it; the window is cancelled the
moment the instance reappears, so a fast restart costs nothing. Setting it
to zero reassigns immediately — supported, not a disabled feature.

A bounded job that completes before a transfer lands finishes on the
instance that claimed it — zero replay, which for a short job is the
cheapest outcome available, not a scheduling failure. Instances only
genuinely share a job whose runtime spans several assignment cycles.

#### Time to balance {#time-to-balance}

One move costs a drain plus the store round trips to publish the
assignment, release the split, and claim it on the other side:

```
one move ≈ the losing worker's drain + a few store round trips
```

Nothing paces the moves against each other: the leader publishes the whole
assignment at once, and every affected worker starts its drain on the
observation that carries its own record, so moves that involve different
workers run concurrently at store latency. `lease_duration` does not gate
this path at all — it is the failover timer, not the rebalance timer.

The drain is usually the larger term, and it is set by how fast the losing
worker's sink can absorb what it has already read, not by anything in the
coordination layer. Measure before reaching for a knob:
`spate_coordination_drain_duration_seconds` on the losing side and
`spate_coordination_assignment_latency_seconds` on the gaining side. Those
are **two families on purpose** — they are recorded in different processes
against separately-observed assignment records, so they neither nest nor
add; read each on the worker that reports it. A drain p99 approaching
`drain_deadline` is the signal that forced (replaying) revocations are
about to start.

If drains are the constraint, the lever is the sink, not the coordinator:
give it headroom, or raise `drain_deadline` so slow drains finish cleanly
instead of being forced. Raising the deadline trades a longer rebalance
for fewer duplicates. It may exceed `lease_duration` — a draining split is
still owned and still heartbeated, so a long drain does not race its own
lease. The one floor startup enforces is `op_timeout`: a deadline shorter
than a single store round-trip would force every revocation before its
final commit could land.

Near the end of a bounded job the assignment re-arms as splits complete,
so a nearly-done split can move more than once before it finishes — but
each hop drains first, so endgame churn costs latency, never rows.
Stickiness keeps this rare. Replayed duplicates among live workers come
only from forced revocations; crash takeover (lease expiry) remains the
irreducible at-least-once replay.

## Tuning

| Knob | Default | Description |
|---|---|---|
| `lease_duration` | 30s | Takeover latency after an ungraceful death. Heartbeats run at a third of it. Lower = faster failover, more store traffic, more sensitivity to pauses. |
| `max_in_flight` | 8 | The working set: splits a worker holds (and processes) at once — also its data-lane count. Size it like a thread pool. |
| `max_attempts` | 4 | Failing tenancies before a split is quarantined. |
| `replan_interval` | 60s | How often the leader re-runs an open plan (growing inputs). Final plans stop replanning. |
| `instance_id` | random | Stable identity for instant reclaim after restarts. Use the pod name. |
| `rebalance_delay` | 20s | How long the leader withholds a departed instance's splits before reassigning them, so a pod bounce reclaims its own work instead of the fleet churning around it. Cancelled early when the instance returns. 0 reassigns immediately. |
| `drain_deadline` | 10s | How long a revoked split may keep draining before the release is forced (and its uncommitted tail replays). Doubles as the no-progress timeout over a drain whose revocation was cancelled: that one is forced only if it commits nothing at all for this long. Larger = more patience with slow-draining sinks, slower rebalances; smaller = faster rebalances, more duplicates. May exceed `lease_duration` — a draining split is still heartbeated, so a long drain does not race its own lease; size it against how long the sink takes to flush a split's tail. See [time to balance](#time-to-balance). |

Split sizing: aim for roughly uniform-cost splits in the tens-of-MB to
~128 MB range (or the row-count equivalent) — big enough that lease
traffic is noise, small enough that takeovers and reassignments move
useful quanta of work. For most sources that is the planner's design rather
than a knob; a source whose input sizes vary widely may expose a target, in
which case its own page documents it.

## Failure modes

| Failure | What happens |
|---|---|
| Replica killed (OOM, node loss) | Its leases expire after one `lease_duration`; peers claim the splits and **resume from the last committed progress**. The uncommitted tail replays: duplicates, never loss. |
| Replica drained (SIGTERM) | Final commit, then release: peers claim immediately, no lease wait, no attempt consumed. |
| Zombie resumes after takeover | Its next commit loses the record CAS: nothing written, split reported lost locally. The duplicate window is at most one commit interval. |
| Leader dies | Any worker takes the leadership lease after it expires, bumps the plan generation (fencing any in-flight stale plan write), and re-runs the planner — idempotently: deterministic split ids make replanning a no-op for existing splits. |
| Coordination store unreachable | Commits go retryable; workers self-fence their splits after one lease without a successful write; everything resumes on reconnect. |
| Poison split | Consumes one delivery attempt per failing tenancy; quarantined at the cap. A bounded job with quarantined splits ends **stalled** (fatal by default), never falsely complete. Watch `spate_coordination_splits_quarantined`. |
| Scale-up | The leader folds the new replicas into the next assignment and moves splits toward weight balance. Each move is a cooperative revocation — the losing worker drains and commits before releasing, so it replays nothing; a drain that is declined or outruns `drain_deadline` is forced instead, at a cost of up to one commit interval of duplicates. See [rebalance cost](#what-a-rebalance-costs). |
| Config divergence | A worker whose planner fingerprint differs is rejected at startup with both fingerprints in the message. |
| Duplicate `instance_id` | Two live twins would ping-pong reclaims forever; the protocol detects the foreign process on the shared id and stops with a fatal, actionable error. |

## Observability

The `spate_coordination_*` families (see
[Metrics](../../METRICS.md))
carry the whole story: `splits_owned` per worker, `live_workers` for the
fleet view, `leader` for who plans, `acquisitions_total` by reason
(`create`/`reclaimed`/`expired`/`reassigned` — `reassigned` is
the healthy rebalance path, `expired` means a worker died),
`revocations_total` by outcome (`requested`/`drained`/`forced`/`cancelled`,
all on the worker giving the split up — `drained` is replay-free, a rising
`forced` means drains are being cut short, so look at that worker's sink
health and `drain_deadline`, and `cancelled` is the leader taking a move
back, which is only worth chasing if it is sustained: membership is
flapping faster than a drain takes), `split_losses_total`
(`fenced`/`starved`/`revoked`), `splits_quarantined` for poison, and
store-op latency histograms for the round-trips to the store.

Time to balance reads from two separate families, one per side:
`drain_duration_seconds` on the worker losing a split and
`assignment_latency_seconds` on the worker gaining one. They are recorded
in different processes and do not compose — do not add or subtract them.
`splits_draining` shows whether a worker is stuck mid-drain while the
fleet is visibly uneven — it counts drains, so a drain left behind by a
cancelled revocation keeps showing until it lands. `spate_coordination_writes_total{outcome="conflict"}`
is fencing working as designed — alarming only in bulk.

Two families were renamed when coordination moved to leader-assigned
balancing: `handoffs_total` → `revocations_total` (new label set), and the
old `revocations_total` → `split_losses_total`. Dashboards carrying the old
names need updating; `handoff_duration_seconds` and `handoffs_in_flight`
are gone entirely.

## Upgrading from the work-stealing balancer

Leader-assigned coordination replaced a peer-to-peer work-stealing
balancer. [ADR-0038](../../adr/0038-leader-computed-sticky-assignment.md) records why; this section is
what an upgrade actually requires.

### The store must be empty (or new)

The on-store record schema went from 2 to 3. **The versions do not
interoperate, and a schema-3 worker will not read a schema-2 store at
all** — it reads the plan record during startup, finds the wrong schema
version, and exits fatally with `upgrade or isolate the store prefix`. The
same pin covers every `spec.` and `split.` record.

So "stop the fleet, restart it on the new build" is *not* sufficient: point
the new fleet at a fresh job name, or an empty store. That discards
committed per-split progress, so an in-flight bounded backfill restarts
from the beginning. Delivery is at-least-once either way — the re-run
duplicates, it does not lose — but drain a job to completion before
upgrading if you would rather not pay for it.

### Configuration

`handoff_rounds` and `handoff_max_grants` are gone; `rebalance_delay`
(default 20s) and `drain_deadline` (default 10s) replace them. Because
`CoordinationConfig` is `deny_unknown_fields`, a YAML file still carrying
the old keys fails to parse rather than silently ignoring them.

One new floor can reject a config you did not change: `drain_deadline` must
be at least `op_timeout`, and both default to 10s. If you raised
`op_timeout` for a slow store, raise `drain_deadline` to match.

### Metrics

| Was | Now |
|---|---|
| `spate_coordination_handoffs_total{outcome}` | `spate_coordination_revocations_total{outcome}` — new label values (`requested`/`drained`/`forced`/`cancelled`) |
| `spate_coordination_revocations_total{reason}` | `spate_coordination_split_losses_total{reason}` — **the old name now means something else**, so an unchanged dashboard silently reads the wrong series |
| `spate_coordination_handoff_duration_seconds{phase}` | `spate_coordination_drain_duration_seconds` and `spate_coordination_assignment_latency_seconds` — two families that [do not compose](../../METRICS.md#the-two-coordination-latencies-do-not-compose) |
| `spate_coordination_handoffs_in_flight` | `spate_coordination_splits_draining` |
| `acquisitions_total{reason="stolen"}` | gone — there is no steal path |
| `acquisitions_total{reason="handoff"}` | `acquisitions_total{reason="reassigned"}` |
| `acquisitions_total{reason="released"}` | folded into `reassigned` — a claiming worker cannot tell a drained revocation from a shutdown hand-back, and a label it cannot populate is a series that reads zero |

### Rust API

Only relevant if you implement the seam yourself or read the metric
handles directly:

- `CoordinationEvent::HandoffRequested` → `RevokeRequested`.
- `SplitSource::begin_handoff`/`handoff_ready` → `begin_revoke`/`drain_ready`,
  and `SplitCoordinator::release_handoff`/`decline_handoff` →
  `release_drained`/`decline_revoke`. Renamed methods that you *overrode*
  fail to compile; ones you left defaulted do not — and the default
  `begin_revoke` declines, which now costs a forced revocation and a
  replayed tail on every rebalance rather than merely declining an offer.
- `HandoffOutcome` and `HandoffPhase` are deleted, along with the
  `L_PHASE` label constant and `AcquireReason::{Stolen, Released}`.
  `AcquireReason::Handoff` is now `Reassigned`.
- `CoordinationMetrics::handoff` → `revocation`;
  `handoff_duration(phase, d)` splits into `drain_duration(d)` and
  `assignment_latency(d)`; `set_handoffs_in_flight` → `set_splits_draining`.
- `SplitSpec::weight` kept its name, type and default but changed meaning:
  it was an ordering hint over count-based balancing, and it is now the
  balance objective itself. A planner that populated it as a ranking key
  rather than a cost will skew the leader's distribution — with no compile
  error to warn you.
