# Scaling out

One process runs one pipeline. Scaling *up* means threads and shards
(see [Tuning](tuning.mdx)); scaling *out* means several
identical replicas dividing one source's work. How that division happens
depends on the source:

| Source kind | Scale-out story |
|---|---|
| Brokered | Native: the source's own group protocol divides the work across replicas. Nothing extra to deploy. |
| Feed-reading | Workers read [work units](../07-reference/glossary.mdx#work-unit) from a durable [feed](../04-connectors/feeds/README.mdx) that one [lister](../07-reference/glossary.mdx#lister) run per job fills. Nothing elects a leader. See [Reading from a feed](#reading-from-a-feed). |
| Custom | A source reads [work units](../07-reference/glossary.mdx#work-unit) from a feed. See [custom sources](../06-extending/custom-source.mdx#feed-reading-sources). |

Which kind each shipped source is, and how to wire it:

## Reading from a feed

Every worker runs one binary and one pipeline file, keeps no volume and never
lists. The job's [lister](../07-reference/glossary.mdx#lister) is a run of the
same binary in lister mode: it reads the workers' pipeline file, builds no sink,
lists the input once, publishes its units to the feed and exits. Its checkpoint
sits at the [job location](../07-reference/glossary.mdx#job-location), so no
process needs a volume. Nothing elects a leader, and nothing fences a second
lister run, so run one per job.

On Kubernetes:

- **The lister run as a `Job`.** The pod's exit status reports the run, a
  failed run exits non-zero, and the Job's restart policy and back-off limit
  run it again, each run resuming after the checkpoint. Set
  `activeDeadlineSeconds` to bound the run as a whole, since the lister adds
  no deadline of its own beyond its feed's and store's limits.
- **A bounded job's workers with a fixed count**, as a `Job` with a fixed
  `parallelism` or a `Deployment` with fixed replicas, or under a scaler whose
  minimum is one. A bounded job's workers end it themselves, each exiting zero
  once [its end check](../02-concepts/09-work-feed.mdx#how-a-bounded-job-ends)
  passes, so a `Job` reports the job's outcome. A scaler that removes every
  worker when the feed reads empty ends the job with no exit status, and a unit
  a stopped worker held then has no reader when the feed delivers it again.
- **Continuous workers as a `Deployment`.**

Start the lister first, or the workers at most one settling window (five minutes
unless `settling_window` sets another) before it: a worker of a bounded job
exits when no job fingerprint appears at the job location within that window. On
a feed that charges a delivery attempt to a worker waiting for the fingerprint,
start the lister first. A lister run builds its feed with the backend's
publish-only handle where it has one, so it joins no group the workers read and
is charged no attempt.

## Failure modes

| Failure | What happens |
|---|---|
| Worker killed (OOM, node loss) | The units it held come back after the feed's redelivery delay and another worker reads each again from its start. The records it had not yet acknowledged replay: duplicates, never loss. |
| Worker drained (SIGTERM) | It reads the units it holds that it can finish by 5s before the drain deadline, and hands back the rest, which another worker reads again from its start. |
| Worker stopped, then another reads its unit | Nothing fences a stopped worker, so two workers can emit the same unit. The sink sees those records twice. |
| A unit that fails on every read | The feed delivers it until the delivery cap and then moves it to its dead-letter destination. A bounded job with dead letters ends **stalled**, never falsely complete. |
| Lister run fails | It exits non-zero. Run again, it resumes after its checkpoint at the job location. |

## Observability

Which worker holds how much of the job shows in `spate_source_lanes_active`
and `spate_source_rebalances_total` (see [Metrics](../../METRICS.md)). A
bounded job that ends with dead letters reports it as a stalled end. The depth
of the feed's dead-letter destination is read from the backend that holds it.
