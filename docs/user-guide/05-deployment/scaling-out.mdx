# Scaling out

One process runs one pipeline. Scaling *up* means threads and shards
(see [Tuning](tuning.mdx)); scaling *out* means several
identical replicas dividing one source's work. How that division happens
depends on the source:

| Source | Scale-out story |
|---|---|
| Kafka | Native: run N replicas in one consumer group; the broker assigns partitions. Nothing extra to deploy. |
| S3 backfill | Native via the coordination seam: the elected leader lists the prefix once and packs it into splits; replicas lease, steal, and take over splits with fenced per-split commits. Wire a coordinator into the source (below) and run N replicas. |
| Custom broker-less sources | The [coordination seam](../02-concepts/07-source-coordination.mdx): a planner, the `CoordinationDriver`, and a coordinator backend. See [custom sources](../06-extending/custom-source.mdx#coordination-aware-sources). |

The rest of this page covers deploying the coordination backend that
broker-less sources share.

## Wiring the S3 source

The coordinator is assembly wiring — no `coordination:` YAML on the
source ([why](../07-reference/configuration.mdx#code-level-knobs-not-yaml)).
Every replica runs the same binary with the same source config (`url`,
`compression`, `split_target_bytes`, and `refresh_listing` are part of
the job fingerprint and must match byte-exactly), plus a coordinator over
the shared store:

```rust
use etl::coordination::store::nats::{NatsConfig, NatsStore};
use etl::coordination::{CoordinationConfig, StoreCoordinator};

let pipeline = Pipeline::from_config(config)?;
let tuning = CoordinationConfig {
    instance_id: std::env::var("POD_NAME").ok(), // unique per replica
    ..CoordinationConfig::default()              // lease 30s, max_in_flight 8, …
};
let store = NatsStore::new(
    NatsConfig::new(vec![std::env::var("NATS_URL")?], "exports-backfill"),
    tuning.lease_duration, // one value drives store TTL and lease — must match
)?;
let coordinator = StoreCoordinator::new(store, tuning, pipeline.io_handle(), None)?;
let source = S3Source::from_component_config(&pipeline.config().source, pipeline.io_handle())?
    .with_framer(|| Box::new(NdjsonFramer::new(64 << 20)))
    .with_coordinator(Box::new(coordinator));
```

(The `etl` facade needs the `coordination-nats` feature for the NATS
store; `coordination` alone gives the in-memory store and the seam.
Runnable two-instance version:
`crates/etl/examples/s3_coordinated_backfill.rs`.)

## NATS: the coordination store

Coordinated instances meet in a NATS JetStream key-value store. Records
never flow through it — it carries split records, leases, and the plan,
at a request rate of roughly one small write per held split per third of
a lease (a handful of writes per second per worker).

Requirements:

- **NATS server ≥ 2.11** with JetStream enabled (`-js`). The lease
  protocol rides on per-message age limits and KV limit markers, which
  shipped in 2.11 — the worker verifies the version at startup and fails
  actionably against an older server.
- One **job name** per coordinated job (the `job` field): it suffixes the
  two KV buckets (`etl_coordination_{job}_state` / `..._lease`). Two
  different jobs must never share one; a fingerprint check rejects
  misconfigured workers before they can touch anything.

Development and CI: a single `nats:2.11` container is enough —

```yaml
# docker-compose.yml
services:
  nats:
    image: nats:2.11-alpine
    command: ["-js"]
    ports: ["4222:4222"]

  pipeline:
    image: your-pipeline
    deploy: { replicas: 2 }
    environment:
      NATS_URL: nats://nats:4222
      # instance_id from the container hostname — unique per replica
```

Production HA: a 3-node NATS cluster with JetStream and `replicas: 3` on
the NATS store config (`NatsConfig`, not the `coordination:` tuning
section below), so the buckets survive a NATS node loss. What a
full NATS outage does to the pipeline: heartbeats fail, workers
**self-fence** after one lease without a successful write (they stop
their splits rather than run unfenced), commits surface as retryable, and
everything resumes where it left off when the store returns — degraded,
never corrupted.

## Kubernetes

A plain `Deployment` — no StatefulSet, no persistent volumes, no
per-replica configuration:

- **`instance_id` from the pod name.** It must be unique per live
  replica; a stable identity lets a restarted pod reclaim its own splits
  instantly instead of waiting out the lease. Two live processes sharing
  an id is detected and fatal. (Pod names contain dots' worth of
  uniqueness already; the id charset is `[A-Za-z0-9_-]` — substitute any
  dots.)
- **`terminationGracePeriodSeconds` > drain timeout.** A SIGTERM'd
  replica drains, commits, and releases its splits on the way out, so
  peers pick them up immediately; a SIGKILL'd one is covered by lease
  expiry instead.
- Readiness/liveness probes are unchanged (the admin server's endpoints).

Scaling events behave like Kafka's *cooperative* rebalances: a new
replica claims unowned splits first, then asks the most-loaded worker to
hand splits over — up to `handoff_max_grants` at a time — until balanced.
A scaled-down replica's released splits are claimed within milliseconds.

### What a rebalance costs {#what-a-rebalance-costs}

A rebalance move is a **cooperative handoff**: the under-target replica
writes a request naming the most-loaded worker, and that victim stops
intake for one split (at an object boundary, for S3), lets everything it
already emitted reach the sink and acknowledge, commits the final
watermark, and releases the split. The new owner resumes from exactly
that commit — **a granted handoff replays nothing**. Its cost is
latency, not rows: the drain is bounded by the split's in-flight depth
(the remainder of the object being read plus queued-but-unacked
records).

The lease steal remains as the fallback for a victim that cannot answer
— dead, wedged, or paused. A request unanswered for `handoff_rounds`
heartbeat rounds (up to one `lease_duration` at the default of 3) falls back
to stealing the lease out from under the owner. A stolen split's new
owner resumes from the last **committed** watermark and re-reads what
came after it, so a fallback steal costs up to one commit interval
(`checkpoint.interval`) of duplicates — and only a split that has
committed at least once can be stolen, because one that has not would
replay in full.

Handoff requests do not wait for that first checkpoint: the grant's
drain-and-commit manufactures the resume point a steal would have to
wait for, so even a freshly-claimed fleet can rebalance cooperatively.

### When a rebalance happens {#when-a-rebalance-happens}

A replica that joins with nothing claimable requests a handoff as soon as
it has observed the fleet — requests are not rate-limited, because the
request key admits exactly one requester per victim and the losers find
out immediately. A bounded job that completes before the transfer lands
finishes on the instance that claimed it — with zero replay, which for a
short job is the cheapest outcome available, not a scheduling failure.
Instances only genuinely share a job whose runtime spans several lease
cycles; if sharing short jobs matters more than anything else, shrink
`lease_duration` rather than adding replicas.

#### Time to balance {#time-to-balance}

A batch of moves costs about one victim drain, plus the store round trips
to ask for it and to claim what comes back:

```
batches to balance ≈ ceil(moves needed / handoff_max_grants)
one batch          ≈ the victim's drain + a few store round trips
```

Asking is not paced by the lease: a worker opens its request on the
observation that put it under target, and the victim answers on the
observation that carries the request, so the happy path runs at store
latency. `lease_duration` sets only the *fallback* — how long an
unanswered request waits before it degrades into a replaying steal, at
`handoff_rounds` rounds of `lease_duration / 3` (jittered) each.

The drain is usually the larger term, and it is set by how fast the
victim's sink can absorb what it has already read — not by anything in
the coordination layer. That is worth measuring before reaching for a
knob: `etl_coordination_handoff_duration_seconds` splits the wait into
`phase="request"` and `phase="drain"`. Note the two are **nested, not
additive** — `request` is measured from going under target to claiming
the split, so it already contains the `drain`. Their difference is what
admission and the claim cost; if that difference is small, the drain is
the whole story.

Raising `handoff_max_grants` overlaps drains, so it helps when a victim
has several splits to give and its sink has headroom. It will not help
when that sink is the constraint: concurrent drains share it, and
finishing them together does not make them finish sooner.

Near the end of a bounded job the balance re-arms as splits complete, so
a nearly-done split can move more than once before it finishes — but
each hop drains before handover, so endgame ping-pong costs latency,
never rows. Replayed duplicates among live workers come only from
fallback steals; crash takeover (lease expiry) remains the irreducible
at-least-once replay.

## Tuning

| Knob | Default | Meaning |
|---|---|---|
| `lease_duration` | 30s | Takeover latency after an ungraceful death. Heartbeats run at a third of it. Lower = faster failover, more store traffic, more sensitivity to pauses. |
| `max_in_flight` | 8 | The working set: splits a worker holds (and processes) at once — also its data-lane count. Size it like a thread pool. |
| `max_attempts` | 4 | Failing tenancies before a split is quarantined. |
| `replan_interval` | 60s | How often the leader re-runs an open plan (growing inputs). Final plans stop replanning. |
| `instance_id` | random | Stable identity for instant reclaim after restarts. Use the pod name. |
| `handoff_rounds` | 3 | Heartbeat rounds a handoff request may stay unanswered before falling back to a lease steal (up to one lease at the default). Larger = more patience with slow-draining victims; smaller = faster escape from wedged ones. |
| `handoff_max_grants` | 2 | Splits a victim drains away at once. Higher = fewer rounds to balance when a victim has several splits to give — but the drains share that victim's sink, so it buys nothing when the sink is the bottleneck, and a bigger intake dip while they run. 1 restores strictly one-at-a-time handoffs. See [time to balance](#time-to-balance). |

Split sizing: aim for roughly uniform-cost splits in the tens-of-MB to
~128 MB range (or the row-count equivalent) — big enough that lease
traffic is noise, small enough that takeovers and steals move useful
quanta of work. For most sources that is the planner's design, not a
knob; the S3 source exposes it as `split_target_bytes` (default 64 MiB)
because object sizes vary wildly between prefixes.

## Failure modes

| Failure | What happens |
|---|---|
| Replica killed (OOM, node loss) | Its leases expire after one `lease_duration`; peers claim the splits and **resume from the last committed progress**. The uncommitted tail replays: duplicates, never loss. |
| Replica drained (SIGTERM) | Final commit, then release: peers claim immediately, no lease wait, no attempt consumed. |
| Zombie resumes after takeover | Its next commit loses the record CAS: nothing written, split reported lost locally. The duplicate window is at most one commit interval. |
| Leader dies | Any worker takes the leadership lease after it expires, bumps the plan generation (fencing any in-flight stale plan write), and re-runs the planner — idempotently: deterministic split ids make replanning a no-op for existing splits. |
| NATS unreachable | Commits go retryable; workers self-fence their splits after one lease without a successful write; everything resumes on reconnect. |
| Poison split | Consumes one delivery attempt per failing tenancy; quarantined at the cap. A bounded job with quarantined splits ends **stalled** (fatal by default), never falsely complete. Watch `etl_coordination_splits_quarantined`. |
| Scale-up | New replicas claim unowned work, then request cooperative handoffs from loaded peers toward ±1 balance. A granted handoff drains and commits before the transfer, so it replays nothing; a victim that cannot answer within `handoff_rounds` loses a committed split to the fallback steal at a cost of up to one commit interval — see [rebalance cost](#what-a-rebalance-costs). |
| Config divergence | A worker whose planner fingerprint differs is rejected at startup with both fingerprints in the message. |
| Duplicate `instance_id` | Two live twins would ping-pong reclaims forever; the protocol detects the foreign process on the shared id and stops with a fatal, actionable error. |

## Observability

The `etl_coordination_*` families (see
[METRICS.md](https://github.com/marcuskainth/etl-rs/blob/main/docs/METRICS.md))
carry the whole story: `splits_owned` per worker, `live_workers` for the
fleet view, `leader` for who plans, `acquisitions_total` by reason
(`create`/`released`/`reclaimed`/`expired`/`stolen`/`handoff`),
`handoffs_total` by outcome (`requested`/`granted`/`timeout`/`aborted` —
`granted` moves are replay-free; a rising `timeout` means fallback
steals are happening, so look at the victims' sink health),
`revocations_total` (`fenced`/`starved`), `splits_quarantined` for
poison, and store-op latency histograms for the NATS round-trips.
`handoff_duration_seconds` by `phase` is the time-to-balance view —
`request` on the asking side, `drain` on the giving side — and
`handoffs_in_flight` shows whether a victim is sitting at
`handoff_max_grants` (the cap is pacing rebalances) or at zero while the
fleet is visibly uneven (requests are not arriving at all).
`etl_coordination_writes_total{outcome="conflict"}` is fencing working as
designed — alarming only in bulk.
