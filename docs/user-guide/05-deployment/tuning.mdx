# Tuning

Every knob below has a safe default; most pipelines change two or three of
them. This page covers what each one moves and how to size them together.
The build settings take their defaults from Cargo and your platform. The
defaults quoted for the pipeline's own settings are the exact values from
[`spate-core/src/config/mod.rs`](repo:crates/spate-core/src/config/mod.rs) and
the sink config structs (also tabulated in the
[configuration reference](../07-reference/configuration.mdx)).

## Where to start

Tune **vertically first, then scale out**. A single process that is not yet at
its CPU, memory, or network limit is the cheapest throughput you will ever get,
and scaling out before you reach that limit multiplies the wrong thing.

The loop is:

1. **Find which side binds.** A pipeline is source-bound, chain-bound,
   queue-bound or sink-bound at any moment, and the metrics say which. See
   [Which side binds](./monitoring.mdx#which-side-binds). Guessing here is the
   most common way tuning time gets wasted.
2. **Raise the binding side** using that component's knobs.
3. **Re-measure.** The bottleneck usually moves rather than disappearing: a
   source that was starving the chain will, once fixed, start saturating the
   sink.
4. **Repeat until a physical resource is saturated**: CPU cores busy, memory
   at the pod limit, or the NIC/broker link full.
5. **Only then scale horizontally**, by adding replicas.

### What vertical scaling buys beyond throughput

Throughput is not the only thing that improves. Sink batches seal on whichever
of `max_rows`, `max_bytes`, or `linger` trips first. A source that cannot keep
up leaves batches sealing on **`linger`**, so the pipeline emits small writes on
a timer regardless of how little it has accumulated. Fix the source and the same
batches seal on **size** instead, giving fewer, larger writes.

That difference dominates for any sink with a per-write cost: a columnar store
where each write becomes a part to merge, an object store billing per PUT, a
warehouse with a commit overhead. Two pods each writing
half-size batches are strictly worse for the destination than one pod writing
full-size ones, even at identical total throughput. How steep that curve is
depends on the sink, and its page says so.

**Horizontal scaling carries a cost beyond the bill.** Each
replica is another member of the source's assignment, another set of
connections, and another participant in every rebalance. Extract the vertical
throughput first.

## Build the binary for throughput

Your pipeline binary builds with your own crate's release profile and your
platform's allocator. Two build settings made the measured pipeline faster: fat
link-time optimization (LTO) and a replacement allocator. A raised target CPU
did not.

The figures in this section come from one pipeline, run by the
[pipeline bench](repo:bench/pipeline). It decodes 627-byte line-delimited
records, stored plain or zstd-compressed, into a typed struct, which allocates
about 26 times a record. It then encodes them into a columnar format for a sink
that discards them. It ran on two Linux hosts with glibc, one x86_64 and one
aarch64, on one pipeline thread unless a figure names four. The builds used
`bytes` 1.12.2, except for the target CPU figures. Those come from an earlier
run on four hosts, three x86_64 and one aarch64, with `bytes` 1.12.1. Each
figure compares two builds over 20 interleaved runs. A
difference is stated as no measurable difference when its 90% confidence
interval includes zero, or when it is no larger than the difference between two
runs of the same build. Other pipeline shapes, operating systems
and C libraries were not measured. The build times come from a clean build of
that bench crate with debug info, on 32 vCPUs.

### Set LTO in your own profile

Cargo reads profiles only from your workspace's root `Cargo.toml`, so the `lto`
setting in Spate's repository does not reach your binary. Cargo's default
release profile does no link-time optimization across crates. Set fat LTO with
one codegen unit in your own `Cargo.toml`:

```toml
[profile.release]
lto = "fat"
codegen-units = 1
```

Fat LTO with one codegen unit made the measured pipeline 2–8% faster. Its build
took about three times as long as Cargo's default, with about three times the
peak memory.

Thin LTO, `lto = "thin"`, made the measured pipeline about 3% faster on x86_64
and made no measurable difference on aarch64. Its build took 11–15% longer.

### Replace the system allocator

Replacing glibc's allocator made the measured pipeline 7–16% faster on both
hosts. To use `mimalloc`, add it to your dependencies:

```toml
[dependencies]
mimalloc = "0.1"
```

Then declare it as the global allocator in your binary:

```rust
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

The jemalloc allocator, through `tikv-jemallocator`, gave a gain in the same
range on the measured pipeline. Each allocator also slowed some encoder
benchmark cases. On x86_64, jemalloc slowed two cases by 6–10%. It also slowed
one case on each host by 1% or less. The `mimalloc` allocator slowed one case
by 4–9%.

At four pipeline threads, the allocator was measured only together with fat
LTO. That build, with jemalloc, was 6–20% faster than Cargo's defaults.

### Leave the target CPU at its default

Rust builds for a baseline CPU of each architecture unless you pass
`-C target-cpu`. Every raised target stayed within 2% of the default on the
measured pipeline. Running a binary built for a newer CPU on an older one is
undefined behavior. Leave the target at its default.

On x86_64 Linux, a non-empty `compiled` field in the `cpu features` log line
means the build raised the target CPU or added a target feature
([Monitoring](monitoring.mdx#check-which-simd-features-a-host-offers)). An
empty field does not rule that out, because the line covers only a fixed set
of SIMD features.

## Threads: `pipeline.threads` vs `pipeline.io_threads`

The process splits work between two pools
([Architecture](../02-concepts/01-architecture.mdx)):

- **Pipeline threads** (plain `std::thread`) run the hot path: lane polling,
  deserialization, the operator chain, shard routing, row encoding.
- **The I/O runtime** (`io_threads` tokio workers, default **2**) runs sink
  shard workers, flush timers, and the admin server. The checkpointer runs
  on the controller thread.

When `pipeline.threads` is unset, the count derives at startup as
`available_parallelism` minus the I/O reserve, floored at 1. The I/O reserve
is one core for every two `io_threads` workers, rounded up, plus one core for
the controller thread. Row encoding runs on the pipeline threads, and so does
compression when the sink supplies a frame codec. The I/O workers carry the
socket writes. With the default `io_threads: 2`:

| `available_parallelism` | I/O reserve | Pipeline threads |
|---|---|---|
| 4 | 2 | 2 |
| 8 | 2 | 6 |
| 32 | 2 | 30 |

`available_parallelism` respects cgroup CPU quotas, so a Kubernetes CPU
**limit** sizes this correctly on its own.

:::warning
A pod without a CPU limit sees the **node's** cores and spawns that many
pipeline threads. If you don't set limits, set `pipeline.threads`
explicitly.
:::

When the tasks on the I/O runtime run short of CPU, raise `io_threads`.
That work is request building, TLS, compression a sink does on the I/O
runtime, and response handling. A write awaiting a slow sink is parked
on the network and holds no I/O worker, so slow writes need no more
`io_threads`, however many are in flight. A writer that blocks its thread
holds a worker for the length of the call. The hot path never runs on the
I/O runtime, so extra workers do nothing for a pipeline whose pipeline
threads are the limit. Each odd-numbered worker (the first, the third, and
so on) takes one core from the derived pipeline-thread count, down to its
floor of 1.

Read `spate_pipeline_io_busy_ratio` before raising `io_threads`: a value that
stays near 1 means the I/O workers are saturated
([Metrics](../../METRICS.md#pipeline--process)). It averages the last 5 minutes
(since start while shorter) and updates every 5 seconds. A worker records its
busy time about every 31 polls, so once the window is full a reading can be off
by up to that much busy time: a few percent for polls under about 500 ms and
about 10% at 1 s polls. Longer polls read late and unevenly.

## Sink batching: `batch.max_rows` / `batch.max_bytes` / `batch.linger`

Each sink shard worker accumulates encoded chunks and seals a batch as soon
as **any** threshold trips (defaults: `max_rows: 500000`,
`max_bytes: 128MiB`, `linger: 1s`; a sealed batch may overshoot by at most
one chunk, since chunks arrive whole):

- **Bigger batches** amortize per-write cost, which for most sinks is the
  dominant term. `max_rows`/`max_bytes` bound the ceiling.
- **`linger`** bounds latency at low throughput: a non-empty batch seals
  this long after its first chunk even if the size thresholds never trip.
  Lower it for latency-sensitive pipelines; raise it if a trickle of tiny
  inserts is fragmenting the sink.
- Every sealed batch is a retry unit and an ack unit: larger batches mean
  coarser replays after a failure.

Watch `spate_sink_batch_rows`/`spate_sink_batch_bytes` and
`spate_sink_flushes_total{reason=...}`: a sink flushing mostly on `linger`
never fills its batches. The size thresholds are irrelevant there, and you
can safely lower `max_bytes` to relax the backpressure budget (next
section).

## Concurrency: `inflight.max_per_shard`

Concurrent sealed batches in flight per shard (default **2**), rotating
across healthy replicas. While all permits are taken the worker stops
consuming its queue, which fills and surfaces upstream as backpressure.
That is the intended signal, not a stall. Raising it buys replica
parallelism at the cost of more memory pinned in flight (it multiplies
directly into the budget rule below).

## The backpressure budget: `backpressure.max_inflight_bytes`

A global cap on bytes admitted into the pipeline but not yet durably
written (default **256MiB**), with pause/resume hysteresis: sources pause
above `high_ratio` (default **0.8**) and may resume below `low_ratio`
(default **0.5**) after at least `min_pause` (default **500ms**; pausing a
lane is not free for every source, and the hysteresis absorbs that cost).

**Size it against the sizing rule**, which
[Backpressure](../02-concepts/03-backpressure.mdx#sizing-the-budget) states
in full along with the measurement behind it. The budget's low watermark
must comfortably hold everything the sink keeps in flight, or a
saturated pipeline lives above the high watermark and duty-cycles against
`min_pause`.

At the default queue size, the pending-writes term
`shards × inflight.max_per_shard × batch.max_bytes` dominates the rule. A queue
sized to stop pauses (see [Queues](#queues)) can match or pass it, so count both
terms when you raise `queue.max_bytes`. Worked example from the flagship YAML
([`kafka_avro_to_clickhouse.yaml`](repo:crates/spate/examples/kafka_avro_to_clickhouse.yaml)):
one shard, 2 in-flight, 128 MiB batches gives `1 × 2 × 128MiB = 256MiB` of
pending writes, doubled for the rule's headroom to 512 MiB, so the
example sets `max_inflight_bytes: 1GiB` (512 MiB at `low_ratio: 0.5`). The
framework **defaults are intentionally not self-consistent** under
saturation: 2 shards at the default batch settings exceed the default
256 MiB budget. That's fine for throttled sources that never fill batches;
for a saturated source, either raise the budget or cap `batch.max_bytes`
near `budget × low_ratio / (2 × shards × max_per_shard)`.

Memory sizing follows: set the container memory limit above
`max_inflight_bytes` **plus whatever the source client buffers on its own**,
with headroom for batches held during retries.

That second term is easy to under-count and it is not a framework number. A
source client with its own read-ahead holds that data before the framework sees
it, so it sits outside the in-flight budget entirely. Where the buffer is
charged per assignment unit rather than per process, it can be an order of
magnitude larger than the budget. Size it from the source's own page before
setting a memory limit.

## Chunk sizing: `chunk.target_bytes` {#chunk-sizing}

Set per sink in YAML as `sink.chunk.target_bytes`, or per branch as
`sinks.<name>.chunk.target_bytes`, beside the sink's component key
([configuration reference](../07-reference/configuration.mdx#chunk)). It never
affects delivery correctness, because a partial chunk is sealed on every commit
tick and at most defers a commit by ~one interval, so it is a deploy-time knob
you can retune without a rebuild. `SinkOptions::with_chunk` is the code-level
equivalent for pipelines assembled programmatically (one or the other, not
both).

The chain terminal encodes rows into a per-shard buffer and seals a **chunk**
once it reaches `target_bytes` (default **64 KiB**), then hands it to that
shard's queue. Chunks are not insert sizes. Shard workers merge them into
full batches, so this knob does not bound insert size. It governs
**handoff rate**: at 64 KiB a 256-byte row yields roughly 250 rows per chunk,
so a fast chain generates tens of thousands of queue operations per shard per
second, each one also a seal and an in-flight budget update.

Raise it when the chain outruns the shard workers. What a larger chunk does to
the queue depends on whether `queue.max_bytes` is set:

- With `queue.max_bytes` unset, each queue holds 8 chunks, so a larger chunk
  also queues more bytes.
- With `queue.max_bytes` set, a larger chunk leaves fewer slots in the same
  bytes, and a shallow queue with fewer slots pauses more often.

Backpressure pauses while the sink itself is idle are diagnosed under
[Queues](#queues).

Leave the chunk size alone for latency-sensitive pipelines: throughput and flush
latency rise together, with **no knee** in the measured range, so there is no
setting that dominates. The default sits at the low-latency end of that range.

Raising it never strands rows or delays commits: a chunk that has not
reached `target_bytes` is sealed anyway on every commit tick
(`checkpoint.interval`), and by the driver's idle timer during a lull. This
matters most for uneven fan-out. A low-volume `split` branch whose buffer
would take minutes to fill holds the acknowledgments (and therefore the
source watermark) of every batch that contributed a row to it, so the commit
tick bounds that hold to the checkpoint period.

## Queues: `queue.max_bytes` {#queues}

The bounded chunk queue between pipeline threads and each shard worker, default
**8** chunks (chunks target 64 KiB, see [`chunk.target_bytes`](#chunk-sizing)).
Set it per sink in YAML as `sink.queue.max_bytes`, or per branch as
`sinks.<name>.queue.max_bytes`
([configuration reference](../07-reference/configuration.mdx#queue)).
`SinkOptions::with_queue` is the code-level equivalent. The pipeline divides
`max_bytes` by the sink's `chunk.target_bytes` once at startup, rounding up, so
the queue holds a number of chunks: `max_bytes: 8MiB` at 64 KiB chunks is 128
chunks.

A full queue rejects the chunk, and the rejection pauses the source whatever the
in-flight budget reads. `spate_queue_full_events_total` counts the rejections.
So a queue that is too shallow pauses the source even when the sink keeps up and
the budget has room.

The default stays at 8 chunks because a shallow queue fails in the direction
that is easier to diagnose: it under-uses a fast sink, where a deep queue can
hide a slow sink behind a buffer. Spate does not derive the size from pipeline
threads or shards, so a pipeline that needs a deeper queue sets
`queue.max_bytes` itself.

Depth buys throughput, and what it costs depends on the sink. Against a sink
with headroom, a deeper queue raised throughput with no measured rise in flush
latency. Against a saturated sink it also raised throughput, at about ten times
the flush p99 (measured by a rig this repository no longer carries).

### Size a queue that does not pause the source

A queue that never pauses the source needs to hold about the bytes the shard
receives during one slow write:

1. Take the bytes per second the source offers each shard.
   `rate(spate_sink_bytes_total[5m])` per `shard` gives it while the pipeline is
   not pausing. While the source pauses, that rate reads below what the source
   offers, so a queue sized from it is a floor: set it, then repeat the reading
   until the pauses stop.
2. Take the slow write time from the p99 of
   `spate_sink_write_duration_seconds{outcome="ok"}`. Its buckets are two to
   three times apart, so use the upper bound of the bucket the p99 falls in.
3. Set `queue.max_bytes` to between that product and twice it. With batches
   much smaller than the default, allow up to three times it.
4. Raise `backpressure.max_inflight_bytes` so that its low watermark holds
   `shards × queue.max_bytes` beside the pending writes, by the
   [budget sizing rule](../02-concepts/03-backpressure.mdx#sizing-the-budget).

**Worked example.** A pipeline writes to 2 shards at the default batch (128 MiB)
and 2 in-flight writes per shard. `rate(spate_sink_bytes_total[5m])` reads about
400 MB/s per shard while the source is not pausing, and the write p99 falls in
the 50–100 ms bucket. 400 MB/s × 0.1 s is about 38 MiB, so `queue.max_bytes`
goes between 38 and 76 MiB: 64 MiB. The budget rule then needs a low watermark
of twice, for the rule's headroom, the pending writes (2 shards × 2 writes × 128
MiB = 512 MiB) plus the queues (2 shards × 64 MiB = 128 MiB): 1,280 MiB, which
at the default `low_ratio` of 0.5 is a 2,560 MiB budget:

```yaml
sink:
  # the backend key and its settings, with 2 shards
  queue:
    max_bytes: 64MiB
backpressure:
  max_inflight_bytes: 2560MiB
```

Without the queue change, the same pipeline would need about a 2 GiB budget, so
the deeper queue costs about 500 MiB of memory.

The rule was measured at the default `inflight.max_per_shard` of 2 only, by a
rig this repository does not carry. A deeper queue adds little latency while the
sink has capacity to spare, and adds it when the sink is at its limit.

Queued bytes decide how often a queue fills. Above a few MiB the chunk size
makes little difference, while on a shallow queue larger chunks leave fewer
slots and fill it sooner. To deepen a queue, raise `queue.max_bytes`.

### Find what fills the queue

Start from [which side binds](monitoring.mdx#which-side-binds). When
`spate_queue_full_events_total` climbs, its `queue` label names the shard:
`chain->sink/shard-3` is shard 3. Read that shard's sink series beside it. A
full queue has three causes, and they read differently:

- **Permits idle.** `spate_sink_inflight_batches` stays below
  `inflight.max_per_shard` and `spate_sink_permit_wait_duration_seconds` stays
  near zero. The shard worker is not taking chunks off the queue as fast as
  bursts arrive, so the sink waits for work while the source pauses. Raise
  `queue.max_bytes`; at high rates across many threads the same measurements
  needed 128 to 256 MiB. When `spate_pipeline_io_busy_ratio` stays above 0.9,
  raise `pipeline.io_threads` first, as the
  [starting alerts](../../METRICS.md#alerting-starting-points) say.
- **Permits busy, store keeping up on average.** In-flight batches sit at the
  cap and permit wait rises. Yet the shard's rate stays well below
  `inflight.max_per_shard` times the mean batch size (`spate_sink_batch_bytes`)
  divided by the mean write time, and write p99 is several times the median. A
  few slow writes hold every permit while rows keep arriving. Size the queue by
  the rule above. More permits would also absorb a slow write, but the rule
  does not cover them. First check that the permits are writing: a batch asleep
  in retry backoff (`spate_sink_retry_backoff_seconds`) or parked on a
  quarantined shard (`spate_sink_shard_healthy == 0`) holds its permit too. The
  [starting alerts](../../METRICS.md#alerting-starting-points) cover both.
- **Rate near capacity.** In-flight batches sit at the cap and the shard's rate
  is close to that capacity, so the sink is behind. Add shards or
  `inflight.max_per_shard`. A deeper queue buys throughput here only by adding
  latency.

Read write latency from `spate_sink_write_duration_seconds{outcome="ok"}`, the
per-attempt write. `spate_sink_flush_duration_seconds` spans seal to settle and
carries the wait for an `inflight.max_per_shard` slot, so it rises under
queueing whether or not the sink slowed down (see
[What a flush contains](../../METRICS.md#what-a-flush-contains)).

**A high pause count is not by itself a misconfiguration.** Against a saturated
sink the *best-latency* configuration also had the *most* pauses.

## Checkpointing: `checkpoint.*`

- `interval` (default **5s**): how often committable watermarks flush to
  the source, **and** the cadence at which partial chunk buffers are sealed
  (every tick broadcasts a chain flush, so a below-target chunk, such as one
  from a low-volume `split` branch, can hold acknowledgments for at most
  one interval). The durability boundary is the sink write, not this interval,
  so shortening it narrows the replay window after a crash and tightens
  worst-case commit lag (≈ two intervals + the sink `linger`), at the cost
  of more commit traffic and slightly smaller chunks. Validation floors it
  at 100ms. `spate_checkpoint_watermark_age_seconds` reads up to that lag on a
  healthy pipeline, so an alert on it sits above the lag.
- `max_pending_batches` (default **1024**): hard ceiling on unacknowledged
  batches per partition. At the limit the partition's lanes are skipped at
  the poll boundary until acknowledgments retire batches, and are paused at
  the source once the partition has stayed there for
  `backpressure.min_pause`. Bounds the replay
  a stalled partition can accumulate, alongside (and independent of) the
  byte budget.
- `drain_timeout` (default **25s**): the shutdown/rebalance drain budget.
  With a feed that hands back, a stop's reading of the units it holds runs
  inside it too, and it must be more than 5s.
  Keep it below `terminationGracePeriodSeconds`. See [Docker](docker.mdx)
  and [Graceful shutdown](../03-guides/graceful-shutdown.mdx).
- `stalled_fail_after` (default **120s**): a partition watermark stalled behind
  a *failed* batch this long fails the pipeline, converting a permanent sink
  failure into a restart-and-replay instead of a process that consumes but
  commits nothing. A
  [seeded S3 run](../04-connectors/sources/s3/README.mdx#a-run-on-a-seeded-feed)
  fails each unit in the batch back to its feed instead.

## Pinning: `pipeline.pinning`

- `none` (default): no core pinning.
- `compact`: pin pipeline thread *i* to core *i*.

`compact` only yields exclusive cores under the kubelet **static CPU
manager** with Guaranteed QoS and integer CPU requests; anywhere else it
sets affinity inside a shared cpuset and can hurt by fighting the
scheduler. Leave it `none` unless you run that setup.

## Where parallelism comes from

Read parallelism is bounded by **lane count**, not thread count. Lanes map
m:n onto pipeline threads, so threads cannot manufacture concurrency a source
did not hand out. If the pipeline is CPU-saturated, more threads help; if it is
lane-starved, only more lanes do, and how a source decides its lane count is
its own affair. Scale horizontally by replicas, and see
[Scaling out](scaling-out.mdx) for how each source divides work across them.
