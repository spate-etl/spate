# Tuning

Every knob below has a safe default; most pipelines change two or three of
them. This page covers what each one moves and how to size them together —
the defaults quoted are the exact values from
`crates/spate-core/src/config/mod.rs` and the sink config structs (also
tabulated in the [configuration reference](../07-reference/configuration.mdx)).

## Where to start

Tune **vertically first, then scale out**. A single process that is not yet at
its CPU, memory, or network limit is the cheapest throughput you will ever get,
and scaling out before you reach that limit multiplies the wrong thing.

The loop is:

1. **Find which side binds.** A pipeline is either source-bound, chain-bound, or
   sink-bound at any moment, and the metrics say which — see
   [Monitoring](./monitoring.mdx). Guessing here is the most common way tuning
   time gets wasted.
2. **Raise the binding side** using that component's knobs.
3. **Re-measure.** The bottleneck usually moves rather than disappearing: a
   source that was starving the chain will, once fixed, start saturating the
   sink.
4. **Repeat until a physical resource is saturated** — CPU cores busy, memory
   at the pod limit, or the NIC/broker link full.
5. **Only then scale horizontally**, by adding replicas.

### Why the vertical work matters even when you could just add pods

Throughput is not the only thing that improves. Sink batches seal on whichever
of `max_rows`, `max_bytes`, or `linger` trips first. A source that cannot keep
up leaves batches sealing on **`linger`** — the pipeline emits small writes on a
timer regardless of how little it has accumulated. Fix the source and the same
batches seal on **size** instead: fewer, larger writes.

That difference is the whole ballgame for any sink with a per-write cost — a
columnar store where each write becomes a part to merge, an object store
billing per PUT, a warehouse with a commit overhead. Two pods each writing
half-size batches are strictly worse for the destination than one pod writing
full-size ones, even at identical total throughput. How steep that curve is
depends on the sink, and its page says so.

The corollary: **horizontal scaling has a real cost**, not just a bill. Each
replica is another member of the source's assignment, another set of
connections, and another participant in every rebalance. Extract the vertical
throughput first.

## Threads: `pipeline.threads` vs `pipeline.io_threads`

The process splits work between two pools
([Architecture](../02-concepts/01-architecture.mdx)):

- **Pipeline threads** (plain `std::thread`) run the hot path: lane polling,
  deserialization, the operator chain, row encoding, shard routing.
- **The I/O runtime** (`io_threads` tokio workers, default **2**) runs sink
  shard workers, flush timers, the checkpointer, and the admin server.

When `pipeline.threads` is unset, the count derives at startup as
`available_parallelism` minus the I/O reserve (the `io_threads` workers plus
one controller thread), floored at 1. `available_parallelism` respects
cgroup CPU quotas, so a Kubernetes CPU **limit** sizes this correctly on its
own.

:::warning
A pod without a CPU limit sees the **node's** cores and spawns that many
pipeline threads. If you don't set limits, set `pipeline.threads`
explicitly.
:::

Raise `io_threads` only if you have many shards with slow, concurrent
writes; the hot path never runs there, so extra I/O workers buy nothing for
CPU-bound pipelines and eat into the derived pipeline-thread count.

## Sink batching: `batch.max_rows` / `batch.max_bytes` / `batch.linger`

Each sink shard worker accumulates encoded chunks and seals a batch as soon
as **any** threshold trips (defaults: `max_rows: 500000`,
`max_bytes: 128MiB`, `linger: 1s`; a sealed batch may overshoot by at most
one chunk, since chunks arrive whole):

- **Bigger batches** amortize per-write cost, which for most sinks is the
  dominant term. `max_rows`/`max_bytes` bound the ceiling.
- **`linger`** bounds latency at low throughput: a non-empty batch seals
  this long after its first chunk even if the size thresholds never trip.
  Lower it for latency-sensitive pipelines; raise it if a trickle of tiny
  inserts is fragmenting the sink.
- Every sealed batch is a retry unit and an ack unit: larger batches mean
  coarser replays after a failure.

Watch `spate_sink_batch_rows`/`spate_sink_batch_bytes` and
`spate_sink_flushes_total{reason=...}`: a sink flushing mostly on `linger`
never fills its batches — the size thresholds are irrelevant there, and you
can safely lower `max_bytes` to relax the backpressure budget (next
section).

## Concurrency: `inflight.max_per_shard`

Concurrent sealed batches in flight per shard (default **2**), rotating
across healthy replicas. While all permits are taken the worker stops
consuming its queue, which fills and surfaces upstream as backpressure —
this is the intended signal, not a stall. Raising it buys replica
parallelism at the cost of more memory pinned in flight (it multiplies
directly into the budget rule below).

## The backpressure budget: `backpressure.max_inflight_bytes`

A global cap on bytes admitted into the pipeline but not yet durably
written (default **256MiB**), with pause/resume hysteresis: sources pause
above `high_ratio` (default **0.8**) and may resume below `low_ratio`
(default **0.5**) after at least `min_pause` (default **500ms**; pausing a
lane is not free for every source, which is what the hysteresis is for). See
[Backpressure](../02-concepts/03-backpressure.mdx) for the model.

**The sizing rule** (from [docs/DESIGN.md](../../DESIGN.md) § Backpressure,
motivated by a measured 24x throughput collapse): the budget's low
watermark must comfortably hold everything the sink legitimately keeps in
flight, or a saturated pipeline lives above the high watermark and
duty-cycles against `min_pause`:

```text
max_inflight_bytes × low_ratio  ≥  2 × ( shards × inflight.max_per_shard × batch.max_bytes
                                       + shards × queue_capacity × chunk.target_bytes )
```

The pending-writes term dominates. Worked example from the flagship YAML
(`crates/spate/examples/kafka_avro_to_clickhouse.yaml`): one shard, 2
in-flight, 128 MiB batches gives `2 × (1 × 2 × 128MiB) = 512MiB`, so the
example sets `max_inflight_bytes: 1GiB` (512 MiB at `low_ratio: 0.5`). Note
the framework **defaults are intentionally not self-consistent** under
saturation: 2 shards at the default batch settings exceed the default
256 MiB budget. That's fine for throttled sources that never fill batches;
for a saturated source, either raise the budget or cap `batch.max_bytes`
near `budget × low_ratio / (2 × shards × max_per_shard)`.

Memory sizing follows: set the container memory limit above
`max_inflight_bytes` **plus whatever the source client buffers on its own**,
with headroom for batches held during retries.

That second term is easy to under-count and it is not a framework number. A
source client with its own read-ahead holds that data before the framework sees
it, so it sits outside the in-flight budget entirely — and where the buffer is
charged per assignment unit rather than per process, it can be an order of
magnitude larger than the budget. Size it from the source's own page before
setting a memory limit.

## Chunk sizing: `chunk.target_bytes` {#chunk-sizing}

Set per sink in YAML — `sink.<type>.chunk.target_bytes`, or per branch as
`sinks.<name>.chunk.target_bytes` ([configuration reference](../07-reference/configuration.mdx#chunk)).
Because it never affects delivery correctness — a partial chunk is sealed on
every commit tick, so at most it defers a commit by ~one interval — it is a
deploy-time knob you can retune without a rebuild; `SinkOptions::with_chunk` is
the code-level equivalent for pipelines assembled programmatically (one or the
other, not both).

The chain terminal encodes rows into a per-shard buffer and seals a **chunk**
once it reaches `target_bytes` (default **64 KiB**), then hands it to that
shard's queue. Chunks are not insert sizes — shard workers merge them into
full batches — so this knob does not bound insert size. What it governs is
**handoff rate**: at 64 KiB a 256-byte row yields roughly 250 rows per chunk,
so a fast chain generates tens of thousands of queue operations per shard per
second, each one also a seal and an in-flight budget update.

Raise it when the chain outruns the shard workers — the symptom is backpressure
pauses while the sink itself is idle (see the note below). Leave it alone for
latency-sensitive pipelines: throughput and flush latency rise together, with
**no knee** in the measured range, so there is no setting that dominates. The
trade curve is on [Chunk sizing](../../benchmarks/chunk-sizing.mdx); the
default sits deliberately at the low-latency end of it.

Raising it never strands rows or delays commits: a chunk that has not
reached `target_bytes` is sealed anyway on every commit tick
(`checkpoint.interval`), and by the driver's idle timer during a lull. This
matters most for uneven fan-out — a low-volume `split` branch whose buffer
would take minutes to fill holds the acknowledgements (and therefore the
source watermark) of every batch that contributed a row to it, so the commit
tick is what bounds that hold to the checkpoint period.

## Queues: `SinkOptions::queue_capacity`

The bounded chunk queue between pipeline threads and each shard worker,
default **8** chunks (chunks target 64 KiB — [`chunk.target_bytes`](#chunk-sizing)).
This is a code-level knob (`Pipeline::sink_with(bundle, SinkOptions)`, see
[Assembling a pipeline](../03-guides/assembling-a-pipeline.mdx)), not YAML —
unlike `chunk`, it stays in code for now (deploy-time exposure is a possible
follow-up). It exists to signal, not to buffer: a full queue is the per-shard
backpressure trigger (`spate_queue_full_events_total`). Keep it small; the
global byte budget, not the queue, is the intended smoothing buffer.

That "keep it small" is measured — see
[Chunk sizing](../../benchmarks/chunk-sizing.mdx) — but it is a genuine trade,
not a free default, and **its price depends on whether your sink is the
constraint.** Depth raised throughput in every regime measured, by 46% to 92%.
What changes is what you pay for it:

| Your sink | Throughput from depth | Flush p99 cost |
|---|---|---|
| **Saturated** — it is the bottleneck | +46% at capacity 1024 | ~10× |
| **Has headroom** — something upstream limits you | +86% by capacity 64 | none measured |

The flush p99 in that table is `spate_sink_flush_duration_seconds`, seal to
settle — the right family for this question, because what depth costs you *is*
the extra time a batch spends waiting before it is durable. It is the wrong
family for "did my sink get slower": these arms were recorded before the split
families existed, so the 10× is a seal-to-settle figure and nothing here
decomposes it into queueing versus write time.

Against a saturated sink the curve is **not** smooth, so choose an end of it
rather than a middle: the first step up costs nearly all of the latency for
almost none of the throughput, while the deepest settings recover the throughput
for comparatively little more. Where the sink has headroom there is no such
trade — flush p99 held flat across the whole 8-to-512 range, because the queue
never filled deeply enough to add any, and the shallow default was simply
throttling a server with room to spare.

The default stays at 8 because a shallow queue fails in the direction that is
easier to diagnose — under-using a fast sink, rather than hiding a slow one
behind a buffer. That is a defensive choice, not a free one.

:::note[Which regime am I in?]
Read `spate_backpressure_pause_events_total` **together with**
`spate_sink_write_duration_seconds{outcome="ok"}` — the per-attempt write, not
`spate_sink_flush_duration_seconds`. Flush duration spans seal to settle and
carries the wait for an `inflight.max_per_shard` slot, so it rises under
queueing whether or not the sink slowed down; that ambiguity is exactly what
sends this diagnosis the wrong way (see [What a flush
contains](../../METRICS.md#what-a-flush-contains)).

- **Pauses high, write p99 flat and low** → the queue is throttling a sink that
  has headroom. Raise `queue_capacity` and watch the pauses reach zero.
  `spate_sink_permit_wait_duration_seconds` confirms it: if the flush p99 you are
  worried about is mostly permit wait, no amount of server tuning will move it.
- **Pauses high, write p99 high** → the sink is genuinely behind. Depth will buy
  throughput but cost latency; add shards or `inflight.max_per_shard` instead.

**A high pause count is not by itself a misconfiguration.** Against a saturated
sink the *best-latency* configuration also had the *most* pauses.

Earlier revisions of this page described the trigger as *rate-driven as well as
capacity-driven*, and told you to reach for chunk size when pauses were high
while the sink was idle. Both were wrong. An iso-buffer re-run — same queued
bytes, different seal size — put the pause count at zero for the small-chunk
arm, so the trigger tracks **queued bytes**, and `queue_capacity` is the lever,
not `chunk.target_bytes`.
:::

## Checkpointing: `checkpoint.*`

- `interval` (default **5s**): how often committable watermarks flush to
  the source, **and** the cadence at which partial chunk buffers are sealed
  (every tick broadcasts a chain flush, so a below-target chunk — a
  low-volume `split` branch, say — can hold acknowledgements for at most
  one interval). This is *not* a durability boundary — the sink write is —
  so shortening it narrows the replay window after a crash and tightens
  worst-case commit lag (≈ two intervals + the sink `linger`), at the cost
  of more commit traffic and slightly smaller chunks. Validation floors it
  at 100ms.
- `max_pending_batches` (default **1024**): unacknowledged batches per
  partition before that partition pauses — a per-partition backpressure
  backstop alongside the byte budget.
- `drain_timeout` (default **25s**): the shutdown/rebalance drain budget.
  Keep it below `terminationGracePeriodSeconds` — see [Docker](docker.mdx)
  and [Graceful shutdown](../03-guides/graceful-shutdown.mdx).
- `stalled_fail_after` (default **120s**): a partition watermark stalled
  behind a *failed* batch this long fails the pipeline, converting a
  permanent sink failure into a restart-and-replay instead of a process
  that consumes but commits nothing.

## Pinning: `pipeline.pinning`

- `off` (default): no core pinning.
- `compact`: pin pipeline thread *i* to core *i*.

`compact` only yields exclusive cores under the kubelet **static CPU
manager** with Guaranteed QoS and integer CPU requests; anywhere else it
merely sets affinity inside a shared cpuset and can hurt by fighting the
scheduler. Leave it `off` unless you run that setup.

## Where parallelism actually comes from

Read parallelism is bounded by **lane count**, not thread count — lanes map
m:n onto pipeline threads, so threads cannot manufacture concurrency a source
did not hand out. If the pipeline is CPU-saturated, more threads help; if it is
lane-starved, only more lanes do, and how a source decides its lane count is
its own affair. Scale horizontally by replicas, and see
[Scaling out](scaling-out.mdx) for how each source divides work across them.
