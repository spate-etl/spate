# Custom sinks

A sink is two pieces, split across the process's two halves
([Architecture](../02-concepts/01-architecture.mdx)):

- **`RowEncoder`** — the CPU half. Turns one record into wire bytes. Runs
  on pipeline threads, where payload borrows are still valid.
- **`ShardWriter`** — the I/O half. Writes one sealed batch to one replica
  endpoint. Runs on sink workers in the I/O runtime.

Everything between is the framework's: chunking, per-shard batching to
`max_rows`/`max_bytes`/`linger`, replica rotation, circuit breakers,
retries, acknowledgments, backpressure. You write the two edges.

Every Rust block below but the last comes from the sink half of
[`custom_source_sink.rs`](repo:crates/spate/examples/custom_source_sink.rs),
a JSON-lines-to-stdout sink fed by a generator source, which needs no
infrastructure and no facade feature beyond the default:

```sh
cargo run -p spate --example custom_source_sink
```

The last one is a shipped connector's own wiring and carries its path.

## The CPU half: `RowEncoder`

One record in, wire bytes appended to the shard's buffer. The example encodes
each order line as a JSON object on a line of its own:

```rust file=crates/spate/examples/custom_source_sink.rs region=encoder
```

Contracts:

- **No I/O, ever.** `encode` runs inside the hot loop on a pinned pipeline
  thread. A network call or blocking syscall here stalls polling for every
  lane on that thread.
- **Frames must concatenate.** Chunks encoded on different pipeline threads
  are merged by shard workers into one batch, so your wire format must be
  valid as a plain concatenation of row encodings (a row-wise binary format
  or newline-delimited text is; a format needing a global header belongs in
  the writer).
- **Errors are record-level by default**, subject to the sink stage's
  `ErrorPolicy` (`ChunkConfig::encode_policy`, default `Skip`, counted in
  metrics). Return an error classed **`Fatal`** to stop the pipeline
  regardless of policy: fatal means the *encoder* is broken (e.g. the row
  type can never match the target schema) and every subsequent record would
  fail identically. See
  [Error handling](../02-concepts/04-error-handling.mdx).
- **The terminal stage clones one encoder per shard**, which is why the type is
  `Clone`. Shards never share encoder state, so anything you buffer is private
  to one shard and you do not need to synchronize it.

### Buffering: encoders that are not row-at-a-time

A columnar format cannot emit bytes per row; it transposes a block and writes
it whole. Defaulted hooks make that fit the same trait:

| Hook | What it is for |
| --- | --- |
| `buffered_bytes()` | Report how much you are holding, so the framework's size accounting stays accurate while nothing has been written to `buf` |
| `finish_chunk()` | Flush your buffered block; called when the chunk seals |

Implement both and `encode` becomes "accumulate a row"; leave them defaulted and
your encoder stays row-at-a-time, which is what most formats want. Because each
shard has its own encoder clone, a buffered block belongs to exactly one shard's
chunk and cannot interleave with another's.

An error from `finish_chunk` stops the pipeline, and the stage drops whatever
that call wrote into `buf` so no partial block ships. That stop is asynchronous.
The chunk stays open until it lands, so a later seal may call `finish_chunk`
again, by then possibly for more rows than the failed call held. Return `Ok`
only from a call whose frame carries every row the chunk holds. What the call
wrote is dropped and not the row count, so an encoder that had already moved its
rows into `buf` when it failed re-encodes them, and keeps failing until it can.
Rows no call finalizes replay, because their acknowledgments fail on teardown.

## The I/O half: `ShardWriter`

One sealed batch out to one replica endpoint. The example's endpoint is a shard
name and its write is a `print!`, so returning `Ok` after it is honest; it also
keeps the rows it printed, which is how the example asserts on placement without
a destination to query. `write_batch` returns a future rather
than being an `async fn`, so whatever runs before that future (here, joining
the frames) happens when the worker calls it, not when the future is polled:

```rust file=crates/spate/examples/custom_source_sink.rs region=writer
```

- **`Ok` is the durable-ack point.** Return `Ok(())` only after the target
  system has durably accepted the batch: a synchronous server ack, a
  delivery confirmation, or here, after printing. The framework releases the batch's
  acknowledgments on `Ok`, letting the source watermark advance
  past that data. Return `Ok` early and a crash loses records, violating
  at-least-once.
- **Retries reuse the sealed batch unchanged**, rotating across healthy
  replicas with capped exponential backoff. `SealedBatch::dedup_token` is
  deterministic per batch: pass it to the target if it supports
  deduplication so same-boundary retries are idempotent (see
  [Delivery guarantees](../02-concepts/02-delivery-guarantees.mdx) for what
  dedup tokens do and do not cover).
- **Classify errors honestly.** Retryable errors get retried; a `Fatal`
  error abandons the batch (its acks fail, the partition watermark stalls,
  and `checkpoint.stalled_fail_after` eventually fails the pipeline so the
  data replays after restart).
- One writer instance is shared by every shard worker (`Send + Sync`); the
  per-replica state lives in `Endpoint`.

### If you hold acknowledgment handles, fail them on teardown

Dropping a record's acknowledgment means *delivered*. That default makes
`filter` and `flat_map` correct at no cost. It also means any component
holding handles for data it has **not** durably written must explicitly fail
them in its `Drop`, or teardown silently reports unwritten data as delivered and
the watermark advances past it.

The framework does this for its own seams: the chain's terminal stage fails
parked chunks and partial buffers, and sink workers fail abandoned batches. If
your connector holds handles anywhere the framework cannot see, such as an
internal queue or a retry buffer of your own, it owes the same.

**Over-failing is always safe.** It costs a replay, never a loss, so when in
doubt, fail. Collections on the sink path already work this way: an `AckSet`
fails its handles on drop and delivers only after a durable write, so teardown
anywhere stalls the watermark rather than committing data that was never
written.

## Handing it to the builder: `SinkParts`

Hand-rolled sinks need no trait impl; `SinkParts` is the bundle. The example
builds one endpoint per shard, each named for its own index, and shortens the
pool's linger so a demo does not wait a second for its first batch:

```rust file=crates/spate/examples/custom_source_sink.rs region=bundle
```

Hand the result to `pipeline.sink(sink)?` and the builder derives the shard
workers, their queues and their metric labels from the topology it carries.

- `SinkParts::new(writer, shard_endpoints, pool)` — the endpoints are
  indexed `[shard][replica]` and must be non-empty with at least one
  replica per shard; the builder rejects ragged or empty topologies before
  anything spawns. `SinkPoolConfig` carries the batching, in-flight, retry,
  and breaker tuning ([Tuning](../05-deployment/tuning.mdx)). It is
  `#[non_exhaustive]`, so build it from `new` or `default()`, as the example
  above does.
- `.with_component_type("...")` — sets the `component_type` metric label
  (default `"custom"`) on every sink series
  ([Monitoring](../05-deployment/monitoring.mdx)).
- `.with_replica_labels(...)` — display labels for per-replica metrics,
  same `[shard][replica]` shape; defaults to
  `"{component_type}-{shard}-{replica}"`.
- `.with_probe(...)` — an optional repeatable connectivity probe. The
  runtime polls it at startup and periodically, driving the
  sinks-connected half of `/readyz`. Without one, readiness can't reflect
  your sink. Probes should use their **own** client set. Sharing the
  writer's connections would report the insert path healthy because
  probing keeps it warm.

Construct the struct via `new` plus the `with_*` methods. It is
`#[non_exhaustive]`, so fields can grow without breaking you. Queue depth between
pipeline threads and shard workers is the builder's knob, not the bundle's:
`Pipeline::sink_with(bundle, SinkOptions::default().with_queue_capacity(n))`.

## The connector pattern: implementing `SinkBundle`

A reusable connector exposes a config-built sink type and implements
`SinkBundle` on it, so applications write one line. A shipped sink does exactly
that (worked reference:
[`spate-clickhouse/src/config.rs`](repo:crates/spate-clickhouse/src/config.rs),
rendered below): `into_parts` moves the writer and the topology its config
produced into `SinkParts::new`, then chains its refinements: the metric
`component_type`, per-replica labels derived from the endpoints themselves, and
the connectivity probe a hand-rolled sink most often leaves unset:

```rust file=crates/spate-clickhouse/src/config.rs region=bundle title="config.rs"
```

`Pipeline::sink` accepts anything implementing `SinkBundle`, and `SinkParts`
itself implements it, which is why hand-rolled sinks skip the impl. The
only bound anywhere is `ShardWriter`, so your connector's client types
never appear in framework APIs (the dependency policy in
[ADR-0011](../../adr/0011-msrv-and-dependency-policy.md)). Connector-specific flows the framework
cannot name, such as a pre-flight schema check that produces the encoder's row
schema, stay concrete pre-steps in your factory, before `into_parts`.

If your connector deserializes a YAML body, don't name a field `chunk`: that
key is **framework-reserved** inside every component body (it carries the
chain terminal's chunking) and is peeled out before your config ever sees it,
so a `chunk` field of your own would never receive a value. See
[the configuration reference](../07-reference/configuration.mdx#chunk).

## Testing

`spate-test` drives chains end to end against capturing sinks, and the
assertions in `custom_source_sink.rs` (observe commits, then trigger
shutdown) are the template for verifying your durable-ack point
gates the watermark. See
[Testing pipelines](../03-guides/testing-pipelines.mdx).
