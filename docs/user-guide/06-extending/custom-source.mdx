# Custom sources

A source is two pieces:

- **`Source`** — the control plane. Lifecycle, lane assignment/revocation
  events, watermark commits, pause/resume. Driven by the runtime's
  controller from a single thread.
- **`SourceLane`** — the data plane. A pollable unit pinned to one pipeline
  thread, yielding payload batches that **borrow** the lane's buffers.

The API is poll-based rather than a `futures::Stream`. Source clients
typically already own their network I/O on their own
threads, and a Stream wrapper adds waker overhead plus `'static`
bounds that break payload borrowing. Rationale in
[ADR-0003](../../adr/0003-poll-based-source-api.md); trait docs in
[`spate-core/src/source/mod.rs`](repo:crates/spate-core/src/source/mod.rs)
and on [docs.rs](../07-reference/README.mdx).

The data-plane and control-plane blocks below come from
[`custom_source_sink.rs`](repo:crates/spate/examples/custom_source_sink.rs),
a generator source counting to a limit per partition, which needs no
infrastructure and no facade feature beyond the default:

```sh
cargo run -p spate --example custom_source_sink
```

## The data plane: `SourceLane` and `PayloadBatch`

A lane polls up to `max_records` payloads, waiting at most `timeout`:

```rust file=crates/spate/examples/custom_source_sink.rs region=lane
```

What the framework holds you to:

- **Payloads borrow the lane.** `Batch` is a GAT borrowing `'_` from the
  lane, so payloads can point straight into your client's buffers, with zero
  copies out of the source. The batch is dropped before the next `poll` on
  the same lane; records derived from it are consumed or encoded within
  that window (the operator chain guarantees this by construction).
- **One `AckRef` per batch.** Issue it through the `AckIssuer` you received
  at `open` (`issuer.issue(partition, last_offset)`, the offset of the
  **last** record in the batch). Every record deserialized from the batch
  clones this handle; the checkpointer advances the partition's watermark
  past the batch only when every clone resolves as delivered. You never
  track individual records.
- **Idle lanes block, never spin.** `Ok(None)` means nothing arrived, but
  reach it by waiting up to `timeout` (a blocking queue read, a condvar,
  worst case a sleep). A zero-timeout poll loop busy-spins a pipeline
  thread at 100% for nothing.

The batch type holds one poll's payloads and streams them out one at a time,
all sharing the batch lifetime:

```rust file=crates/spate/examples/custom_source_sink.rs region=batch
```

`RawPayload.key` feeds the sink's shard routing hash. Populate it if your
source has message keys.

## The control plane: `Source`

The control plane owns whatever the lanes are built from, and the `Source` impl
is the runtime's entire view of it. This one deals its lanes on the first call
and idles forever after; a real source services its client here on every call:

```rust file=crates/spate/examples/custom_source_sink.rs region=control
```

The example records its watermarks in a map its own assertions read back. Store
them wherever your source resumes from instead.

- **`open`** runs once, before anything else, and hands you the
  `AckIssuer`. Connect here.
- **`poll_events`** services control-plane work (rebalance callbacks,
  statistics) and returns the next `SourceEvent`: for a simple source
  `LanesAssigned(lanes)`, `LanesRevoked { lanes, barrier }`, or `Idle`
  (the full set, including the additive and completion events, is under
  [Epochs and rebalances](#epochs-and-rebalances)). The runtime calls it
  regularly **regardless of backpressure state**. Pausing data never
  pauses the control plane, which is how group liveness survives a slow
  sink.
- **`commit`** receives per-partition committable watermarks. Each is
  **one past the last acknowledged offset**; store it as-is. This is the
  framework's convention everywhere, and the industry's. Interval-driven;
  durability is per your source's own policy.
- **`flush_commits`** (default no-op) must synchronously flush stored
  positions; the runtime calls it at shutdown and revocation.
- **`pause`/`resume`** (default no-ops) are the backpressure hooks: stop
  and restart fetching for specific lanes. Sources that can't pause rely on
  bounded-queue pushback alone, but a pausable source keeps memory flat
  under sink pressure.

**Class a rejected credential or TLS handshake `Fatal`.** That covers a
certificate your TLS stack fails to verify, a fatal TLS alert from the server
listed in `spate::error::TLS_REJECTION_ALERTS`, no protocol version, cipher
suite or other handshake parameter in common, an authentication or
authorization error from the server, and a 401 or 403 from the service
unless its error code names throttling or a limit that clears by itself. A
failure to obtain credentials or reach the server stays `Retryable`, and so
do a connection reset, closed or timed out during the handshake and a
malformed TLS message. Under TLS 1.3 a server refuses a client certificate
after the handshake completes, so look for its alert on the first read as
well as on the connect call. `spate::error::find_source` finds your TLS
library's error behind the client's wrappers, including inside an `io::Error`.
With a rustls client, `spate::tls_rejection!(rustls, &err)` applies the whole
TLS part of the rule.
[ADR-0081](../../adr/0081-a-rejected-credential-or-tls-handshake-is-fatal-unless-throttled.md)
states the rule.

## Framing: turning bytes into records

A source emits `RawPayload`s; a deserializer decodes one payload into records.
For a **message** source the message boundary *is* the record boundary, so
nothing extra is needed. For a **streaming** source (an object-storage backfill,
an HTTP chunked body, a WebSocket stream) one transfer is a large byte stream
that must be cut into records *before* the deserializer sees them. That cutting
is **framing**. The *seam* is transport-agnostic and lives in
`spate_core::framing`, but the concrete framer is a property of the **format**,
so it is owned by the format crate and handed to a source at assembly time. The
trait is quoted here to be read rather than run. You implement it in a format
crate, and each method's contract is cut to the one line that matters at this
distance:

```rust
pub trait RecordFramer: Send {
    fn push(&mut self, bytes: &[u8]) -> io::Result<()>;   // fed decoded bytes
    fn finish(&mut self) -> io::Result<()>;               // end of stream/object
    fn pop(&mut self) -> Option<Vec<u8>>;                 // next completed record
    fn decoded_bytes(&self) -> u64;                       // metrics
    fn resync_delimiter(&self) -> Option<u8> { None }     // byte a reader may start after
}
```

A framer **must be a pure function of the byte stream**. The record sequence
must not depend on how bytes arrive in chunks, so a source that resumes by
record index replays deterministically. The framer is owned by the **format**
crate, not the source. A newline-delimited format ships a line framer and a
container format ships a block framer. `FramerWriter` bridges a `Write`-based
decompressor to a framer so compression stays orthogonal. A streaming source
takes its framer at construction and stays format-agnostic, so every streaming
source reuses every format's framer. Worked reference:
[`spate-s3`](repo:crates/spate-s3) and its `with_framer`.

Tell the framework how your payloads are framed with **`framing_contract`**, so
framing is established once (on the source) instead of coordinating it with the
deserializer by hand. The whole override is the signature and one of two
answers:

```rust
fn framing_contract(&self) -> FramingContract {
    FramingContract::PerRecord    // one record per payload → deserializer decodes a single unit
    // default is WholePayload    // whole payloads → the deserializer frames (e.g. JSON ndjson/array)
}
```

The contract reaches the chain as `ctx.source_framing`, and a format crate's
deserializer builder reads it there to derive its own granularity and to
reject a double-framing configuration where the source frames *and* the
deserializer frames (worked reference: [`spate-json`](repo:crates/spate-json)'s
`JsonDeserializerBuilder::for_source_framing`). Not every layout fits this
model. Columnar, footer-indexed formats (Parquet/ORC/Arrow) have no
per-record byte boundary and belong to a future record-batch reader source,
not a framer.

## Epochs and rebalances

Assignment changes are where at-least-once is won or lost:

- **`LanesAssigned` bumps the assignment epoch** in the checkpointer, and
  acks issued under a previous epoch are discarded, so a stale ack from a
  revoked assignment can never advance a new epoch's watermark.
- **`LanesAssigned` is eager**: `begin_epoch` replaces all trackers, so a
  `LanesAssigned` event must describe the **full** assignment following a
  full revocation, not a delta. (The controller defensively drains and
  commits live lanes if a source violates this.)
- **`LanesAdded` is the additive alternative**: new lanes join the
  *current* epoch; existing lanes and their in-flight acks are untouched.
  Lane ids must be new, never reused from the source's lifetime,
  and each lane's partition must be above every partition admitted to
  the epoch so far, revoked and retired ones included. Feed readers emit
  this for each unit part they take up, so a routine gain never drains
  flowing lanes.
- **`LanesRevoked` carries a `DrainBarrier`.** The runtime trips it for the
  owning pipeline threads, which stop the lanes, flush in-flight records,
  and arrive at the barrier. Complete the revocation, final synchronous
  commit included, only after `DrainBarrier::wait` returns. This is the
  choreography that lets a scale-down cost only the uncommitted tail; see
  [Delivery guarantees](../02-concepts/02-delivery-guarantees.mdx).
- **`LanesRetired` removes finished lanes without a barrier**, strictly
  for lanes whose input is fully delivered, acknowledged, *and committed*
  (e.g. a feed unit part whose last record was acknowledged and settled), so
  by contract nothing unflushed or uncommitted can exist behind them. If
  any in-flight data or uncommitted acknowledgment may remain, use
  `LanesRevoked`.
- **`CommitReady { partitions }` is a latency hint**: the named lanes have
  decided end-of-input, and a commit outside the periodic tick is
  worthwhile now. The runtime commits those partitions only, at a
  tightened cadence for one commit interval and then on every
  control-plane poll, until their lanes leave through `LanesRetired` or
  `LanesRevoked` or a new `LanesAssigned` begins. A partition whose lane
  never leaves stays on that cadence for the life of the lane. Correctness
  never depends on it.

:::warning
Never block inside `poll_events` waiting on data-plane progress you
yourself gate. The one sanctioned wait is `DrainBarrier::wait` during a
revocation, where the runtime guarantees the pipeline threads are draining
toward it.
:::

## Testing

Drive your source without a full pipeline: construct a `Checkpointer`, call
`open` with `SourceCtx::new(cp.handle())`, poll events, poll lanes, and
assert on committed watermarks. The bottom half of
[`custom_operator.rs`](repo:crates/spate/examples/custom_operator.rs) does
exactly this with the memory source, and
[Testing pipelines](../03-guides/testing-pipelines.mdx) covers the
`spate-test` harness. To run it for real, hand it to the builder:
`pipeline.sink(...)?.chains(...).run(source)`. The source stays a terminal
generic, so no registration is needed
([Assembling a pipeline](../03-guides/assembling-a-pipeline.mdx)).

## Feed-reading sources

A source whose input is a queue of
[work units](../07-reference/glossary.mdx#work-unit) reads it through the `Feed`
trait in [`spate-core/src/feed/mod.rs`](repo:crates/spate-core/src/feed/mod.rs).
The [feed](../07-reference/glossary.mdx#feed) delivers each unit at least once,
and the source acknowledges a unit when it is done with it. The trait is
synchronous, so `poll_events` drives it from the controller thread.
[Work feed](../02-concepts/09-work-feed.mdx) explains the model behind the rules
below.

The pipeline file names the feed in its
[`feed:` section](../07-reference/configuration.mdx#feed). Accept the section in
`configure_feed`. The runtime calls it before `open`, with the section, the feed
it names, and the feed's `FeedOrigin`: `Section` when the runtime built the
feed, `Given` when code passed it to `Pipeline::feed` and may still publish into
it. Keep the feed, and read the section's common keys, such as `units_held`.
`SourceCtx::threads` gives the pipeline thread count at `open`, for a source
that sizes its read parallelism from it; it is `None` when the source is opened
by hand, as in [Testing](#testing). The
default `configure_feed` refuses the section, so a source that reads no feed
fails at startup when one is set. The runtime builds the in-process feed for
`feed: { memory: {} }` and logs nothing about who publishes to it, since only
the source knows. A source that does not publish to the feed it reads says so in
its own log when it opens.

Your source follows these rules:

- **Acknowledge a unit only after you have read it to its end and the sink
  has acknowledged every record in it.** A unit you read in several parts is
  acknowledged once, after every part meets that rule. A unit whose input was
  replaced while you read it may instead be acknowledged once a unit naming
  the input's current state is stored in the feed and the sink has
  acknowledged every record you read from it.
- **Fail a unit you cannot read.** The feed delivers it again, and moves it to
  its dead-letter destination at its delivery cap.
- **Key the units you hold by `Receipt`.** A second delivery of a unit you
  already hold arrives under a new receipt with the same unit id, and you read
  it again from its start. No feed deduplicates by unit id.
- **Let go of a delivery whose receipt answers `Gone`.** The feed has
  delivered that unit again or already settled it, so retrying the call
  cannot succeed.
- **Renew every unit you hold on each `poll_events` call, and in
  `renew_held`.** A backend that leases units extends a lease only while its
  holder renews it, so a control plane that stops running gives its units
  back to the feed. While a revocation waits for its drain, for up to
  `checkpoint.drain_timeout`, the runtime calls `renew_held` and no
  `poll_events`. Renew there, and settle and report nothing.
- **Never wait on the feed inside `poll_events`.** Hand the feed a waker from
  `wake_channel` with `set_waker`. When there is nothing to do, park on the
  paired `FeedPark` for at most the `timeout` that `poll_events` was given. A
  park uses up the feed's signal, so call `receive` with the room you have
  before you park.
- **Give each lane a clone of the same waker.** A lane signals it once, when
  it reaches the end of its input or cannot read its unit, after making that
  state visible to the control plane. The park then ends at once, so
  `poll_events` sees the lane's end without waiting out the `timeout`.
- **End a bounded job through an `EndCheck`.** While your reader holds no
  unit, ask it what to read next, start that read without waiting on it, and
  report each answer with the instant from your clock. Call `restart` as soon
  as the reader holds work again, and drop every read outstanding: the check
  tells answers apart only by kind. Report `Drained` on `Completed`, and fail
  the run on `Stalled` or `Failed`, and on a marker read that cannot succeed.
  A feed whose `read_depth` returns `None` cannot end a bounded job, so refuse
  it in `open`.
- **On a feed that hands back, read on what you hold when the stop begins.**
  When `SourceCtx::stop` is set and `Feed::hands_back` answers `true`, call
  `stop_receiving` once, receive nothing more, and keep reading and renewing
  the units you hold. Answer `reading_on_stop` with whether any held unit is
  not yet read to its end. The runtime calls `stop_reading` once, at the first
  `false` or at the stop reserve (`STOP_RESERVE`, 5s before the drain
  deadline): `hand_back` every unit you have not read to its end there, and let
  go of it. A unit read to its end stays held and is acknowledged by the final
  commit. A failed run calls `stop_reading` at once, with no reading.

The scripted feed in `spate-test` lets a test play the feed's side. This
reader, from [`spate-test/tests/feed.rs`](repo:crates/spate-test/tests/feed.rs),
holds a unit, sees it delivered again, and lets go of the lapsed receipt when a
renewal answers `Gone`:

```rust file=crates/spate-test/tests/feed.rs region=reader
```

`FeedScript` also scripts a duplicate delivery (`deliver` with an id already
delivered), a dead letter, a publish that is refused or held until the test
confirms it, and the answers to depth reads (`answer_depth`). It scripts a
refusal of the next `receive`, `renew`, `acknowledge` or `fail` with a given
error kind (`refuse_next_receive` and its siblings), which leaves the feed's
state as it was, and `refusals_left` counts the refusals not yet served. With
`hand_back_on_stop` it answers `hands_back` with `true`. It records every
acknowledgment, failure, renewal, depth read, `Gone` answer, `stop_receiving`
call (`stopped_receiving`), hand-back (`handed_back`) and close bound
(`closes`) for the test to assert on.

To implement a feed backend, keep every method free of waits:

- Run receives, lease renewals and publishes on a task or thread the backend
  owns. `receive` returns what that task has buffered, and the other methods
  hand their request to it. `Ok` means the backend accepted the request.
- Mint a new `Receipt` for every delivery, and count deliveries in
  `Delivery::deliveries`, starting at 1.
- Signal the waker when a unit becomes ready to receive, including one that
  arrived before `set_waker`, and after a `receive` that takes some units and
  leaves others. A `receive` that takes nothing sends no signal, so a reader at
  capacity can still park.
- Settle each publish through the `Confirmer` from `confirmation()`, and
  confirm only once the unit is stored. A confirmer dropped unsettled reads as
  `Retryable`, because the unit may or may not have been stored.
- Answer `read_depth` if your backend can count what it holds and what it has
  dead-lettered. Read the counts on your own task and settle the
  `DepthReporter` from `depth_reading()`. Set `approximate` when the counts
  are estimates, and count in `unsent` the acknowledgments and failures you
  have accepted and not yet applied. The default returns `None`, and such a
  feed serves continuous jobs only.
- Answer `hands_back` with `true` if a stopping reader should read your units on
  to the stop reserve and then return the ones it has not finished. Then
  `stop_receiving` stops your receive task, `hand_back` returns one held unit
  without counting it as a failure, and `close` sends what you still have queued
  and gives up what you hold, within the bound it is given, settling the
  `Confirmation` it returns when done. The runtime calls `close` once, after the
  final commit. Startup refuses a `checkpoint.drain_timeout` no longer than
  `STOP_RESERVE` for such a feed. The defaults answer `false` and do nothing.

A backend also answers to its name in the `feed:` section:

- Return your `feed:` key from `backend`. The runtime refuses a feed whose
  key differs from the one the section names. The scripted test feed returns
  `"scripted"`.
- Build the backend from a `FeedSection`, and refuse a section whose key is
  not yours. Decode your own keys from the section's backend body, and refuse
  a common key your backend cannot honor.

is the smallest complete backend. Worked reference:
