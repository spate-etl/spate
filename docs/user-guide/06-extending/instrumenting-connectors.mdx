# Instrumenting connectors

The engine already measures the pipeline your connector plugs into — records,
bytes, poll and flush durations, retries, errors, watermark age, end-to-end
latency — without you writing a line of instrumentation. This page is about the
seams where a connector *adds* to that picture: feeding a framework handle with
signals only the connector can see (consumer lag, a rebalance), carrying the
right labels so your series line up with everyone else's, and — when you need
something the taxonomy doesn't cover — registering your own metric on the same
facade the framework uses.

The taxonomy every framework series belongs to is [docs/METRICS.md](../../METRICS.md);
the operator's-eye view of the model is
[Monitoring](../05-deployment/monitoring.mdx). Read the first for names, the
second for the hot-path rules. This page mirrors
`crates/spate/examples/custom_metrics.rs`
(`cargo run -p spate --example custom_metrics`).

## What you get for free

Every stage is pre-instrumented by the engine, not by the connector. A source's
records and bytes are counted as the driver polls it; a sink's flushes, batch
sizes, retries, and errors are counted by the sink worker as it drains and
writes; the checkpointer owns commit and watermark metrics. A hand-rolled
`Source`/`RowEncoder`/`ShardWriter` inherits all of it the moment it is wired
into a pipeline. So the question is never "how do I emit `spate_sink_records_total`" —
the framework does — but "what does my connector know that the framework can't
measure from the outside?"

## Feeding a framework handle

Some signals live inside the connector and nowhere else: per-partition lag that
only the client can compute, an assignment callback firing. The framework
defines the handle
([`SourceMetrics`](../07-reference/README.mdx)); the connector holds it and
drives it. The handle arrives on `SourceCtx` at `open` — take it there, never
through a builder of your own:

```rust
// crates/spate-kafka/src/source.rs
fn open(&mut self, ctx: SourceCtx) -> Result<(), SourceError> {
    // The runtime shares the same handles it uses itself.
    self.metrics = ctx.stage_metrics.clone();
    // ...
}

// ...later, inside the poll/statistics path:
if let Some(m) = &self.metrics {
    // Only for partitions whose lag the client actually measured.
    m.set_partition_lag(partition, lag);
}
```

The handle is resolved once at build time and injected; the connector never
looks up a metric name on the hot path, it only calls methods on a handle it was
handed. Lag is the *only* part of it a source drives: take `ctx.stage_metrics`
at `open` and call `set_partition_lag` and `retain_partitions`. Leave the rest
alone — records, bytes, poll duration, rebalance counts, and active lanes are
all recorded by the runtime from the events your source returns, so a source
that also increments `rebalance_assigned` makes the counter read double.

:::danger[Take the handle from `SourceCtx`, publish only measured values, and clean up what you lose]
All three of these are scar tissue.

**Take the handle from `SourceCtx`.** A builder the runtime cannot reach is
dead code, not an option: the runtime registers the series either way, so a
connector that never receives its handle leaves the gauge rendering a permanent
`0`. For lag that is the worst possible failure — a maximally backlogged source
reports nothing wrong and every alert keyed on it stays green.

**Publish a value only once you have really measured it.** A
registered-but-unwritten gauge renders `0`, and for lag a `0` is
indistinguishable from "caught up". `SourceMetrics::set_partition_lag`
registers a partition's series on first call, so *not calling it* is how you
say "unknown". A client that reports "I don't know this partition's lag" must
be passed through as silence, never flattened to zero.

**Clean up the series you stop owning.** A per-partition series does not go
away when you lose the partition: the exporter has no deletion and no idle
timeout is configured, so dropping your handle is invisible — the series
renders its last value for the life of the process, and a reader summing across
members counts that partition twice. Two things are needed. Filter publication
to the live assignment, since a stale client snapshot still lists partitions
you have lost; and call `SourceMetrics::retain_partitions` with the **new**
assignment once the assignment change settles, which zeroes what you lost. Do
not prune on revocation: a source whose protocol revokes everything before
handing most of it back would blank partitions you still own and are still
draining.

Worked reference for all three: `crates/spate-kafka/src/source.rs` and
`crates/spate-kafka/src/metrics.rs`.

Test the wiring, not the registration: assert a **value** arrives end to end.
A test that only asserts the family appears in the exposition passes happily
against all three of these bugs.
:::

:::note
`SourceMetrics` is the one framework handle a connector is expected to drive
today. Sink-side signals (flush outcomes, retries, replica health) are derived
by the sink worker and circuit breaker from the results your `ShardWriter`
returns — you report them by returning the right outcome, not by touching a
metrics handle. See [Custom sinks](custom-sink.mdx).
:::

## Labeling your component

Every framework series carries three standard labels — `pipeline`, `component`,
`component_type` — plus stage-specific ones (`shard`, `replica`, `partition`).
`component` and `pipeline` come from `with_metrics(pipeline, component)` at
assembly. The two you set as a connector author are on the sink builder:

- `SinkParts::with_component_type("...")` sets `component_type`
  (default `"custom"`) on every sink series. Every shipped sink sets it to the
  system it writes to, and yours should read as whatever names your
  implementation.
- `SinkParts::with_replica_labels(...)` supplies the display names bound to the
  `replica` label, so per-replica health and error series identify the right
  endpoint.

[Custom sinks](custom-sink.mdx) is the reference for both — this page doesn't
repeat the plumbing. The rule to internalize: pick a stable, low-cardinality
`component_type` and give replicas human-meaningful names.

## Owning a metric family

When the taxonomy genuinely lacks something your connector or pipeline needs,
register it through a [`Meter`](../07-reference/README.mdx). A `Meter` is a
small, cloneable scope bound to one component's three standard labels: every
handle it mints inherits them, and its name is **auto-prefixed under the `spate_`
umbrella**, so your series sit right alongside the framework's and an operator
finds the whole pipeline's telemetry under one greppable `spate_` root.

```rust
use spate_core::metrics::Meter;

// A connector claims its namespace; a pipeline author uses `Meter::new`.
let meter = Meter::with_namespace("kafka", "orders", "orders_kafka", "kafka");
// Pass the LOCAL name — the Meter prepends `spate_kafka_` for you.
let schema_fetches = meter.counter("schema_fetches_total", &[("registry", "prod".into())]);
let fetch_seconds = meter.histogram("fetch_duration_seconds", &[]);

// Hot path: touch only the handles, per batch.
schema_fetches.increment(n);
fetch_seconds.record(elapsed);
```

This renders:

```text
spate_kafka_schema_fetches_total{pipeline="orders",component="orders_kafka",component_type="kafka",registry="prod"}
```

The rules the `Meter` enforces so you don't have to think about them:

- **You never type the prefix.** `Meter::new(...)` uses the `custom` namespace
  (`spate_custom_*`) — the bucket for pipeline-author metrics;
  `Meter::with_namespace(...)` claims a connector segment
  (`spate_<namespace>_*`). The namespace is validated once at construction and **cannot
  be a reserved framework stage root** (`source`, `sink`, `deser`, …), so a
  custom family can never collide with a current or future framework metric.
  This is the shape Prometheus's own `namespace_subsystem_name` convention
  describes: a single application prefix, with everything below it owned by
  the application.
- **Standard labels are automatic.** The `extra` slice is `&[]` for none;
  values are `SharedString`, so `"prod".into()` and an owned `String` from
  config both work. Push per-instance identity (a topic, a shard) into `extra`
  labels, not the name, keeping the name low-cardinality.
- **Store the handles** (`Counter` / `Gauge` / `Histogram`, re-exported from
  `spate_core::metrics`) in your own struct — no direct `metrics` dependency.

A crate that provides **both a source and a sink**, appearing at both ends of
one pipeline, is separated by the runtime, not by you: when it injects a
component's `Meter` it derives the end from the source-vs-sink position and
scopes the family `spate_<namespace>_source_*` / `spate_<namespace>_sink_*`, so
its source `bytes_total` and its sink `bytes_total` land under distinct names.
Your connector code is identical at either end — you never name the role, and a
`Meter` local name may not itself begin with a role segment (`source_` /
`sink_`), which is reserved for exactly this scoping. Instance identity — two
sinks of the same type — stays in the `component` label, where same-meaning
series belong.

### From a pipeline author's operators

A `Meter` is also how you instrument an **operator** you write. Operator
closures are pure (`.map` / `.inspect` take a bare function — there is no
per-record context, by design), so the pattern is *mint at build time, close the
handle over the closure*. The chain factory hands you a
[`ChainCtx`](../07-reference/README.mdx); call `ctx.meter(component,
component_type)` there (it uses the `custom` namespace):

```rust
.chains(move |ctx| {
    // Registers `spate_custom_enrich_hits_total` — you pass the local name.
    let hits = ctx.meter("enrich", "map").counter("enrich_hits_total", &[]);
    chain(deser)
        .with_metrics(ctx.pipeline, "enrich")
        .inspect(move |r| if is_hit(r) { hits.increment(1); })
        .sink(ctx.sink("default"))
        .build()
})
```

`ctx.meter(...)` fills in the pipeline name for you; you name the component and
its type. `Counter` is `Arc`-backed, so closing it over a closure that the
runtime clones once per pipeline thread is correct — every thread feeds one
series.

## Dropping to the raw facade

If you need a metric **outside** the governed `spate_` namespace — mirroring a
third-party library's own naming, say — record it straight onto the
[`metrics`](https://crates.io/crates/metrics) facade. You get no standard labels
and no namespace enforcement, so the collision-avoidance is yours: prefix with
your own name, **not** `spate_` (that umbrella belongs to the `Meter`).

```rust
// Pre-register once, at build time; you own the whole name.
let schema_fetches = metrics::counter!("myconn_schema_fetches_total", "registry" => "prod");
schema_fetches.increment(n);
```

[Monitoring § The hot-path discipline](../05-deployment/monitoring.mdx) and the
`custom_metrics.rs` example own this pattern in full. Prefer the `Meter` above
unless you specifically want to live outside the `spate_` taxonomy.

## Contracts

The framework's own stages follow these, and so must anything you add — the
handle method shapes exist to make them the path of least resistance:

- **Pre-register at build time.** Resolve every name and label once and keep the
  handle; never resolve a metric name or build a label set on the per-record
  path. `SourceMetrics::new(...)` and `metrics::counter!(...)` both belong in
  construction, not the poll loop.
- **Count at batch boundaries.** Increment counters once per batch with the
  batch's totals; observe a batch's duration once (as a mean where per-record
  granularity would matter), never per record.
- **Follow the naming rules.** `_total` on counters, a unit suffix
  (`_seconds` / `_bytes` / `_rows`) on anything measured in a unit. Through a
  `Meter` the `spate_<namespace>_` prefix is added for you (you pass the local
  name); only a raw-facade metric needs a prefix you choose yourself, and that
  one must **not** be `spate_`. Name a latency histogram `*_duration_seconds`
  specifically: the exporter's default bucket layout is matched by that suffix,
  so a bare `*_seconds` histogram renders as a summary instead (see
  [Metrics § Histogram buckets](../../METRICS.md)).
- **Keep cardinality bounded.** `shard` and `replica` are bounded by cluster
  topology and always on; `partition` is gated behind
  `metrics.per_partition_detail` (default off) precisely because it is unbounded
  — with the single exception of `spate_source_lag_records`, which is ungated
  because it has no aggregate series to fall back to (see the box above).
  Don't attach an unbounded label (a key, an offset) to any series.
- **One live owner per gauge series.** A handle struct claims its series when it
  is constructed, and a duplicate claim on the same key is refused rather than
  shared — two live owners would be two writers racing to describe one piece of
  state, and the exposition cannot show that happened. Through the builder a
  collision is fatal (`BuildError` / `StartError`). Direct construction cannot
  fail a build, so it logs and the loser becomes a **shadow**: it still counts,
  because counters sum, but it publishes no gauge. A shadow is the failure you
  are most likely to meet in tests — see [Testing](#testing) below for why your
  fixtures need per-test labels.

:::warning
The exporter installs a **process-global** recorder, and a handle binds to
whatever recorder exists at construction. In a real pipeline
`Pipeline::from_config` installs the exporter from your YAML *before* any handle
is built; if you register metrics in a standalone tool, call `metrics::install`
first or your handles record into the void. See
[Monitoring](../05-deployment/monitoring.mdx).
:::

## Testing

Assert your instrumentation the way the framework tests its own: build a
**local** (non-global) recorder, exercise the code, and match against the
rendered exposition — no global install, so tests stay isolated and parallel.
`metrics::with_local_recorder(&recorder, || { /* drive the connector */ })` then
`handle.render()` gives you the scrape text to `assert!(...contains(...))`
against, exactly as `crates/spate/examples/custom_metrics.rs` and the `metrics`
module's own tests do.

**Give each test its own `pipeline` and `component` labels.** A local recorder
isolates the *exposition*, but it does not isolate the gauge-ownership claim
described above, which is process-wide. `cargo test` runs a binary's tests in
one process, so two tests building the same handle with the same labels have the
second one become a shadow — its counters still sum, but its gauges publish
nothing, and the assertion fails somewhere unrelated to the change that broke
it. Distinct labels per test avoid the collision entirely.

## From a built-in source or sink

A `Meter` you construct with `Meter::new(...)` — or take from `ChainCtx` —
covers pipeline authors. A **built-in `Source` or sink `ShardWriter`** doesn't
construct one: the runtime hands it a pre-scoped `Meter` at construction, so a
connector never wires the pipeline name, the labels, or the prefix.

- **Declare a `component_type`.** A source overrides
  [`Source::component_type`](../07-reference/README.mdx) (default `"source"`); a
  sink sets it via `SinkParts::with_component_type` (default `"custom"`). That
  string is both the standard `component_type` label *and* the metric namespace,
  so it must be a distinct, non-reserved segment: the defaults (`"source"`,
  `"custom"`) opt out (see below), and `"custom"` in particular is reserved for
  pipeline-author metrics.
- **Receive the `Meter`.** A source reads `Option<Meter>` from
  `SourceCtx` in `open`; a sink's writer overrides
  `ShardWriter::attach_metrics(&mut self, Option<Meter>)` (called once before the
  writer is shared). The runtime scopes it by **role** — `source`/`sink` derived
  from the wiring position — so one crate's source families land under
  `spate_<namespace>_source_*` and its sink families under
  `spate_<namespace>_sink_*`, under distinct names. The connector's code is
  identical at either end.

```rust
// A source, in open():
fn component_type(&self) -> &str { "kafka" }
fn open(&mut self, ctx: SourceCtx) -> Result<(), SourceError> {
    if let Some(m) = &ctx.meter {
        self.queued = Some(m.gauge("fetch_queue_messages", &[])); // spate_kafka_source_fetch_queue_messages
    }
    // ...
}
```

`SourceCtx` also carries `per_partition_detail` (the `metrics` config flag), so
a connector's own per-partition families honor the operator's cardinality
choice. It gates your families and the framework's `spate_checkpoint_*` detail;
it does **not** gate `spate_source_lag_records`, which is ungated by design.

The `Meter` is `None` when the `component_type` can't scope a family: a reserved
root (an undeclared source keeps `"source"`) or the author-reserved `"custom"`
(a sink's default) opts out silently, and a value that is a legal label but an
illegal metric-name segment (a hyphen, say) is logged at `warn` and
also yields `None` — so a component only gets a scope once it declares a
distinct, well-formed `component_type`.

Worked reference for the full production shape, including lazily-registered
per-endpoint series and detail-gated per-partition series:
`crates/spate-kafka/src/metrics.rs`, whose families are documented on the
[Kafka source](../04-connectors/sources/kafka/README.mdx#metrics) page. For a
minimal template see `crates/spate-test`'s `MemorySource` / `CaptureWriter`,
exercised end-to-end in `crates/spate-test/tests/component_metrics.rs`.
