# Continuous integration

How this repository decides what to run, what blocks a merge, and what is
allowed to fail after one. Most of this is only interesting if you are changing
the workflows themselves — but the first rule below explains why a check you
expected to see may not have run, and the last few explain the traps that have
already caught someone.

If you are looking for the commands to run locally before opening a pull
request, those are in
[CONTRIBUTING.md](https://github.com/spate-etl/spate/blob/main/CONTRIBUTING.md).

## The two workflows

There are two, and the split between them is a rule rather than a habit:
**anything whose job is to stop a change entering `main` runs on the pull
request; the scheduled tier is only for detecting the world changing underneath
a static tree** (a new advisory, a yanked crate, a dependency floor that stopped
building). A scheduled failure lands after the merge that caused it, which is
useless as a gate.

- **`ci.yml`** — `pull_request`, `push` to main, and `merge_group`. Three tiers:
  a cheap always-run tier (`lint`, `workflows`, `deny`, `changelog`), an
  expensive tier scoped by `scripts/ci-changes.sh`, and `ci-gate`. The expensive
  tier `needs: [changes, lint, workflows]` and deliberately **not** `deny` — a
  lint error should stop the fan-out, but the licence gate is independent of
  whether the code compiles and would tax every green PR with its ~2 minutes.

  `changelog` is the one tier-1 job nothing `needs:`, and that is deliberate
  rather than an oversight to tidy up. Folding it into `workflows` would put a
  missing release note in front of the whole expensive tier, so somebody who
  forgot one sentence would learn nothing else about their branch. On its own it
  blocks the merge through `ci-gate` without blocking the feedback.
- **`scheduled.yml`** — nightly (advisories, `minimal-versions`, loom, docs
  build and deploy) and weekly (feature powerset, container coverage, benches),
  selected by which cron fired. `workflow_dispatch`
  takes a `tier` input for testing. A `report` job files one tracking issue for
  any job that fails without its own reporting.

**Miri does not run anywhere, and that is deliberate.** The old nightly ran
`cargo miri test -p spate-core`, which took six hours and hit the 360-minute cap.
`spate-core` contains no `unsafe` at all, so there was nothing there for Miri to
find. The workspace's only `unsafe` is `erase_lifetime` in
`crates/spate-kafka/src/lane.rs` — a lifetime-only transmute of an rdkafka
`BorrowedMessage` — and Miri could not check that either: it reaches straight
into librdkafka, which Miri cannot interpret. So the honest statement is not
"there is no unsafe" but "the one piece of unsafe we have is outside what Miri
can see, and the crate Miri *was* pointed at has none". If `unsafe` appears in
code Miri can actually interpret, that is the trigger to bring it back.

`actionlint` is **not** run in CI, only locally. `taiki-e/install-action` has no
manifest entry for it, so putting it in CI would mean either a runtime-resolved
binary or a digest-pinned Docker image — neither worth it yet. It catches real
problems (it found two in this workflow set), so run it before pushing workflow
edits. `shellcheck` *is* in CI, over `scripts/*.sh`.

## The gate

**`ci-gate` is the only job that should ever be a required status check.** It
carries `if: always()`, `needs:` every other job, and fails on any dependency
that failed or was *cancelled* while accepting `skipped`. Two traps behind that:
a workflow skipped by `on: paths:` never reports at all and blocks a required
check forever (which is why the triggers here are unfiltered and all filtering
is per-job `if:`), and a *skipped* check reports as success — so a gate without
`always()` green-lights exactly the runs it exists to stop.

## What runs, and what decides it

`scripts/ci-changes.sh` decides what runs. Container suites are selected by a
reverse-dependency closure over the crate graph: a change confined to
`crates/spate-s3` runs `-p spate-s3` and `-p spate`, because the facade depends on it.
Note what that does *not* mean — the facade's own e2e suite drives Kafka and
ClickHouse, so a spate-s3 change still boots those. The closure answers "can this
break it", not "does this exercise it", and narrowing it by hand would buy back
those boots at the price of a table `cargo metadata` can no longer verify.

That table is hand-written and `--self-test` checks it two ways: the closure
against `cargo metadata`, and `CONTAINER_PKGS` against which crates actually
carry `#[ignore]`d tests. Run it after adding a crate or a dependency edge.
Classification is an ignore-list, not an allow-list — anything not recognised as
documentation counts as code, because an allow-list fails open when a new source
directory appears. The diff is taken against the **merge base** with
`--no-renames` and `-z`: the base-branch tip would drag in everything `main` has
gained since the branch last moved, rename detection prints only the
destination (so moving a `.rs` file out of a crate would look like a docs
change), and `core.quotePath` C-quotes non-ASCII filenames into matching
nothing.

### Forcing a suite on

Three labels override the path selection upward:

| Label | Effect |
| --- | --- |
| `ci: docker` | Runs every container suite, whatever the paths selected |
| `ci: loom` | Runs the loom models, which are otherwise nightly only |
| `ci: bench` | Runs the instruction-count benches, whatever the paths selected |

They exist for the change whose blast radius the path rules cannot see — a
refactor that moves code between crates, or a fix under an invariant you want
proven before merge rather than the next morning.

They can only add work. That is a property of the code rather than a rule
somebody has to remember: the override appends to the selected set and never
assigns over it, so its result is a superset of the path-derived one by
construction, and `--self-test` asserts that for a matrix of label and
starting-set combinations. Nothing switches a suite off. The classifier fails
closed on purpose, and a label that could clear a selection would make it fail
open with a checkbox instead.

Applying a label re-triggers the workflow, because `labeled` is in the trigger's
`types:`. Removing one does not, since removing it cannot turn anything off — the
path-derived baseline simply stands again on the next push.

One deliberate interaction: the override is applied *after* the rules that defer
container suites on the two bot pull requests — a Dependabot bump and the
release pull request — so labelling one `ci: docker` is a maintainer overruling
that deferral for a single pull request.

Both defer for the same reason. A version bump touches `Cargo.lock`, which the
path rules read as moving the whole dependency graph and answer with every
container suite; the push-to-main run boots them again minutes after the merge
regardless. The release pull request has the stronger case of the two, because
release-plz rewrites it on every push to `main` and its source tree is
byte-identical to the `main` commit that just ran the suites. Both keep the
whole cheap tier — lint, deny, the full test suite, each-feature and MSRV.

## The Actions allowlist

The organisation permits GitHub-owned actions, verified-publisher actions, and
an explicit list of patterns; everything else is refused. Two things about that
are worth knowing before adding an action, because neither is discoverable from
this repository.

**A refused action does not fail the job — the run never starts.** It reports
`startup_failure` with no annotation naming the action, and the reason appears
only in the run's error text. A `startup_failure` also cannot be re-run: it
needs a fresh event, so reopening the pull request is the way to retry.

**The allowlist applies to actions your actions use.** `release-plz/action`
calls `cargo-bins/cargo-binstall` and `release-plz/git-config` internally, and
both had to be listed. No grep over this repository finds them — they live
inside a third-party composite action. Listing every direct `uses:` is
necessary and not sufficient:

```sh
grep -rhoE 'uses: [^ ]+' .github/workflows/*.yml .github/actions/*/action.yml \
  | sed 's/uses: //' | grep -v '^\./' | sed 's/@.*//' | sort -u
```

So after adding a third-party action, run the workflow once and read the
failure if there is one. That is the only way a transitive dependency surfaces.

## Action pinning and the shared preamble

GitHub Actions are pinned to full commit SHAs. Use
`pinact run .github/workflows/*.yml .github/actions/*/action.yml` — note the
second glob, because the toolchain and tool pins live in the composite
action and the first glob alone would miss them. Run it rather than editing
them by hand. It is not a complete check, though: `pinact` accepted a pin that
was an annotated *tag object* rather than the commit it points at — a SHA
GitHub answers `No commit found` for, so the workflow could never have resolved
it — and it accepted a real SHA carrying a version comment three majors out of
date. `zizmor` caught both, through its `ref-version-mismatch` audit. Run both.

Note `pinact` refuses to pin a *branch* ref
(`dtolnay/rust-toolchain@stable`) or a tool-alias ref
(`taiki-e/install-action@nextest`), because in both cases the ref name selects
behaviour. **No workflow takes either exception** — both are SHA-pinned
with the selector moved into an explicit `toolchain:`/`tool:` input, which is
stronger, and is the pattern to keep. The shared preamble lives in
`.github/actions/setup-rust` (a composite action, so it runs in the caller's job
and costs no extra runner); the caller does its own `actions/checkout` first,
because a `uses: ./...` action cannot check out the tree that contains it.

## The documentation site

The documentation site (Docusaurus) lives in `website/` and renders the
`docs/` tree in place; built on every docs pull request by `ci.yml`'s `site`
job and deployed to Cloudflare Pages by the nightly tier of `scheduled.yml`
(`baseUrl` is `/`). The PR build deliberately stages neither rustdoc nor the
licence texts — both are deploy-time artifacts, and generating them cost every
*Rust* pull request a full `cargo doc` plus an `npm ci` it had no other use for.

Two consequences, both deliberate and both worth stating plainly. **The whole
published site trails `main` by up to a day**, not just `/api/`, because the
deploy is nightly rather than per-push. And `cargo doc` and `about/html.hbs`
are not exercised before merge, so a rustdoc-breaking doc comment or a broken
licence template merges green and fails that night — which is why a
`docs-build` failure files an issue rather than going unnoticed.

```sh
cd website && npm ci            # first-time setup (CI uses Node 24; engines say >= 18)
npm start                       # local preview at http://localhost:3000/
npm run build                   # production build into website/build
CI=true npm run build           # what CI actually runs — see below
```

`website/.npmrc` sets `ignore-scripts=true`, so dependency lifecycle hooks never
run on install. Prefer `npm ci` over `npm install` — it installs the committed
lockfile verbatim instead of re-resolving it.

The site builds under **Docusaurus Faster** (`future.faster`, stable since 3.10
and the default in v4): Rspack and SWC in place of webpack, Babel and Terser.
Measured on this site, cold: **10s → 3s**, and 2s with the Rspack persistent
cache in `website/node_modules/.cache` retained. CI restores that cache *after*
`npm ci`, which is not stylistic — `npm ci` deletes `node_modules` before
installing, so a cache restored earlier is thrown away and the step silently
does nothing. `faster` also requires `future.v4.removeLegacyPostBuildHeadAttribute`,
which is enabled on its own rather than via `v4: true`; the other v4 flag,
`useCssCascadeLayers`, changes CSS precedence and wants its own visual check.

**Verify the site with `CI=true npm run build`.** The client-redirects plugin is
registered only when `process.env.CI === 'true'`, so a plain `npm run build`
silently skips redirect validation — and a redirect whose target page was deleted
is a hard build failure. Deleting a docs page means deleting any redirect aimed
at it; without `CI=true` you will not find out until the PR is red.

The `/api/` rustdoc is generated into `website/static/api/` (gitignored) by the
nightly deploy only, not by the PR build. To populate it locally: `cargo doc
--workspace --exclude benchmarks --no-deps --all-features`, then copy
`target/doc/.` into `website/static/api/`. The site builds fine without it —
the navbar and footer reach rustdoc through `pathname:///api/`, which
deliberately bypasses Docusaurus's link checker.

Verify gates by **explicit exit codes** (redirect to a log, check `$?`);
piped `grep`/`tail` chains have masked real failures in this repo.

## The test suite

Tests run under [cargo-nextest](https://nexte.st) (`cargo install cargo-nextest`
or `brew install cargo-nextest`; config in `.config/nextest.toml`). It runs one
process per test concurrently, where `cargo test` runs one binary at a time —
plain `cargo test --workspace` still works but is many times slower. Two costs it
hides, both measured on this workspace:

- The suite's in-process time is ~150s spread over ~40 binaries; serially that
  is the sum, concurrently it is the max.
- **On macOS, every freshly linked binary stalls 13–35s at 0% CPU on its first
  exec** while Gatekeeper/XProtect scans it (per inode; re-exec is instant).
  Across the workspace that alone was ~30 min per edit-test cycle. Add your
  terminal to *System Settings → Privacy & Security → Developer Tools* to
  exempt it; verify with
  `cp target/debug/deps/<bin> /tmp/probe && time /tmp/probe --list`.

`--all-features` enables `spate-kafka/tls` → `rdkafka/ssl-vendored`, which compiles
OpenSSL from source. Drop it when you don't need the TLS surface. It also enables
`spate-coordination/testing`, which exposes `clock::TestClock` — that feature is off
by default and must never be enabled by the `spate` facade: a `TestClock` in
production stops the coordination control loop dead.

Three nextest profiles: `default` (local), `ci`, and `docker`. Use `--profile
docker` for anything `--run-ignored` — `default` hard-kills a test at 120s, which
a cold container pull can exceed, and the SIGKILL reports `TIMEOUT`
indistinguishably from a real hang.

Both `ci` and `docker` retry once. The container suites earn it on measurement
rather than on the assumption that container failures are infrastructural: the
servers they boot become ready in about a second and have never taken more than
six, while *starting* a container is near-instant once warm but costs ten to
sixteen seconds on a job's first boot, and has been seen to exceed sixty. That
spread belongs to the docker daemon, and no fixture change reaches it.

A retry does not hide the failure it absorbs. A fixture that boots a container
waits for it to answer a real query, and on timeout reports that container's
liveness, exit code and log tail; a retried test lands as a flaky annotation in
the container job's JUnit report. A retry that starts recurring with a cause
attached is a signal to delete the retry, not to trust it.

`benchmarks/` sets `autobins = false`, so a new rig in `benchmarks/src/bin/` is
invisible to cargo until it also has a `[[bin]]` stanza (with `test = false`).
`benchmarks::manifest::every_rig_is_declared_as_a_bin` fails if the two diverge.
Note the rigs are not built by `cargo nextest run`; `cargo clippy
--workspace --all-targets` is what compile-checks them (and the examples) — on
every PR **that touches Rust**, since that step carries
`if: needs.changes.outputs.rust == 'true'`. A docs-only PR compile-checks
nothing, which is the point, but it does mean the rigs are unguarded on exactly
those PRs. `cargo bench --no-run` adds only release-profile breakage on top of
that, and costs a second full dependency build, so it runs in the weekly tier.

## Performance gates

Three things on the pull-request path answer performance questions without
reading a clock: an allocation gate, a request-shape gate, and a tier of jobs
that counts instructions. A hosted runner is contended and virtualised, so a
wall-clock figure measured there describes the machine as much as the change —
which is why no wall-clock number gates anything here. What these three
compare is counts, which do not move with the runner's load. Instruction
counts carry one caveat of their own, in "the shard matrix" below: the runner
*image* still decides which instruction-set width a bench executes.

`alloc-assertions` runs the counting-allocator test over the chain hot path
(`cargo test -p spate-core --release --test chain_alloc`). Its bounds are
absolute rather than relative to a stored baseline, so it compares against
nothing and cannot drift: an allocation that scales with record count fails it.
It builds in the release profile, because the bounds are calibrated against
optimised code — and it pays for that by sharing the `release` cache entry the
scheduled release-profile jobs populate from `main`.

`crates/spate-s3/tests/request_shape.rs` is the second, and it counts calls
rather than bytes: how many listings a coordinated backfill issues and how
many fetches each object costs, with the byte ranges asserted alongside. It
needs no container — a temporary directory behind the object-store client, an
in-process coordination store, and a recording wrapper that tallies the calls
— so it runs with the ordinary test suite rather than behind the Docker job,
and a change that quietly turns one fetch into two fails it. One assertion
there does read a clock, as a floor rather than a budget: the run has to
outlive the interval at which an open plan would re-list, or a listing count
of one proves nothing.

`perf-counters` runs the gungraun benches, which count instructions,
branches and cache references under callgrind, and heap shape — allocated
blocks and peak bytes — under DHAT in the same run. The decode benches cover
the error path alongside the happy paths: a malformed payload's
decode-until-error cost is what every bad record pays whichever record error
policy is configured. On a pull request the
comparison is a paired measurement inside the one shard: the merge base is
checked out and measured first as a named baseline, then the head run
compares against it — so the comparator is always the merge base, never a
cache whose newest entry could be any branch's. `scripts/gungraun-report.sh`
parses the machine-readable summaries into one table, in the step summary of
the job that aggregates them, and fails loudly if the summary schema version
ever drifts from the one its field paths were written against. The baseline
leg is scaffolding, not the gate: it discovers benches from the merge-base
tree by naming convention, carries `continue-on-error`, and wipes a partial
measurement — so a merge base that predates a bench reports that bench as
*new*, one with no benches reports no baseline, and one that no longer builds
on today's toolchain reports no baseline rather than blocking a pull request
on code its author did not write. Push and merge-group runs report absolute
counts.

### What the benches measure

The counted benches follow the hot paths: the operator chain and its split
terminal, the checkpoint and backpressure bookkeeping around it, payload
decoding and record framing, row and message encoding for the wire with the
routing in front of it, and the planning, assignment, claim scanning and
descriptor decoding a coordinated backfill does. A new one is written as a
single workload shape parameterised over the axis that changes its cost — a
listing profile, a codec, an entry point — rather than one case per function,
because attribution below the shape comes from the callgrind profile the run
already writes, and a finer set of cases would only duplicate it. That is the
rule for a new bench rather than a description of every existing one — several
predate it and carry a case per entry point.

Where a bench generates its own corpus, that corpus comes from a fixed
sequence and is pinned by a test — `crates/<crate>/tests/bench_fixtures.rs`,
in six of the seven benched crates. A count is only comparable when both legs
of the comparison packed byte-identical input, so a generator free to drift
between them is a difference the report would charge to the change.
`spate-core` is the gap in that rule rather than an exception to it: nothing
pins what its rigs under `crates/spate-core/benches/support/` build.

The wall-clock benches beside them gate nothing. A pull request only
type-checks them, through the same `clippy --all-targets` that covers the
examples; the weekly tier builds them all in the bench profile and then runs
three by name — the divan chain bench, and two of the three criterion targets
against a baseline the previous week's run left in a cache. `spate-json`'s
criterion bench is built and never run, because each criterion target needs
its own step and it has none.

That comparison is drawn across two rented machines, so read it as evidence
the benches still produce numbers rather than as a regression signal. Nothing
blocks on the delta. The rotation step after it fails when *no* criterion
target wrote a baseline at all — the case where the comparison was vacuous —
which means one target silently dropping out is not what it catches.

Where a format crate wraps a third-party parser, the parser's own floor
belongs in the wall-clock bench: cases that call it directly, beside the
counted bench measuring the crate's path over the same bytes. The first is
what the underlying library costs and the second is what the framework adds to
it, and reading the second without the first turns a parser's regression into
an unexplained framework one. `crates/spate-json/benches/decode.rs` is the
worked example, with two caveats. The floor is in the tree for a person to
run, not on a schedule; and it covers only the default parser, so the crate's
second compiled feature arm is counted without one.
`crates/spate-avro/benches/decode.rs` has no floor at all — its non-crate
cases time a flattening helper and a `memcpy`, neither of which is the Avro
decoder.

One bench carries a design claim alongside its costs.
`crates/spate-core/benches/chain.rs` drives the production path — a boxed
chain fed borrowed payload batches through deserialize, filter, flat_map,
encode and hand-off — against the owned-payload equivalent, and that contrast
is what the zero-copy seam rests on: the borrowed chain allocates a fixed
number of times per batch and nothing per record, while the owned one
allocates once per record. Read the arms' allocation counts against each
other, not their wall clocks — they fan out differently, so only the
allocation contrast is like-for-like. Where the type erasure sits
was settled on a prototype of the same seam rather than by this rig: one
virtual call per batch is what the chain is built to, because a boundary per
stage scales with the stage count and blocks vectorisation, while a per-batch
boundary's own cost amortises away once each stage does realistic per-record
work. What holds the first claim true afterwards is the counted sibling
`chain_gungraun.rs`: it carries both arms as cases and runs DHAT alongside
callgrind, so each arm's heap shape and instruction count move under one
comparison. `alloc-assertions` is the narrower gate beside it — the borrowed
chain alone, against absolute bounds rather than a baseline — and it is what
fails if allocations start scaling with record count. Neither asserts that the
gap between the two arms stays open, so that part is re-established by running
the rig rather than watched for.

### The shard matrix

`perf-counters` is a matrix, one job per (package, compiled feature arm), and
that shape is forced rather than chosen. gungraun writes a summary to

```
target/gungraun/<package>/<bench-stem>/<group>/<fn>/<case>/summary.json
```

which has no feature component anywhere in it — the saved-baseline setting
changes filenames *within* that directory, not the directory. Two feature
builds of one bench in one workspace therefore overwrite each other's summary
*and* each other's saved baseline, and nothing reports it: the result is a
wrong number, silently. A job per arm gives each arm its own runner and its own
target tree, which is what makes the axis safe to have.

An arm is a label and a cargo feature list, and the table pairing them sits in
`scripts/ci-changes.sh` beside the rules that pick the packages — the matrix is
that same question with a second axis, and a file of its own would be a third
thing the apparatus list has to know about. The table is written rather than
derived, because a crate's feature keys are not its performance arms: most are
optional column types or transport knobs no bench executes, and the powerset
would be exponentially many shards for one real question. An arm earns a shard
by changing the code under the benches. `make self-test` checks every arm
against `cargo metadata`, so an arm naming a feature its package does not
declare fails the gate rather than burning a shard.

Three properties keep a matrix run from reporting a confidently wrong number,
and each of them is a mechanism rather than a convention.

**A shard whose merge base cannot build its arm has no baseline.** The baseline
leg runs the merge base's *own* copy of `scripts/gungraun-benches.sh`, and that
copy may predate the feature axis — in which case it ignores the arm and
measures the default build, so a comparison between the two legs is a
comparison between two different builds rendered as a delta. The shard
therefore probes first: asking the merge base's copy to run a package that
cannot exist reaches the empty-selection exit without invoking cargo if the
copy understands the axis, and the unknown-argument exit if it does not. Only
the first answer earns a baseline. The unmodified build skips the probe, which
is the rule rather than an exception to it: it asks the merge base for no
feature flag at all — what every copy of the script has always done — so both
legs build the same thing whatever the merge base knows.

**A shard that measured no baseline says so, rather than reading as new.** The
report distinguishes a bench with no comparison because it is new from one with
no comparison because its shard's baseline leg never produced one, and it can
only do that if the shard states which. Every shard states it, including by
stating the empty string.

**Row identity is stamped, not inferred.** A summary describes a bench, not the
build that produced it: the package survives only as an absolute directory path
on the machine that measured it, and the schema has no notion of cargo features
at all. So the identity that tells two rows of one matrix run apart does not
exist in the data, and each shard writes it in — a `spate_shard` object naming
its package, its arm and its baseline — before uploading its summaries.
`scripts/gungraun-report.sh` documents the contract it reads; the shard step in
`ci.yml` is the other half of it.

A dependent job downloads every shard's artifact, concatenates them and renders
the single table. Concatenation is the whole merge: the report sorts its rows by
shard and bench, so the order artifacts arrive in is not an order.

`perf-warm` is the third job of the tier, and it is load-bearing rather than a
nicety. A matrix multiplies a cold dependency compile by the shard count
instead of dividing it, so without a warm cache a fan-out of shards is slower
than measuring the same crates one after another. The counter tier has its own
cache entry, populated by
that one job from `main`: the bench profile inherits release, but the graph does
not — these builds pull each benched crate's dev-dependencies and the harness,
which no other release-profile job compiles. Sharing an entry with a narrower
job means whichever finishes first defines it, and the narrow one always
finishes first. The shards consume that entry and never write it, so the job
that compiled the most is the one whose tree they restore.

Two facts about the instrument itself are worth keeping in view. valgrind
emulates CPUID, so which instruction-set width a bench executes is decided by
the runner image rather than by the code — a runner-image bump can move a count
with nothing in this repository changing, which is why the shards log the
valgrind version alongside the measurement. And determinism is a property of
the instrument, not a guarantee about every bench: one encoder bench does not
reproduce bit-for-bit across two runs of the same commit. Its spread sits well
inside the advisory thresholds, and it belongs to that bench rather than to the
tier — so read a sub-threshold move on it as noise, not as signal.

Both legs, and `make bench-gungraun`, take **which benches exist** from one
place: `scripts/gungraun-benches.sh`. A list written into the workflow could
name a bench the Makefile did not, and the two sides of a comparison would
then measure different things without anything failing — so the baseline leg
runs the merge base's own copy of the script, and a merge base predating the
script reports no baseline like one that no longer builds. Its exit codes
separate the three outcomes the workflow acts on differently: every bench
ran, a bench failed, or this tree has none for the crates it was given.

Which of those benches a given pull request runs is a second question, and
`scripts/ci-changes.sh` answers it — described below. Its automatic set comes
from the same discovery, so a crate is measured by the pull request that gives
it a bench; the label and the apparatus paths take the discovered set whole.
Both legs of a shard are handed the identical answer either way, so the
comparison cannot end up measuring different sets on its two sides. `make
bench-gungraun` takes no list at all and stays the local convenience: it runs
every bench in the tree.

`make check-gungraun-benches` proves the exit-code contract, and that every
discovered bench declares a `harness = false` target. Without that stanza cargo
auto-discovers the file anyway, under the default libtest harness, and the
bench compiles cleanly and then fails at run time complaining about arguments
rather than about the missing target. It also proves the feature arm reaches
every cargo invocation and no other, by capturing the argument list a stub
cargo was handed: a seam asserted only in prose is one that passes whether or
not it is wired up.

The numbers are advisory and the jobs are not. The rendering step carries
`continue-on-error: true`, so a count that moved does not block a merge; all
three jobs of the tier are in `ci-gate`'s `needs:`, so a bench that stops
building or dies under valgrind does. The matrix carries `fail-fast: false` for
the same reason: `ci-gate` counts `cancelled` as failure, so fail-fast would
turn one real failure into several, all but one of them unattributable, and
throw away the measurements of every arm that was fine.

### The collected region

A third outcome belongs with the second rather than the first: a bench that
runs and reports a number it did not measure. Collection under callgrind is
bounded by a toggle on the module the benchmark macro wraps the function in,
and a toggle flips collection rather than forcing it on — so work the optimiser
leaves in an unstable shape inside that module can fall outside the collected
region, and whatever else runs while collection is on is counted in its place.
That is usually the C runtime freeing a corpus the fixture built outside the
region. Nothing else in the tier sees it: the bench builds, exits 0, reports a
plausible count in the millions, satisfies the summary schema, and renders a
row that every later comparison is then measured against.

`scripts/gungraun-collected-region.sh` reads the callgrind profile each case
leaves under `target/gungraun` and requires **at least 10% of a case's
collected instructions to be attributed to the binary under measurement, and at
least 1,000 of them**. Composition is the primary signal and magnitude
corroborates it, because a lost region has two faces: one leaves the C runtime
behind and reports a number nobody would question, the other leaves a handful
of instructions belonging to the toggled wrapper — application code, so
composition reads 100% and objects to nothing. Each rule is blind to the face
the other catches. Every case is judged separately, since a bench does not
necessarily lose its region in all of them. The
classification is the ELF object callgrind records against each instruction,
not a pattern over function names: every crate here and every Rust dependency
is compiled into the bench executable, so what falls outside it is the C
runtime the process links dynamically — the allocator, `memcpy`, the loader.
The binary is identified from the profile's own `cmd:` header, which is the
program valgrind ran, so no list of library names has to be kept current for
each platform. The parser is held to callgrind's own arithmetic — the self
costs it sums must equal the `summary:` lines the profile declares — and
refuses to judge a profile it cannot account for, rather than computing a share
from whatever it managed to read.

A case is not always one profile. callgrind writes one output per thread the
process ran, so a bench whose setup spawns a helper — a loopback stub that
answers one request, say — leaves a second file beside the first, complete and
well-formed and declaring zero cost, because that thread never entered the
collected region. Every part of a case is summed before anything is judged.
Judged a file at a time, that zero-cost part reads as a region that collected
nothing — the exact shape the guard exists to reject — and a healthy pull
request is refused for it. The parts of a case are the files in one directory,
which is what the harness writes per case, so grouping by directory rather than
by filename is what keeps a threaded bench whole. Summing is the more lenient
reading of the two, and that is the right trade: collection is toggled on the
thread that enters the measured function, so one part carries the cost and the
rest declare zero. A part that produced no records at all, or one that declares
no total of its own, is refused rather than skipped — an absence cannot
corroborate a sum.

The threshold is a floor on composition rather than on a count, so it does not
move when a bench gets faster or slower — and because it is a ratio, it reads
within a few points of itself on two architectures whose absolute counts do not
agree at all. Measured across every case in the tree, the lowest healthy share
is 33.35% on the runner architecture and 28.67% on the one a reproduction was
built on, against a reproduced degenerate case at 0.47%. That leaves a gap with
nothing in it; any threshold inside it separates the two. It sits at the bottom of the gap because the two errors are
not symmetric — a degenerate bench that passes becomes a baseline every later
comparison inherits, while a healthy bench that fails blocks a pull request
that did nothing wrong. The low end of the healthy range is genuine rather than
marginal: a decoder that allocates a tree per record spends most of its
instructions inside the allocator, and a guard that condemned it would be
calling allocation a defect.

This step gates. It runs on the head leg of every shard, labelled with that
shard's package and arm so a failure in a six-way matrix says which job
produced it and which case, and it carries no `continue-on-error`: a count that
moved is advisory because a reader can judge it, and a region that measured the
allocator is a broken bench. The merge-base leg is exempt for the reason it is
exempt from everything else — it is scaffolding, and code the author did not
write is not theirs to fix.

The convention the guard exists to enforce sits on the bench author's side: the
measured work goes in a named `#[inline(never)]` function the benchmark
function calls, which is a frame the toggle cannot lose. The benches that
predate the guard escape the problem because each reaches its workload through
a single cross-crate call, which has the same property by accident;
[CONTRIBUTING.md](https://github.com/spate-etl/spate/blob/main/CONTRIBUTING.md)
states the rule where a bench is written. `make check-collected-region` holds
the guard to both shapes using captured profiles and needs no valgrind, so it
runs on every pull request rather than only on a benched one.

A pull request's movement surfaces in two places, and nothing blocks on
either. The report marks any row that crosses the advisory thresholds —
instructions up 5%, allocated blocks moving by more than one in either
direction, peak heap up 5% — and a separate workflow, `perf-label.yml`,
syncs the `affects-performance` label from the same verdict: added when a
threshold is crossed, removed when it stops, so the label self-clears when a
fix lands. The thresholds are provisional, borrowed from the closest worked
reference in the ecosystem; tightening them from this repository's own
observed deltas is deliberately deferred until enough real pull requests
have been through the job, because a threshold set too tight turns an
advisory signal into a rerun button.

The label workflow is the privileged half of a two-workflow split, and the
split is a security boundary rather than an organisational one. The benches
execute the pull request's code, so the counter tier runs with a read-only
token and hands over exactly one boolean as an artifact; `perf-label.yml`
runs with `pull-requests: write`, checks out nothing, executes nothing from
the pull request, binds its download to the triggering run, and treats the
artifact as untrusted input parsed as `true`, `false`, or ignored. The two
workflows can never execute together before a merge — the label half runs
the default branch's definition — so the write side of that one-file
contract runs on every pull request instead, as `make check-perf-report`. The
report itself deliberately never leaves the step summary: re-posting
fork-authored markdown from a privileged workflow is the vulnerability class
this design exists to avoid. Two consequences worth knowing: a CI run that
fails or skips the benches leaves the label untouched (a stale label beats
stripping a true one because a docs push skipped the benches), and
hand-applying the label only lasts until the next benched push.

The tier is selected by its own classification output, `bench`, and a second
output, `bench-shards`, is the matrix itself: a JSON array of
`{package, arm, cargo_features}` objects that `fromJSON` hands to
`strategy.matrix.include`. The two must agree — an empty `include:` is a
workflow-level error rather than a skipped job — so the classifier keeps them
consistent where it emits them rather than leaving the workflow to check.

The unit of selection is the whole crate rather than the modules a bench
imports, because codegen is crate-global: an edit anywhere in a measured crate
can shift inlining and with it the count. A path that reaches no measured crate
selects nothing here, whatever other jobs it selects — with one exception,
below.

The set is derived from what the benches discover rather than from a list, so
a crate is measured by the same pull request that gives it a bench:

- A crate that has a bench selects itself.
- `crates/spate-core/` selects every benched crate. Every crate depends on it,
  and by the same crate-global codegen argument a change there can move a count
  in any of them.
- A crate with no bench selects nothing.

Cost is bounded by the reach of the change rather than by a list. Each selected
crate crosses to one shard per arm, and each shard is two builds and two
valgrind runs — merge base and head — so a change confined to one benched crate
pays for that crate's arms, and only a change to the crate everything depends
on pays for all of them. The shards run concurrently, so the tier's wall clock
is the slowest arm rather than the sum. Both legs of a shard are given the same
package and the same arm, since measuring a different build on the two sides of
a comparison is the drift the single bench list exists to prevent.

`ci: bench` is how a path that selects less asks for the full set — a
dependency swap, or a refactor that moves code between crates.

The exception is the measuring apparatus. A change to the classifier, the
discovery script, the report script, the collected-region guard, `ci.yml` or
the shared setup action selects every benched crate, whatever crates it
touches, because each of them can alter the outcome for all of them — the last
because which cache a shard restores decides whether it compiles the bench
graph from scratch. Without that rule the pull request rewriting how benches
are chosen is the one that never runs them — a fail-open in the one classifier
built to fail closed. The list appears twice in `scripts/ci-changes.sh`, in the
classifying `case` and in the loop `--self-test` walks, so a file added to one
and not the other fails the gate rather than silently stopping forcing a
re-measurement.

`make self-test` holds these rules to their word. It asserts the shape of the
selection — the core crate selecting every benched crate, a benched crate
selecting itself, a crate without one selecting nothing — and that discovery
finds any bench at all, since an empty set would satisfy the rest while
nothing was measured. It asserts the arm table too: every arm names a feature
its package declares, exactly one arm per crate is the unmodified build, labels
are unique and carry only characters that survive JSON and an artifact name
unescaped, and at least one crate is measured under more than one arm — an axis
of size one everywhere would be a green run measuring less than it claims. It
then classifies a synthetic path list through the real arms, so each rule above
— including the apparatus one — fails the gate rather than this page when it
stops being true.

The runner binary's version must match the `gungraun` dependency exactly — a
mismatch fails every bench with a version error rather than a measurement —
so the workflow derives it from the locked workspace resolution
(`cargo metadata --locked`) at install time rather than hardcoding it. The
version is pinned by `Cargo.lock` like any other dependency; a dependency
bump carries the runner with it, and there is no second copy to drift.

That same resolved version is the cache key for the built binary, which is
otherwise a minute of compilation on every run that measures anything —
there is no checksummed prebuilt to fetch, so the alternative is building it
each time. Pinning the version on both the install and the key is what makes
the cache safe to trust: a restored binary can only ever be the one this
lockfile asks for, and a mismatch would be a hard error rather than a wrong
number anyway.

## Coverage

Coverage is `cargo llvm-cov`, reported to Codecov under two flags. `unit` runs on
every PR (docker-free) and is what the 80% **patch** target gates on
(`codecov.yml`, informational until calibrated). It is produced by the same run
as the tests — `cargo llvm-cov nextest` writes `target/nextest/ci/junit.xml` too,
so there is one instrumented run per PR rather than the suite executing twice.
`with-containers` runs in the **weekly** tier and merges the `#[ignore]`d
container suites in; `codecov.yml` sets `carryforward: true` on that flag
precisely so it can update on a slower cadence than `unit`. Measured before
splitting them: docker-free the workspace is at **87.6%** line coverage, spate-s3
92.2% and spate-kafka 91.5% — the container suites move the total by single digits
and cost ~an hour of serial docker, so they report rather than gate. Lowest crate
is spate-clickhouse at 77.6%; that is the one a patch target can realistically bite
on. Reproduce locally with:

```sh
cargo llvm-cov nextest --profile ci --workspace --all-features --summary-only \
  --ignore-filename-regex '(/tests/|/benchmarks/)'
```

Both suites publish their JUnit report as a check annotation — `Test results`
from the fast suite, `Container test results` from the container job. That is
what keeps `retries = 1` from hiding a flake behind a green run, and it is the
reason both jobs declare `checks: write`: without it the publish step reports
`Resource not accessible by integration` and continues, leaving the job green
and the annotation never written.

The loom invocation must stay `--lib`: doc tests compiled under `--cfg loom`
construct loom-typed primitives outside a model and abort. The same applies
to any test or module touching loom-aware dependencies outside a model —
tokio (net disappears under the cfg), quanta via the prometheus exporter,
and `AckRef` internals — gate those with `#[cfg(not(loom))]`.

Docker-backed integration tests (testcontainers) are `#[ignore]`d by default;
run them explicitly. MSRV is 1.94 — CI checks it; don't use newer features.
