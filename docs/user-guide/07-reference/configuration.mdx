# Configuration reference

This is the appendix of every configuration key: its type, default, and
meaning. It is a lookup, not a walkthrough. For how the file is loaded and
how connector sections reach their factories, see
[Configuring pipelines](../03-guides/configuring-pipelines.mdx).

One YAML file configures one process. The framework owns the typed sections
`pipeline`, `admin`, `checkpoint`, `backpressure` and `metrics`, validated
strictly (`deny_unknown_fields` at every level, so typos fail at startup with
the offending YAML path). The `source`, `deserializer`, and `sink` sections are
single-key mappings selecting a component type; their bodies are opaque to the
framework and deserialized by the component's own factory. The optional
[`feed`](#feed) section names the work feed a feed-reading source reads.

```yaml
pipeline: { name: orders, threads: 4, io_threads: 2 }
checkpoint: { interval: 5s, max_pending_batches: 1024 }
backpressure: { max_inflight_bytes: 256MiB }
admin: { listen: 0.0.0.0:9090 }     # /metrics, /healthz, /readyz
metrics: { exporter: prometheus }
source:
  kafka: { ... }          # body owned by spate-kafka
deserializer:
  avro: { ... }           # body owned by spate-avro (or json: { ... } — optional section)
sink:
  clickhouse: { ... }     # body owned by spate-clickhouse
```

**Conventions used in this appendix.** Keys are shown in `backticks`. A Default
cell is one of exactly three forms (`docs/STYLE.md` § 3): `required`, a
backticked literal, or `none` for optional-and-unset. Durations use humantime
syntax (`5s`, `100ms`, `2m`); byte sizes accept binary suffixes (`256MiB`,
`1GiB`) or a plain integer for bytes. Framework-section defaults are the exact
values from
[`spate-core/src/config/mod.rs`](repo:crates/spate-core/src/config/mod.rs); the
sink-pool and code-level defaults come from
[`spate-core/src/sink/config.rs`](repo:crates/spate-core/src/sink/config.rs) and
[`spate-core/src/pipeline/builder.rs`](repo:crates/spate-core/src/pipeline/builder.rs).

:::note
This appendix is **non-exhaustive**: each connector owns the keys inside its
`source`/`deserializer`/`sink` body, and custom connectors add their own. The
framework-owned keys are the single source of truth here; connector-owned keys
are documented on each [connector's page](../04-connectors/README.mdx) and
indexed below.
:::

## Environment interpolation

The raw text interpolates against the process environment **before** YAML
parsing, anywhere in the file (including connector bodies). Substitution is
textual and pre-parse, so quote the site (`password: "${PASSWORD}"`) when a
value may contain YAML-significant characters. See
[Configuring pipelines](../03-guides/configuring-pipelines.mdx#environment-interpolation)
for the parsing caveats.

| Key | Type | Default | Description |
|---|---|---|---|
| `${VAR}` | interpolation | — | The value of `VAR`; startup error if **unset** (an empty value is allowed). |
| `${VAR:-default}` | interpolation | — | The value of `VAR`, or `default` if **unset or empty**. |
| `${VAR:?message}` | interpolation | — | The value of `VAR`; startup error citing `message` if **unset or empty**. |
| `$$` | literal | — | A literal `$`. |

## `pipeline:`

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | `required` | Pipeline identity; the `pipeline` label on every metric. Must be non-blank. |
| `threads` | integer | `none` | Pipeline thread count. Unset: `available_parallelism` minus the I/O reserve (one core per two `io_threads`, rounded up, plus 1 for the controller), at least 1. Cgroup-aware — set explicitly on pods without CPU limits ([Tuning](../05-deployment/tuning.mdx)). Must be ≥ 1 when set. |
| `io_threads` | integer | `2` | Worker threads for the I/O runtime (sink workers, admin server). While `threads` is unset, each odd-numbered worker (the first, the third, and so on) takes one core from the derived pipeline thread count, down to its floor of 1. Must be ≥ 1. |
| `pinning` | `off` \| `compact` | `off` | Core pinning for pipeline threads. `compact` pins thread *i* to core *i* — only useful with exclusive cores (Kubernetes static CPU manager + Guaranteed QoS). |

## `checkpoint:`

| Key | Type | Default | Description |
|---|---|---|---|
| `interval` | duration | `5s` | How often committable watermarks are flushed to the source, and the cadence at which partial chunk buffers are sealed (while the pipeline is unblocked, a below-target chunk is sealed within ~one interval). Not a durability boundary (the sink write is); shorter intervals narrow the post-crash replay window and tighten worst-case commit lag. Must be ≥ `100ms`. |
| `max_pending_batches` | integer | `1024` | Hard ceiling on unacknowledged batches per partition: at the limit, the partition's lanes are skipped at the poll boundary until acknowledgments retire batches ([Backpressure](../02-concepts/03-backpressure.mdx#the-checkpoint-ceiling)). Must be ≥ 1. |
| `drain_timeout` | duration | `25s` | Shutdown/rebalance drain budget for in-flight sink batches. Keep comfortably below `terminationGracePeriodSeconds` ([Docker](../05-deployment/docker.mdx)). Must be `> 0`, and more than `5s` with a feed that hands back ([Graceful shutdown](../03-guides/graceful-shutdown.mdx#the-drain-choreography)). |
| `stalled_fail_after` | duration | `120s` | A partition watermark stalled behind a *failed* batch this long fails the pipeline, so a permanent sink failure becomes restart-and-replay instead of consuming while committing nothing. Must be `> 0`. |

## `backpressure:`

See [Backpressure](../02-concepts/03-backpressure.mdx) for the model and
[Tuning](../05-deployment/tuning.mdx) for the sizing rule tying these to the
sink batch settings.

| Key | Type | Default | Description |
|---|---|---|---|
| `max_inflight_bytes` | bytes | `256MiB` | Global cap on bytes admitted into the pipeline but not yet durably written. Must be `> 0`. |
| `high_ratio` | float | `0.8` | Fraction of the budget at which sources are paused. |
| `low_ratio` | float | `0.5` | Fraction of the budget below which sources may resume. Ratios must satisfy `0 < low_ratio < high_ratio <= 1`. |
| `min_pause` | duration | `500ms` | Minimum pause before resuming — avoids flapping, since resuming a paused lane is not free for every source. |

## `admin:`

The HTTP server carrying `/metrics`, `/healthz` and `/readyz`. See
[Monitoring](../05-deployment/monitoring.mdx) for how it pairs with
`metrics.exporter`, and [Docker](../05-deployment/docker.mdx) for the probe
semantics.

| Key | Type | Default | Description |
|---|---|---|---|
| `listen` | socket address \| `none` | `0.0.0.0:9090` | Bind address. `none` runs no server: no probes, no scrape endpoint, and the port stays free. An address the process cannot take fails the start, naming that address. A port of `0` asks the kernel to pick a free one, and the start logs the address the server bound. |

## `metrics:`

See [Monitoring](../05-deployment/monitoring.mdx).

| Key | Type | Default | Description |
|---|---|---|---|
| `exporter` | `prometheus` \| `none` | `prometheus` | `prometheus` mounts `/metrics` on the admin server; `none` installs no recorder, and `/metrics` answers 404. A pipeline's series go to a recorder already in the process, if there is one. |
| `per_partition_detail` | bool | `false` | Emit per-partition gauge series (`partition` label). Off by default: cardinality grows with the assignment. Does **not** gate `spate_source_lag_records`, which is always per partition. |
| `e2e_basis` | `ingest` \| `event` | `ingest` | Time basis for `spate_e2e_latency_seconds`. `ingest` is immune to producer clock skew; `event` measures true pipeline lag against record event time. |

## Sink pool (`batch` / `inflight` / `retry`) {#sink-pool}

Every sink connector maps its `batch`, `inflight`, `retry`, and `breaker`
sub-sections onto the framework's `SinkPoolConfig`
([`spate-core/src/sink/config.rs`](repo:crates/spate-core/src/sink/config.rs)).
The keys and defaults are **framework-owned and identical across sinks**, and
this table is their single source of truth; each connector page shows only the
keys it adds on top. See [Tuning](../05-deployment/tuning.mdx) for how to size
them.

| Key | Type | Default | Description |
|---|---|---|---|
| `batch.max_rows` | integer | `500000` | Row count that seals a batch. |
| `batch.max_bytes` | bytes | `128MiB` | Encoded (uncompressed) byte size that seals a batch. |
| `batch.linger` | duration | `1s` | Max time an unsealed batch waits before flushing — bounds latency at low throughput. |
| `inflight.max_per_shard` | integer | `2` | In-flight batches allowed per shard worker before backpressure. |
| `retry.initial` | duration | `100ms` | First retry backoff after a retryable batch failure. Must be non-zero and no larger than `retry.max`. |
| `retry.max` | duration | `10s` | Backoff ceiling. Must be non-zero. Once the delay reaches it, it stays there for the rest of that batch's retries. |
| `retry.multiplier` | float | `2.0` | Exponential backoff growth factor. Must be finite and within `[1.0, 1e9]` — below `1.0` the delay would shrink each attempt instead of backing off. |
| `retry.jitter` | float | `0.2` | Fraction of each delay randomized away. Must be finite and within `[0.0, 1.0]`, both ends allowed. Jitter only ever **shortens**: the sleep lands in `[(1 - jitter) × delay, delay]`, never above it and never at zero. |
| `retry.max_attempts` | integer | `0` | Attempt cap; `0` = unbounded (retry until the drain deadline — the at-least-once default). |
| `breaker.failure_threshold` | integer | `3` | Consecutive failures before a shard/replica endpoint is quarantined. |
| `breaker.open_for` | duration | `5s` | Quarantine duration before a half-open probe. Also caps how long a batch parked behind a fully-probing shard waits before re-checking of its own accord, clamped to `[100ms, 30s]` — a backstop against a signal that never arrives, never the thing recovery depends on. Must be non-zero and at most one year. |
| `breaker.half_open_probes` | integer | `1` | Concurrent probe writes allowed while half-open, per probe episode. Must be at least 1 — `0` fails startup, because taken literally it would mean the replica never recovers: the first probe is admitted regardless and nothing could ever re-admit the slot afterwards. |

The `retry` and `breaker` bounds above are enforced at load by
`RetryConfig::validate` and `BreakerConfig::validate`, which every sink calls,
so a bad multiplier, a zero retry delay, a zero or overlong `open_for`, or a
zero probe budget fails startup with the offending key rather than surfacing in
the write loop. They rule out the nonsensical, not the aggressive;
`initial: 1ns` passes. Both are
independently total at the point of use. The backoff saturates at `retry.max`
and never yields a zero-delay retry, and the breaker floors `half_open_probes`
at 1 and caps `open_for` at a year. A sink assembled in code rather than
YAML therefore cannot escape those guarantees by skipping validation.

There is **no upper bound on `retry.max`**, because a sink fronting an
expensive or rate-limited destination may want a very patient
policy. But `max_attempts: 0` (unbounded) together with a `retry.max` over five
minutes logs a warning at startup: once a shard backs off to that ceiling it
sleeps that long between attempts and never abandons the batch, so a stalled
shard is indistinguishable from a healthy idle one. Bound it with
`retry.max_attempts` or lower `retry.max` if you did not mean it. Delivery is
unaffected either way, since the drain deadline aborts an in-flight write at
shutdown and its data replays.

If you *did* mean it, `spate_sink_retry_backoff_seconds{shard}` is the live
counterpart to that startup warning: it reads the backoff a shard is currently
sleeping between attempts on an available replica (`0` when it is not backing
off), so a patient policy stays legible on a dashboard instead of looking like
an idle shard. Alert above `(1 - jitter) × retry.max` rather than at
`retry.max`, because the sleep is jittered downwards, so the gauge never sits
exactly on the ceiling. When every replica is quarantined the shard sleeps
waiting for the earliest of a probe window and an in-flight probe reporting, and
this gauge reads `0`; `spate_sink_shard_healthy` covers that state.

Connectors add their own keys on top of these; a client-level timeout, for
instance, is the connector's own, not the shared pool's. Those live on the
respective connector pages, indexed [below](#source-deserializer-sink).

## Chunk handoff (`chunk`) {#chunk}

`chunk:` tunes the chain terminal's per-shard chunking, the granularity at
which encoded rows are sealed and handed to the shard workers. Like the sink
pool above it is **framework-owned and identical across sinks**, and it sits
inside the sink body (`sink.<type>.chunk`, or per branch as
`sinks.<name>.chunk`), but it configures the *chain terminal*, not the sink
worker, so the framework reads it directly and connectors neither declare nor
see it. It is purely performance-shaping and never affects delivery correctness:
a below-target chunk is sealed on every `checkpoint.interval` tick regardless,
so the most a larger target can do is defer a commit by roughly one tick. It
can never hold offsets back indefinitely. See
[Chunk sizing](../05-deployment/tuning.mdx#chunk-sizing) for how to size it.

```yaml
sink:
  clickhouse:
    chunk: { target_bytes: 512KiB, encode_policy: skip }
```

| Key | Type | Default | Description |
|---|---|---|---|
| `target_bytes` | bytes | `64KiB` | Seal and send a chunk once its frame reaches this size. Workers merge chunks into full batches, so this does **not** bound insert sizes — it governs handoff rate. Must be `> 0` (rejected at load, naming `chunk.target_bytes`). |
| `encode_policy` | `skip` \| `fail` | `skip` | Policy for record-level encoder failures ([Error handling](../02-concepts/04-error-handling.mdx)). `skip` drops the record (metrics-counted); `fail` stops the pipeline. A fatal encoder error stops the pipeline regardless. |

Each `sinks.<name>.chunk` is independent, so a split tunes every destination
separately. The knob can instead be set in code via `SinkOptions::with_chunk`
(the install-time counterpart to the
[code-level knobs](#code-level-knobs-not-yaml) below); setting **both** the YAML
`chunk:` block and `with_chunk` on one sink is a load error, since it is
declared in exactly one place.

:::note
`chunk` is a **framework-reserved key** inside any sink body: the framework
strips it before the connector sees the body. A custom connector must not define
its own `chunk` field (it would be shadowed on a sink section, and the reserved
key is rejected on a `source`/`deserializer` section).
:::

## `source:`, `deserializer:`, `sink:`

Each is a single-key mapping in which the key selects the component and the body
belongs to it. The framework requires exactly one `source`, exactly one of
`sink` **or** `sinks`, and treats `deserializer` as optional.

| Section | Required | Body documented in |
|---|---|---|
| `source` | yes | [Kafka](../04-connectors/sources/kafka/README.mdx), [S3](../04-connectors/sources/s3/README.mdx), [Datagen](../04-connectors/sources/datagen/README.mdx), [Memory](../04-connectors/memory.mdx), or your own ([Custom sources](../06-extending/custom-source.mdx)) |
| `deserializer` | no — sources that emit ready-made records need none | [Avro](../04-connectors/formats/avro/README.mdx), [JSON](../04-connectors/formats/json/README.mdx) |
| `sink` **or** `sinks` | yes (exactly one) | [ClickHouse](../04-connectors/sinks/clickhouse/README.mdx), [Kafka](../04-connectors/sinks/kafka/README.mdx), [Memory](../04-connectors/memory.mdx), or your own ([Custom sinks](../06-extending/custom-sink.mdx)) |

**Security is per connector, and some of it is a build feature rather than a
key.** Each connector's page carries its own auth and TLS section; the matrix
of which is which is in
[Securing connections](../03-guides/securing-connections.mdx).

### `sinks:` map of named sinks {#sinks}

A pipeline that writes to more than one destination declares `sinks:`, a
`name -> component` map, **instead of** `sink:` (setting both, or neither, is a
load error). Each entry is an ordinary single-key component with its own full
configuration.

| Rule | Behavior |
|---|---|
| Selection | The chain's [split terminal](../02-concepts/06-multi-sink.mdx) resolves each branch by name (`ctx.sink("type_a")`). |
| Metric label | The entry name is the `component` label on that sink's `spate_sink_*` metrics. |
| `sink:` equivalence | A single `sink:` equals a one-entry `sinks:` map under the reserved name `"default"`, which keeps the historical label `component="sink"`. |
| Reserved names | `sink` and the empty string are rejected at load, so no two sinks can share a label. |

For the worked `sinks:` example and the routing DSL, see
[Configuring pipelines](../03-guides/configuring-pipelines.mdx#multiple-named-sinks)
and [multi-sink split](../02-concepts/06-multi-sink.mdx);
[ClickHouse multi-table](../04-connectors/sinks/clickhouse/multi-table.mdx)
shows the connector end-to-end.

## `feed:` {#feed}

Optional. The [feed](glossary.mdx#feed) a feed-reading source reads its
[work units](glossary.mdx#work-unit) from. One key names the backend, and its
body holds that backend's own keys. `units_held` applies whatever the backend;
`attempt_cap` applies to the in-process feed and the
[Kafka feed](../04-connectors/feeds/kafka/README.mdx), and a backend that cannot
honor it refuses it; a source that re-enqueues units caps them at it, and its
page says so. `location` names a job location for a source that reads one, and
`settling_window` times the end of a job that names one; the in-process feed
refuses both. Set on a source that reads no feed, the section fails startup. The
common keys and the backend count are checked when the file loads, and so are a
`location` or a `settling_window` beside `memory` and a `settling_window` out of
range, which the runtime also refuses when code passes the feed. The `memory`
body is checked when the pipeline starts, before the source opens, unless code
passes a feed to `Pipeline::feed`.

```yaml file=crates/spate/examples/s3_backfill.rs region=feed
```

The block is rendered from
[`s3_backfill.rs`](repo:crates/spate/examples/s3_backfill.rs).

| Key | Type | Default | Description |
|---|---|---|---|
| `<backend>` | component | `required` | Exactly one key naming the backend. `memory` is the in-process feed, which takes no keys of its own. It holds units within this process. A source that lists its own input publishes to it, and its page says so; code can publish to it by keeping a `MemoryFeed` handle and passing it to `Pipeline::feed`, and such a run ends only at a shutdown. Units from another process need a durable backend. Any other name is a backend built in code; its page under [Feeds](../04-connectors/feeds/README.mdx) documents its body. |
| `units_held` | integer | `none` | How many units the source holds and reads at once. A source that reads one unit in parts can count each part in progress against it, and its page says so. Unset, the source's own default applies, and its page states the figure. At least 1. |
| `attempt_cap` | integer | `10` | The delivery on which the in-process feed moves a failed unit to its dead-letter list, and the [Kafka feed](../04-connectors/feeds/kafka/README.mdx) moves it to its dead-letter destination. That feed also moves a unit whose recorded deliveries have reached the cap, without delivering it again. A backend that cannot honor the key refuses it. A source that re-enqueues units caps their re-enqueues at it, and its page says so. At least 1. |
| `location` | string | `none` | A [job location](glossary.mdx#job-location), an object-store prefix, for a source that reads one. A job on a durable feed that names one is bounded, and one that names none is continuous. That source's page says what the prefix holds. The in-process feed refuses it. |
| `settling_window` | duration | `5m` | The [settling window](glossary.mdx#settling-window) of a bounded job: how long a worker waits for its lister's job fingerprint at startup, and how long the feed must read empty between two reads of the lister's end marker before the job [ends](../02-concepts/09-work-feed.mdx#how-a-bounded-job-ends). From `20s` to `24h`; a backend whose counts settle more slowly refuses a shorter one, and its page says so. Refused on the in-process feed, which ends a job with no window, and by a source on a durable feed with no `location`. |

The runtime builds the in-process feed itself from `memory`. Any other backend
is built in code from the section and passed to `Pipeline::feed`, and the
runtime refuses a feed whose backend differs from the key the section names. The
section's backend keys, and `attempt_cap` as the feed's delivery cap, apply
only when a feed is built from the section, so a feed passed to
`Pipeline::feed` keeps the settings it was built with. `units_held`, `location`
and `settling_window` apply to every feed, since the source reads them, and so
does `attempt_cap` as the re-enqueue cap of a source that re-enqueues units.

## Code-level knobs (not YAML) {#code-level-knobs-not-yaml}

These knobs live in the assembly code rather than the file, because they
are properties of the program you write, not the deployment.

| Key | Type | Default | Description |
|---|---|---|---|
| `SinkOptions::queue_capacity` | integer | `8` | Bounded chunk-queue depth between pipeline threads and each shard worker (`Pipeline::sink_with`). Must be non-zero. |

The chain-terminal chunking (`target_bytes`, `encode_policy`) moved to the
per-sink YAML [`chunk:` block](#chunk); `SinkOptions::with_chunk` is its
install-time equivalent for pipelines assembled in code (mutually exclusive with
the YAML block on the same sink).
