# Configuration reference

This is the appendix of every configuration key: its type, default, and
meaning. It is a lookup, not a walkthrough — for how the file is loaded and
how connector sections reach their factories, see
[Configuring pipelines](../03-guides/configuring-pipelines.mdx).

One YAML file configures one process. The framework owns four typed sections —
`pipeline`, `checkpoint`, `backpressure`, `metrics` — validated strictly
(`deny_unknown_fields` at every level, so typos fail at startup with the
offending YAML path). The `source`, `deserializer`, and `sink` sections are
single-key mappings selecting a component type; their bodies are opaque to the
framework and deserialized by the component's own factory.

```yaml
pipeline: { name: orders, threads: 4, io_threads: 2 }
checkpoint: { interval: 5s, max_pending_batches: 1024 }
backpressure: { max_inflight_bytes: 256MiB }
metrics: { exporter: prometheus, listen: 0.0.0.0:9090 }
source:
  kafka: { ... }          # body owned by etl-kafka
deserializer:
  avro: { ... }           # body owned by etl-avro (or json: { ... } — optional section)
sink:
  clickhouse: { ... }     # body owned by etl-clickhouse
```

**Conventions used in this appendix.** Keys are shown in `backticks`; a blank
default (`—`) means the key is **required**. Durations use humantime syntax
(`5s`, `100ms`, `2m`); byte sizes accept binary suffixes (`256MiB`, `1GiB`) or a
plain integer for bytes. Framework-section defaults are the exact values from
`crates/etl-core/src/config/mod.rs`; the sink-pool and code-level defaults come
from `crates/etl-core/src/sink/config.rs` and
`crates/etl-core/src/pipeline/builder.rs`.

:::note
This appendix is **non-exhaustive**: each connector owns the keys inside its
`source`/`deserializer`/`sink` body, and custom connectors add their own. The
framework-owned keys are the single source of truth here; connector-owned keys
are documented on each [connector's page](../04-connectors/README.mdx) and
indexed below.
:::

## Environment interpolation

The raw text interpolates against the process environment **before** YAML
parsing, anywhere in the file (including connector bodies). Substitution is
textual and pre-parse, so quote the site (`password: "${PASSWORD}"`) when a
value may contain YAML-significant characters — see
[Configuring pipelines](../03-guides/configuring-pipelines.mdx#environment-interpolation)
for the parsing caveats.

| Key | Type | Default | Description |
|---|---|---|---|
| `${VAR}` | interpolation | — | The value of `VAR`; startup error if **unset** (an empty value is allowed). |
| `${VAR:-default}` | interpolation | — | The value of `VAR`, or `default` if **unset or empty**. |
| `${VAR:?message}` | interpolation | — | The value of `VAR`; startup error citing `message` if **unset or empty**. |
| `$$` | literal | — | A literal `$`. |

## `pipeline:`

| Key | Type | Default | Description |
|---|---|---|---|
| `name` | string | — | Pipeline identity; the `pipeline` label on every metric. Must be non-blank. |
| `threads` | integer | derived | Pinned pipeline thread count. Unset: `available_parallelism` minus the I/O reserve (`io_threads` + 1 controller), at least 1. Cgroup-aware — set explicitly on pods without CPU limits ([Tuning](../05-deployment/tuning.mdx)). Must be ≥ 1 when set. |
| `io_threads` | integer | `2` | Worker threads for the I/O runtime (sink workers, checkpointer, admin server). Must be ≥ 1. |
| `pinning` | `off` \| `compact` | `off` | Core pinning for pipeline threads. `compact` pins thread *i* to core *i* — only useful with exclusive cores (Kubernetes static CPU manager + Guaranteed QoS). |

## `checkpoint:`

| Key | Type | Default | Description |
|---|---|---|---|
| `interval` | duration | `5s` | How often committable watermarks are flushed to the source, and the cadence at which partial chunk buffers are sealed (while the pipeline is unblocked, a below-target chunk is sealed within ~one interval). Not a durability boundary (the sink write is); shorter intervals narrow the post-crash replay window and tighten worst-case commit lag. Must be ≥ `100ms`. |
| `max_pending_batches` | integer | `1024` | Maximum unacknowledged batches per partition before that partition pauses (a per-partition backpressure backstop). Must be ≥ 1. |
| `drain_timeout` | duration | `25s` | Shutdown/rebalance drain budget for in-flight sink batches. Keep comfortably below `terminationGracePeriodSeconds` ([Docker](../05-deployment/docker.mdx)). Must be `> 0`. |
| `stalled_fail_after` | duration | `120s` | A partition watermark stalled behind a *failed* batch this long fails the pipeline, so a permanent sink failure becomes restart-and-replay instead of consuming while committing nothing. Must be `> 0`. |

## `backpressure:`

See [Backpressure](../02-concepts/03-backpressure.mdx) for the model and
[Tuning](../05-deployment/tuning.mdx) for the sizing rule tying these to the
sink batch settings.

| Key | Type | Default | Description |
|---|---|---|---|
| `max_inflight_bytes` | bytes | `256MiB` | Global cap on bytes admitted into the pipeline but not yet durably written. Must be `> 0`. |
| `high_ratio` | float | `0.8` | Fraction of the budget at which sources are paused. |
| `low_ratio` | float | `0.5` | Fraction of the budget below which sources may resume. Ratios must satisfy `0 < low_ratio < high_ratio <= 1`. |
| `min_pause` | duration | `500ms` | Minimum pause before resuming — avoids flapping (pausing a Kafka partition purges its prefetch, so resume is not free). |

## `metrics:`

See [Monitoring](../05-deployment/monitoring.mdx).

| Key | Type | Default | Description |
|---|---|---|---|
| `exporter` | `prometheus` \| `none` | `prometheus` | `prometheus` mounts `/metrics` on the admin server; `none` records to a no-op recorder. |
| `listen` | socket address | `0.0.0.0:9090` | Admin server bind address (`/metrics`, `/healthz`, `/readyz`). |
| `per_partition_detail` | bool | `false` | Emit per-partition gauge series (`partition` label). Off by default: cardinality grows with the assignment. Does **not** gate `etl_source_lag_records`, which is always per partition. |
| `e2e_basis` | `ingest` \| `event` | `ingest` | Time basis for `etl_e2e_latency_seconds`. `ingest` is immune to producer clock skew; `event` measures true pipeline lag against record event time. |

## Sink pool (`batch` / `inflight` / `retry`) {#sink-pool}

Every sink connector maps its `batch`, `inflight`, `retry`, and `breaker`
sub-sections onto the framework's `SinkPoolConfig` (`crates/etl-core/src/sink/config.rs`).
The keys and defaults are **framework-owned and identical across sinks** — this
table is their single source of truth; each connector page shows only the keys
it adds on top. See [Tuning](../05-deployment/tuning.mdx) for how to size them.

| Key | Type | Default | Description |
|---|---|---|---|
| `batch.max_rows` | integer | `500000` | Row count that seals a batch. |
| `batch.max_bytes` | bytes | `128MiB` | Encoded (uncompressed) byte size that seals a batch. |
| `batch.linger` | duration | `1s` | Max time an unsealed batch waits before flushing — bounds latency at low throughput. |
| `inflight.max_per_shard` | integer | `2` | In-flight batches allowed per shard worker before backpressure. |
| `retry.initial` | duration | `100ms` | First retry backoff after a retryable batch failure. Must be non-zero and no larger than `retry.max`. |
| `retry.max` | duration | `10s` | Backoff ceiling. Must be non-zero. Once the delay reaches it, it stays there for the rest of that batch's retries. |
| `retry.multiplier` | float | `2.0` | Exponential backoff growth factor. Must be finite and within `[1.0, 1e9]` — below `1.0` the delay would shrink each attempt instead of backing off. |
| `retry.jitter` | float | `0.2` | Fraction of each delay randomized away. Must be finite and within `[0.0, 1.0]`, both ends allowed. Jitter only ever **shortens**: the sleep lands in `[(1 - jitter) × delay, delay]`, never above it and never at zero. |
| `retry.max_attempts` | integer | `0` | Attempt cap; `0` = unbounded (retry until the drain deadline — the at-least-once default). |
| `breaker.failure_threshold` | integer | `3` | Consecutive failures before a shard/replica endpoint is quarantined. |
| `breaker.open_for` | duration | `5s` | Quarantine duration before a half-open probe. |
| `breaker.half_open_probes` | integer | `1` | Probe writes allowed while half-open. |

The `retry` bounds above are enforced at load by `RetryConfig::validate`, which
every sink calls, so a bad multiplier or a zero delay fails startup with the
offending key rather than surfacing in the write loop. They rule out the
nonsensical, not the merely aggressive: `initial: 1ns` passes. The backoff
itself is independently total — it saturates at `retry.max` and never yields a
zero-delay retry — so a sink assembled in code rather than YAML cannot escape
those guarantees by skipping validation.

There is deliberately **no upper bound on `retry.max`** — a sink fronting an
expensive or rate-limited destination may legitimately want a very patient
policy. But `max_attempts: 0` (unbounded) together with a `retry.max` over five
minutes logs a warning at startup: once a shard backs off to that ceiling it
sleeps that long between attempts and never abandons the batch, so a stalled
shard is indistinguishable from a healthy idle one. Bound it with
`retry.max_attempts` or lower `retry.max` if you did not mean it. Delivery is
unaffected either way — the drain deadline aborts an in-flight write at
shutdown, and its data replays.

If you *did* mean it, `etl_sink_retry_backoff_seconds{shard}` is the live
counterpart to that startup warning: it reads the backoff a shard is currently
sleeping between attempts on an available replica (`0` when it is not backing
off), so a patient policy stays legible on a dashboard instead of looking like
an idle shard. Alert above `(1 - jitter) × retry.max` rather than at
`retry.max` — the sleep is jittered downwards, so the gauge never sits exactly
on the ceiling. When every replica is quarantined the shard sleeps waiting for
a probe window and this gauge reads `0`; `etl_sink_shard_healthy` covers that
state.

Connectors add their own keys on top of these — e.g. ClickHouse's
`timeouts.{send,end}` (its HTTP client, **not** the shared pool) and Kafka's
top-level `delivery_timeout`. Those live on the respective connector pages.

## `source:`, `deserializer:`, `sink:`

Each is a single-key mapping — the key selects the component, the body belongs
to it. The framework requires exactly one `source`, exactly one of `sink` **or**
`sinks`, and treats `deserializer` as optional.

| Section | Required | Body documented in |
|---|---|---|
| `source` | yes | [Kafka](../04-connectors/sources/kafka/README.mdx), [Memory](../04-connectors/memory.mdx), or your own ([Custom sources](../06-extending/custom-source.mdx)) |
| `deserializer` | no — sources that emit ready-made records need none | [Avro](../04-connectors/formats/avro/README.mdx), [JSON](../04-connectors/formats/json/README.mdx) |
| `sink` **or** `sinks` | yes (exactly one) | [ClickHouse](../04-connectors/sinks/clickhouse/README.mdx), [Kafka](../04-connectors/sinks/kafka/README.mdx), [Memory](../04-connectors/memory.mdx), or your own ([Custom sinks](../06-extending/custom-sink.mdx)) |

**TLS & SASL.** Kafka security (TLS, mTLS, SASL SCRAM/PLAIN) is configured
through the Kafka connector's `rdkafka:` passthrough, gated behind the opt-in
`kafka-tls` **build feature** (not a YAML key); ClickHouse encrypts over
`https://` replica URLs with no feature flag. See
[Securing connections](../03-guides/securing-connections.mdx).

### `sinks:` — multiple named sinks {#sinks}

A pipeline that writes to more than one destination declares `sinks:` — a
`name -> component` map — **instead of** `sink:` (setting both, or neither, is a
load error). Each entry is an ordinary single-key component with its own full
configuration.

| Rule | Behavior |
|---|---|
| Selection | The chain's [split terminal](../02-concepts/06-multi-sink.mdx) resolves each branch by name (`ctx.sink("type_a")`). |
| Metric label | The entry name is the `component` label on that sink's `etl_sink_*` metrics. |
| `sink:` equivalence | A single `sink:` equals a one-entry `sinks:` map under the reserved name `"default"`, which keeps the historical label `component="sink"`. |
| Reserved names | `sink` and the empty string are rejected at load, so no two sinks can share a label. |

For the worked `sinks:` example and the routing DSL, see
[Configuring pipelines](../03-guides/configuring-pipelines.mdx#multiple-named-sinks)
and [multi-sink split](../02-concepts/06-multi-sink.mdx);
[ClickHouse multi-table](../04-connectors/sinks/clickhouse/multi-table.mdx) shows the
connector end-to-end.

## Code-level knobs (not YAML)

These knobs live in the assembly code rather than the file, because they
are properties of the program you write, not the deployment.

| Key | Type | Default | Description |
|---|---|---|---|
| `SinkOptions::queue_capacity` | integer | `8` | Bounded chunk-queue depth between pipeline threads and each shard worker (`Pipeline::sink_with`). Must be non-zero. |
| `ChunkConfig::target_bytes` | integer | `65536` (64 KiB) | Chunk seal size at the chain's terminal stage. Workers merge chunks into full batches, so this does not bound insert sizes. A below-target chunk is sealed anyway on every `checkpoint.interval` tick (and on idle), so while the pipeline is unblocked its buffer holds acknowledgements for at most ~one interval; the acks themselves resolve through the sink's batch `linger` and write. |
| `ChunkConfig::encode_policy` | `Skip` \| `Fail` | `Skip` | Policy for record-level encoder failures ([Error handling](../02-concepts/04-error-handling.mdx)). |

**Coordination is assembly wiring, not source YAML.** A coordinated
source takes a fully built coordinator through its `with_coordinator`
builder (e.g. `StoreCoordinator` over the NATS store, with a
`CoordinationConfig` for `lease_duration`, `instance_id`,
`max_in_flight`, …) — no connector grows per-backend config keys or
compile-time features, and new store backends need no connector changes.
The wiring recipe lives in
[Coordination-aware sources](../06-extending/custom-source.mdx#coordination-aware-sources)
and the deployment shape in [Scaling out](../05-deployment/scaling-out.mdx);
what stays in the source YAML is the work and how this instance reads it.
For S3 the two are worth telling apart: `url`, `compression`,
`split_target_bytes` and `refresh_listing` shape the *work itself*, form
the job fingerprint, and must be byte-equal across every instance, while
`prefetch_bytes`, `chunk_bytes` and `store` are local read tuning and may
differ per replica.
