Spate 0.4.0 came out on 1 November, and its S3 source now reads its work from a
queue. At eight hosts the SQS feed kept 99.7% of a static split's throughput,
where split coordination in 0.3 kept 67%. A lister run publishes the prefix to
SQS or Kafka as work units, and every instance reads its units from that feed.
The same feed carries storage notifications, so a job can now read new objects
as they land, and a backfill that names a job location now ends on its own once
its work is read.

The Kafka source and sink now read and write ZSTD batches, and the source now
stops on a corrupt message, which 0.3 could commit past. The ClickHouse sink now
compresses inserts on the pipeline threads.

## Breaking changes

The changes to a pipeline file fail at load or at startup, with an error that
names the key, so a pipeline meets them before it reads a record. Those come
first, with the old form and the new. The changes to code come last, and only a
custom connector or a hand-built pipeline meets them.

**The S3 source now reads only through a feed.** A pipeline with an S3 source
must now name a `feed:` section. `feed: { memory: {} }` runs the source in one
process that lists its own prefix, as a 0.3 pipeline with no `coordination:`
section did.

```yaml
# 0.3
source:
  s3:
    url: s3://events/2026/
# 0.4
source:
  s3:
    url: s3://events/2026/
feed: { memory: {} }
```

The 0.3 form fails at startup on 0.4:

```text
Failed(FatalErrorReport { component: "source", reason: "source open failed: source error (Fatal): the S3 source reads work units from a feed, and the pipeline names none; add a `feed:` section, such as `feed: { memory: {} }` for a run in one process" })
```

**Split coordination is removed.** I removed it because a work feed does the
same job with a queue that already gives at-least-once delivery. [The S3 source
reads its work from a feed](#the-s3-source-reads-its-work-from-a-feed) has the
reasons and the figures. The `spate-coordination` crate goes with its memory and
NATS stores, and so do the `coordination` and `coordination-nats` features, the
`coordination:` section, `S3Source::with_coordinator`, and the `refresh_listing`
source key. A `Cargo.toml` that names one of the features no longer resolves:

```toml
# 0.3
spate = { version = "0.3", features = ["s3", "coordination-nats"] }
# 0.4
spate = { version = "0.4", features = ["s3", "sqs"] }
```

```text
package `coordinated-backfill` depends on `spate` with feature `coordination-nats` but `spate` does not have that feature.
```

A pipeline file that keeps either key fails to load:

```text
invalid configuration at `coordination`: unknown field `coordination`, expected one of `pipeline`, `admin`, `backpressure`, `checkpoint`, `metrics`, `source`, `deserializer`, `sink`, `sinks`, `feed` at line 8 column 1
source.s3.refresh_listing: unknown field `refresh_listing`, expected one of `url`, `compression`, `split_target_bytes`, `prefetch_bytes`, `chunk_bytes`, `store`
```

A coordinated job started on 0.3 cannot resume on 0.4, so it has to finish on
0.3 or run again through a feed. A run through a feed lists the prefix again,
and a sink without idempotence then sees those records twice.

**An unrecognized S3 `store` key now fails at load.** In 0.3 the source skipped
a key it did not recognize, so a misspelled `endpoint` built a client for the
default AWS endpoint and sent it requests signed with the configured
credentials.

```text
invalid configuration: source.s3.store."endpont" is not an object_store S3 option
```

**The Kafka connectors now refuse more `rdkafka:` keys.** The sink now sets
`allow.auto.create.topics=false`, so a sink pointed at a missing topic fails its
readiness probe. In 0.3 the probe's metadata read was enough to create the topic
with the broker's defaults, wherever the broker allows auto-creation. Both
connectors refuse the key, and the sink refuses an owned property written with a
`topic.` prefix, such as `topic.acks`:

```text
invalid configuration: sink.kafka: rdkafka."allow.auto.create.topics" cannot be overridden: forced off: a write to, or a metadata read of, a missing topic must fail, and never create the topic with the broker's defaults
invalid configuration: sink.kafka: rdkafka."topic.acks" cannot be overridden: forced to `all`: the framework commits source offsets once a delivery report confirms, so a report under weaker acks would turn at-least-once into at-most-once (`topic.acks` sets the same librdkafka property as `acks`)
```

The source now reads `topic.auto.offset.reset` as its reset policy. In 0.3 it
read only `auto.offset.reset`, so a new consumer group configured with
`topic.auto.offset.reset: earliest` skipped every record already in the topic.
Setting both keys now fails at load:

```text
invalid configuration: source.kafka.rdkafka sets both "auto.offset.reset" and "topic.auto.offset.reset": librdkafka reads them as one property and applies them in no set order; set one
```

The source now also refuses `topic.auto.commit.enable`,
`topic.enable.auto.commit`, and `topic.auto.commit.interval.ms`, which the
consumer never read. Every Kafka client now sends a `client.id` of
`spate-<section>-<role>`, such as `spate-sink-producer`, unless `rdkafka:` sets
one, so a broker quota set on librdkafka's default of `rdkafka` stops matching.
The source now also stops on a corrupt message, as [The Kafka source stops on a
corrupt message](#the-kafka-source-stops-on-a-corrupt-message) sets out.

**An Avro registry password now needs a username.** In 0.3 a `registry` section
with `password` and no `username` loaded, and the password was never sent.

```text
avro configuration: registry.password is set, but registry.username is not
```

**The ClickHouse sink now manages `decompress`.** The sink sets it because it
now compresses each chunk itself, so `settings: { decompress: … }` is now
rejected. Under `compression: lz4` or `compression: zstd`, server error 271 now
stops the sink. That error means the server could not decode a block.

```text
invalid configuration: sink.clickhouse: setting `decompress` is managed by the sink and cannot be overridden
```

**Some metric families are removed, and `feed` is now reserved.** Dashboards and
alerts built on these need updating:

- The 23 `spate_coordination_*` families are removed. An alert on
  `spate_coordination_splits_quarantined` can move to
  `spate_feed_dead_letter_units`, aggregated across instances with `max`.
- `spate_s3_source_objects_listed_total` is removed, because nothing increments
  it.
- `feed` is now a reserved namespace. A connector or pipeline that registered
  its own `spate_feed_*` families, or a `Meter` local name that starts with
  `feed_`, must rename it.

**The code changes reach only custom connectors and hand-built pipelines.** A
pipeline built with `Pipeline::from_config` needs none of them:

- The split branch's `spate::ops::SinkCtx` is now `SplitTarget`, and `Sink<F>`
  is now `SplitBranch<F>`.
- `ShardWriter::attach_metrics` now takes a `SinkMetricsCtx`, and
  `Feed::attach_metrics` now takes a `FeedMetricsCtx`.
- `MetricsHandle::spawn_upkeep` returns a `TaskHandle`, and dropping it now
  stops the upkeep task. Keep the handle for as long as the metrics should stay
  current.
- `EncodedChunk` now has a `raw_len` field, and `RuntimeOptions` now has a
  `dead_letter_read_interval` field, so a struct literal of either sets the
  field or ends with `..Default::default()`.
- A hand-assembled ClickHouse pipeline must now attach the sink's codec with
  `ShardQueues::with_frame_codec`, using `parts.frame_codec`. Without it the
  sink records a fatal error and sends no request.
- `PipelineRuntime::run` now refuses a current-thread I/O runtime, because in
  0.3 the tasks on one ran only during startup and drain steps.
- `ExitReport.final_watermarks` now lists only the partitions the source still
  held at the final commit, and a source that emits `SourceEvent::LanesAdded`
  must number each added partition above every partition admitted to the epoch
  so far.
- `Source::configure_coordination` and `Source::commit_final` are removed. The
  final commit of a stop is a call to `Source::commit`.
- In `spate-test`, a captured write now reads `ScriptedResult::Pending` until it
  returns.

## The S3 source reads its work from a feed

I replaced split coordination with a work feed because of what it cost to keep
correct. The S3 source now reads work units from the feed that the pipeline's
top-level `feed:` section names. Every assignment, renewal, and completion under
split coordination was a fenced write to a shared store, and more often than
not, that was where the bugs were, as
[#1111](https://github.com/spate-etl/spate/issues/1111) records. A queue does
that work without a shared store, because it already hands each message to one
reader at a time, hides it while it is read, and delivers it again when the
reader dies.
[ADR-0080](/docs/adr/a-work-feed-replaces-leased-fenced-split-coordination)
records the decision.

There are three backends. The in-process feed runs one instance and keeps
nothing across a restart. [`spate-sqs`](/docs/user-guide/connectors/feeds/sqs),
behind the `sqs` feature, reads an SQS standard queue, and the [Kafka
feed](/docs/user-guide/connectors/feeds/kafka) in `spate-kafka` reads a set of
Kafka topics as one consumer group. A durable backend is built in code from the
same section and passed to `Pipeline::feed`. This is the section of a bounded
job on SQS:

```yaml
feed:
  sqs:
    queue_url: "${SQS_QUEUE_URL}"
    visibility: 60s
  units_held: 8
  location: "${JOB_LOCATION}"
  settling_window: 1m
```

`units_held` bounds how many units an instance reads at once, and by default it
is twice the pipeline thread count. A unit is deleted from the queue once the
sink has acknowledged every record in it, and a unit whose worker dies returns
to the queue after `visibility`, for another instance to read.

Before 0.4 shipped, I measured the feeds against split coordination on eight
`c8g.16xlarge` hosts reading one S3 prefix. The SQS feed kept 99.7% of a static
split's throughput and the Kafka feed kept 97.6%, while split coordination kept
67%. [Split coordination lost a third of S3 throughput](/blog/work-feed-scaling)
has the runs, where the time went, and what a killed host costs on each feed.

## A bounded backfill ends on its own

A backfill is now two runs of the same binary. A lister run,
`S3Source::list_once`, lists the prefix once and publishes its objects to a
durable feed. It writes a job fingerprint at the job location that the `feed:`
section names, and it writes an `end` marker there once the feed has confirmed
every unit. Each worker checks the fingerprint before it reads a unit, and the
job ends once the end marker is there and the feed has stayed empty over the
settling window. The window defaults to five minutes and can be set anywhere
between 20 seconds and 24 hours. On SQS it must be at least one minute, because
SQS's message counts take a minute to settle.

I ran the `s3_sqs_backfill` example against ElasticMQ, with 12 objects, each
holding 20 records, and a settling window of one minute:

```text
2026-11-01T14:39:13.642067Z  INFO spate_s3::lister: wrote the end marker at the job location after the feed confirmed every unit of this lister run location=file:///tmp/spate-jobs/backfill/ run=4cc4a4eca8134c979e99696090958e9a units=1 objects=12
2026-11-01T14:39:13.644747Z  INFO spate_core::feed::end_check: end marker found; the job ends once the feed stays empty over the settling window run=4cc4a4eca8134c979e99696090958e9a window=60s
2026-11-01T14:40:28.667778Z  INFO spate_s3::job_end: the bounded job has read all of its work and its dead-letter destination is empty; ending the run
pipeline exit: Completed; rows written: 240
```

The run ended 75 seconds after the lister finished, once the window had passed.
A job whose dead-letter destination holds a unit ends with a failure, and the
error names the destination and its count. I added an object that does not
decode as gzip and set the queue's `maxReceiveCount` to 2:

```text
pipeline exit: Failed(FatalErrorReport { component: "source", reason: "poll_events failed: source error (Fatal): bounded feed job stalled: the dead-letter destination holds units (the dead-letter queue http://127.0.0.1:9324/000000000000/stall-dlq: 1 visible, 0 delayed, 0 in flight, 0 unsent (approximate)); fix their cause, then copy them into a re-run's feed" })
```

On an S3 store the lister keeps a checkpoint at the job location, so a lister
run that stops resumes after its last checkpoint. A local directory lists its
keys in no order, so a lister there keeps none, and says so in a startup
warning. Two lister runs at two locations publish every unit twice, and nothing
detects it.

## New objects arrive through storage notifications

A `feed:` section with no `location` is a continuous job, which reads the
storage notifications published to the feed until it is stopped. S3 sends an
`ObjectCreated` notification to an SQS queue for each object written, and Ceph
RGW can send its notifications to Kafka. This replaces `refresh_listing`, which
re-listed the whole prefix to find new objects. The feed section is the bounded
one without its job keys:

```yaml
feed:
  sqs:
    queue_url: "${SQS_QUEUE_URL}"
    visibility: 60s
  units_held: 8
```

The `s3_sqs_notifications` example writes 12 objects to a RustFS bucket and
publishes the notification S3 would send for each, since no local store sends
them to SQS. I ran it against RustFS and ElasticMQ and stopped it with `SIGTERM`
after 45 seconds, and it printed:

```text
published 12 notifications
pipeline exit: Completed; rows written: 240
```

Each notification names the object's ETag, and the source reads the object under
that ETag. When the object is overwritten while it is read, the source delivers
the records it has read, publishes a new unit at the key's current ETag, and
acknowledges the old one once the feed has stored the new one and the sink has
acknowledged every record read. Once a unit reaches the `feed:` section's
`attempt_cap`, which defaults to 10, the source acknowledges it without
publishing a new one, and `spate_s3_source_overwrites_dropped_total` counts the
drop. A continuous job reads no object written before the bucket's notifications
were configured, and an object that both a listing and a notification announce
is read twice
([ADR-0072](/docs/adr/missed-storage-notifications-are-not-reconciled-by-re-listing)).

## Small S3 objects share a unit

The lister now packs objects at or below `split_target_bytes` into shared units
of up to 16 objects, and the `s3_sqs_backfill` run published its 12 objects as
one unit. The S3 source reads them whole on one lane, one after another, and
acknowledges the unit once after the last. When a lane starts handing on one GET
window, the source now starts the GET for the next one, and at the last window
of an object it reads the first window of the next object in the unit. On small
objects the feeds read at 3.5 times coordination's rate, and the [small-object
section](/blog/work-feed-scaling#small-objects-widen-the-gap-to-35-times) of the
scaling post has the runs
([ADR-0085](/docs/adr/the-lister-packs-small-objects-into-shared-work-units),
[ADR-0087](/docs/adr/a-lane-reads-its-next-window-while-it-hands-on-the-current-one)).

The read-ahead costs memory, because a lane can hold three windows, about `3 ×
units_held × prefetch_bytes` in total. At the defaults that is 48 MiB per
pipeline thread, up from 32 MiB in 0.3. Lower `prefetch_bytes` or `units_held`
to keep the old footprint. If one object of a unit fails, the whole unit is
failed back to the feed, and at the cap it is dead-lettered with every object it
names.

## A stopping worker hands back what it has not read

On a graceful stop, a source on the SQS or Kafka feed now stops receiving units
and keeps reading the ones it holds. It reads until each is finished or until 5
seconds before `checkpoint.drain_timeout` runs out, and then hands back the
units it has not finished for another instance to read. The SQS feed makes each
of them visible at once. The Kafka feed commits each partition up to its first
unfinished unit and leaves the group. Records already read from a handed-back
unit are read again by its next reader. The [graceful
shutdown](/docs/user-guide/guides/graceful-shutdown) guide has the order of each
step.

The 5-second reserve means a `drain_timeout` of 5 seconds or less now fails at
startup with either feed:

```text
run error: invalid runtime configuration: checkpoint.drain_timeout must be more than 5s, the stop reserve of the `sqs` feed; found 5s
```

## Kafka reads and writes ZSTD batches

The Kafka source and the Kafka feed now read ZSTD-compressed batches, and the
Kafka sink now accepts `compression: zstd`. In 0.3 librdkafka was built without
ZSTD, so the source retried a ZSTD batch until the topic's retention deleted it.
All that time it logged a warning and read nothing further from the partition,
while its health probes stayed healthy. The sink failed to create its producer
for `compression: zstd`.

A partition the group had committed did not move past the batch, so an upgraded
pipeline on the same group resumes from its committed offset. A partition the
group had never committed starts under `auto.offset.reset`, and under the
default, `auto.offset.reset: latest`, it skips the ZSTD batch and every record
written before the upgraded pipeline starts reading the partition. A batch in a
codec librdkafka cannot read now fails the pipeline with librdkafka's error
text, before any record after it is delivered. The regression test,
`zstd_batches_are_read`, produces 20 records as ZSTD batches to librdkafka's
mock cluster and reads every one of them back.

## The Kafka source stops on a corrupt message

The Kafka source now fails the pipeline when librdkafka reports a message as
corrupt, and the records before it that the sink has not yet written are not
acknowledged. librdkafka runs a CRC check only with `check.crcs: "true"`, and
reports `BadMessage` when that check fails. In 0.3 the source retried the error,
which meant it could commit past the corrupt message. For message format v0 or
v1, librdkafka skipped the offset when the same fetch held later messages. For a
record batch in format v2, the source either retried forever behind a healthy
probe or, under `auto.offset.reset: latest`, committed past the batch and the
valid records after it.

After a restart, a partition with a committed offset is read from it, and the
pipeline stops again at the same message, because librdkafka checks the same
data again. To resume, move the group's committed offset past the corrupt
message, which skips that record. A fatal error librdkafka reports for a
partition after records in the same poll, such as `TopicAuthorizationFailed`
after the consumer loses `Read` on the topic, now fails the pipeline too. In 0.3
the partition could stop reading with no error reported. The regression test,
`a_corrupt_batch_fails_the_lane`, stores a corrupt batch between two valid
records on the mock cluster and checks that the record before it is delivered,
and nothing at or after it.

## ClickHouse inserts compress on the pipeline threads

With `compression: lz4` or `compression: zstd`, the ClickHouse sink now
compresses each chunk on the pipeline thread when the chunk seals and reuses one
ZSTD context per thread, so a retry resends the stored bytes. In 0.3 the I/O
runtime compressed every frame inside `send`, and a retry compressed it again.
[Insert compression on the pipeline
threads](/blog/compression-on-the-pipeline-threads) has the measurements and
what it costs a host where the pipeline threads are already the limit.

Since the I/O workers no longer carry the compression, the derived pipeline
thread count keeps fewer cores for them. When `pipeline.threads` is unset, the
pipeline runs `available_parallelism` minus one core for every two `io_threads`
workers, rounded up, minus one core for the controller. With the default
`io_threads: 2`, a 4-core host now runs 2 pipeline threads, where it ran 1, and
a 32-core host runs 30, where it ran 29. To keep the old count, set
`pipeline.threads` to it.

Native blocks now reach `chunk.target_bytes`. In 0.3 the encoder overestimated
the block it was building, and the gap grew with each `LowCardinality` column. A
table with four `LowCardinality(String)` columns and an
`Array(LowCardinality(String))` column got blocks of about 42 KB at the default
64 KiB target. The same setting now gives fewer, larger blocks, and if you
raised `chunk.target_bytes` to make up for small blocks, you can lower it again.

## S3 objects that 0.3 could not read

The S3 source now reads every listed object under the key the listing returned.
In 0.3 it requested a different key for an object whose key held a non-ASCII
character or one of `%` `#` `[` `]` `{` `}` `<` `>` `^` `~` `|` `\` `` ` `` `"`
`*` `?`, and the store answered "not found". I wrote three objects,
`plain.ndjson`, `50%off.ndjson`, and `café.ndjson`, to a RustFS bucket and
backfilled the prefix on each release. On 0.3.0 the source looked for
`in/50%25off.ndjson`, and the run ended with no rows:

```text
pipeline exit: Failed(FatalErrorReport { component: "source", reason: "poll_events failed: source error (Fatal): coordinated job stalled: 0 splits completed but 1 are quarantined and out of delivery attempts; inspect spate_coordination_splits_quarantined and requeue or exclude them" })
rows written: []
```

The three objects shared one split, so `plain.ndjson` went unread with the other
two. On 0.4.0, with `feed: { memory: {} }` added:

```text
pipeline exit: Completed
rows written: ["{\"key\":\"50%off.ndjson\"}", "{\"key\":\"café.ndjson\"}", "{\"key\":\"plain.ndjson\"}"]
```

A key the S3 client cannot address at all is now a unit of its own. Such a key
has an empty segment (`d//x.ndjson`), a `.` or `..` segment, or an ASCII control
character, or it starts or ends with `/`. It fails on its first read with the
key in its reason, so a bounded job reads every other object and then ends
stalled. In 0.3 one such key failed the pipeline at its first listing, and a key
with a leading or trailing `/` was read under the key without it. A folder
marker such as `dir/`, with no bytes, is skipped.

Three smaller fixes are in the same source. A pipeline thread whose S3 lanes
have all read their input to the end now waits on its control channel. In 0.3 it
ran a full core until the sink acknowledged their last records, which took up to
one `batch.linger` for small objects. A dropped lane now ends the task that
reads its objects, also while that task waits to retry. An error from a failed
read or listing now carries at most 512 characters of the store's response body.

## Seeing the I/O runtime and the feed in metrics

Each pipeline now exports `spate_pipeline_io_busy_ratio`, the fraction of time
the I/O runtime's async workers spent running tasks, averaged over the trailing
5 minutes and updated every 5 seconds. Without it a saturated I/O runtime looked
like a slow sink. When a full 5-minute window averages 0.9 or above, the
pipeline logs one warning that names `pipeline.io_threads`, and logs it again
only after the average has read below 0.9 for a full 5 minutes. The [tuning
guide](/docs/user-guide/deployment/tuning) covers when to raise it.

The runtime records every call a source makes on its feed under `spate_feed_*`,
whatever the backend, and the SQS and Kafka feeds add their own families under
`spate_sqs_feed_*` and `spate_kafka_feed_*`. `spate_feed_dead_letter_units`
reports how many units the dead-letter destination holds. Each instance reads it
at startup and then once a minute, so a continuous job, which never ends on its
own, still has a dead-letter alert. On SQS each of those reads is one request
per instance. On the Kafka feed the gauge never falls, so alert on a rise there.
`spate_queue_depth` now falls as the sink drains its queue, where in 0.3 it held
the reading of the last send.

[guy-with-a-why](https://github.com/guy-with-a-why) wrote the feed call metrics,
the dead-letter gauge, the backend `Meter`, and the queue depth fix
([#1514](https://github.com/spate-etl/spate/pull/1514),
[#1515](https://github.com/spate-etl/spate/pull/1515),
[#1516](https://github.com/spate-etl/spate/pull/1516),
[#1306](https://github.com/spate-etl/spate/pull/1306)).
