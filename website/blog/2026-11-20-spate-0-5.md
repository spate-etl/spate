Spate 0.5.0 came out on November 20, and it does more with each host. The Kafka
source can now run several consumers in one process, and in tuning runs on a
Kafka to ClickHouse rig two consumers read 22% faster than one. Framing NDJSON,
decoding gzip, validating Avro strings, and encoding ClickHouse strings now take
fewer instructions per byte, most of them through SIMD. On aarch64, decoding a
gzip object now takes about half the instructions it did.

The Kafka source now keeps a partition's records under `auto.offset.reset:
latest` when it restarts before its first commit. On ClickHouse 26.2 and later,
the ClickHouse sink now drops a retried batch whatever `deduplicate_insert` is
set to.

0.5.0 also fixes ten security vulnerabilities, six of them rated high. Upgrade
every Spate crate you use to 0.5.0.
[Security fixes](/blog/releases/0.5#security-fixes) lists each advisory.

To upgrade, raise each Spate crate to `0.5` in `Cargo.toml` and run
`cargo update`. Some fixes change what a running pipeline does, such as the
bound on admin connections and the S3 prefix check, and the breaking changes
below cover each of them.

## Breaking changes

Most of the breaking changes refuse a value at load, with an error that names
the key, so you meet them before a pipeline reads a record. A few load without
an error and change what a running pipeline does: the Kafka source's first
commit under `latest`, the Kafka feed's wait on open transactions, the cap on
partitions per consumer, the TLS trust store, the Avro schema cache and decode
bounds, the S3 source's prefix check on a work unit, the admin server's
connection bound, and the ClickHouse sink's refusal of a server older than 26.2
at startup. The pipeline-file changes come first. The changes to code come last,
and only a custom connector or a hand-built pipeline meets them.

**Durations outside the range a client reads now fail at load.** Spate passed
these durations to librdkafka, which reads intervals in whole milliseconds and
keeps only the low 32 bits. A value under `1ms` reached it as `0`, and `0`
turned statistics, interval commits, or the delivery timeout off. A very large
value wrapped to a much shorter one. A Kafka `commit_interval` of `0s` meant
offsets were committed only on a rebalance or a shutdown, so a restart after a
crash replayed every record since the last of those. The Kafka source's
`commit_interval` must now be from `1ms` to `1day`. The `statistics_interval` of
the Kafka source, sink, and feed must now be `0s` or in the same range, and the
`delivery_timeout` of the Kafka sink and feed must now be at least `1ms`:

```text
source.kafka.commit_interval: must be from 1ms to 1day; found 0s: librdkafka reads the interval in whole milliseconds up to 24h and turns interval commits off at 0
source.kafka.statistics_interval: must be 0s or from 1ms to 1day; found 500us: 0s disables statistics, and librdkafka reads whole milliseconds up to 24h
sink.kafka.delivery_timeout: must be from 1ms to 24days 20h 31m 23s 647ms; found 500us: librdkafka reads whole milliseconds up to i32::MAX and reads 0 as no timeout
```

A `negative_cache_ttl` of `0s` held a batch whose schema id the registry
answered with `404`, and each replay asked the registry again. The Avro
deserializer's `negative_cache_ttl` must now be at least `100ms`:

```text
avro configuration: `negative_cache_ttl` must be at least 100ms; found 0s: a shorter entry can expire before the blocked record is replayed, and each replay then fetches the schema id again
```

A value past about 292 billion years used to panic the runtime when it was added
to a clock reading. The keys `checkpoint.interval` and
`checkpoint.drain_timeout` now have a ceiling of one day, a sink's
`batch.linger` now has a ceiling of one year, and `inflight.max_per_shard` is
now capped at the largest count `tokio`'s semaphore holds:

```text
invalid configuration: checkpoint.interval must be from 100ms to 1day; found 2days
sink.kafka: batch.linger must be from 0s to 1year; found 2years
```

**URLs that carry credentials, or that the source cannot read, now fail at
load.** An S3 `url` or `store` endpoint with a user and password in it loaded,
the password was never sent, and it could appear in the error a failed run
returned and in its log. The SQS feed's `queue_url` and `endpoint` are now held
to the same rule, and must now be `http` or `https`:

```text
source.s3.url: carries userinfo; the store does not read it; set credentials under the source's `store` or the environment
source.s3.store."endpoint": carries userinfo; the store does not read it; set credentials under the source's `store` or the environment
feed.sqs.queue_url: carries userinfo; credentials come from the AWS SDK's default provider chain
```

Before, a `gs://` or `az://` URL loaded and failed when the source started,
unless the binary turned on `object_store`'s own feature for that store. The S3
source now reads `s3://`, `s3a://`, `file://`, and `https://` on an S3 or R2
host, and refuses any other scheme at load:

```text
source.s3.url: the source reads s3://, s3a://, file://, and https:// on an S3 or R2 endpoint host; for another S3-compatible store, write s3://<bucket>/<prefix> with the endpoint under the source's `store`, got gs://events/2026/
```

**The ClickHouse sink now owns `database` and `deduplicate_insert`.** With
`database` under `settings`, inserts could go to a table in that database while
the startup schema check read the table in the typed `database`, so rows could
reach a table that was never checked. Naming either key under `settings` now
fails at load:

```text
sink.clickhouse: settings."database" cannot be overridden: owned by the typed `database` field: the startup checks read the table in that database, and inserts go to the table they checked
```

[ClickHouse retries stay deduplicated](#clickhouse-retries-stay-deduplicated)
has the `deduplicate_insert` change.

**The Kafka source now commits a partition's first position under `latest`.**
For a partition with no committed offset, the source now commits the partition's
end before it first reads the partition, and a later start resumes from that
commit. [Kafka under `latest` keeps its
records](#kafka-under-latest-keeps-its-records) sets out what changes. When the
pipeline fails on one of a partition's first records, a restart now stops the
source on that record again, until the committed offset is moved past it.

**A bounded job on the Kafka feed now waits for another writer's open
transaction.** The feed now reads each partition's end at the high watermark
when it counts the units left, so a unit behind an open transaction counts.
Before, such a job could end `Completed` and exit 0 over unread units. The feed
sets `isolation.level` itself, so naming it under `feed.kafka.rdkafka` now fails
at load. The feed puts no bound on the wait, and a hung transaction is ended
with the broker's tools or a stop.

**A Kafka consumer assigned more than 10,000 partitions now stops.** Each
partition took about 6 KiB, so a large enough assignment could exhaust the
process's memory. The Kafka source and the Kafka feed now fail before the
consumer is assigned. A member alone in its group is assigned every partition,
so run enough members, through `consumers` or more processes, that none holds
more than 10,000 with one member gone.

**A TLS client with no usable trust store now fails at startup.** The ClickHouse
sink, the Avro registry client on Linux, and the SQS feed used to log a warning
and fall back to the Mozilla roots compiled into the binary. They now fail at
their `tls.root_ca` key with an error that names the fixes. [TLS uses the system
trust store or the CA you
name](#tls-uses-the-system-trust-store-or-the-ca-you-name) has the details.

**The Avro deserializer now bounds its schema cache and what one datum can
cost.** The schema cache now holds at most 1,024 compiled schemas and an
estimated 64 MiB of them, and evicts the oldest schema no record has used since
the cache last looked at it. An evicted id is fetched again on its next record.
A registry schema estimated at more than 64 MiB once compiled is now refused,
and its records take the error policy. No setting raises the bound, so such a
schema has to be registered with fewer aliases or less nesting, or split into
named types referenced by name.

The value and serde deserializers, `build_value` and `build_serde`, now refuse a
datum nested more than 32 levels deep, one whose arrays and maps claim more
items than the payload has bytes (or 65,536, if that is more), and one whose
decoded values would take more than 1,024 bytes per payload byte (or 64 MiB, if
that is more). With a `reader_schema` that recurses through a union, they also
refuse a datum whose resolution would grow past a bound set by its size. A
refused datum is a malformed record, so it follows the Skip or Fail error
policy. Datums these two deserializers decoded in 0.4.0 are now refused when
they pass a bound: a list whose `next` field is `["null", "Node"]` takes three
levels per node, so they now accept 10 nodes of it at the top of a datum, and up
to 9 through a recursive reader schema when each node has one other field.
`build_datum` keeps its limit of 128 levels.

**The S3 source now reads a work unit's keys only under its prefix.** A unit
whose descriptor names a key outside the prefix of the source's `url` is now
failed back to the feed, with the key in the reason, and after the feed's
delivery cap it moves to the dead-letter destination. A key is under the prefix
when it starts with the prefix followed by `/`, the rule a storage
notification's key already met. Units a lister run publishes are under its own
`url`, so a job whose lister and workers name the same `url` needs no change,
and a source whose `url` names the whole bucket still reads every key. If you
publish descriptors yourself, or run workers under a narrower `url` than the
lister, name only keys under each worker's prefix.

**The admin server now serves at most 256 connections at once.** A connection
accepted past that closes the oldest one, so `/healthz` and `/readyz` are still
answered while slow clients hold the rest. Each connection now carries one
request and closes after 30 seconds at the latest. A failed `accept`, such as
one that runs out of file descriptors, now logs a warning and retries a second
later, where it used to stop the admin server for the life of the process.

**The code changes reach only custom connectors and hand-built pipelines:**

- `Pipeline::sink` and its siblings now run `SinkPoolConfig::validate`, and
  return `BuildError::Config` for a zero `batch.max_rows`, `batch.max_bytes`,
  or `inflight.max_per_shard`, or a retry or breaker section that fails its own
  check. The Kafka and ClickHouse sinks already refused these values at load.
- `KafkaFeed::connect`, `KafkaFeedPublisher::connect`, and `SqsFeed::connect`
  now return `spate_core::feed::ConnectError`, the one error type every feed
  backend now returns from `connect`, so `KafkaFeedError` and `SqsError` are
  removed. A match on `Refused(reason)` becomes
  `ConnectError::Refused { reason, .. }`.
- `WatermarkController::tick` now takes the queue reading as a closure, so a
  caller that passed a `bool` now passes `|| value`.
- The types `spate_clickhouse::TlsSection` and `spate_avro::TlsSection` are now
  `spate::tls::TlsSection`, re-exported under their old paths.
- `AdminServer::run` now returns `()`, and returns only on shutdown, so a caller
  that handled its `io::Result` drops that handling. It needs a tokio runtime
  with its time driver enabled; the pipeline's own runtime enables it.

## Several Kafka consumers in one process

The Kafka source used to run one consumer, so every partition was fetched
through one connection per broker. A source bound by those fetches had no way to
put more in flight short of running more processes. `source.kafka.consumers` now
sets how many consumers the source runs, and each one is a separate member of
the consumer group with its own share of the partitions
([ADR-0090](/docs/adr/a-kafka-source-runs-a-configured-number-of-consumers)):

```yaml
source:
  kafka:
    brokers: kafka-0:9092
    topic: events
    group_id: events-loader
    consumers: 2
```

I measured it in tuning runs on a Graviton4 host, with a Kafka to Avro to
ClickHouse pipeline in a 32-CPU quota, and each configuration ran twice. Two
consumers read 22% faster than one, and four only 11% faster, because each
consumer waited out librdkafka's `fetch.queue.backoff.ms` once its partition
queues filled. The source now sets that backoff to 10 ms unless the `rdkafka`
map sets it. With ClickHouse writing to a `Null` table and the 10 ms backoff,
one consumer read 37.2M rows/s and two read 48.2M, at which point the pipeline
used its whole CPU quota. [Why four Kafka consumers ran slower than
two](/blog/four-kafka-consumers) has the runs and what each consumer costs.

With more than one consumer, consumer `k` sends a `client.id` with a `-k`
suffix, so a broker quota keyed on the unsuffixed id no longer applies to it.
The `spate_kafka_source_*` series also carry a `client="consumer-k"` label.
Setting `group.instance.id` requires `consumers: 1`. The [Kafka source tuning
page](/docs/user-guide/connectors/sources/kafka/performance-tuning#more-consumers-in-one-process)
says when to raise the count.

## Fewer instructions per byte for NDJSON, gzip, Avro, and ClickHouse

Every byte a pipeline reads crosses a framer, a decoder, and an encoder on a
pipeline thread, so the instructions each one spends per byte bound what one
host can move. This release cuts them on six of those paths. The figures below
are instruction counts from CI's counted benchmark job on each pull request,
base against head, on x86_64 and aarch64:

| Path | Change | x86_64 | aarch64 |
| --- | --- | --- | --- |
| S3 framing, plain NDJSON objects | line ends found with `memchr` | −71.0% to −71.9% | −69.5% to −70.6% |
| NDJSON decode | the same search in the deserializer's split | −10.4% to −13.6% | −9.4% to −12.9% |
| gzip objects | decoded by `zlib-rs` | −16.2% to −17.4% | −48.8% to −49.8% |
| Avro, long text field | UTF-8 checked by `simdutf8` | −44.5% | −39.0% |
| ClickHouse RowBinary encode | short strings copied without a `memcpy` call | −18.9% | −17.1% |
| ClickHouse Native encode | no allocation per new `LowCardinality` value | −13.8% | −18.2% |

Two of these have a cost. In the datum deserializer, an Avro string shorter than
64 bytes now goes through a length test before the standard library's check, so
records whose strings are all short decode with 0.4–0.8% more instructions. A
corrupt gzip object can now fail sooner, with fewer of its records read before
the failure.

The JSON deserializer used to hash a payload's key once per record, and now
hashes it once per payload. On a keyed payload of 2,000 records, this saves
2–4%.

On x86_64 the parsing and decompression libraries choose their SIMD code from
the CPU at run time, so the same binary runs on every host. Each process now
logs the features it compiled in and the features the host offers, once, when
the first pipeline starts. This is the line on an aarch64 Mac:

```text
2026-11-19T18:21:07.050160Z  INFO spate_core::telemetry::cpu: cpu features arch=aarch64 compiled=neon,crc detected=neon,crc
```

On this host the `compiled` and `detected` lists match, because NEON is part of
the aarch64 baseline.

The Kafka sink can now serialize records with `simd-json`, behind the
`kafka-json-simd` feature and `KafkaJsonEncoder::with_simd_json`. It spends
fewer instructions than `serde_json` on records that carry long text, and more
on records of short strings and numbers, so it is opt-in.

## A faster pipeline binary with mimalloc and fat LTO

A pipeline binary builds with its own crate's release profile and the platform's
allocator, so Spate's own profile never reaches it. The [tuning
guide](/docs/user-guide/deployment/tuning#build-the-binary-for-throughput) now
has a section on the two settings that made a measured pipeline faster. On two
Linux hosts with glibc, one x86_64 and one aarch64, with each figure comparing
two builds over 20 interleaved runs, replacing glibc's allocator with `mimalloc`
made the pipeline 7–16% faster, and fat LTO with one codegen unit made it 2–8%
faster:

```toml
[profile.release]
lto = "fat"
codegen-units = 1

[dependencies]
mimalloc = "0.1"
```

```rust
#[global_allocator]
static GLOBAL: mimalloc::MiMalloc = mimalloc::MiMalloc;
```

Fat LTO took about three times as long to build, with about three times the peak
memory. Raising the target CPU stayed within 2% of the default on every host I
measured, and a binary built for a newer CPU is undefined behavior on an older
one, so the guide says to leave it. [A new allocator sped a Rust pipeline up
7–16%](/blog/build-settings) has the runs.

## Kafka under `latest` keeps its records

Under `auto.offset.reset: latest`, the default, a partition with no committed
offset used to start at its end each time the Kafka source started, until the
first commit. Any of these then moved the commit past records no sink wrote: a
restart of a quiet partition, a restart with the sink down, a process joining
the group, or a member the group removed. The source now commits a partition's
end before it first reads the partition, so every later start resumes from a
committed offset for as long as the group holds it
([ADR-0091](/docs/adr/a-kafka-partition-keeps-its-first-position-under-latest)).

Records the source already skipped are not recovered. You can reach them only by
moving the group's committed offset back. On the first start after upgrading, a
partition with no commit still starts at its end. A partition added to the topic
also starts at its end, and so does a group left empty past its offset
retention. [How auto.offset.reset: latest skipped Kafka
records](/blog/auto-offset-reset-latest) traces the 135 retained records the
source skipped, and why.

## ClickHouse retries stay deduplicated

The ClickHouse sink sends each batch with a deduplication token, so a retried
batch is dropped by the server. On ClickHouse 26.2 and later, the
`deduplicate_insert` setting decides this over `insert_deduplicate`. Before,
`deduplicate_insert` set to `disable` by the writer's user, its profile, the
server default, or the sink's own `settings` landed a retried batch twice. The
sink now sets `deduplicate_insert` to `enable` on every insert, and refuses it
under `settings`:

```text
sink.clickhouse: settings."deduplicate_insert" cannot be overridden: forced to `enable`, so the server deduplicates a retried batch by its token whatever the server or profile default
```

The sink's startup settings check now includes `deduplicate_insert` too, so a
replica older than 26.2, or one whose settings constraint pins
`deduplicate_insert` to another value, now fails startup with the server's
reason.

## A ClickHouse replica that never answers fails startup

A ClickHouse replica that accepts the connection and never answers used to leave
the pipeline waiting in startup with no log line. The new `timeouts.startup`, 30
seconds by default, bounds each request the sink sends while it is built: the
schema read, the settings check, and the `distributed_check` queries. Such a
replica now fails startup with an error naming the replica and the setting.
Raise the bound if a replica takes longer than that to answer `system.columns`:

```yaml
sink:
  clickhouse:
    table: events
    shards: [{ replicas: ["http://ch-0:8123"] }]
    timeouts:
      startup: 30s
```

## TLS uses the system trust store or the CA you name

On Linux, the ClickHouse sink, the Avro registry client, the SQS feed, and the
S3 source now read their trust roots through one loader
([ADR-0105](/docs/adr/connectors-share-one-trust-root-loader-in-core)). The
loader reads the system trust store, and `SSL_CERT_FILE` or `SSL_CERT_DIR`
replace it when set. The first three used to fall back to the Mozilla roots
compiled into the binary when that store was empty, as on a container image with
no CA package. They now fail at startup instead, so a binary trusts only the
roots its host holds. On macOS and Windows the Avro registry client and the S3
source keep the operating system's verifier.

A private CA goes under `tls.root_ca`. The S3 source and the SQS feed now read
that key too, and trust its certificates in addition to the system store:

```yaml
source:
  s3:
    url: s3://events/2026/
    tls:
      root_ca: /etc/ssl/private-ca.pem
```

A certificate from an unknown issuer now fails with a hint to add the issuing CA
to the system trust store, or to `tls.root_ca`.

A connector that sends a credential over a connection without TLS now logs one
warning naming the credential's key: a Kafka `sasl.password` under
`sasl_plaintext`, a ClickHouse password over `http://`, and an Avro registry
password over `http://`.

## S3 events from EventBridge, and the S3 source on Lambda

The S3 source now reads the S3 events an EventBridge rule sends to its feed,
besides the notifications a bucket sends straight to the queue. EventBridge
sends an object's key without URL encoding, and the source reads an `Object
Created` event at that key. The event meets the same bucket, prefix, size, key,
and ETag checks as a notification. The other S3 event types, such as `Object
Deleted`, are acknowledged with nothing read. Before, the source failed every
EventBridge event back, and the feed dead-lettered it at its cap.

A new `lambda-s3` example now runs the S3 source on AWS Lambda, one SQS batch of
notifications per invocation, and writes the records to ClickHouse. It returns
each message whose unit did not finish as a batch item failure, so SQS delivers
only those messages again, and it stops the run before the invocation's
deadline. [Running on AWS
Lambda](/docs/user-guide/connectors/sources/s3#running-on-aws-lambda) covers the
model and what it leaves out.

## A Kafka partition left off its leader fails the pipeline

A partition leader move can leave librdkafka fetching an owned partition from a
broker that no longer leads it. The client never moves it back, so the partition
stops being consumed with no error. The Kafka source now reads each partition's
broker and leader from librdkafka's statistics. When they differ for longer than
`misplaced_partition_timeout`, 60 seconds by default, across at least three
snapshots, the source fails with an error that names the partition and both
brokers, and a restart resumes the partition from its committed offset.

```yaml
source:
  kafka:
    brokers: kafka-0:9092
    topic: events
    group_id: events-loader
    misplaced_partition_timeout: 60s
```

Setting `misplaced_partition_timeout` to `0s` turns the check off. It is also
off when `statistics_interval` is `0s`, and when the `rdkafka` map sets a
non-empty `client.rack`, since that lets the brokers send fetches to a follower.
The regression test, `poll_events_fails_on_a_partition_left_off_its_leader`,
feeds the source statistics that place a partition on broker 1 while broker 2
leads it, and checks that the source fails.
